## 0. 이 연동의 성격 한 줄

**돈은 토스가 받고, "누가 무엇을 살 수 있는가"는 우리가 기억한다.**

우리 서버는 결제창도 카드도 승인도 보지 않는다. 우리가 가진 유일한 값은 `orderId` 하나이고,
그것을 익명키에 묶어 보관하는 것이 이 도메인 전체다. **그 매핑이 끊기면 사용자는 돈을 내고 못 쓴다.**

# I. 개발할 기능 요구사항

## 1-1. 서버가 만들어야 하는 것 (4개 엔드포인트)

| # | 엔드포인트 | 하는 일 | 인증 | 근거 |
|---|---|---|---|---|
| **F1** | `GET /api/v1/payments/products` | 판매 중인 `sku` 와 상품 유형을 내려준다. **가격은 안 내려준다** | 불필요 | U1 |
| **F2** | `POST /api/v1/payments/grant` | `orderId` 를 받아 **토스에 결제 사실을 확인한 뒤** 이용권을 준다 | `X-Anonymous-Key` | U2·U3·U4 |
| **F3** | `GET /api/v1/payments/entitlement` | "지금 쓸 수 있는가"를 답한다 | `X-Anonymous-Key` | U5 |
| **F4** | `POST /api/v1/webhooks/toss/payment` | 구독 상태 변경을 수신해 반영한다 | **Basic Auth** (게이트 밖) | U9·U10·U11 |

여기에 **엔드포인트가 아닌 횡단 요구** 3개가 붙는다.

| # | 요구 | 내용 | 근거 |
|---|---|---|---|
| **F5** | 이용 게이트 | 유료 기능 요청을 이용권 없이 거부. **401 과 구분되는 403** | U6 |
| **F6** | 횟수권 소모·복구 | 작업 시 −1, 작업 실패 시 되돌린다 | U7·U8 |
| **F7** | `orderId` 비노출 | 로그·예외·에러 응답 본문에 원문을 남기지 않는다 | U14 |

### F2 가 이 도메인의 심장이다

`processProductGrant` 콜백과 미결 주문 복원이 **같은 엔드포인트**를 쓴다. 멱등하기 때문이다.
단건과 구독도 같은 엔드포인트다 — **상품 판별은 클라가 아니라 토스 응답의 `sku` 로 한다.**

```
POST /api/v1/payments/grant
X-Anonymous-Key: {hash}
{ "orderId": "…" }        ← sku 를 클라에서 받지 않는다 (클라 주장을 믿지 않는다)
```

> `sku` 를 클라에서 안 받는 결정이 부수 효과로 문제 하나를 더 닫는다:
> **낮은 앱 버전의 `getPendingOrders` 는 `sku` 없이 `orderId` 만 준다.** 서버가 `orderId` 만으로
> 상품을 역추적할 수 있어야 하는데, 이미 그렇게 설계되어 있다.

## 1-2. 클라가 해야 하는 것

| # | 요구 | 왜 서버가 대신 못 하나 |
|---|---|---|
| **C1** | `getProductItemList()` 의 `displayAmount` 로 가격 표시 | SDK 만이 스토어 결제창과 일치하는 금액을 안다 |
| **C2** | 상품 유형에 따라 주문 생성 함수 분기 | `CONSUMABLE → createOneTimePurchaseOrder`, `SUBSCRIPTION → createSubscriptionPurchaseOrder` |
| **C3** | `processProductGrant` 안에서 F2 호출 후 **200 일 때만 `true` 반환** | 콜백이 클라 JS 에서 돈다 |
| **C4** | **앱 기동 시 `getPendingOrders()` 복원** | 검수 필수 시나리오 ③. 서버가 미결 주문을 스스로 알 방법이 없다 |
| **C5** | 지급 성공 후 `completeProductGrant({ params: { orderId } })` | SDK 함수라 서버가 못 부른다 |
| **C6** | 미지원 버전 방어 · `cleanup()` 호출 | — |

> ⚠️ **C4 가 없으면 F2·F3 이 아무리 완벽해도 "결제는 됐는데 못 쓰는" 사용자가 남는다.**
> 30초 초과·앱 강제종료·네트워크 단절은 정상 흐름에서도 일어난다.

## 1-3. 요구사항 간 의존 — 빠뜨리면 통째로 죽는 것

```
F4(웹훅) ──┬─ U10 등록 검증 이벤트를 204 로 받아야 → 콜백 URL 이 활성화됨
           └─ 이게 없으면 U9(갱신 반영)가 통째로 동작 안 함

F5(게이트) ── 익명키 인증 게이트가 웹훅에도 걸리면 → 토스 웹훅이 401 로 튕김
              ❗ 현재 auth §4-2 공개 목록에 웹훅이 없다 = 지금 상태로는 실제로 튕긴다
```

# II. 신뢰성 대책

결제 도메인의 신뢰성은 "장애가 안 나게 한다"가 아니라 **"장애가 나도 사용자가 돈을 잃지 않게 한다"** 이다.
아래는 **실제로 일어나는 실패**와 그 대책이다. 가정이 아니라 문서·커뮤니티에 근거가 있는 것만 적었다.

## 2-1. 실패 지점별 대책 (한눈에)

| # | 실패 | 결과 | 대책 |
|---|---|---|---|
| R1 | 콜백이 아예 안 돈다 (앱 강제종료·웹뷰 이탈) | 결제됨 + 미지급 | **C4 복원** — `getPendingOrders` |
| R2 | 30초 초과 | 토스가 "환불 신청하세요" 화면 노출 | **붙잡지 않고 `false` 반환 → 복원에 맡김.** 재시도 루프 금지 |
| R3 | 같은 `orderId` 로 지급이 여러 번 | 🔴 **횟수권 잔량이 부풀어 무료 이용권 유출** | **`orderId` 기준 멱등.** 재요청은 에러가 아니라 **200** |
| R4 | 클라가 결제 없이 `grant` 호출 | 무료 지급 | **`get-order-status` 서버 검증** (U2) |
| R5 | `orderId` 탈취·추측 | 남의 주문 가로채기 | **선점 규칙 + U14 비노출 + 브루트포스 방어** |
| R6 | 위조 웹훅 | 결제 없이 기간권 활성화 | **Basic Auth + IP 화이트리스트 + "웹훅으로 구독을 만들지 않는다"** |
| R7 | 웹훅 유실 | 🔴 **낸 사람을 막는다** | `previous` 와 우리 상태 비교로 **감지**. 보정은 🔶-6 |
| R8 | 웹훅 중복·순서 역전 | 상태 되감김 | `eventType+orderId+occurredAt` 판별 · `occurredAt` 과거면 무시 |
| R9 | 토스 API 장애 | 지급 불가 | `502 PAY_006` → 복원에 맡김. **부트스트랩에는 전파되지 않는다** |
| R10 | 작업 실패 | 2,200원 내고 결과물 없음 | **횟수권 되돌림** (U8) |
| R11 | 웹훅 타임존 모호 | 만료 판정 최대 9시간 오차 | **우리가 기준을 정해 변환**해서 저장·응답 (🔶-7) |
| R12 | 익명키 소실 (탈퇴·재출시) | 이용권 승계 불가 | **막을 수 없다.** 재출시 전 선행 해결 과제로 명시 |

## 2-2. 핵심 대책 4가지 상세

### ① 서버 권위 — "결제했다"는 클라의 말을 믿지 않는다

```
클라: POST /grant { orderId }
서버: → 토스 get-order-status(orderId)   ← 여기서 처음으로 사실이 확인된다
     → status 가 지급 대상일 때만 이용권 부여
```

**다만 이 검증의 한계를 정확히 알아야 한다.**
서버가 확인할 수 있는 것은 **"이 `orderId` 가 결제됐다"뿐이고, "누구 것인가"는 끝까지 클라의 주장**이다.
`get-order-status` 응답에 소유자 필드가 없고, 사용자를 한정하는 `x-toss-user-key` 는 토스 로그인 사용자용인데
우리는 그 값이 없다.

> 그래서 **선점 규칙은 보안 통제가 아니라 리스크 수용 선언**이다 —
> "먼저 지급을 요청한 익명키가 소유자". 보안인 척 쓰면 안 된다.
> 실질 위험이 낮다고 보는 근거는 `orderId` 가 결제한 기기 밖으로 나가지 않는다는 점이고,
> 그래서 **U14(비노출)가 여기서 실효 있는 방어**가 된다.
> ⚠️ `orderId` 엔트로피가 검증되지 않았다(🔶-12) — 추측 가능하면 이 근거가 무너진다.

### ② 멱등 — 중복은 예외가 아니라 정상이다

중복 지급 요청이 오는 **정상 경로**가 최소 3개다:

```
① 복원 흐름이 이미 지급된 주문을 다시 보냄
② 네트워크 실패 후 클라 재시도
③ 30초 타임아웃으로 false 반환했는데 실은 서버가 성공했음
```

**"중복이면 에러"로 만들면 복원 흐름 자체가 깨진다.** 그래서 이미 지급된 주문의 재요청은 **200** 이다.
프론트가 그 200 을 받고 `completeProductGrant` 로 미결 상태를 닫을 수 있어야 하기 때문이다.

> 🔴 **횟수권과 기간권의 위험도가 다르다.** 기간권은 상태 세팅이라 중복이 무해하지만,
> 횟수권은 `+1` 이 누적된다. 멱등의 근거를 **`orderId` 하나에** 둔다.
> ⚠️ 하필 `completeProductGrant` 의 중복 호출 멱등성이 문서화돼 있지 않다(🔶-13).

### ③ 30초 예산 — 통제 가능한 구간과 아닌 구간

```
[통제 가능] 우리 서버 응답 시간 = get-order-status 왕복 + DB 쓰기
[통제 불가] 토스의 ack 반영 — true 를 반환했는데도 30초 뒤 환불 안내가 뜬 사례가 있다
```

- 우리 지급 API 에 **상한을 두고, 초과하면 실패로 처리해 복원에 맡긴다.** 붙잡고 있는 것보다 낫다.
- ⚠️ **타이머 기점이 문서에 없다**(결제 승인 시점인지 콜백 진입 시점인지) → 보수적으로 잡는다.
- ⚠️ 구독 문서에는 30초 문구가 없지만 **같은 제약을 전제로 설계한다.**
  없는 쪽으로 가정했다 틀리면 결제 직후 환불 화면이 뜨고, 반대 방향의 손해는 없다.

### ④ 웹훅 — 유실 방향에 따라 손해가 비대칭이다

| 유실한 웹훅 | 결과 | 심각도 |
|---|---|---|
| **만료** 웹훅 | 안 낸 사람에게 열어준다 | 🟡 우리 손해 |
| **갱신** 웹훅 | **낸 사람을 막는다** | 🔴 환불 + 검수 반려 |

보정 수단을 정할 때 이 비대칭을 기준으로 삼는다.

**구조적 리스크**: 서버가 구독 상태를 조회할 API 가 **없다.**
서버가 아는 기간권 상태 = **최초 지급 시 주문 검증 + 그 이후 웹훅 누적**이다.
웹훅이 유실되면 서버 상태가 실제와 어긋나고 **바로잡을 조회 수단이 우리에게 없다.**

**처리 원칙**

| 상황 | 처리 |
|---|---|
| 검증 실패 | 처리하지 않는다 |
| 반영 실패 | **그래도 204 로 답한다** — 재전송 정책이 문서에 없어 재시도에 기댈 수 없다. 유실은 우리가 감당한다 |
| 모르는 `orderId` | **기록만 하고 무시** — 위조 웹훅이 할 수 있는 최대치를 "없는 구독 생성"에서 "기존 구독 흔들기"로 줄인다 |
| `previous` 불일치 | **그 사이 웹훅을 놓친 것** — 감지는 확정, 보정은 🔶-6 |
| `RESTARTED` | ❗`changeReason` 만 믿지 않고 **`current.autoRenew` 를 함께 본다**(false 로 유지된 사례 보고됨) |

## 2-3. 검증할 수 없는 구간 — 알고 시작한다

| 대상 | 샌드박스 | 결과 |
|---|---|---|
| 단건(소모품) | ✅ | 출시 전 검증 가능 |
| **구독** | ❌ **미지원** | **실결제로만 검증된다** |
| `getAnonymousKey` | ⚠️ mock | E2E 는 실기기 QR 필요 |

- ⚠️ **QR 테스트에서 실결제가 발생한다**(토스 직원 확인). 테스트 비용·환불 절차를 미리 잡는다.
- ⚠️ **구독 부분은 자동화 테스트로 계약 준수를 증명할 수 없다.**
  테스트는 "우리 규칙이 맞게 도는가"까지만 답하고, **"토스와 실제로 맞물리는가"는 실결제가 답한다.**

# III. 앱인토스와 주고받는 API

## 3-1. 방향별 지도 — 우리가 상대하는 접점은 4개다

| # | 방향 | 수단 | 인증 | 쓰는 곳 |
|---|---|---|---|---|
| **①** | 토스 앱 → 클라 JS | **콜백** `processProductGrant` | — | 결제 성공 시 지급 트리거 |
| **②** | 클라 → 토스 앱 | **SDK 함수** (`IAP.*`) | — | 목록·주문·복원·완료·구독조회 |
| **③** | 우리 서버 → 토스 서버 | **REST** `get-order-status` | **mTLS 단독** | 주문 검증 (유일한 서버 API) |
| **④** | 토스 서버 → 우리 서버 | **웹훅** | **Basic Auth** | 구독 상태 변경 (구독 전용) |

> ❗ ①은 HTTP 가 아니라 **앱↔웹뷰 브릿지 함수 호출**이다. ④와 혼동하면 설계가 통째로 어긋난다.
> ❗ **단건에는 ④가 없다.** 문서화된 웹훅 이벤트 2종은 둘 다 구독 스코프다.

## 3-2. ② 클라 SDK — 함수별 매개변수 의미

### `getProductItemList()`

| 반환 필드 | 타입 | 의미 |
|---|---|---|
| `sku` | string | **상품 고유 ID. 주문 생성에 그대로 넘기는 값** |
| `type` | `CONSUMABLE`\|`NON_CONSUMABLE`\|`SUBSCRIPTION` | 상품 유형. **어느 주문 함수를 쓸지 결정** |
| `displayAmount` | string | **화면에 표시할 금액.** 스토어 결제창과 일치하는 유일한 값 |
| `displayName` · `description` · `iconUrl` | string | 표시용 |
| `renewalCycle` | `WEEKLY`\|`MONTHLY`\|`YEARLY` | 구독만. **매월 = 30일 고정 (달력 월 아님)** |
| `offers` | Offer[] **?** | ⚠️ **optional** — 없으면 필드 자체가 안 온다 |

⚠️ `type` 이 없는 정의도 문서에 존재한다 → **`type` 부재를 방어**한다.

### `createOneTimePurchaseOrder` / `createSubscriptionPurchaseOrder`

| 매개변수 | 필수 | 의미 |
|---|---|---|
| `options.sku` | ✅ | 구매할 상품 ID (`productId` 는 deprecated) |
| `options.offerId` | ❌ (구독만) | 적용할 오퍼. **생략/null 이면 기본 가격** |
| `options.processProductGrant` | ✅ | **결제 성공 시 토스가 호출하는 콜백.** `boolean \| Promise<boolean>` 반환 |
| `onEvent` | ✅ | 결제 흐름 결과 통지 |
| `onError` | ✅ | 에러 통지 |
| **반환값** | — | `cleanup` 함수. **반드시 호출** |

**`processProductGrant` 가 받는 인자**

| 인자 | 단건 | 구독 | 의미 |
|---|---|---|---|
| `orderId` | ✅ | ✅ | **주문 식별자. 우리가 다루는 유일한 값** |
| `subscriptionId` | — | ❌ **optional** | ⚠️ 서버 설계에서 필수로 가정하면 안 된다 |

**반환값의 의미**

| 반환 | 결과 |
|---|---|
| `true` | 지급 성공. 정상 종료 |
| `false` / 30초 초과 | **"{앱이름}에 문제가 생겼어요. 환불을 신청해주세요" 페이지 노출** |

> ❗ `false` 는 **결제 취소가 아니다.** 주문은 미결 상태로 남고 복원 대상이 된다.
> 사용자 안내 문구가 "결제 실패"가 되면 사실과 다르다.

### 복원·완료 함수 — 용도가 겹치지 않는다

| 함수 | 반환 | 무엇을 잡나 |
|---|---|---|
| `getPendingOrders()` | `{ orders: Order[] } \| undefined` | **결제 완료 + 미지급.** 30초 초과·강제종료·네트워크 단절 건 |
| `getCompletedOrRefundedOrders()` | `{ hasNext, nextKey?, orders[] }` | **지급 완료 + 환불된 주문.** 기기 변경 복원용 |
| `completeProductGrant({ params: { orderId } })` | `Promise<boolean \| undefined>` | 지급 완료를 토스에 통보 |

`Order` 필드 의미

| 필드 | 의미 | 주의 |
|---|---|---|
| `orderId` | 주문 식별자 | 항상 온다 |
| `sku` | 상품 ID | ⚠️ **SDK 1.4.2 미만·낮은 앱 버전에서는 안 온다** |
| `paymentCompletedDate` | 결제 완료 시각 | ⚠️ SDK 1.4.8+. 인터페이스는 `?`, 산문은 '필수' — **선택으로 방어** |

⚠️ **`getPendingOrders` 응답에 단건/구독 구분 필드가 없다.** 복원 시 어느 지급 경로로 보낼지
서버가 판단해야 한다 → **F2 가 `sku` 로 상품을 판별하는 설계가 이 문제도 함께 해결한다.**

⚠️ **웹 SDK 의 `getCompletedOrRefundedOrders` 는 파라미터를 받지 않고 항상 첫 페이지(50건)만** 준다.
→ **커서 페이지네이션을 우리 API 계약에 넣으면 안 된다.**

⚠️ `completeProductGrant` 는 **IAP 함수 중 유일하게 `{ params: { ... } }` 중첩 구조**다.
호출하지 않으면 주문이 `PAYMENT_COMPLETED` 로 남고 콘솔에도 '지급완료'가 안 뜬다.

### `getSubscriptionInfo({ params: { orderId } })` — 클라 전용

| 필드 | 의미 | 우리 취급 |
|---|---|---|
| `status` | 구독 상태 6종 (→ §3-5) | 참고용 |
| `expiresAt` | 만료 예정 시각 (`null` 가능) | ⚠️ 구매 직후 `null` 사례 보고됨 |
| `gracePeriodExpiresAt` | 유예 만료 시각 (**`expiresAt` 과 다른 시점**) | 웹훅에는 없는 필드 |
| `isAutoRenew` | 자동 갱신 여부 | — |
| `isAccessible` | "이용 가능한가" | ❌ **쓰지 않는다** — 산식이 문서에 없고, 토스 직원도 `status` 기준을 권했다 |
| `catalogId` | 카탈로그 ID | 웹훅에는 없는 필드 |

⚠️ **이 값은 클라가 보낸 것이다.** 서버 권위 원칙상 그대로 받아 쓰지 않는다.

## 3-3. ③ 서버 API — `get-order-status` (IAP 서버 API 는 이것 하나뿐)

```
POST https://apps-in-toss-api.toss.im/api-partner/v1/apps-in-toss/order/get-order-status
인증: mTLS 단독 — OpenAPI spec 의 parameters 가 []  (헤더 인증 없음)
한도: 미니앱당 분당 3,000회
```

**요청**

| 필드 | 필수 | 의미 |
|---|---|---|
| `orderId` | ✅ | 조회할 주문 ID. **단일 필드** |

**응답 봉투 — 2단 구조다**

```json
{ "resultType": "SUCCESS",
  "success": { "orderId": "…", "status": "PURCHASED", "reason": "완료된 주문이에요.",
               "sku": "…", "statusDeterminedAt": "…" } }
```

| 필드 | 항상 오나 | 의미 |
|---|---|---|
| `resultType` | ✅ | 처리 결과 봉투 (→ 아래) |
| `success.orderId` | ✅ | 요청한 값과 동일 |
| `success.status` | ✅ | **주문 상태 8종** (→ §3-4) |
| `success.reason` | ✅ | status 의 사람이 읽는 설명 |
| `success.sku` | ❌ | ⚠️ `MINIAPP_MISMATCH`·`NOT_FOUND`·`ERROR` 일 때 **안 온다** |
| `success.statusDeterminedAt` | ❌ | 상태 확정 시각. 위와 동일하게 안 올 수 있다 |

**`resultType` 이 가질 수 있는 값 — `SUCCESS`/`FAIL` 이 전부가 아니다**

| 값 | 의미 |
|---|---|
| `SUCCESS` | 성공 |
| `FAIL` | 비즈니스 실패 |
| `HTTP_TIMEOUT` · `NETWORK_ERROR` · `EXECUTION_FAIL` · `INTERRUPTED` · `INTERNAL_ERROR` | 내부 전달 실패 |

> ❗ **"SUCCESS 가 아니면 전부 실패"로 처리한다.**
> ❗ **비즈니스 오류가 HTTP 200 으로 내려온다.** HTTP 상태만 보고 성공 판정하면 안 된다.
> (요청 필드 검증 실패만 400, 미분류 서버 오류가 500)

**실패 응답**

| 필드 | 의미 |
|---|---|
| `error.errorCode` | 오류 코드. **`4095`(분당 3,000 초과)만 문서화돼 있다** — 전역 목록 비공개 |
| `error.reason` | 사람이 읽는 설명 |
| `error.data.retryAfterSeconds` | 한도 초과 시 백오프에 쓴다 |
| `error.errorType` | 내부 분류값 — **구분에 쓰지 말 것**(문서 지시) |

⚠️ **권장/최대 타임아웃 값이 문서 어디에도 없다**(🔶). QPM 이 엔드포인트별인지 합산인지도 미명시.

## 3-4. 주문 `status` 8종 — 의미와 우리 처리

| status | 토스의 의미 | 우리 판정 | 프론트 |
|---|---|---|---|
| `PURCHASED` | 구매 완료 ("완료된 주문이에요.") | **200 지급** | `true` 반환 → 진행 |
| `PAYMENT_COMPLETED` | **결제 완료 · 상품 지급은 안 끝남** | 🔶-1 **200 지급(제안)** ⚠️ 문서 근거 없음 | 동일 |
| `ORDER_IN_PROGRESS` | 주문 진행 중 | `409 PAY_002` | `false` + "잠시 후 반영" → 복원에 맡김 |
| `FAILED` | 구매 실패 | `409 PAY_003` | `false` + 문의. **재시도 금지** |
| `REFUNDED` | 환불됨 | `409 PAY_003` | 동일 |
| `NOT_FOUND` | 주문 없음 | `404 PAY_004` | `false` + 문의. 재시도 금지 |
| `MINIAPP_MISMATCH` | 우리 미니앱 주문이 아님 | `404 PAY_004` | 동일 |
| `ERROR` | 카탈로그 조회 실패 등 비정상 | `502 PAY_006` | `false` + 재시도 → 복원에 맡김 |
| *(다른 익명키 귀속 — 토스 조회 이전)* | — | `409 PAY_005` | 조용히 건너뜀 |

> 🔴 **`PAYMENT_COMPLETED` 를 지급 대상으로 볼지가 이 도메인 최대 미확정(🔶-1)이다.**
> 틀리면 **이중 지급(무료 이용권 유출) 또는 지급 누락(돈 내고 못 씀)** 으로 직결된다.
> ⚠️ `PAYMENT_COMPLETED → PURCHASED` **전이 트리거도 문서에 없다** — `completeProductGrant` 가
> 트리거인지 확인 문장이 없다.
> ⚠️ **`MINIAPP_MISMATCH` 와 `NOT_FOUND` 의 구분 기준**, `ERROR` 재시도 여부도 미명시.

## 3-5. 구독 `status` 6종 — 의미와 게이트 개폐

**토스의 상태 어휘를 게이트에 그대로 쓰지 않는다.** "구독이 어떤 상태인가"와 "열어줄 것인가"는 별개다.

| status | 토스의 의미 | 우리 판정 | 왜 |
|---|---|---|---|
| `ACTIVE` | 활성 | ✅ **연다** | — |
| `IN_GRACE_PERIOD` | 결제 실패 후 유예 기간 | 🔶-3 ✅ **연다(제안)** | 카드 문제로 잠깐 실패한 유료 사용자를 막는 손해가 더 크다 |
| `ON_HOLD` | 결제 보류 | 🔶-3 ❌ **막는다(제안)** | 유예가 끝난 상태다 |
| `PAUSED` | 사용자 일시정지 | 🔶-3 ❌ **막는다(제안)** | 사용자 의사다 |
| `EXPIRED` | 만료 | ❌ 막는다 | — |
| `REVOKED` | 회수(환불 등) | ❌ 막는다 | — |
| *(구독 이력 없음)* | — | ❌ 막는다 | 횟수권만 본다 |

⚠️ **6종의 전이 조건·유예 기간 길이·`REVOKED` 와 `EXPIRED` 의 차이가 문서에 없다.** 한 단어 대응표뿐이다.

**최종 판정식**: `이용 가능 = 기간권이 살아 있다 OR 횟수권 잔량 > 0`
프론트는 **`accessible` 하나만 보고 분기**한다. `status` 는 안내 문구용이다.

## 3-6. ④ 웹훅 — 페이로드 필드와 `changeReason` 12종

**이벤트는 정확히 2종**

| eventType | 언제 | 페이로드 |
|---|---|---|
| `callback.registration_verification` | URL 등록·변경 시 | `{ eventType, occurredAt }` **2필드뿐. challenge·에코백 없음** |
| `subscription.status_changed` | 구독 상태 확정 시 | 아래 |

**필드 의미**

| 필드 | 필수 | 의미 |
|---|---|---|
| `eventType` | ✅ | 고정값 |
| `eventVersion` | ✅ | 고정 `"1.0"` |
| `occurredAt` | ✅ | 발생 시각. ⚠️ **timezone 없는 ISO-8601, 기준 타임존 미확답** |
| `orderId` | ✅ | **주문 식별자. 사용자와 연결하는 유일한 고리** |
| `sku` | ✅ | 상품 SKU |
| `changeReason` | ✅ | 변경 사유 12종 (→ 아래) |
| `subscription.previous` | ❌ | 변경 **전** 스냅샷. `CREATED` 등에서 생략 |
| `subscription.current` | ✅ | 변경 **후** 스냅샷 |

**스냅샷 필드 — SDK 와 이름이 다르다**

| 웹훅 | SDK 대응 | 의미 |
|---|---|---|
| `status` | `status` | 구독 상태 6종 |
| `accessGranted` | `isAccessible` | 접근 권한 부여 여부 |
| `expiresAt` | `expiresAt` | 만료 시각 (`null` 가능) |
| `autoRenew` | `isAutoRenew` | 자동 갱신 여부 |
| **(없음)** | `gracePeriodExpiresAt` | ⚠️ **웹훅만으로는 절대 채울 수 없다** |
| **(없음)** | `catalogId` | 동일 |

**`changeReason` 12종**

| changeReason | 의미 | 우리 처리 |
|---|---|---|
| `CREATED` | 구독 생성 | 기간권은 **F2 로만 만든다.** 웹훅으로 새로 만들지 않는다(§4-7) |
| `RENEWED` | 갱신 | `expiresAt` 연장 |
| `RECOVERED` | 결제 실패 상태에서 복구 | `current.status` 기준으로 재판정 |
| `RESTARTED` | 구독 재시작 | ❗**`current.autoRenew` 를 함께 본다** (false 유지 사례 보고) |
| `ENTERED_GRACE_PERIOD` | 유예 기간 진입 | 🔶-3 유지(제안) |
| `ON_HOLD` | 결제 보류 | 🔶-3 차단(제안) |
| `PAUSED` | 일시정지 | 🔶-3 차단(제안) |
| `AUTO_RENEW_ENABLED` | 자동 갱신 활성화 | 표시만 갱신 |
| `AUTO_RENEW_DISABLED` | **해지 예약** | **만료일까지 계속 열어준다** (아직 유효 기간이다) |
| `EXTENDED` | 기간 연장 | `expiresAt` 갱신 |
| `EXPIRED` | 만료 | 회수 |
| `REVOKED` | 회수 또는 **환불** | **즉시 회수** |

> **판정의 기준은 `changeReason` 이 아니라 `current.status` 다.** `changeReason` 은 사유이자
> 반영 트리거일 뿐이다. 12종에 1:1 로 로직을 붙이면 미문서화 값이 추가될 때 깨진다.

⚠️ **멱등 이벤트 ID 가 없다.** 중복 판별 키는 `eventType + orderId + occurredAt` 조합뿐이다.
⚠️ **재전송 정책이 문서·커뮤니티 어디에도 없다.** 재시도 여부·횟수·백오프 전부 미확인.
⚠️ **페이로드에 `subscriptionId`·`catalogId` 가 없다.** SDK 가 주는 세 식별자의 관계가 정의돼 있지 않다.

⚠️ **Inbound 는 6개 엔트리 전부** 열어야 한다. 하나만 열면 나머지 5개 출발지의 웹훅이 차단된다.
⚠️ **mTLS 발급 절차 공식 문서가 유실 상태다**(순환 참조 + 404) → 채널톡 문의 필요. **연동 착수 자체가 막힌다.**
⚠️ npm SDK 2.6.2 미만에는 **구독에서 `processProductGrant` 가 호출되지 않는 버그**가 있었다.

# IV. 착수 전 확정해야 할 것

| 우선 | 항목 | 막히는 것 |
|---|---|---|
| 🔴 1 | **`PAYMENT_COMPLETED` 를 지급 대상으로 볼 것인가** (🔶-1) | 이중 지급 ↔ 지급 누락 |
| 🔴 2 | **갱신 시 `orderId` 가 유지되는가** | 유일한 연결고리다. 새 값이면 **갱신 시점에 매핑이 끊긴다** |
| 🔴 3 | **mTLS 인증서 발급 절차** | 서버 연동 착수 불가 |
| 🟡 4 | `completeProductGrant` 중복 호출 멱등성 (🔶-13) | 횟수권이 샌다 |
| 🟡 5 | 30초 타이머 기점 + 구독 적용 여부 (🔶-10) | 타임아웃 예산 |
| 🟡 6 | 웹훅 재전송 정책 · 기준 타임존 (🔶-7) | 유실 복구 / 만료 판정 9시간 오차 |
| 🟡 7 | `IN_GRACE_PERIOD`·`ON_HOLD`·`PAUSED` 개폐 (🔶-3) | 게이트 판정 |
| 🟢 8 | `orderId` 형식·엔트로피 (🔶-12) | 선점 규칙의 리스크 수용 근거 |
| 🟢 9 | `sku` 명명 규칙 · 가격 변경 절차 | 상수 하드코딩 가능 여부 |

**보고된 이상 동작 (토스 미확인)**
- `RESTARTED` 웹훅인데 `current.autoRenew` 가 `false` 유지 → **`changeReason` 단독 판정 금지**
- 플랜 전환 시 **기존 구독이 살아 있는 채 신규 구독이 동시 활성화되어 중복 결제**된 사례
- `processProductGrant` 가 **`true` 를 반환했는데도** 30초 뒤 환불 안내가 뜬 사례
