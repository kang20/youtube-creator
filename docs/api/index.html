인증

이 서비스는 토스 로그인을 쓰지 않는다. 익명키로 로그인(부트스트랩)하고, 이후 전 API 는 JWT Bearer 토큰으로 인증한다.

헤더 어디서 값

Authorization

인증 필요 엔드포인트 전부

Bearer {accessToken} — 부트스트랩이 발급

X-Anonymous-Key

부트스트랩에서만

클라 getAnonymousKey() 의 hash

  • access 토큰은 30분 유효. 만료(AUTH_004)를 받으면 POST /api/v1/auth/refresh 로 갱신 후 1회만 재시도한다 — 이 흐름은 HTTP 인터셉터 한 곳에 둔다(진입 절 참조).

  • refresh 토큰은 14일·회전식 — 갱신할 때마다 새 값으로 바뀌고 이전 값은 즉시 무효다. 로컬에만 보관하고 어떤 로그·화면에도 남기지 않는다.

  • 익명키는 미니앱마다 고유하고 같은 사용자는 항상 같은 값을 받는다(토스 계정 기준). 아는 사람이 곧 그 사용자가 되므로 취급 수준은 자격증명에 준한다 — 부트스트랩 외에는 실지 않는다.

인증 (auth)

익명키 로그인은 부트스트랩(진입 절)이 담당한다 — 부트스트랩이 곧 로그인이고 토큰 발급 지점이다. 이 장은 토큰 갱신 계약만 다룬다. 요구 정본은 backend/docs/domain/auth.md v4.

토큰 갱신 — POST /api/v1/auth/refresh

인증 게이트 밖이다 — 자격 증명이 만료된 상태에서 부르는 API 이기 때문이다. 본문의 refresh 토큰이 자격 증명이다.

HTTP request

POST /api/v1/auth/refresh HTTP/1.1
Content-Type: application/json;charset=UTF-8
Content-Length: 47
Host: api.example.com

{
  "refreshToken" : "AAAA-current-refresh"
}

String

진입 (bootstrap)

미니앱 진입 직후 1회 호출해 "나는 누구인가 + 쓸 수 있는가"를 한 번에 받는다. 부트스트랩이 곧 로그인이다 — 응답에 access·refresh 토큰이 동봉된다(v4). 요구 정본은 backend/docs/domain/auth.md §5-2 (v4) · 이용권 스키마는 payment.md §5-3.

POST /api/v1/bootstrap

공개 경로(게이트 밖 — 토큰 발급 지점이라 토큰을 요구할 수 없다). 단 X-Anonymous-Key 헤더는 필수다 — 없으면 등록할 대상이 없어 401 AUTH_001, 형식 위반이면 401 AUTH_002. 멱등하다 — 몇 번 호출해도 사용자는 하나이고 응답도 같다.

HTTP request

POST /api/v1/bootstrap HTTP/1.1
X-Anonymous-Key: toss-anon-hash-0123456789abcdef
Host: api.example.com
Content-Type: application/x-www-form-urlencoded

Path Type Description

Boolean

이번 진입으로 등록됐으면 true — 온보딩 분기

String

최초 등록 시각

auth.accessToken

String

JWT(30분). 이후 전 API 의 Authorization: Bearer 로 보낸다. 만료(AUTH_004)면 /auth/refresh 로 갱신

auth.refreshToken

String

갱신용 불투명 값(14일·회전). 로컬에만 보관한다. 재호출 = 재로그인 — 매번 새로 발급되고 기존 값은 폐기되지 않는다

  • newUser 로 온보딩 노출을 분기한다.

  • auth.accessToken/auth.refreshToken 을 로컬에 보관한다 — 이후 전 API 는 Authorization: Bearer {accessToken}, 만료 시 갱신은 인증 절 참조.

  • 재호출 = 재로그인 — 토큰이 새로 발급된다(기존 refresh 는 폐기되지 않는다 — 다기기 정상 케이스).

  • entitlement 는 이용권 상태 절(payment)과 같은 모양이다 — S1 배지를 즉시 렌더링하고, 분기는 accessible 하나로만 한다.

결제 (payment)

돈은 토스가 받고, "누가 무엇을 쓸 수 있는가"는 서버가 기억한다. 요구 정본은 backend/docs/new-domain/payment-v2.md [주문 애그리거트] 절이다.

엔드포인트는 지급 하나뿐이다.

  • 상품 조회 API 가 없다. 가격은 결제 SDK 가 정본이라 서버가 말하면 결제창과 어긋난다. 상품 코드도 코드가 아니라 설정에 있고, 비어 있는 유형은 어떤 주문으로도 지급되지 않는다(미노출 상품).

  • 이용권 조회 API 가 없다. 기간권과 횟수권을 합성하는 읽기 모델이 아직 없다 — 진입 응답의 이용권 필드도 비어 있다. 프론트 계약으로 확정되기 전이다(payment-v2.md "이번 범위에서 미뤄둔 것").

  • 소모(차감) API 가 없다. 부르는 쪽이 자막 생성 작업인데 그 도메인이 아직 없다.

POST /api/v1/payments/grant — 지급

결제된 주문을 우리 이용권으로 바꾼다. 인증 필요. processProductGrant 콜백과 미결 주문 복원이 같은 엔드포인트를 쓰고, 단건·구독도 같은 엔드포인트다 — 무엇을 샀는지는 서버가 토스에 직접 물어 판별한다.

HTTP request

POST /api/v1/payments/grant HTTP/1.1
Content-Type: application/json;charset=UTF-8
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwicm9sZSI6IlVTRVIiLCJpYXQiOjE3ODcxNDE3OTcsImV4cCI6MTc4NzE0MzU5N30.q41pqHQ2OAV1-Qi_VBxdOU7P2rssBEWAb1jzmaKCZgc
Content-Length: 58
Host: api.example.com

{
  "orderId" : "13c9a1ff-6f0e-4a2b-9f10-5c7a1e2d3b4c"
}

Response fields

Path Type Description

granted

Boolean

지급됐으면 true. 재요청도 true 다(멱등)

productType

String

무엇을 지급했는지 — CONSUMABLE(횟수권) · SUBSCRIPTION(구독). 화면 분기용

  • sku 를 요청에 싣지 않는다. 클라이언트의 주장으로 상품을 정하지 않는다. 서버가 토스에 주문 상태를 조회해 받은 상품 코드로만 판별하고, 모르는 코드면 남의 상품이므로 지급하지 않는다.

  • 같은 주문을 몇 번 요청해도 정확히 한 번만 지급하고, 재요청도 200 granted: true 다. 멱등의 근거는 orderId 하나다. 중복을 오류로 만들면 복원 흐름 자체가 깨진다.

  • 먼저 지급을 요청한 사용자가 주문의 소유자가 된다(선점). 토스에 "이 주문이 누구 것인가"를 물어볼 수단이 없어서, 소유자는 끝까지 클라이언트의 주장이다. 보안 통제가 아니라 먼저 온 쪽을 지키는 규칙이다.

  • 응답에 잔량이 없다. 잔량의 권위는 횟수권 쪽에 있고 지급 경로에는 그것을 읽을 수단이 없다. productType 은 화면 분기용이다 — CONSUMABLE(횟수권) · SUBSCRIPTION(구독).

  • 30초 안에 답한다. 넘기면 사용자에게 환불 안내 화면이 노출된다. 시간이 모자라면 붙잡지 않고 실패로 답하며, 남은 것은 복원이 처리한다.

주문 식별자는 어떤 응답에도 실리지 않는다 — 성공 응답에도, 실패 메시지에도 없다. 주문 식별자를 아는 것은 미지급 주문을 가로챌 수 있는 것과 같다.

구독 (subscription)

매월 자동 갱신되는 계약과 그 계약이 만드는 기간권. 요구 정본은 backend/docs/new-domain/payment.md [구독 애그리거트] 절이다.

서버가 구독 상태를 물어볼 API 는 없다. 최초 결제 이후의 상태 변화를 아는 경로는 웹훅 하나뿐이고, 어긋나도 바로잡을 조회 수단이 없다. 그래서 이 도메인의 엔드포인트는 둘 다 상태를 받아 반영하는 경로이며, 조회 경로가 아니다.

구독을 만드는 API 는 없다. 구독은 결제 지급(POST /api/v1/payments/grant)이 확정될 때 서버 내부에서 열린다 — 웹훅으로도, 재확인으로도 구독은 생기지 않는다.
