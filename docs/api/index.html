인증

이 서비스는 토스 로그인을 쓰지 않는다. 익명키로 로그인(부트스트랩)하고, 이후 전 API 는 JWT Bearer 토큰으로 인증한다.

헤더 어디서 값

Authorization

인증 필요 엔드포인트 전부

Bearer {accessToken} — 부트스트랩이 발급

X-Anonymous-Key

부트스트랩에서만

클라 getAnonymousKey() 의 hash

  • access 토큰은 30분 유효. 만료(AUTH_004)를 받으면 POST /api/v1/auth/refresh 로 갱신 후 1회만 재시도한다 — 이 흐름은 HTTP 인터셉터 한 곳에 둔다(진입 절 참조).

  • refresh 토큰은 14일·회전식 — 갱신할 때마다 새 값으로 바뀌고 이전 값은 즉시 무효다. 로컬에만 보관하고 어떤 로그·화면에도 남기지 않는다.

  • 익명키는 미니앱마다 고유하고 같은 사용자는 항상 같은 값을 받는다(토스 계정 기준). 아는 사람이 곧 그 사용자가 되므로 취급 수준은 자격증명에 준한다 — 부트스트랩 외에는 실지 않는다.

인증 (auth)

익명키 로그인은 부트스트랩(진입 절)이 담당한다 — 부트스트랩이 곧 로그인이고 토큰 발급 지점이다. 이 장은 토큰 갱신 계약만 다룬다. 요구 정본은 backend/docs/domain/auth.md v4.

토큰 갱신 — POST /api/v1/auth/refresh

인증 게이트 밖이다 — 자격 증명이 만료된 상태에서 부르는 API 이기 때문이다. 본문의 refresh 토큰이 자격 증명이다.

HTTP request

POST /api/v1/auth/refresh HTTP/1.1
Content-Type: application/json;charset=UTF-8
Content-Length: 47
Host: api.example.com

{
  "refreshToken" : "AAAA-current-refresh"
}

refreshToken

String

보관 중인 refresh 원문 — 본문이 곧 자격 증명이다(Authorization 불필요). 이 요청이 성공하는 순간 이 값은 폐기된다(회전)

Vary: Origin

Path Type Description

String

새 JWT(30분). 이후 전 API 의 Authorization: Bearer 로 쓴다

String

회전식이다. 응답을 받는 순간 요청에 쓴 refresh 는 폐기된다 — 반드시 새 쌍으로 교체 보관한다. 같은 refresh 를 다시 보내면 서버가 탈취 신호로 간주해 그 사용자의 refresh 전부를 폐기한다 (AUTH_005 → 부트스트랩 재로그인. 익명키는 SDK 가 늘 주므로 마찰 없음).

응답 프론트 행동

200

새 쌍 보관 → 원 요청 1회 재시도

401 AUTH_005 (만료·미존재·재사용)

부트스트랩 재실행(재로그인) → 원 요청 1회 재시도

  • 갱신·재로그인·재시도는 각 1회씩만 — 무한 루프 금지. AUTH_004 → refresh → 재시도 는 HTTP 인터셉터 한 곳에 두고 화면 코드는 모르게 한다.

진입 (bootstrap)

미니앱 진입 직후 1회 호출해 "나는 누구인가 + 쓸 수 있는가"를 한 번에 받는다. 부트스트랩이 곧 로그인이다 — 응답에 access·refresh 토큰이 동봉된다(v4). 요구 정본은 backend/docs/domain/auth.md §5-2 (v4) · 이용권 스키마는 payment.md §5-3.

POST /api/v1/bootstrap

공개 경로(게이트 밖 — 토큰 발급 지점이라 토큰을 요구할 수 없다). 단 X-Anonymous-Key 헤더는 필수다 — 없으면 등록할 대상이 없어 401 AUTH_001, 형식 위반이면 401 AUTH_002. 멱등하다 — 몇 번 호출해도 사용자는 하나이고 응답도 같다.

HTTP request

POST /api/v1/bootstrap HTTP/1.1
X-Anonymous-Key: toss-anon-hash-0123456789abcdef
Host: api.example.com
Content-Type: application/x-www-form-urlencoded

Name Description

X-Anonymous-Key

익명키 — getAnonymousKey() 값. v4 부터 이 엔드포인트에서만 쓴다(이후 전 API 는 Authorization: Bearer)

갱신용 불투명 값(14일·회전). 로컬에만 보관한다. 재호출 = 재로그인 — 매번 새로 발급되고 기존 값은 폐기되지 않는다

String

entitlement.subscription.autoRenew

Boolean

자동 갱신 예정

  • newUser 로 온보딩 노출을 분기한다.

  • auth.accessToken/auth.refreshToken 을 로컬에 보관한다 — 이후 전 API 는 Authorization: Bearer {accessToken}, 만료 시 갱신은 인증 절 참조.

  • 재호출 = 재로그인 — 토큰이 새로 발급된다(기존 refresh 는 폐기되지 않는다 — 다기기 정상 케이스).

  • entitlement 는 이용권 상태 절(payment)과 같은 모양이다 — S1 배지를 즉시 렌더링하고, 분기는 accessible 하나로만 한다.

결제 · 이용권 (payment)

돈은 토스가 받고, "누가 무엇을 쓸 수 있는가"는 서버가 기억한다. 결제의 절반은 클라 SDK 안에서 일어나므로, 이 장은 HTTP 계약과 함께 클라이언트 책임을 명시한다. 요구·정책의 정본은 backend/docs/domain/payment.md 다.

이용권은 두 종류다: 횟수권(단건 2,200원 · 1회) · 기간권(월 구독 3,960원 · 무제한, 30일 주기).

가격을 서버가 내려주지 않는다. 응답의 sku 로 SDK getProductItemList() 결과를 찾아 displayAmount 를 표시한다 — SDK 만이 스토어 결제창과 일치하는 금액을 안다. 가격 하드코딩 금지.

  • productType 으로 주문 함수를 가른다 — CONSUMABLE → createOneTimePurchaseOrder, SUBSCRIPTION → createSubscriptionPurchaseOrder.

  • 상품 키(oneTime/subscription)가 null 이면 그 결제 버튼을 숨긴다 (미노출 상품).

  • 구독 최소 앱 버전이 단건보다 높다 — Android 5.253.0 / iOS 5.250.0 (단건 5.219.0). 미만 버전에서는 구독 버튼을 숨기고 단건만 노출한다.

지급 (grant)

POST /api/v1/payments/grant — 인증 필요. processProductGrant 콜백과 미결 주문 복원이 같은 엔드포인트를 쓴다(멱등). 단건·구독도 같은 엔드포인트 — 상품 판별은 서버가 토스 응답의 sku 로 한다. sku 를 요청에 싣지 않는다.

기타 클라 책임 (검수 항목):

  • 결제 중 음악·영상을 일시정지하고 종료 후 재개한다.

  • 주문 함수의 반환값 cleanup() 을 반드시 호출한다.

  • 결제 시작 전 SDK 에러(USER_CANCELED·UNSUPPORTED_APP_VERSION 등)는 서버 호출 없이 사유를 사용자에게 알린다.

미결 주문 복원 — 필수 (검수 시나리오 ③)

이 절에는 서버 스니펫이 없다 — 전부 클라 전용 흐름이다. 그래도 필수 계약이다. 이 흐름이 없으면 "결제는 됐는데 못 쓰는" 사용자가 남는다. 30초 초과·앱 강제종료·네트워크 단절은 정상 흐름에서도 일어난다.

앱 기동(부트스트랩 성공) 직후, 화면을 막지 않고 배경에서:

IAP.getPendingOrders()
 ├─ undefined(미지원) / 빈 배열 → 통과
 └─ 주문 N건 → 각 orderId 마다 POST /api/v1/payments/grant
     ├─ 200          → completeProductGrant({ params: { orderId } }) 로 미결 종료
     │                  ⚠️ 반환이 boolean | undefined — undefined 방어
     ├─ 409 PAY_002  → 닫지 않고 다음 기동에 재시도
     ├─ 409 PAY_003 / 404 PAY_004 → 지급 대상 아님 → completeProductGrant 로 닫는다
     ├─ 409 PAY_005  → 남의 주문. 조용히 건너뛴다 (사용자에게 노출 금지)
     └─ 502 PAY_006  → 다음 기동에 재시도. 알리지 않는다

  • 진입이 느려지면 검수 "인터랙션 2초"에 걸린다 — 반드시 배경 실행.

이용 게이트 — 403 두 종류

유료 기능(작업 생성)은 이용권 게이트를 거친다. 403 이 두 종류이고 화면이 정반대다:

코드 의미 프론트 행동

403 PAY_001

이용 가능한 이용권이 없다

결제 유도 화면

403 PAY_007

구독 상태 확인이 필요하다 (STALE)

재확인 흐름 (결제 유도 금지)

  • 401 에 결제 유도를 띄우지 않는다 — 인증 문제이지 결제 문제가 아니다. 이미 결제한 사용자에게 다시 결제를 요구하게 된다. 401 처리는 공통 규격(인증 게이트) 절을 따른다.

  • 결제 유도 화면에는 닫기 경로를 반드시 둔다 — "나갈 선택지가 없는 경우"는 다크패턴으로 출시 불가 사유다.

  • 작업 목록·상태·결과 조회는 게이트 밖이다 — 이미 만든 결과물은 이용권 없이도 본다.
