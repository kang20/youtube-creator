# diagram — 도메인 다이어그램 작성

요청한 주제 하나를 **Mermaid 다이어그램 한 장**으로 그려 도메인 폴더에 남긴다.

- **근거는 도메인 정의서다.** 정의서에 없는 관계·상태·호출을 그림으로 발명하지 않는다.
  그림은 읽기 보조물이고, 계약의 정본은 언제나 정의서다.
- **Mermaid 만 쓴다.** PlantUML·이미지 첨부를 만들지 않는다 — 텍스트라야 diff 가 읽히고,
  GitHub·IDE 가 그대로 렌더링한다.
- **이 스킬은 코드를 작성하지 않는다.**

## 입력

- `{주제}` — 무엇을 그릴 것인가 (예: `job state machine`, `자막 생성 시퀀스`, `유스케이스`)
- `{도메인}` — 어느 도메인의 것인가. 말하지 않았으면 주제에서 추론하고, **모호하면 묻는다**

## 산출물 위치

```
backend/docs/new-domain/{도메인}/{주제}.md          한 도메인 안에서 닫히는 그림
backend/docs/new-domain/{a}-{b}/{주제}.md           두 도메인에 걸친 그림 (알파벳순 폴더)
```

- `{주제}` — 소문자 kebab-case. 예: `job-state-machine.md` · `subtitle-flow.md` · `usecase.md`
- **도메인명을 파일명에 넣지 않는다** — 폴더가 이미 말한다.
  `subtitle/subtitle-state.md` 가 아니라 `subtitle/job-state-machine.md` 다.
- 폴더 규약의 정본은 [backend/CLAUDE.md](../../../backend/CLAUDE.md) "도메인 문서 위치" 다.
- 파일이 이미 있으면 **덮어쓰지 않고** 갱신 여부를 사용자에게 확인한다.

## 절차

### 0. 대상 판정

- backend 브랜치인지 확인
- `{도메인}` 을 정한다. `backend/docs/new-domain/` 의 폴더 목록과 대조한다.
  - 정의서가 없는 도메인이면 **`/usecase {name}` 선행을 안내하고 중단한다.**
    요구가 없는데 그림을 그리면 그 그림이 요구가 된다.
  - 두 도메인에 걸치면 `{a}-{b}/` 폴더를 쓴다. 없으면 만든다.
- **정의서 안에 같은 그림이 이미 있는지 확인한다.**
  - 있으면 그 사실을 알리고 **어느 쪽을 정본으로 할지 묻는다.** 둘 다 두면 한쪽이 먼저 낡는다.
  - 옮기기로 했으면 정의서 쪽에는 **파일을 가리키는 링크 한 줄만** 남긴다.

### 1. 근거 수집

- 정의서를 읽는다 — 요구 섹션의 `[대괄호]` 개념, `## 용어 사전` 의 영문명, `## 도메인 모델` 의 애그리거트
- **용어 사전의 영문명을 그대로 쓴다.** 그림이 다른 이름을 쓰면 계약이 두 갈래가 된다
- 정의서에서 답이 안 나오는 부분은 **그리지 않고 🔶 로 남긴다.** 추측해서 채우면 그 추측이 계약처럼 읽힌다

### 2. 종류 선택

주제에 맞는 것을 고른다. 아래 표에 없는 것을 요청받으면 **가장 가까운 것으로 근사하고 그 사실을 밝힌다.**

| 무엇을 보여주려는가 | Mermaid |
|---|---|
| 상태가 어떤 조건으로 어떻게 바뀌는가 | `stateDiagram-v2` |
| 누가 누구를 어떤 순서로 부르는가 | `sequenceDiagram` |
| 구성요소와 관계는 어떻게 생겼는가 | `classDiagram` |
| 데이터가 어떻게 엮이는가 | `erDiagram` |
| 처리가 어떤 갈래로 흐르는가 | `flowchart TD` |
| 사용자가 무엇을 할 수 있는가 (유스케이스) | `flowchart LR` — ⚠️ 아래 주의 |
| 시스템 경계와 바깥이 어떻게 붙는가 | `C4Context` |

> ⚠️ **Mermaid 에는 UML 유스케이스 다이어그램이 없다.** `flowchart LR` 로 액터와 유스케이스를
> 좌우로 놓고 선을 잇는 것이 실무적 대안이다. 액터는 `([...])`, 유스케이스는 `(...)` 로 모양을 갈라
> 둘을 구분한다. **이것이 근사라는 사실을 문서 안에 적는다** — UML 규격이라고 착각하면 안 된다.

### 3. 작성

파일 뼈대는 이렇다.

````markdown
# {제목}

> 근거: [{정의서}]({name}-v{n}.md) — {어느 섹션을 옮긴 것인지}
> **정본은 정의서다.** 이 그림은 읽기 보조물이고, 어긋나면 정의서가 이긴다.
> 작성 {YYYY-MM-DD}

```mermaid
...
```

## 읽는 법

- {그림만 봐서는 안 보이는 것 한 줄}
- {틀리기 쉬운 지점}
````

- **머리말에 근거와 "정본은 정의서"를 반드시 쓴다.** 이 한 줄이 없으면 다음 사람이 그림을 계약으로 읽는다
- `## 읽는 법` 은 **그림이 말하지 못하는 것만** 적는다. 노드를 하나씩 설명하지 않는다
- 한 파일에 다이어그램은 **한 장**이다. 두 장이 필요하면 주제가 둘인 것이므로 파일을 나눈다
- 한글 라벨을 그대로 쓴다. 상태값·클래스명 같은 **코드 식별자만 영문**이다

### 4. 확인

- 코드펜스가 ` ```mermaid ` 로 열리고 닫히는가
- 첫 줄이 유효한 다이어그램 타입 선언인가
- 정의서에 없는 노드·전이가 섞이지 않았는가 — 섞였으면 지우거나 🔶 로 내린다
- 용어 사전의 영문명과 어긋난 이름이 없는가

## 작성 원칙

- **그림 한 장이 답하는 질문은 하나다.** 상태 전이와 호출 순서를 한 장에 겹치면 둘 다 안 읽힌다
- **노드 수가 열다섯을 넘으면 질문이 너무 크다.** 쪼갠다
- 예외·실패 경로를 빼지 않는다. 정상 흐름만 그린 그림은 구현할 때 가장 먼저 배신한다
- `note` 는 **그림으로 표현할 수 없는 제약**에만 쓴다. 설명을 옮겨 적는 자리가 아니다
- 색·스타일 지정을 하지 않는다. 렌더러마다 다르게 보이고, 의미가 색에 실리면 흑백에서 죽는다

## `/domain-model` 과의 경계

둘 다 Mermaid 를 쓰지만 산출물과 목적이 다르다. **겹치면 한쪽이 낡는다.**

| | `/domain-model {module}` | `/diagram {주제}` |
|---|---|---|
| 산출물 | `backend/docs/model/master.md` **한 파일에 통합** | 도메인 폴더의 **개별 파일** |
| 범위 | 모든 모듈의 구조를 한 그림에 | 주제 하나 |
| 종류 | `classDiagram` 고정 | 주제에 맞는 것 |
| 질문 | "전체가 어떻게 생겼나" | "이것이 어떻게 도는가" |

- **구조 그림은 `/domain-model` 몫이다.** 애그리거트·속성·관계를 그리려면 그쪽을 쓴다
- 상태·순서·흐름처럼 **시간이 들어가는 그림**이 이 스킬의 자리다

## 성공 조건

- [ ] 파일이 `backend/docs/new-domain/{도메인}/{주제}.md` 에 있다 (도메인명 중복 없는 파일명)
- [ ] 머리말에 **근거 정의서 링크**와 "정본은 정의서" 선언이 있다
- [ ] 다이어그램이 **한 장**이고 유효한 Mermaid 타입으로 열린다
- [ ] 용어 사전에 있는 개념을 **그 영문명 그대로** 부른다
- [ ] 정의서에 없는 노드·전이를 발명하지 않았다
- [ ] 정의서 안의 같은 그림과 **중복되지 않는다** (옮겼으면 정의서에 링크만 남았다)
- [ ] 예외·실패 경로가 빠지지 않았다
- [ ] 코드가 작성되지 않았다
- [ ] 커밋됨 (`docs({도메인}): {주제} 다이어그램`)

## 안전장치

- **정의서 선행** — 정의서가 없는 도메인에는 그리지 않는다
- **정본 불가침** — 그림은 정의서를 대체하지 않는다. 어긋나면 정의서가 이긴다
- **중복 금지** — 같은 그림을 두 곳에 두지 않는다
- **추측 금지** — 정의서에서 답이 안 나오면 🔶 로 남긴다
- **Mermaid 전용** — 이미지·PlantUML 을 만들지 않는다
- **그림까지만** — 코드를 작성하지 않는다
