# develop-design — 도메인 모델 작성

확정된 요구를 받아 **무엇을 어떤 단위로 다룰지**를 모델로 굳힌다
→ `backend/docs/new-domain/{name}/{name}-v{n}.md` 의 `## 도메인 모델` 섹션

- **산출물은 새 파일이 아니다.** `/usecase` 가 만든 **같은 도메인 정의서에 이어 쓴다.**
  요구와 모델이 한 파일에 있어야 요구가 바뀔 때 모델이 같이 눈에 들어온다.
  두 파일로 갈라 두면 한쪽만 고친 상태가 오래 살아남는다.
- **`backend/docs/domain/` 은 레거시(읽기 전용)다.** 새 도메인은 `backend/docs/new-domain/` 에만 쓴다.
  레거시 5종(`auth.md`·`auth-design.md`·`payment.md`·`payment-design.md`·`subtitle.md`)은
  선례 참조로만 읽고 삭제·이동·재작성하지 않는다.
- **이 스킬은 코드를 작성하지 않는다.** 구현은 `/implement {name}` 몫이다.

## 입력

- `{name}` — 도메인명 (소문자)
- 모드: **신규 모델** | **리팩터링** (사용자 의도에서 판단, 모호하면 질문)
- **선행 입력**: 같은 파일의 **요구 섹션** — 여기에 `## 용어 사전`·`## 참고자료` 가 있으면 함께 읽는다.
  - **요구 섹션은 상태 헤더 다음의 첫 번째 `## ` 섹션이다. 제목 문자열로 찾지 않는다.**
    제목은 `## {도메인명} 도메인` 형식이고 `{도메인명}` 은 한글이어도 되고 영문이어도 된다
    (선례 `## 결제 도메인` 이 정상이다).
  - 요구가 요구·정책의 정본이다. 모델 섹션은 그것을 **중복 기술하지 않는다.**
  - **용어 사전의 영문명이 코드 식별자의 계약이다.** 사전에 **있는** 개념은 그 영문명을 그대로 쓴다.
    사전에 없는 **구조물 이름**(_Domain Service_·_Value Object_·_Enum_·_Policy Constant_ 의 클래스명)은
    모델이 새로 만들어도 된다 — 용어 사전은 사람이 말로 부르는 비즈니스 개념을 담는 곳이다.
  - `## 🔶 결정 필요` 의 `### 요구 🔶` 에 **한 건이라도 남아 있으면 시작하지 않는다** (아래 사전 검증).

> 도메인 정의서에는 값 대신 링크를 쓴다. 복사본은 원본보다 먼저 낡는다.

## 절차

### 0. 사전 검증

- backend 브랜치인지 확인
- **모드를 먼저 정한다** — 신규 모델 | 리팩터링. 사용자 의도에서 판단하고 모호하면 묻는다.
  **진입 조건이 모드마다 다르므로 모드를 정하기 전에는 아무것도 검증하지 않는다.**

#### 신규 모델 모드 — 정의서가 있어야 시작한다

- `backend/docs/new-domain/{name}/{name}-v*.md` 존재 확인. **없으면 `/usecase {name}` 선행 안내 후 중단**
  (요구가 없는데 모델을 그리면 그 모델이 요구가 돼버린다)
- **`### 요구 🔶` 잔여 확인.** 한 건이라도 남아 있으면 그 목록을 그대로 보여주고
  `/usecase {name}` 로 확정을 먼저 받으라고 안내한 뒤 **중단**한다.
  요구가 흔들리는 상태에서 모델을 굳히면 같은 파일을 두 번 갈아엎는다.
- **상태 헤더가 `요구 확정({날짜})` 이상인지 확인한다.** `요구 초안` 인데 🔶 가 0건이면
  헤더 갱신이 누락된 것이므로 사용자에게 확인한다.
- **`## 도메인 모델` 이 이미 있으면 덮어쓰기 금지** → 갱신 모드로 사용자 확인을 받는다.
  - 확정 전(🔶 남은 초안)이면 그냥 고친다. 버전이 아니다.
  - 이미 **설계 확정**된 문서를 고치는 것이면 **버전 올림**이다:
    `git mv {name}-v{n}.md {name}-v{n+1}.md` 로 rename 하고, 추가 항목에 **(v{n+1})**,
    바뀐 값은 ~~이전~~ → 새값 **(v{n+1})**, 없앤 항목은 **빗금 + 사유**로 남긴다.
    **빗금 항목을 지우지 않는다** — "없다"가 아니라 "있었는데 왜 없앴다"가 남아야 같은 논의가 반복되지 않는다.
    rename 뒤 다른 문서가 걸어둔 링크를 `grep` 으로 찾아 함께 고친다.

#### 리팩터링 모드 — 정의서가 없어도 진행한다

산출물이 도메인 정의서가 아니라 `backend/docs/ops/refactor-{name}.md` 다.
정의서 부재를 중단 사유로 쓰지 않는다 — 그러면 정의서가 없는 레거시가 영영 리팩터링 대상이 못 된다.

- **정의서가 없어도 진행한다.** `### 요구 🔶` 잔여·상태 헤더를 진입 조건으로 걸지 않는다.
- 대상이 **레거시 도메인(`backend/docs/domain/`)이면 그 문서는 계획서에서 현재 상태의 인용원으로만 쓴다.**
  **레거시 파일은 고치지 않는다**(읽기 전용 5종).
- `backend/docs/new-domain/{name}/{name}-v{n}.md` 가 있으면 현재 모델의 근거로 함께 읽는다.
  리팩터링으로 **모델이 바뀌면** 그 갱신분만 정의서로 흡수한다(확정 문서였으면 위 버전 올림 규칙과 같다).
- `backend/docs/ops/refactor-{name}.md` 가 이미 있으면 덮어쓰기 금지 → 갱신 여부를 사용자에게 확인한다.

### 1. 선례 조사 (코드 기반)

유사 기능의 **실제 코드**를 읽는다 — 엔티티·서비스·리스너·타입 ID.
"○○ 모듈과 같은 패턴" 한 줄이 구현 절반의 스펙이므로, 짐작이 아니라 파일을 열고 확인한다.

**모듈 의존 그래프를 먼저 그려본다.** 두 모듈이 서로를 참조하면 `ApplicationModules.verify()` 가 깨진다.

- 그래프는 **머릿속 작업물이다. 산출물에 모듈 매핑표를 쓰지 않는다** — 파일 배치의 정본은
  [architecture.md](../../../backend/docs/rule/architecture.md) 다.
- **예외는 하나다: 의존 방향 한 줄은 `### 애그리거트 간 관계` 에 남긴다.**
  (예: "구독은 주문을 참조하지 않는다. 지급 사실은 이벤트로 흐른다")
  이 한 줄이 developer 가 `{module}/package-info.java` 의 `allowedDependencies` 를 도출하는 근거다.
  방향을 적지 않으면 구현자가 매번 다시 추론하고, 추론이 갈리면 `ApplicationModules.verify()` 에서야 깨진다.
- 그래도 **매핑표·패키지 경로·클래스 배치는 쓰지 않는다.** 남기는 것은 "누가 누구를 모르는가" 뿐이다.
- 의존이 순환하면 **한쪽을 이벤트로 뒤집을 지점**을 정하고, 그 결과만 애그리거트의 `#### 규칙`
  문장으로 녹인다. (예: "작업 실패는 이 애그리거트가 조회하지 않는다. 실패 사실을 받아 해제한다")

선례가 없으면(첫 도메인이면) 그 사실을 명시하고, 이 모델이 이후 선례가 된다는 전제로 쓴다.

### 2. 모델링

애그리거트 경계 → 구성요소 → 규칙 순으로 정한다.

- **변경 트리거가 다르면 애그리거트를 나눈다.** 합치면 동시성 대책이 전부 한 행에 몰린다.
- 애그리거트끼리는 **연관관계를 갖지 않고 식별자로만 참조한다.**
- 요구 섹션의 **[대괄호] 개념이 전부 모델에 대응되는지** 대조한다. 빠지면 요구 누락이다.
- 동시성은 **별도 섹션을 만들지 않고** 해당 애그리거트의 `#### 규칙` 문장에 녹인다.

> **대안을 비교해 하나를 고른 지점**이 있으면 `/adr-create` 로 따로 기록할지 사용자에게 제안한다.
> 도메인 정의서는 "무엇을 어떻게"를 담고 버전이 오르면 갱신되지만, ADR 은 **"왜 그렇게 정했나"** 를
> 그 시점 판단으로 동결한다. 기각안이 한 줄로 담기엔 아까운 논의가 그 대상이다.
> **대안이 하나뿐이었던 결정은 ADR 로 만들지 않는다** — 기각 카드가 없는 ADR 은 빈 껍데기다.

### 3. 작성

[references/template.md](references/template.md) (신규) 또는
[references/refactoring.md](references/refactoring.md) (리팩터링) 를 따른다.

- 섹션 위치는 고정이다: `## 용어 사전` 뒤, `## 🔶 결정 필요` 앞.
- 정하지 못한 것은 본문에 **마크만** 달고(`### 만료 완충(EXPIRY_BUFFER) 🔶`)
  내용은 `## 🔶 결정 필요` 의 `### 모델 🔶` 에 모은다.
  형식: `- **{한 줄 질문}** — 제안: {값}. 근거: {한 줄}. 위치: {본문 어디}`
- **`### 요구 🔶` 와 `### 모델 🔶` 두 그룹 제목은 항상 둘 다 있다.**
  항목이 없는 그룹은 **제목 아래를 비운다** — `- 없음` 같은 불릿을 쓰지 않는다.
  불릿이 없는 빈 그룹은 **0건으로 센다.**
- 상태 헤더의 상태와 🔶 건수를 갱신한다.
- 모델이 만든 이름 중 **사용자가 대화에서 실제로 부르는 말**이 있으면
  `/usecase 용어 {name}` 으로 사전에 올리자고 **제안한다** — 이 스킬이 직접 용어 사전을 고치지 않는다.
  강제가 아니다. 사람이 부르지 않는 구조물 이름은 제안 대상도 아니다.

### 4. 검증 — `spec-verifier` 에이전트에 위임

**신규 모델 모드만 해당한다.** 문서를 다 쓰면 **사용자에게 보고하기 전에** 검증 에이전트를 호출한다.
자기가 쓴 문서를 자기가 보면 "쓰면서 확인했다"고 느낀 항목을 다시 안 본다.

```
Agent(subagent_type="spec-verifier",
      prompt="backend/docs/new-domain/{name}/{name}-v{n}.md 를 검증. 단계: develop-design. {v}회차")
```

- **기호를 섞지 않는다.** `{n}` = 정의서 버전 · `{v}` = spec-verifier 검증 회차(1..3).
  파일명의 `{n}` 과 회차의 `{v}` 는 다른 값이다 — 한 문장에 둘 다 나오므로 기호를 분리한다.
  (전체 기호 정리: `{n}`=정의서 버전 · `{k}`=리뷰 회차 · `{r}`=내부 라운드 · `{v}`=spec-verifier 검증 회차)
- **단계 토큰은 `develop-design` 고정이다.** 이 스킬은 다른 값을 넘기지 않는다.
  단계를 빼면 검증자가 섹션 존재로 단계를 추론하게 되고, 틀린 표로 검사하면 PASS 도 FAIL 도 무의미하다.
- **리팩터링 모드는 이 에이전트를 호출하지 않는다** — 대상 파일이 도메인 정의서가 아니라
  `backend/docs/ops/refactor-{name}.md` 다. 검사 표가 그 파일을 판정하지 못한다.
  대신 아래 '성공 조건 — 리팩터링 모드' 를 이 스킬이 직접 대조한다.
  단, 리팩터링으로 **모델이 바뀌어 정의서를 갱신했다면** 그 갱신분은 신규 모델 모드와 똑같이 검증한다.
- **FAIL** → 수정 후 재호출(`{v}` 를 1 올려 알린다). **최대 3회.**
- 같은 항목이 두 번 연속 FAIL 이면 수정 방향이 틀린 것이므로 사용자에게 묻는다.
- **⚠️ 확인 요청**·**판정 보류** 항목(임의 확정 의심, 커밋 여부)은 이 스킬이 대화 맥락으로 직접 판단한다.

### 5. 보고 + 다음 단계

- 핵심 모델 결정(특히 애그리거트를 나눈 이유, 동시성 대책)을 요약 보고하고 확인받는다
- `### 모델 🔶` 목록을 제시해 확정을 유도한다
- 커밋: `docs({name}): 도메인 모델 작성` / `docs({name}): 리팩터링 계획 작성`
- **모델 🔶 이 전부 확정되면** 상태 헤더를 `설계 확정({날짜})` 으로 바꾸고
  `docs({name}): 설계 확정` 커밋 → `/implement {name}` 안내

### 신규 모델 모드

아래를 **전부** 만족해야 끝난 것이다.
판정은 [spec-verifier](../../agents/spec-verifier.md) 가 독립 컨텍스트에서 대조한다 —
**검사 표가 정본이며, 표에 없는 항목은 이 스킬이 직접 확인한다.**

- [ ] `## 도메인 모델` 이 **애그리거트 단위**로 나뉘고, 애그리거트 사이가 `---` 로 갈린다
- [ ] 모든 구성요소에 스테레오타입이 있고 **7종 어휘만** 썼다
      (_Aggregate Root_ · _Entity_ · _Value Object_ · _Domain Service_ · _Enum_ · _Read Model_ · _Policy Constant_)
- [ ] 소제목이 `#### 속성` / `#### 행위` / `#### 규칙`(Enum 은 `#### 상수`) 이고,
      해당 없는 소제목은 **생략**됐다 (억지로 채우지 않았다)
- [ ] **동시성이 별도 섹션이 아니라 `#### 규칙` 문장으로 녹아** 있다
- [ ] `### 오류 코드(ErrorCode)` 와 `### 애그리거트 간 관계` 섹션이 있다
- [ ] `### 애그리거트 간 관계` 에 **의존 방향 한 줄**이 있다 (예: "구독은 주문을 참조하지 않는다.
      지급 사실은 이벤트로 흐른다") — developer 가 `allowedDependencies` 를 여기서 도출한다
      ⚠️ 선례 `payment-v2.md` 는 이 한 줄을 **v2 에서야 넣었다** — v1 작성 시점에 그 규약이 없었다.
      v1 판을 베낀 문서에는 빠져 있다. **신규 문서는 반드시 넣는다.**
- [ ] **용어 사전에 있는 개념**을 모델이 그 영문명 그대로 부른다 (다른 이름으로 부르면 계약이 두 갈래가 된다).
      검사는 **한 방향뿐이다** — 사전에 없는 **새 구조물 이름**(_Domain Service_·_Value Object_·_Enum_·
      _Policy Constant_ 의 클래스명)은 모델이 만들어도 되고, 그것을 지적하지 않는다
- [ ] 요구 섹션의 **모든 [대괄호] 개념이 모델에 대응**된다
- [ ] **모듈 매핑표·테스트 계획·트랜잭션 다이어그램·의사코드·자바 코드·DDL 이 하나도 없다**
      (위 의존 방향 한 줄은 매핑표가 아니다 — 방향과 이유만 적고 패키지 경로·배치를 적지 않았다)
- [ ] 헥사고날 용어(포트·어댑터·인바운드/아웃바운드·레이어·presentation)가 **하나도 없다**
- [ ] 요구·정책·API JSON 을 **중복 기술하지 않았다**
- [ ] 정하지 못한 것이 본문 마크 + `### 모델 🔶` 항목으로 짝지어 있다 (임의 확정이 없다)
- [ ] 코드가 작성되지 않았다 (이 스킬은 문서까지)
- [ ] 커밋됨

### 리팩터링 모드

산출물이 도메인 정의서가 아니므로 **spec-verifier 가 판정하지 않는다.** 이 스킬이 직접 대조한다.

- [ ] 계획이 `backend/docs/ops/refactor-{name}.md` 에 있다 (도메인 정의서에 섞지 않았다)
- [ ] [references/refactoring.md](references/refactoring.md) 의 **7개 절이 전부** 있다
      (동기/문제점 · As-Is · To-Be · 변경 범위&영향 · 단계별 작업 · 검증 · 롤백/리스크)
- [ ] 동기가 **측정 가능한 신호**로 적혔다 (`verify()` 실패 메시지·커버리지 사각·중복 라인 수 —
      "지저분하다"는 동기가 아니다)
- [ ] To-Be 에 `ApplicationModules.verify()` 통과 여부와 `allowedDependencies` 변화가 적혔다
- [ ] 변경 범위 표에 **테스트 파일이 빠짐없이** 들어 있다
- [ ] 단계마다 커밋이 끊기고, 각 단계 뒤 `./gradlew test` 로 그린을 유지한다고 적혔다
- [ ] **모델 변경분이 도메인 정의서 `## 도메인 모델` 로 흡수**됐다
      (애그리거트 경계·속성·행위·규칙이 달라졌으면 정의서를 갱신했고, 확정 문서였으면 버전 올림)
- [ ] 파일 이동·클래스 분리·패키지 재배치를 **도메인 정의서에 쓰지 않았다** (모델의 변화가 아니다)
- [ ] 레거시 `backend/docs/domain/` 문서를 고치지 않았다 (현재 상태로만 인용)
- [ ] 코드가 작성되지 않았다 (이 스킬은 계획까지)
- [ ] 커밋됨

## 안전장치

- **요구 확정 선행(신규 모델 모드)** — `### 요구 🔶` 가 남아 있으면 모델을 쓰지 않는다.
  **리팩터링 모드는 이 조건을 걸지 않는다** — 산출물이 정의서가 아니다(0단계)
- **한 파일 원칙** — 정본은 `{name}-v{n}.md` 하나다. `-design.md` 같은 파생 파일을 만들지 않는다.
  같은 폴더의 ADR(`/adr-create`)·다이어그램(`/diagram`)은 파생이 아니라 **다른 종류**다 —
  정의서를 대체하지 않고, 어긋나면 정의서가 이긴다
- **레거시 불가침** — `backend/docs/domain/` 의 5종은 읽기만 한다
- **기존 섹션 덮어쓰기 금지** — `## 도메인 모델` 이 있으면 갱신 모드로 사용자 확인 후
- **빗금 보존** — 버전을 올릴 때 없앤 항목은 사유와 함께 남긴다
- **문서 기반·추측 금지** — 근거 없는 내용은 `### 모델 🔶` 로 남긴다
- **모델까지만** — 코드를 작성하지 않는다
- **규칙 정합성 self-check** — architecture / testing / error-handling 과 모순되면 수정한다
- **MVP 범위 우선** — 요구의 범위 밖 항목은 모델에서도 범위 밖이다

```
/usecase {name}              요구      ┐
/usecase {name} {정보}        참고자료   ├→ backend/docs/new-domain/{name}/{name}-v{n}.md
/usecase 용어 {name}          용어 사전  ┘        (하나의 도메인 정의서)
    │  (요구 🔶 전부 확정 후)
    ▼
/develop-design {name}       도메인 모델 → 같은 파일에 '## 도메인 모델' 추가   [이 스킬]
    │  (모델 🔶 전부 확정 후)
    ▼
/implement {name}            developer ⇄ tester (5라운드) → code-reviewer (3회)
    ▼
/docs-sync                   테스트 리포트 + REST Docs + main 문서 push
    ▼
/domain-model {module}       모델 그림 → backend/docs/model/master.md
```
