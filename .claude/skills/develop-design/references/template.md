# 도메인 모델 섹션 양식 + 작성 원칙

> `backend/docs/new-domain/{name}/{name}-v{n}.md` 안의 **`## 도메인 모델` 섹션** 양식이다.
> 별도 파일을 만들지 않는다 — 요구를 쓴 그 파일에 이어 쓴다.
> 리팩터링 계획은 [refactoring.md](./refactoring.md) 를 쓴다.

**유일한 양식 선례는 [payment-v2.md](../../../../backend/docs/new-domain/payment/payment-v2.md) 다. 반드시 읽고 그 밀도·문체를 따른다.**

## 섹션이 놓이는 자리

도메인 정의서의 섹션 순서는 고정이다. 모델은 **용어 사전 뒤, 🔶 앞**이다.

```
# {Name} 도메인 정의서
> 상태 헤더

## {도메인명} 도메인          ← 요구        (/usecase 가 쓴다)
## 참고자료 — {제목}         ← 0..n개(선택) (/usecase 가 쓴다)
## 용어 사전                ← 선택        (/usecase 가 쓴다)
## 도메인 모델              ← 여기        (/develop-design 이 쓴다)
## 🔶 결정 필요             ← 모든 단계가 누적한다
## 변경 이력                ← v2 이상일 때만
```

**요구 섹션은 상태 헤더 다음의 첫 번째 `## ` 섹션이다. 제목 문자열로 찾지 않는다.**
제목은 `## {도메인명} 도메인` 형식이고 `{도메인명}` 은 한글이어도 되고 영문이어도 된다
(선례 `## 결제 도메인` 이 정상이다). 이름을 강제하지 않으므로 위치로 식별한다.

## 양식

```markdown
## 도메인 모델

> **애그리거트는 {n}개다.** {나눈 이유 한 줄 — 변경 트리거가 다르다는 사실}
> 애그리거트끼리는 **연관관계를 갖지 않고 식별자로만 참조한다.**
> {이 도메인이 다른 모듈의 무엇을 알지 못하는지 한 줄}

---

### [{한글명} 애그리거트]

### {한글명}({English})

_Aggregate Root_

#### 속성

- `id`: `Long` — 대리키. 밖으로 나가지 않는다
- `{field}`: `{Type}` {의미}. **UNIQUE**
- `{field}`: {의미}

#### 행위

- `static {method}()`: {무엇을 하는가}
  - {필요하면 조건 한 줄}
- `{method}()`: {무엇을 하는가}

#### 규칙

- {불변식 한 문장} — {왜 그런가}
- {금지 한 문장}. {안 지키면 무슨 일이 나는가}
- {동시성이 있으면 여기 문장으로 녹인다}

### {한글명}({English})

_Value Object_

#### 속성

- `value`: {무엇}

#### 규칙

- {이 타입을 따로 만든 이유}

### {한글명}({English})

_Enum_

#### 상수

- `{CONSTANT}`: {의미} — {부연}

### {한글명}({CONSTANT_NAME})

_Policy Constant_

#### 규칙

- {이 값이 무엇을 완충하는가}. {우리가 정한 정책이라는 사실}
- **{플랫폼이 주는 비슷한 값}과 다른 것이다.** 앞은 {외부}가 주는 사실, 이것은 우리가 고른 숫자다

---

### [{다른 한글명} 애그리거트]

...

---

### 오류 코드(ErrorCode)

_Enum_

#### 상수

- {거절 사유를 의미 문장으로 적는다 — enum 이름은 여기서 확정하지 않는다}
- ...

#### 규칙

- {어떤 거절과 어떤 거절이 다른 코드여야 하는가, 왜}
- {오류 메시지에 실으면 안 되는 값}

---

### 애그리거트 간 관계

- {서로를 참조하지 않는다는 사실과 연결고리가 되는 값}
- {의존 방향 한 줄 — 누가 누구를 모르고, 그 사실이 무엇으로 흐르는가}
- {한 덩어리로 일어나야 하는 쓰기와 그 이유}
- {생명주기가 서로 다른 짝}
- {여러 애그리거트를 한 번에 보는 것은 읽기뿐이라는 선언}
```

## 스테레오타입 — 7종만 쓴다

| 스테레오타입 | 언제 쓰는가 | 판별 질문 |
|---|---|---|
| _Aggregate Root_ | 그 자체로 저장·조회되고, 자기 불변식을 스스로 지키는 것 | "밖에서 이 단위로 트랜잭션을 여는가" |
| _Entity_ | 식별자로 구분되지만 애그리거트 루트에 딸려서만 살고 죽는 것 | "루트 없이 단독으로 저장할 일이 있는가" — 없으면 Entity |
| _Value Object_ | 값으로만 판단되는 것. **밖으로 나가는 식별자만 타입을 만든다** | "이 값이 모듈 경계를 넘는가, 아니면 강제할 규칙이 붙는가" — 둘 다 아니면 원시 값 그대로 쓴다 |
| _Domain Service_ | **상태를 갖지 않는** 순수 판정, 또는 외부 왕복 | "저장소를 알아야 하는가" — 알아야 하면 서비스가 아니라 애그리거트의 책임이다 |
| _Enum_ | 닫힌 값 목록 | "값이 늘어나면 코드도 같이 바뀌어야 하는가" |
| _Read Model_ | **조회 시점에 조립**하는 응답 모양. 테이블도 애그리거트도 아니다 | "이걸 쓰는 경로가 있는가" — 있으면 Read Model 이 아니다 |
| _Policy Constant_ | **우리가 정한 정책값** | "플랫폼이 주는 사실인가, 우리가 고른 숫자인가" — 후자만 여기다 |

- **대리키는 타입을 만들지 않는다.** `id: Long` 이면 충분하다. 타입 ID 는 밖으로 나가는 식별자에만 붙인다
  (→ [architecture.md](../../../../backend/docs/rule/architecture.md) "타입화된 식별자").
- _Policy Constant_ 와 플랫폼 값을 섞지 않는다. 예: 결제 실패 유예는 토스가 주는 사실이고,
  만료 완충은 우리가 정한 정책이다. **둘이 같은 말로 불리면 개폐표를 읽을 수 없다.**
- _Policy Constant_ 는 소제목으로 **`#### 규칙` 만 둔다.** 속성·행위를 만들지 않는다 —
  값 하나에 이름을 붙인 것이므로 속성 목록이 붙는 순간 그것은 애그리거트로 자란다.
  값 자체를 확정하지 못했으면 제목에 🔶 를 달고 내용은 `### 모델 🔶` 로 올린다.
- _Domain Service_ 를 "서비스니까"로 만들지 않는다. 상태를 만지는 순간 그것은 애그리거트의 행위다.

## 애그리거트 경계 — 변경 트리거가 다르면 나눈다

- **기준은 하나다: 무엇이 이 데이터를 바꾸는가.** 트리거가 다르면 나눈다.
  (주문은 지급이, 구독은 웹훅이, 잔량은 소모가, 티켓은 작업이 바꾼다 → 4개)
- 합치면 동시성 대책이 전부 한 행에 몰린다. 서로 무관한 두 갱신이 같은 잠금을 다투게 된다.
- **애그리거트끼리는 연관관계를 갖지 않는다.** 식별자 값으로만 참조한다 —
  객체 참조를 두면 경계가 없는 것과 같고, 모듈을 가를 때 통째로 딸려온다.
- 다른 모듈의 엔티티를 알지 못한다. 사용자는 언제나 `UserId` 같은 **값**으로 표현한다.
- 여러 애그리거트를 한 번에 보는 것은 **읽기뿐이다.** 쓰기는 어디서도 합쳐지지 않는다.
- 의존이 순환하면 한쪽을 **이벤트로 뒤집고**, 그 결과만 규칙 문장으로 적는다.
  ("실패 사실을 조회하지 않는다. 받아서 해제한다")

## `### 애그리거트 간 관계` — 의존 방향 한 줄은 반드시 남긴다

모듈 매핑표는 쓰지 않는다. **예외는 하나, 의존 방향 한 줄이다.**

- 형식은 "**누가 누구를 모르는가 + 그 사실이 무엇으로 흐르는가**" 다.
  예: "구독은 주문을 참조하지 않는다. 지급 사실은 이벤트로 흐른다"
- 이 한 줄이 developer 가 `{module}/package-info.java` 의 `allowedDependencies` 를 도출하는 근거다.
  방향이 문서에 없으면 구현자가 매번 다시 추론하고, 추론이 갈리면 `ApplicationModules.verify()` 에서야 깨진다.
- 순환이 보이면 **한쪽을 이벤트로 뒤집은 결과**를 이 줄에 적는다. 순환을 그대로 적으면 구현도 그대로 순환한다.
- 그래도 **패키지 경로·클래스 배치·매핑표는 쓰지 않는다.** 남기는 것은 방향과 그 이유뿐이다 —
  배치의 정본은 [architecture.md](../../../../backend/docs/rule/architecture.md) 다.

## 동시성 — 별도 섹션이 아니라 규칙 문장이다

동시성 전용 섹션을 만들지 않는다. **그 불변식을 가진 애그리거트의 `#### 규칙` 에 한 문장으로 녹인다.**
섹션으로 떼어내면 규칙과 대책이 멀어져서, 규칙만 읽은 사람이 그대로 구현한다.

쓰는 법은 셋이다.

1. **깨지는 경로를 먼저 적는다** — "왜 안 되는가"가 없으면 다음 사람이 같은 코드를 다시 짠다
2. **대책을 조건으로 말한다** — 락 종류·SQL 을 쓰지 않는다. 구현 재량이다
3. **새면 무슨 일이 나는가**를 붙인다 — 손해의 크기가 대책의 강도를 정한다

선례 두 개가 정본이다.

- 잔량(`CreditBalance`)
  - "**잔량을 바꾸는 행위를 엔티티가 갖지 않는다.** 읽어서 계산한 뒤 저장하면,
    잔량 1을 두 요청이 함께 읽고 둘 다 통과한다"
  - "잔량은 절대 음수가 되지 않는다. 이 불변식은 **'잔량이 남아 있을 때만 줄인다'는 갱신 조건**이 지킨다"
  - "음수 금지를 저장소 제약으로 걸지 않는다. 걸면 잔량 부족이 오류로 튀어 정상 판정 경로와 갈라진다"
- 구독(`Subscription`)
  - "**순서 판정과 반영은 분리될 수 없다.** 읽어서 비교한 뒤 쓰면 동시에 도착한 두 웹훅이 둘 다 통과한다.
    **판정 조건을 갱신문 자체에 넣는다**"
- 이용 티켓(`UsageTicket`)
  - "확정과 해제는 예약 상태일 때만 일어나야 하고, **그 판정과 전이는 갈라질 수 없다**"
  - "확정과 해제는 각각 한 번만 일어난다. **해제가 두 번 일어나면 잔량이 두 번 올라 무료 이용권이 샌다**"

멱등도 같은 자리에 쓴다 — "멱등 판정을 '조회해서 없으면 삽입'으로 하지 않는다.
동시에 들어온 두 요청이 둘 다 조회를 통과한다. **UNIQUE 제약 하나가 멱등의 유일한 근거다**".

## 작성 문체

- **번호 체계를 쓰지 않는다.** U1/U2, §5-2 같은 번호를 붙이지 않는다. 계층 불릿 산문이다.
  (요구 추적은 구현 단계의 `backend/workspace/{name}/v{n}/requirements.md` 가 맡는다)
- 한 불릿 = 한 사실. 두 줄을 넘기지 않는다.
- **"왜"를 같은 불릿이나 바로 아래 하위 불릿에 붙인다.** 규칙만 나열하면 다음 사람이 그 규칙을 지운다.
- 표는 **열거**에만 쓴다(상태 값 목록, 외부 스펙 표). 규칙은 불릿이다.
- 속성은 이름·타입·의미를 적고 제약은 굵게(**UNIQUE**). **대리키인지 밖으로 나가는 식별자인지 밝힌다.**
- 행위는 메서드명과 "무엇을 하는가"까지다. **시그니처를 완성하지 않는다** — 파라미터·반환형은 구현 재량이다.
- 오류 코드 상수는 **의미 문장**으로 적는다. enum 이름을 여기서 확정하지 않는다(영문명의 정본은 용어 사전).
- 용어 사전에 **있는** 개념은 그 영문명을 그대로 쓴다 — 어긋나면 계약이 두 갈래가 된다.
  모델이 만드는 **구조물 이름**(_Domain Service_·_Value Object_·_Enum_·_Policy Constant_ 의 클래스명)은
  용어 사전 대상이 **아니다.** 용어 사전은 사람이 말로 부르는 비즈니스 개념을 담는다.
  - 그중 **사용자가 대화에서 실제로 부르는 말**이 있으면 `/usecase 용어 {name}` 으로 올리자고 **제안한다.**
    이 스킬이 직접 용어 사전을 고치지 않는다.
- 정하지 못한 것은 제목에 **마크만** 단다: `### 만료 완충(EXPIRY_BUFFER) 🔶`
  내용은 `## 🔶 결정 필요` 의 `### 모델 🔶` 에 모은다.
- **`## 🔶 결정 필요` 아래에는 `### 요구 🔶` 와 `### 모델 🔶` 두 그룹 제목이 항상 둘 다 있다.**
  항목이 없는 그룹은 **제목 아래를 비운다** — `- 없음` 같은 불릿을 쓰지 않는다.
  불릿이 없는 빈 그룹은 **0건으로 세고 형식 검사 대상이 아니다.**

## 이 양식에 **없는** 것

옛 설계서에 있던 아래 셋은 여기 쓰지 않는다. 각각 담당이 따로 있다.

| 빠진 것 | 어디가 담당하는가 |
|---|---|
| 모듈 매핑표 (`package-info`·`allowedDependencies`·파일 배치) | [architecture.md](../../../../backend/docs/rule/architecture.md) 가 정본이고, `package-info.java` 는 developer 가 만든다. 모델은 배치를 말하지 않는다 — **예외는 `### 애그리거트 간 관계` 의 의존 방향 한 줄뿐이다** |
| 동시성 상세 섹션 (시나리오 표·대안 비교·SQL) | 해당 애그리거트의 `#### 규칙` 문장. 대안 비교가 아까우면 `/adr-create` |
| 테스트 계획 | [testing.md](../../../../backend/docs/rule/testing.md) + 구현 단계의 `backend/workspace/{name}/v{n}/requirements.md` |

같은 이유로 **트랜잭션 다이어그램·의사코드·자바 코드·DDL 도 쓰지 않는다.**
모델은 "무엇이 무엇인가"까지고, "어떻게 만드는가"는 구현의 몫이다.
요구·정책·API JSON 도 **다시 적지 않는다** — 같은 파일 위쪽에 이미 있다.

## Modulith 용어 주의

이 프로젝트는 **레이어드/헥사고날 구조를 쓰지 않는다**(→ [architecture.md](../../../../backend/docs/rule/architecture.md)).
아래 용어를 쓰지 않는다 — 규칙과 충돌하고, 처방도 틀리게 나온다.

| 쓰지 않는 말 | 대신 |
|---|---|
| 인바운드/아웃바운드 포트, 어댑터 | 애그리거트의 행위, 모듈 공개 API |
| 레이어(presentation/application/infra) | 애플리케이션 모듈(패키지) |
| 순환 참조 → 포트 분리 | 순환 의존 → **이벤트로 뒤집기** |

## 선례 — payment-v2.md 의 `## 도메인 모델`

전문은 [payment-v2.md](../../../../backend/docs/new-domain/payment/payment-v2.md) 에 있다. 구성은 다섯 구획이다.

```
[주문 애그리거트]      Order(AR) · OrderId(VO) · ProductType(Enum) · ProductCatalog(DS) · OrderVerifier(DS)
[구독 애그리거트]      Subscription(AR) · SubscriptionStatus(Enum) · WebhookEvent(VO) · AccessGate(DS) · EXPIRY_BUFFER(PC) 🔶
[횟수권 애그리거트]    CreditBalance(AR) · Balance(VO)
[이용 티켓 애그리거트] UsageTicket(AR) · UsageTicketId(VO) · TicketStatus(Enum) · TicketSource(Enum)
[읽기 모델]           Entitlement(RM) · Membership(VO)
--- 오류 코드(ErrorCode) · 애그리거트 간 관계
```

머리말과 첫 구획을 그대로 옮긴다. **이 밀도가 기준이다.**

```markdown
> **애그리거트는 4개다.** 변경 트리거가 서로 다르기 때문이고, 하나로 합치면 동시성 대책이 전부 한 행에 몰린다.
> 애그리거트끼리는 **연관관계를 갖지 않고 식별자로만 참조한다.**
> 사용자는 언제나 `UserId` 로만 표현한다 — 결제 도메인은 `User` 엔티티를 알지 못한다.

---

### [주문 애그리거트]

### 주문(Order)

_Aggregate Root_

#### 속성

- `id`: `Long` — 대리키. 밖으로 나가지 않는다
- `orderId`: `OrderId` 주문 식별자 - Natural ID. **UNIQUE**
- `userId`: `UserId` 소유자
- `sku`: 상품 코드. 토스가 답한 값이다
- `productType`: `ProductType` 상품 유형
- `grantedAt`: 지급 일시

#### 행위

- `static grant()`: 지급. 검증된 주문 정보로 원장 한 행을 만든다.
- `ownedBy()`: 이 주문이 해당 사용자의 것인지 판정한다

#### 규칙

- 주문 식별자는 중복될 수 없다. **이 제약 하나가 멱등의 유일한 근거다**
- 멱등 판정을 "조회해서 없으면 삽입"으로 하지 않는다. 동시에 들어온 두 요청이 둘 다 조회를 통과한다
- 한 주문의 소유자는 한 번 정해지면 바뀌지 않는다. 소유자 필드는 수정할 수 없다
- 주문은 지급 이후 상태가 변하지 않는다. **취소·환불로도 변하지 않는다** — 환불은 우리가 처리하지 않는다

### 주문 식별자(OrderId)

_Value Object_

#### 속성

- `value`: 토스가 발급한 주문 식별값

#### 행위

- `masked()`: 로그·응답에 쓸 마스킹 값을 만든다
- `toString()`: **항상 마스킹된 값을 반환한다**

#### 규칙

- 원문 값은 밖으로 나가지 않는다. 응답 본문·예외 메시지·로그 어디에도 싣지 않는다
- 주문 식별자를 아는 것은 미지급 주문을 가로챌 수 있는 것과 같다
- 그래서 마스킹을 호출자의 선택에 맡기지 않고 **값 객체가 강제한다**
```

읽기 모델과 마무리 두 섹션도 같은 방식이다.

```markdown
### [읽기 모델]

### 이용권(Entitlement)

_Read Model_

#### 규칙

- 조회 시점에 조립한다. **테이블도 애그리거트도 아니다**
- 진입 시 함께 내려가는 경로와 단독 조회 경로가 **같은 모양**을 내려준다
- 이 모델을 만드는 동안 토스를 부르지 않는다. 외부 장애가 진입 화면으로 번지면 안 된다

---

### 오류 코드(ErrorCode)

_Enum_

#### 상수

- 남의 주문에 지급을 요청했다 — 선점 위반
- 우리 상품이 아니다 — 카탈로그에 없는 상품 코드
- 횟수권이 부족하다

#### 규칙

- 이용권이 없어서 거부하는 것과 인증에 실패한 것은 **다른 코드**다. 프론트의 행동이 다르다
- 오류 메시지에 주문 식별자를 싣지 않는다

---

### 애그리거트 간 관계

- 네 애그리거트는 **서로를 참조하지 않는다.** 연결고리는 `UserId` 와 `OrderId` 값뿐이다
- 주문과 구독은 최초 지급 시 **함께 만들어져야 한다.** 주문만 남으면 돈을 내고 못 쓰고,
  이용권만 오르면 멱등이 깨져 재요청 때 또 오른다
- 이용 티켓은 잔량과 별개로 산다. 티켓의 생명주기는 작업의 생명주기이고, 잔량의 생명주기는 사용자의 생명주기다
- 이용권 읽기 모델만이 네 애그리거트를 한 번에 본다. **쓰기는 어디서도 합쳐지지 않는다**
```

> ⚠️ **이 선례에는 의존 방향 한 줄이 없다** — v1 작성 시점에 그 규약이 없었다.
> **신규 문서는 반드시 넣는다.** (위 "`### 애그리거트 간 관계` — 의존 방향 한 줄은 반드시 남긴다" 절)
> 발췌를 그대로 베끼면 빠지는 항목이므로, 베낀 뒤 그 한 줄을 따로 채운다.
