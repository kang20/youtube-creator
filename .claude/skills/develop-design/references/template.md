# 설계서 템플릿 (신규 개발) + 작성 원칙

> `backend/docs/domain/{name}-design.md` 의 양식.
> 리팩터링 계획은 [refactoring.md](./refactoring.md) 를 쓴다.

## 템플릿

```markdown
# {Name} 도메인 설계

> 비즈니스 요구사항(유스케이스 명세): [{name}.md](./{name}.md) — **요구·정책·API 계약의 정본**. 이 문서는 소프트웨어 설계만 다룬다.
> **대응 유스케이스 버전: v{n}** ← 이 값이 {name}.md 의 현재 버전과 다르면 미반영 상태다
> 서버 계약(정본): [api-spec.md](../../../docs/server/api-spec.md) {반영 여부}
> 구조 규칙: [architecture.md](../rule/architecture.md) · 에러: [error-handling.md](../rule/error-handling.md) · 테스트: [testing.md](../rule/testing.md) · REST Docs: [rest-docs.md](../rule/rest-docs.md)
> 상태: 설계 확정 대기 — 승인 후 구현 착수 | ✅ v{n} 구현 완료({날짜})

## 1. 목적과 범위
- 한 줄 요약 + "요구는 {name}.md §N 을 따르고 여기 중복 기술하지 않는다".
- **이번 구현 산출물** 불릿 (신규 모듈 / 신규 API / 기존 확장)
- **범위 외** 명시

## 2. 도메인 경계
**책임** — 이 모듈이 단일 권위를 갖는 것.
**다른 모듈과의 관계**
| 상대 모듈 | 관계 | 경계 처리 |
- 경계 처리 열에 구체 수단을 쓴다:
  - `도메인 이벤트 {X}Event 발행 → @ApplicationModuleListener 구독` (**기본**)
  - `모듈 공개 API {Other}Api 직접 호출` — allowedDependencies 에 명시할 때만
  - `@NamedInterface 로 일부만 노출`
- **기본은 이벤트다.** 직접 의존은 동기 응답이 꼭 필요할 때만 쓰고, 그때도 `package-info.java` 의
  `allowedDependencies` 에 적어 의도를 고정한다 (→ [architecture.md](../rule/architecture.md)).

### 2-1. ⚠️ 설계 쟁점 (있으면)
- 문제 → 왜 생기는가 → 해결 구조(그림) → 규칙 정합성. 쟁점이 없으면 섹션 생략.
- **순환 의존**이 보이면 여기서 해소한다. 두 모듈이 서로의 서비스를 참조하면
  `ApplicationModules.verify()` 가 깨진다 — 한쪽을 **이벤트 구독으로 뒤집는 것**이 정석이다.

## 3. 엔티티
```
{Entity}                         -- 성격 주석 (불변/멱등 등)
  필드     타입     -- 의미
  UNIQUE/INDEX 제약
```
- 선례 패턴 명시 (BaseTimeEntity 상속 여부, ID 타입, surrogate PK vs 복합 PK 선택 이유).
- ⚠️ **운영은 `ddl-auto: validate`** — 스키마는 배포로 만들어지지 않는다.
  신규 테이블·컬럼은 수동 DDL(`backend/deploy/sql/{name}-v1.sql`)이 **배포보다 먼저** 적용돼야 한다.
  컬럼 제거는 "앱 배포 → 사용 중지 확인 → 다음 배포에서 DROP" 2단계.

## 4. 모듈 매핑 (Spring Modulith)
| 위치 | 산출물 | 공개 여부 |
- `{name}/package-info.java` — `@ApplicationModule(displayName, allowedDependencies = {...})`
- `{name}/{Name}Service.java`(·`{Name}Api.java`) — **모듈 루트의 public 타입 = 다른 모듈이 볼 수 있는 전부**
- `{name}/{Name}Controller.java` — HTTP 진입점 (모듈 안에 둔다)
- `{name}/dto/` — 요청·응답 record
- `{name}/internal/**` — 엔티티·리포지토리·구현체. **모듈 밖에서 참조 불가(Modulith 가 강제)**
- `{name}/{Name}Event.java` — 다른 모듈에 알릴 사실
- 각 산출물의 메서드 시그니처 수준까지. 쟁점(§2-1)과 연결되는 결정은 근거를 링크.

## 5. 비즈니스 로직 (서비스 흐름)
### 5-1, 5-2... 유스케이스별 의사코드
```
method(args):                    -- @Transactional 여부
  단계 → 에러코드 분기
```
- 트랜잭션 경계와 롤백 의미(부분 성공 없음 등)를 명시.
- 유스케이스 명세의 U-번호를 참조한다 (`U3 구현` 처럼).

## 6. 동시성 제어 (경쟁 쓰기가 있으면 — 상세)
### 6-1. 불변식과 경쟁 시나리오 — | # | 시나리오 | 발생 경로 | 요구 결과 |
### 6-2. 함정 분석 — 왜 단순한 방법이 안 되는가
### 6-3. 대안 비교와 채택 — | 방식 | 판정 | 이유 | (기각 사유 포함)
### 6-4. 채택안 상세 — SQL/판정 매트릭스, **테스트 프로파일(H2) 호환성**
### 6-5~. 파생 연산 동시성 · 집계 읽기 일관성 · 의도적으로 수용한 것
- 경쟁 쓰기가 없으면 섹션 전체를 생략한다(억지로 채우지 않는다).

## 7. 기존 코드 리팩터링 (기존 파일을 건드리면)
| 파일 | 변경 | 영향 |
- 변경 파일 전수 + 영향 범위. "변경 없음 = 정책"인 파일도 그 사실을 적는다.
- **삭제된 요구가 남긴 코드**(유스케이스에서 빗금 처리된 것)는 여기 **제거 대상**으로 올린다.
  안 지우면 죽은 코드로 남고 테스트가 없으니 커버리지 게이트가 먼저 걸린다.

## 8. API 계약 · REST Docs
- 계약 상세는 유스케이스 명세가 정본 — 여기는 **스니펫 매핑만**:
| 메서드 | 경로 | 인증 | 스니펫 ID |
- adoc 신설/갱신 대상(`src/docs/asciidoc/{name}.adoc` + `index.adoc` include), `/docs-sync` 반영 계획.
- 네이밍 규약은 [rest-docs.md](../rule/rest-docs.md).

## 9. 에러 코드 (ErrorCode 에 {NAME} 섹션 추가)
| enum | 코드 | HttpStatus | 메시지 |
- 기존 공통 게이트가 자동 처리하는 것은 신설하지 않고 그 사실만 기록.
- 네이밍은 [error-handling.md](../rule/error-handling.md).

## 10. 테스트 계획
| 테스트 | 종류 | 핵심 케이스 |
- 종류 선택 기준은 [testing.md](../rule/testing.md) — ControllerTest(REST Docs) /
  `@ApplicationModuleTest` / 단위 / 비TX(동시성).
- **이번 변경 파일은 라인 100%** — 전역 게이트 수치는 testing.md 가 정본이고, 그건 레포 하한일 뿐이다.
  도달 못 하는 라인이 있으면 (a) 테스트로 덮거나, (b) 죽은 코드면 제거하거나,
  (c) 도달 불가 방어선이면 근거와 함께 명시한다. "그냥 안 덮음"은 없다.
- **어떤 테스트가 어떤 라인을 덮는지**를 여기 미리 그린다. 구현 때 사각이 안 생긴다.
- 통합 테스트로 재현 불가한 동시성 교차는 단위(목) 또는 비TX 멀티스레드 테스트로.

## 11. 구현 단계 (체크리스트)
- [ ] 커밋 단위별 체크박스 — `feat({name})` / `test({name})` / `chore(db)` / `docs(api)`
      (첫 feat 커밋이 §4 매핑대로 골격+구현을 함께 담는다)
- [ ] `./gradlew test --tests "*ModularityTest"` — 모듈 경계 통과
- [ ] **변경 파일 라인 커버리지 100% 확인** → `/code-review`
- [ ] `/docs-sync`

## 12. 결정 필요 (Open Questions)
```

## 작성 원칙 — 양식이 이렇게 생긴 이유

- **유스케이스 명세와 중복 금지** — 요구·정책·API JSON 을 설계서에 복사하면 요구가 바뀔 때
  두 문서가 어긋난다. 설계서는 "어떻게"만, "무엇·왜"는 링크.
- **대안 비교는 기각 사유까지** — 채택안만 적으면 다음 사람이 같은 대안을 다시 검토한다.
  기각 표(❌/△/✅)가 리뷰 시간을 아낀다.
- **선례를 이름으로 인용** — "○○ 모듈과 동일 패턴" 한 줄이 구현 절반의 스펙이다.
  실제 코드를 읽고 쓴다. 선례가 없으면(첫 도메인) 이 문서가 선례가 된다는 전제로 쓴다.
- **구현 중 설계가 바뀌면 역반영** — 구현에서 발견한 엣지는 설계서에 다시 기록해야
  문서가 정본으로 남는다. §11 체크리스트에 완료 갱신 포함.
- **경쟁 쓰기 = 전용 섹션** — 동시성을 불릿 한 줄로 뭉개면 반드시 구현에서 터진다.
  불변식 → 시나리오 → 대안 → 판정 매트릭스 순서를 강제한다.
- **변경 파일 100% 커버리지는 타협하지 않는다** — 전역 게이트는 레포 전체 하한일 뿐,
  이번에 손댄 파일은 100% 가 기준이다. §10 에 미리 그려두면 구현 때 사각이 안 생긴다.

## Modulith 용어 주의

이 프로젝트는 **레이어드/헥사고날 구조를 쓰지 않는다**(→ [architecture.md](../rule/architecture.md)).
설계서에 아래 용어를 쓰지 않는다 — 규칙과 충돌하고, 처방도 틀리게 나온다.

| 쓰지 않는 말 | 대신 |
|---|---|
| 인바운드/아웃바운드 포트, 어댑터 | 모듈 공개 API(`{Name}Service`·`{Name}Api`), `internal/` |
| 레이어(presentation/application/infra) | 애플리케이션 모듈(패키지) |
| 순환 참조 → 포트 분리 | 순환 의존 → **이벤트로 뒤집기** |
