# 리팩터링 계획 템플릿

> 신규 도메인 모델은 [template.md](./template.md) 를 쓴다.
> 이 양식은 **동작을 바꾸지 않고 구조만 바꿀 때**. 동작이 바뀌면 그건 신규 개발이다.

## 진입 조건

**도메인 정의서가 없어도 진입한다.** 산출물이 정의서가 아니므로 `### 요구 🔶` 잔여·상태 헤더를
진입 조건으로 걸지 않는다 — 걸면 정의서가 없는 레거시가 영영 리팩터링 대상이 못 된다
(→ [SKILL.md](../SKILL.md) 0단계 '리팩터링 모드').
대상이 레거시 도메인(`backend/docs/domain/`)이면 그 문서는 **현재 상태의 인용원으로만** 쓰고
**레거시 파일은 고치지 않는다.**

## 산출물이 어디 있는가

리팩터링 계획은 **도메인 정의서가 아니다.** 요구도 모델도 아니고, 끝나면 역할이 끝나는 작업 계획이다.

- 계획 파일: `backend/docs/ops/refactor-{name}.md` — 신규 도메인의
  `backend/docs/new-domain/{name}/{name}-v{n}.md` 에 섞지 않는다.
  섞으면 "지금 이 도메인이 무엇인가"와 "이번에 무슨 순서로 옮기는가"가 한 파일에서 뒤엉킨다.
- **모델이 바뀌는 부분만 도메인 정의서로 흡수한다.** 애그리거트 경계·속성·행위·규칙이 달라지면
  그것은 계획이 아니라 모델의 변화이므로 `## 도메인 모델` 을 갱신한다
  (확정된 문서면 버전 올림 — `git mv {name}-v{n}.md {name}-v{n+1}.md`, 없앤 항목은 빗금 + 사유).
- **파일 이동·클래스 분리·패키지 재배치는 모델의 변화가 아니다.** 도메인 정의서에 쓰지 않는다 —
  파일 배치의 정본은 [architecture.md](../../../../backend/docs/rule/architecture.md) 다.
- 대상 도메인의 정의서가 아직 `backend/docs/domain/` 에만 있는 레거시라면
  **그 레거시 문서를 고치지 않는다**(읽기 전용). 계획서에서 현재 상태로만 인용한다.
- **이 계획서는 `spec-verifier` 가 판정하지 않는다.** 검증 에이전트의 검사 표는 도메인 정의서용이라
  이 파일을 판정할 기준이 없다. 성공 조건은 [SKILL.md](../SKILL.md) 의 '성공 조건 — 리팩터링 모드' 이고,
  이 스킬이 직접 대조한다.
  단, 모델이 바뀌어 `## 도메인 모델` 을 갱신했다면 **그 갱신분은** 신규 모델 모드와 똑같이 검증한다
  (`단계: develop-design`).

```markdown
# {Name} 리팩터링 계획

> 대상: {패키지/모듈/클래스}
> 도메인 정의서: [{name}-v{n}.md](../new-domain/{name}/{name}-v{n}.md) — 모델이 바뀌면 그쪽을 갱신한다
> 구조 규칙: [architecture.md](../rule/architecture.md) · 테스트: [testing.md](../rule/testing.md)
> 상태: 승인 대기 | ✅ 완료({날짜})

## 1. 동기 / 문제점
- 현재 구조의 문제 (중복, 모듈 경계 위반, 순환 의존, 복잡도).
- **측정 가능한 신호**를 적는다: `verify()` 실패 메시지, 커버리지 사각, 중복 라인 수 등.
  "지저분하다"는 동기가 아니다.

## 2. 현재 구조 (As-Is)
- 핵심 파일·의존 관계 요약. `./gradlew test --tests "*ModularityTest"` 로 생성된
  모듈 다이어그램(`build/spring-modulith-docs/`)을 근거로 쓴다.

## 3. 목표 구조 (To-Be)
- 변경 후 구조. `ApplicationModules.verify()` 를 통과하는지, `allowedDependencies` 가
  어떻게 바뀌는지 명시.
- **모델이 바뀌는가**를 여기서 판정한다. 바뀌면 도메인 정의서의 `## 도메인 모델` 갱신을
  이 계획의 1단계로 올린다 — 코드가 먼저 움직이면 문서가 영영 못 따라온다.

## 4. 변경 범위 & 영향
| 파일 | 변경 | 영향 (호출부/테스트) |
|------|------|---------------------|
- 테스트 파일도 빠짐없이. 리팩터링은 테스트가 같이 움직인다.

## 5. 단계별 작업 (안전한 순서)
- [ ] 1단계: ... (커밋: `refactor({name}): ...`)
- [ ] 2단계: ...
- **각 단계 후 `./gradlew test` 로 그린 유지.** 한 번에 다 바꾸고 마지막에 돌리지 않는다.
- 단계 사이에 커밋을 끊어야 되돌릴 지점이 생긴다.

## 6. 검증
- `./gradlew check` — 모듈 경계 + 커버리지 게이트 통과
- **동작 동일성 확인 방법** — 기존 테스트가 그대로 통과하는 것이 1차 근거.
  테스트가 없던 코드를 건드리면 **먼저 특성화 테스트를 붙이고** 시작한다.

## 7. 롤백 / 리스크
- 위험 요소와 되돌리기 방법. 배포까지 갔다면 이전 이미지 롤백 경로도.
```

## 리팩터링에서 자주 나오는 함정

- **테스트 없는 코드를 먼저 고치는 것** — 안전망 없이 구조를 바꾸면 회귀를 못 잡는다.
  커버리지가 비어 있으면 리팩터링 전에 채우는 것이 1단계다.
- **구조 변경과 동작 변경을 한 커밋에 섞는 것** — 리뷰가 불가능해지고 롤백 단위가 사라진다.
- **`verify()` 를 마지막에 한 번만 돌리는 것** — 모듈 경계는 단계마다 확인한다.
  깨진 지점을 좁게 잡을수록 원인 추적이 싸다.
- **모델이 바뀌었는데 계획서만 고치는 것** — 계획서는 작업이 끝나면 죽는 문서다.
  거기 남은 규칙은 다음 사람이 못 찾는다. 규칙은 도메인 정의서로 올린다.
