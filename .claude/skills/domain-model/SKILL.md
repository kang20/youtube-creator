# domain-model — 도메인 모델 시각화

**그림은 한곳에, 말은 딴 데.**

```
backend/docs/model/
├── master.md              전 모듈 통합 다이어그램 — Mermaid 코드블록만. 산문·표 금지
├── {module}-notes.md      책임·불변식·경계 규칙·주의사항·미확정   (항상)
├── {module}-state.md      상태 전이                              (상태 필드가 있을 때만)
└── {module}-flow.md       모듈 간 상호작용 흐름                   (다른 모듈과 얽힐 때만)
```

`master.md` 는 **열면 그림만 보인다.** 설명이 필요하면 그건 이미 `master.md` 감이 아니다.

Modulith `Documenter` 는 "모듈이 서로 어떻게 얽히는가"까지만 자동으로 그린다.
**모듈 안이 어떻게 생겼는가는 자동 추출이 불가능하다** — 이 스킬이 그 자리를 메운다.

**이 스킬은 코드를 작성하지 않는다.** 문서만 만든다.

## 왜 자동화가 아니라 수기인가

| 그리려는 것 | 자동 추출 | 이유 |
|---|---|---|
| 모듈 간 의존 | ✅ Modulith `Documenter` | 패키지 의존에서 기계적으로 나온다 |
| 애그리거트 루트 목록 | ⚠️ 탐지는 되나 문서화 불가 | 엔티티가 `internal` 이라 캔버스의 *exposed* 필터에 걸린다 |
| **애그리거트 경계** | ❌ | "어디까지가 한 트랜잭션 단위인가"는 설계 의도다 |
| **엔티티 책임·불변식** | ❌ | 코드에 없다. 사람 머릿속에 있다 |
| **엔티티 간 논리 참조** | ❌ | 물리 FK 를 쓰지 않으므로 스키마에 관계가 없다 |

→ **코드에서 뽑을 수 있는 건 뽑고, 설계 의도는 사용자에게 묻는다.** 추측해서 채우지 않는다.

## 입력

- `{module}` — Modulith 모듈명 (`auth` · `payment` · `shared` · `config` · `bootstrap`)
  - 사용자가 한글 표시명(`인증` · `결제·이용권`)으로 부를 수 있다 → `package-info.java` 의
    `displayName` 으로 대조해 패키지명을 찾는다
  - 모듈명이 모호하거나 없는 모듈이면 **묻는다**. 임의로 고르지 않는다

## 참조 (필요할 때 읽는다)

| 무엇이 필요할 때 | 어디를 |
|---|---|
| 파일별 양식·Mermaid 작성 규약 | [references/template.md](references/template.md) |
| 모듈 경계·의존·이벤트 규칙 | [architecture.md](../../../backend/docs/rule/architecture.md) |
| 이 모듈의 요구·정책 | `backend/docs/domain/{module}.md` |
| 이 모듈의 설계 결정 | `backend/docs/domain/{module}-design.md` |
| 왜 그렇게 정했나 | `backend/docs/adr/` |
| 정본 — 실제 코드 | `backend/src/main/java/kang20/ytcreator/{module}/` |

> **정본은 코드다.** 설계서와 코드가 다르면 **코드를 그리고**, 그 불일치를 `{module}-notes.md` 에 남긴다.
> 문서를 믿고 코드에 없는 것을 그리지 않는다.

## 절차

### 0. 사전 검증
- backend 브랜치인지 확인
- `backend/docs/model/{module}-notes.md` 가 **이미 있으면 덮어쓰지 않는다** → 갱신 모드로 사용자 확인
  - 갱신 모드에서는 헤더의 `근거 커밋` 과 현재 HEAD 를 비교해 **그 사이 변경된 파일부터** 본다
- `master.md` 는 **항상 부분 갱신**이다 — 이 모듈 구역만 고치고 다른 모듈 구역은 손대지 않는다
- 대상 모듈에 엔티티가 하나도 없으면(`config` · `bootstrap` 등) 그 사실을 보고하고
  **`master.md` 없이 `{module}-flow.md` 만 쓸지** 묻는다

### 1. 코드에서 사실 수집 (추측 금지)

이 순서로 **전부** 읽는다. 요약본이 아니라 실제 파일을 연다.

1. `{module}/package-info.java` — 표시명 · `allowedDependencies` · 모듈 타입
2. `{module}/internal/entity/**` — 필드 · 타입 · 제약(`nullable` · `unique` · `length`) · enum · 생성자 · 상태 판정 메서드
3. `{module}/internal/**/repository/**` — 어떤 엔티티에 리포지토리가 있는가
   (**리포지토리가 있는 엔티티 = 애그리거트 루트 후보**. 확정은 2단계에서 사용자와)
4. `{module}/*Port.java` 등 모듈이 **밖에 노출한 타입** — 다른 모듈이 이 모듈을 어떻게 쓰는가
5. `{module}/internal/service/**` — 트랜잭션 경계 · 한 메서드가 함께 저장하는 엔티티들
   (**같은 트랜잭션에서 함께 바뀌는 엔티티 = 같은 애그리거트 후보**)
6. 이벤트 발행/구독 — `@EventListener` · `ApplicationEventPublisher`
7. 이 모듈을 참조하는 **다른 모듈** — `allowedDependencies` 에 이 모듈이 있는 쪽

### 2. 애그리거트 경계 판정 — **사용자에게 확인받는다**

수집한 사실로 **경계 초안**을 만들되, 근거를 함께 제시하고 확인받는다.

```
초안: payment 모듈 = 애그리거트 3개
  ① PaymentOrder (단독)         근거: 전용 리포지토리 · 다른 엔티티와 함께 저장되지 않음
  ② Subscription ← UsageTicket  근거: {메서드}가 한 트랜잭션에서 함께 씀
  ③ CreditBalance (단독)        근거: 전용 리포지토리 · 낙관적 락 필드 보유
이대로 맞나?
```

- 근거가 갈리면(리포지토리는 따로인데 같이 저장된다 등) **양쪽 해석을 보여주고 묻는다**
- 사용자가 정정하면 그대로 따른다 — 코드보다 설계 의도가 우선인 유일한 항목이다
- **확정된 경계와 코드 실제 접근 경로가 다르면** 그림은 확정안대로 그리고,
  이탈 사실과 그 이유를 `{module}-notes.md` 에 기록한다 (고칠 대상인지 예외인지도 함께)
- 끝내 확정되지 않으면 🔶 로 `{module}-notes.md` 에 남긴다. **임의 확정 금지** (CLAUDE.md 규칙)

### 3. 작성

[references/template.md](references/template.md) 의 파일별 양식과 Mermaid 규약을 따른다.

**작성 순서를 지킨다** — `master.md` 를 먼저 그리고, 거기서 넘친 것을 분리 파일로 민다.

1. `master.md` 의 이 모듈 구역 — 애그리거트 지도 + ERD
2. `{module}-notes.md` — 책임·불변식·경계 규칙·주의사항·미확정
3. `{module}-state.md` — 상태 필드가 있을 때만
4. `{module}-flow.md` — 다른 모듈과 얽힐 때만

**내용이 없으면 파일을 만들지 않는다.** 빈 껍데기 문서는 만들지 않는다.

### 4. 렌더링 검증

작성 후 **Mermaid 문법을 점검한다.** 깨진 다이어그램은 없는 것만 못하다.

- 코드펜스가 ` ```mermaid ` 로 열렸는가
- `flowchart` 노드 라벨에 한글·`·`·`(` 가 들면 **따옴표로 감쌌는가** (`A["결제·이용권"]`)
- `erDiagram` 의 엔티티명에 하이픈·점이 없는가 (Mermaid 가 파싱 못 한다)
- 관계 카디널리티 기호가 짝이 맞는가 (`||--o{` · `||..o{`)
- **`master.md` 에 Mermaid 코드블록과 HTML 주석 외의 것이 없는가**

문법이 의심스러우면 **다이어그램을 단순화한다**. 화려함보다 렌더링이 우선이다.
실제 렌더링을 돌리지 않았다면 **"문법 점검만 했다"고 사실대로 보고한다.**

### 5. 보고 + 커밋
- 애그리거트 경계 판정과 그 근거를 요약 보고
- 코드와 설계서가 어긋난 지점이 있으면 **반드시 짚어서 보고** — 이 스킬의 부산물 중 가장 값어치 있다
- 만든/고친 파일 목록을 보고 (`master.md` 는 어느 구역을 고쳤는지)
- 커밋: `docs({module}): 도메인 모델 시각화` / 갱신 시 `docs({module}): 도메인 모델 갱신 — {무엇}`

## 성공 조건

### `master.md`
- [ ] **Mermaid 코드블록과 HTML 주석(`<!-- -->`) 외에 아무것도 없다** — 제목·산문·표·링크 전부 금지
- [ ] 이 모듈의 **모든 엔티티**가 애그리거트 지도와 ERD에 빠짐없이 있다
- [ ] 애그리거트 **경계를 넘는 참조가 ID 값 참조로 그려졌다** (객체 참조로 그리지 않았다)
- [ ] 애그리거트 내부는 실선, 경계를 넘으면 **점선(`..`)** 으로 구분됐다
- [ ] 다른 모듈 구역을 건드리지 않았다
- [ ] 근거 커밋·갱신일·분리 문서 목록이 **HTML 주석**으로 있다

### 분리 문서
- [ ] `{module}-notes.md` 에 엔티티마다 **책임 한 줄 + 불변식**이 있다 (필드 나열만 하지 않았다)
- [ ] 애그리거트 경계가 **사용자 확인을 거쳤다** (추측으로 확정하지 않았다)
- [ ] 확정안과 코드가 다르면 그 **이탈이 기록**됐다 (고칠 것인지 예외인지 판정 포함)
- [ ] 상태 필드가 있는 엔티티는 `{module}-state.md` 가 있다 (없으면 파일을 만들지 않았다)
- [ ] 다른 모듈과 얽히면 `{module}-flow.md` 에 **핵심 흐름 1~2개**가 있다
- [ ] 각 파일 헤더에 **근거 커밋 해시**와 갱신일, `master.md` 로 돌아가는 링크가 있다

### 공통
- [ ] Mermaid 문법 오류가 없다
- [ ] 요구·API JSON·커버리지 수치를 **복사하지 않고 링크**했다
- [ ] 코드가 작성되지 않았다
- [ ] 커밋됨

## 안전장치

- **`master.md` 는 Mermaid 전용** — 설명을 넣고 싶어지면 그건 분리 문서 감이다. 예외 없다
- **`master.md` 는 부분 갱신** — 호출된 모듈 구역만 고친다. 다른 모듈 그림을 건드리지 않는다
- **코드가 정본** — 설계서에만 있고 코드에 없는 것은 그리지 않는다. 불일치는 notes 에 남긴다
- **추측 금지** — 애그리거트 경계·불변식은 사용자에게 묻는다. 🔶 를 임의 확정하지 않는다
- **덮어쓰기 금지** — 기존 분리 문서가 있으면 갱신 모드로 확인
- **빈 파일 금지** — 내용이 없으면 그 파일을 만들지 않는다
- **문서만** — 코드·테스트·빌드 설정을 건드리지 않는다
- **Mermaid 만** — PlantUML 을 쓰지 않는다. GitHub 이 렌더링하지 못한다
- **MVP 범위 우선** — 백로그·미구현 기능은 그리지 않는다

## 갱신 주기

자동 검사를 걸지 않는다 — **수기 문서라 드리프트를 기계가 못 잰다.**
대신 아래 시점에 사용자가 이 스킬을 다시 부른다.

```
엔티티 필드 추가/삭제 · 새 엔티티 · 애그리거트 경계 변경 · 모듈 간 새 호출/이벤트
   → /domain-model {module}   (갱신 모드 — master.md 는 해당 구역만)
```

`/implement` 로 도메인을 구현한 직후, `/docs-sync` 마감 전이 가장 자연스러운 자리다.

## 파이프라인 위치

```
/usecase {name}          요구      docs/domain/{name}.md
/develop-design {name}   설계      docs/domain/{name}-design.md
/implement {name}        구현      src/main · src/test
   ▼
/domain-model {module}   모델 그림  docs/model/master.md + {module}-*.md   [이 스킬]
   ▼
/docs-sync               마감
```
