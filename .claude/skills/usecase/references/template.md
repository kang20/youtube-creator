# 도메인 정의서 템플릿 + 작성 원칙

> `backend/docs/new-domain/{name}/{name}-v{n}.md` 의 양식.
> **유일한 선례는 [payment-v2.md](../../../../backend/docs/new-domain/payment/payment-v2.md) 다. 먼저 읽고 밀도를 맞춘다.**
> 선례 payment-v2.md 는 이 양식을 그대로 따른다 — 예외 절은 없다.

정의서는 **파일 하나**다. 요구·참고자료·용어 사전·도메인 모델이 한 파일에 순서대로 쌓인다.
`/usecase` 가 앞의 셋을, `/develop-design` 이 `## 도메인 모델` 을 채운다.
섹션 순서는 **고정**이다 — 요구를 읽고 용어를 확인한 뒤 모델로 내려가는 순서가 곧 이해 순서다.

## 섹션 구조 (순서 고정)

| 섹션 | 성격 | 누가 쓰나 |
|---|---|---|
| `# {Name} 도메인 정의서` + 상태 헤더 | 머리말 | 요구 모드가 만들고 이후 단계가 갱신 |
| `## {도메인명} 도메인` | 요구 | `/usecase {name}` |
| `## 참고자료 — {제목}` | 0..n개(선택) | `/usecase {name} {정보}` |
| `## 용어 사전` | 선택 | `/usecase 용어 {name}` |
| `## 도메인 모델` | 모델 | **이 자리는 `/develop-design` 이 만든다** — `/usecase` 는 제목도 만들지 않는다 |
| `## 🔶 결정 필요` | 미확정 누적 | 모든 단계 |
| `## 변경 이력` | v2 이상일 때만 | 버전 올린 단계 |

> **요구 섹션은 상태 헤더 다음의 첫 번째 `## ` 섹션이다. 제목 문자열로 찾지 않는다.**
> 제목은 `## {도메인명} 도메인` 형식을 쓰되 `{도메인명}` 은 **한글이어도 되고 영문이어도 된다**
> — 선례 `## 결제 도메인` 이 정상이다. 이름을 강제하지 않는다.
> 요구 섹션을 찾아야 하는 모든 도구·에이전트는 **위치**로 찾는다.

## 템플릿

````markdown

> **버전 v{n}** · 상태: 요구 초안 | 요구 확정({날짜}) | 모델 초안 | **설계 확정({날짜})** | 구현 완료({날짜})
> 🔶 {n}건 — '## 🔶 결정 필요' 참조        ← 0건이면 "🔶 없음 (전부 확정)"

## {도메인명} 도메인        ← 한글/영문 자유. 기계적 식별은 '상태 헤더 다음 첫 `## ` 섹션'
````

## 작성 원칙 — 양식이 이렇게 생긴 이유

### 번호를 쓰지 않는다

`U1`·`§5-2` 같은 번호를 문서에 박지 않는다. **계층 불릿 산문**이다.

- 번호를 붙이면 요구가 **체크리스트처럼 읽힌다.** 한 줄씩 독립된 항목으로 보이고, 항목 사이의
  인과("이 규칙 때문에 저 규칙이 성립한다")가 사라진다. 도메인은 목록이 아니라 서술이다.
- 번호는 **바뀌는 순간 거짓말이 된다.** 요구 하나를 지우면 뒤 번호가 전부 밀리거나 결번이 생기고,
  그 번호를 참조하던 커밋·테스트·리뷰 기록이 통째로 다른 것을 가리킨다.
- 번호를 붙이는 순간 **번호를 관리하는 일**이 생긴다. 문서의 목적은 요구를 합의하는 것이지
  일련번호를 유지하는 것이 아니다.
- **그럼 추적은 어떻게 하나** — tester 가 구현 단계에서
  `backend/workspace/{name}/v{n}/requirements.md` 를 만들어 요구 섹션 불릿 전부 + 도메인 모델
  `#### 규칙` 불릿 전부를 `REQ-1..REQ-n` 으로 뽑는다. **번호는 문서가 아니라 workspace 에 산다.**
  workspace 는 커밋되지 않으므로 번호가 낡아도 문서가 오염되지 않는다.
- 번호 영구 결번 규칙은 **이 정의서 본문에서** 사라졌다. 에러 코드 결번은 그대로 남는다
  → [versioning.md](./versioning.md).

### 한 불릿 = 한 사실

- 두 줄을 넘기지 않는다. 넘으면 두 사실이 붙어 있는 것이고, 하나를 부정할 때 나머지가 딸려 죽는다.
- 핵심 개념은 `[대괄호]` 로 표시한다 — 예: `[이용권]` `[소모 시점]` `[기간권의 제지 조건]`.
  대괄호를 단 말은 **용어 사전에 전부 올라가야 한다.** 없으면 누락이다.

### "왜"를 반드시 붙인다

규칙만 나열하면 다음 사람이 그 규칙을 되돌린다. 근거는 같은 불릿이나 바로 아래 하위 불릿에 붙인다.

- 나쁜 예: "잔량은 절대 음수가 되지 않는다."
- 좋은 예: "잔량은 절대 음수가 되지 않는다." + 하위 불릿 "이 불변식은 '남아 있을 때만 줄인다'는 갱신 조건이 지킨다"

의도적으로 감수한 트레이드오프는 감수한다는 사실 자체를 쓴다 —
"선점은 검증이 아니라 그 사실을 감수하겠다는 선언이다"처럼.

### 표는 열거에만

- 표를 쓰는 곳: 상태 값 목록, 외부 API 스펙, 용어 사전, 변경 이력.
- 규칙은 불릿이다. 표에 넣으면 "왜"를 쓸 칸이 없어 근거가 통째로 증발한다.

### 요구 섹션은 경계 선언으로 닫는다

마지막에 **"이 도메인이 하지 않는 일이 있다"** 와 필요하면 **"승계되지 않는 것이 있다"** 를 둔다.

- 안 그으면 다음 단계가 범위를 발명한다. 모델·구현·테스트가 각자 다른 경계를 가정하면
  리뷰에서야 어긋난 것이 드러난다.
- "안 한다"뿐 아니라 **누구의 몫인가**까지 쓴다. 주체가 없는 배제는 결국 우리에게 돌아온다.

### 데이터 모델은 여기 없다

요구 섹션에 테이블·엔티티·컬럼이 박히면 설계 자유도가 죽고, 요구가 바뀔 때 두 군데를 고치게 된다.
같은 파일이지만 `## 도메인 모델` 섹션이 단일 위치다.

### API 스펙은 참고자료로 뺀다

엔드포인트·요청/응답 JSON·플랫폼 제약은 요구 섹션에 섞지 않는다.
요구는 **우리가 정한 것**이고 스펙은 **남이 정해 준 것**이라, 섞이면 어느 쪽을 우리가 바꿀 수 있는지
구분되지 않는다.

### 선례 정렬

새 규칙을 만들기 전에 기존 도메인 문서에 같은 패턴이 있는지 본다. 같으면 "○○ 선례와 동일"이라고
쓰는 게 프론트·구현자 모두에게 싸다. 규칙 문서 5종(`backend/docs/rule/`)에 이미 있는 것은
복사하지 않고 **링크만 건다** — 복사본이 먼저 낡는다.

## 용어 사전 규약

- 그룹별 표. 열은 `용어 | 영문명 | 정의` **셋 고정**이다.
- **영문명이 코드 식별자의 계약이다.** 클래스·메서드·필드·에러코드는 이 표의 말만 쓴다.
  이 문장은 `## 용어 사전` 섹션 맨 위(표 바로 앞)에 **인용문으로 명시한다.**
  - 표 밖의 말로 코드를 쓰기 시작하면 문서와 코드가 서로를 못 찾고, 리뷰가 이름 논쟁으로 소모된다.
- 계층 관계는 `├` / `└` 로 표기한다 — 예: `이용권` 아래 `횟수권` · `기간권`.
- 요구 섹션의 `[대괄호]` 개념은 **전부** 이 표에 있어야 한다. 없으면 누락이다.
- 정의는 "무엇인가"에 더해 **무엇과 혼동되는가**를 쓴다.
  예: "구독은 기간권을 만들어내는 **원인**이다 — 기간권 자체와 구분한다".
- 이름을 못 정한 것은 🔶 로 내린다. 임시 이름을 확정처럼 적으면 그대로 코드가 된다.
  - 그 항목이 들어가는 그룹은 `### 모델 🔶` 이다 → 아래 "🔶 규약".
- 에러 코드 영문명도 이 표가 정본이다. 네이밍 규약은
  [error-handling.md](../../../../backend/docs/rule/error-handling.md) 를 따른다.

## 참고자료 섹션 규약

선례는 payment-v2.md 의 `참고자료 — 플랫폼 API 스펙` 이다. 그 절이 지키는 규율 넷을 그대로 따른다.

- **출처 URL 과 조회 날짜가 필수다.** 재확인했으면 최초 조회 날짜도 함께 남긴다.
  플랫폼 문서는 말없이 바뀐다. 날짜 없는 사본은 언제 기준인지 알 수 없어 못 믿는다.
- **원문이 정본이고 이것은 사본이라고 명시한다.** 사본을 정본으로 착각하면 스펙이 바뀐 뒤에도
  우리 문서만 보고 구현하게 된다.
- **확인 안 되는 것을 "없다는 사실 자체가 결과"로 남긴다.** 별도 표로 모으고 각 항목에
  **그것 때문에 무엇을 판단할 수 없는지**를 적는다. 빈칸을 추측으로 메우면 그 추측이 요구가 된다.
- **재조회로 뒤집힌 것은 지우지 않고 정정으로 남긴다.** 틀렸던 결론에 빗금을 치고,
  실제로 무엇이었는지와 **왜 틀렸는지**를 함께 쓴다.
  payment-v2.md 의 사례가 정확히 그렇다 — "스펙이 기능별 문서에만 있으리라 가정한 것이 원인"이라고
  적혀 있어서, 다음 사람은 가이드 문서까지 훑고 나서야 "없다"를 선언한다.
- 스펙이 도메인 규칙의 근거일 때는 **"도메인 규칙과의 연결"** 을 붙인다.
  표만 옮겨 두면 왜 이 스펙을 우리 문서에 넣었는지 아무도 모른다.
- 토스 연동은 [toss-integration.md](../../../../backend/docs/rule/toss-integration.md) 가 정본이다.
  이미 그 문서에 있는 결론은 복사하지 않고 링크한다.

## 🔶 규약

- **본문에는 마크만 단다.** 예: `### 만료 완충(EXPIRY_BUFFER) 🔶`
- 내용은 전부 `## 🔶 결정 필요` 에 모은다. 두 그룹으로 나눈다.

  ```
  ### 요구 🔶      ← /usecase 가 채운다
  ### 모델 🔶      ← /develop-design 이 채운다 + 용어 사전의 미확정
  ```

  본문에 흩어 두면 "지금 남은 결정이 몇 개인가"에 답할 수 없다. 그 답이 다음 단계 진입 조건이다.
- **용어 사전의 미확정(영문명 미정 포함)은 `### 모델 🔶` 에 넣는다** —
  영문명은 코드 식별자 계약이라 **구현 진입**을 막아야 하고,
  요구 확정과 develop-design 진입은 막을 이유가 없다.
  - 용어 사전은 `/usecase` 의 산출물이지만 그룹은 `### 요구 🔶` 가 아니다.
    그룹은 "누가 썼나"가 아니라 **"무엇을 막아야 하나"** 로 가른다.
- **두 그룹 제목은 항상 둘 다 둔다.** 요구 모드가 문서를 처음 만들 때 `### 요구 🔶` 와 `### 모델 🔶`
  제목을 미리 만들어 두고, 모델 그룹은 비어 있는 채로 남긴다.
  - 제목이 조건부로 생겼다 없어지면 `/develop-design` 과 spec-verifier 가 매번 "있나 없나"를 먼저
    따져야 한다. 자리를 고정하면 채우기만 하면 된다.
  - 이것은 `## 도메인 모델` 을 미리 만드는 것과 **다르다.** 그 제목은 여전히 만들지 않는다 —
    `/develop-design` 이 갱신 모드로 오판한다.
- **항목이 없는 그룹은 제목 아래를 비운다.** `- 없음` 같은 불릿을 쓰지 않는다.
  - `- 없음` 은 형식 검사에 걸리는 **가짜 항목**이라 건수를 1건으로 부풀린다.
  - **빈 그룹은 0건으로 세고, 항목 형식 검사 대상이 아니다.**
- 항목 형식: `- **{한 줄 질문}** — 제안: {값}. 근거: {한 줄}. 위치: {본문 어디}`
- 확정되면 항목을 지우고, 본문을 확정문으로 고치고, **상태 헤더의 🔶 건수를 갱신한다.** 셋은 한 묶음이다.
  - 그룹의 마지막 항목이 확정되면 **제목은 남기고 아래만 비운다.** 제목까지 지우지 않는다.

### 🔶 를 붙이는 기준

| 상황 | 처리 |
|---|---|
| 사용자가 명시적으로 정했다 | 확정 — 본문에 확정문으로 |
| 계약·구현에 필요한데 사용자가 안 정했다 | **🔶 + 제안값 + 근거** |
| 기존 규칙 문서를 그대로 따른다 | 🔶 아님 — 링크만 (중복 개설 금지) |
| 응답 스키마·에러 분기에 영향 주는 정책 | 🔶 (계약이므로) |
| 계약과 무관한 순수 화면 재량 | "프론트 재량" 표기 후 넘어감 |

**임의 확정 금지.** 사용자가 안 정한 것을 확정으로 적지 않는다. 제안값은 붙이되 확정 표기는 하지 않는다.

## 첫 도메인일 때 (선례가 없을 때)

`backend/docs/new-domain/` 에 `payment/` 밖에 없거나 비어 있으면 "선례 정렬"이 성립하지 않는다.
이때는 반대로 **이 문서가 이후 모든 도메인의 선례가 된다**는 전제로 쓴다.

- 공통이 될 규칙(멱등 처리 방식, 페이지네이션 기본값, 소프트삭제 여부, rate limit)은
  이 도메인에만 해당하는 것처럼 쓰지 말고 **"공통 규약으로 승격 후보"** 라고 표시한다.
- 확정되면 그 규칙은 `backend/docs/rule/` 의 해당 문서로 올려 다음 도메인이 링크만 하게 만든다.
- 에러 코드도 마찬가지 — 이 도메인 전용인지 공통 게이트인지 구분해서 적는다.
- `backend/docs/domain/` 의 다섯 문서(`auth.md` · `auth-design.md` · `payment.md` ·
  `payment-design.md` · `subtitle.md`)는 **옛 양식 레거시**다.
  판단의 선례로 읽되 **양식은 따르지 않는다.** 그 문서들은 번호 체계를 쓴다.
