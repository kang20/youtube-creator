# 유스케이스 명세 템플릿 + 작성 원칙

> `backend/docs/domain/{name}.md` 의 양식. 아래 템플릿을 그대로 채우되,
> 각 섹션의 "왜 이렇게 생겼는지"는 맨 뒤 [작성 원칙](#작성-원칙--양식이-이렇게-생긴-이유)을 보고 밀도를 맞춘다.

## 템플릿

```markdown
# {기능명} — 비즈니스 요구사항 설계서 ({name} 도메인)

> **성격**: {한 줄 — 무엇이고 왜 만드는가. 핵심 훅이 있으면 명시}
> 비즈니스 요구사항: {날짜} 사용자 결정(§9-1) · 참고 UX: {있으면}
> 관련: {관련 도메인 문서·PRD·api-spec 링크}
> 상태: **요구사항 초안 — §9 🔶 확정 필요** | **v1 확정({날짜})** | **v2 확정({날짜}) — 변경분 §9-2**
>   (설계서 링크 `→ 설계: [{name}-design.md](./{name}-design.md)` 는 **확정 후에만** 붙인다 — 초안 단계엔 아직 없는 파일)

## 용어
| 용어 | 의미 |     ← 문서 내 혼동될 개념만 (예: 투표(poll) vs 표(vote))

## 1. 배경 · 목적
- 왜 이 기능인가 — 제품 관점 근거 2~3줄. 핵심 훅(행동 유도 장치)이 있으면 명시.

## 2. 범위 결정 — 무엇을 하고 / 안 하는가
| 구분 | 포함 여부 | 내용 |
- ✅/❌ 로 경계를 먼저 못박는다. ❌ 는 백로그(§8)로 연결.
- 책임 주체가 갈리면 표기 (예: "블라인드는 ✅(프론트)").

## 3. 기능 요구사항
| # | 요구 | 설명 |
- U1, U2... 번호 부여 — 이후 설계·테스트·커밋·REST Docs 스니펫이 이 번호를 참조한다.
- **번호는 재사용하지 않는다** (→ [versioning.md](./versioning.md)).

## 4. 비즈니스 규칙 (정책 상세)
### 4-1, 4-2... 규칙 그룹별 서브섹션
- 노출/권한 규칙은 표로 (조회자 상태 × 보이는 것).
- 멱등·중복·불변 규칙은 "왜"와 함께 (예: 표가 쌓인 뒤 항목이 바뀌면 의미 왜곡).
- ⚠️ 의도적으로 수용한 트레이드오프는 사용자 결정 날짜와 함께 기록.
- 검증 규칙(길이·개수·중복)은 표로.

## 5. API 계약 (초안 — 확정 후 api-spec 반영)
### 5-1. 기존 확장 — {기존 엔드포인트}   ← 요청/응답 JSON 예시 + 규칙 불릿
### 5-2. 신규 — {METHOD} {경로}
- 기존 선례와 같은 경로 스타일·멱등 규칙이면 그 사실을 명시.
- 인증 요구는 헤더 단위로 적는다 (익명키 필요 / 로그인 필요 / 불필요).

## 6. API 호출 흐름 (프론트 ↔ 백엔드)
### 6-1... 시나리오별 ASCII 흐름 — 성공/에러 분기까지:
```
[화면·행위]
 → METHOD /경로 { body }
    ├─ 200 → 프론트가 할 일
    ├─ 401 {코드} → 프론트 재시도/로그인 유도
    └─ 409 {코드} → 안내 문구
```
- 프론트가 렌더링·분기 책임을 지는 지점을 명시한다 (계약의 절반은 프론트 동작).

## 7. 에러 코드 · 정책
| 코드 | HTTP | 의미 |
- 기존 공통 게이트가 자동 적용되는 것은 코드 신설 없이 그 사실만 기록
  (현재 공통 코드는 [ErrorCode.java](../../../../backend/src/main/java/kang20/ytcreator/shared/exception/ErrorCode.java) 참조).
- 네이밍 규약은 [error-handling.md](../../../../backend/docs/rule/error-handling.md) 가 정본.
- **신규 코드가 0개면 표를 생략**하고 "신규 에러 코드 없음 — 기존 게이트({코드들})로 전부 커버" 한 줄로 닫는다.

## 8. 백로그 (이번 범위 제외)
- §2 의 ❌ 항목 + 논의 중 나온 확장 아이디어.

## 9. 결정 · 변경 이력
### 9-1. 결정 이력
- 확정: "> 확정 완료(사용자 결정, 날짜)" 블록에 (MM-DD) 단위로 기록.
- 미확정: 🔶 번호 목록 — 각각 제안값과 근거를 붙인다. 전부 확정되면 "🔶 미확정 없음 (전부 확정)".

### 9-2. 버전 이력 (v2 이상일 때만)
| 버전 | 날짜 | 변경 | 사유 |
|---|---|---|---|
| v2 | MM-DD | +U7 초안 임시저장 / ~~U3 익명 댓글~~ / 제목 20→40자 | 사용자 결정(§9-1) |
- 한 줄에 `+추가 / ~~삭제~~ / 변경전→변경후` 를 모아 그 버전의 변경분만 적는다.

## 10. 다음 단계
1. [ ] §9-1 🔶 사용자 확정
2. [ ] `/develop-design {name}` — 소프트웨어 설계(데이터 모델·모듈 매핑·동시성)
3. [ ] api-spec 반영 → `/docs-sync` (프론트 계약 변경 시 동기화 필수)
```

## 작성 원칙 — 양식이 이렇게 생긴 이유

- **확정/🔶 구분이 이 문서의 존재 이유** — 사용자(기획자)가 말한 것과 스킬이 제안한 것을 섞으면
  나중에 "누가 언제 정했는지"를 잃는다. 결정마다 날짜를 남긴다.
- **API 호출 흐름(§6)은 생략하지 않는다** — 프론트/백이 한 레포라도 작업 주체가 갈리므로
  에러 분기별 프론트 행동이 곧 계약이다. 성공 케이스만 그리면 절반짜리 문서다.
- **데이터 모델은 여기 없다** — 요구 단계 문서에 테이블이 박히면 설계 자유도가 죽고,
  요구가 바뀔 때 두 군데를 고치게 된다. 설계서(`{name}-design.md`)가 단일 위치.
- **선례 정렬** — 새 규칙을 만들기 전에 기존 도메인 문서에 같은 패턴이 있는지 본다.
  같으면 "○○ 선례와 동일"이라고 쓰는 게 프론트·구현자 모두에게 싸다.
- 표는 짧은 열거에만, 규칙의 "왜"는 표 밖 불릿으로.

## 🔶 를 붙이는 기준

| 상황 | 처리 |
|---|---|
| 사용자가 명시적으로 정했다 | 확정 — §9-1 에 날짜와 함께 |
| 계약에 필요한데 사용자가 안 정했다 | **🔶 + 제안값 + 근거** |
| 기존 공통 규약을 그대로 따른다 | 🔶 아님 — 출처만 링크 (중복 개설 금지) |
| 응답 스키마·에러 분기에 영향 주는 화면 정책 | 🔶 (계약이므로) |
| 계약과 무관한 순수 화면 재량 | "프론트 재량" 표기 후 넘어감 |

## 첫 도메인일 때 (선례가 없을 때)

`backend/docs/domain/` 이 비어 있으면 "선례 정렬"이 성립하지 않는다. 이때는 반대로
**이 문서가 이후 모든 도메인의 선례가 된다**는 전제로 쓴다:

- 공통이 될 규칙(커서 페이지네이션 기본값, 멱등 처리 방식, 소프트삭제 여부, rate limit)은
  이 도메인에만 해당하는 것처럼 쓰지 말고 **"공통 규약으로 승격 후보"** 라고 표시한다.
- 확정되면 그 규칙은 `docs/server/api-spec.md` 로 올려 다음 도메인이 링크만 하게 만든다.
- 에러 코드도 마찬가지 — 이 도메인 전용인지 공통 게이트인지 구분해서 적는다.
