# 버저닝 규약 — 도메인 정의서를 고칠 때

> `backend/docs/new-domain/{name}/{name}-v{n}.md` 의 공통 규약.
> `/develop-design` 과 `/implement` 도 이 파일을 참조한다 — **표기 규칙의 단일 위치**.

## 기호 (모든 문서 공통)

| 기호 | 뜻 | 범위 |
|---|---|---|
| `{n}` | **정의서 버전** — 파일명 `{name}-v{n}.md` 의 그 값 | 1.. |
| `{k}` | **리뷰 회차** — code-reviewer 판정 회차 | 1..3 |
| `{r}` | **내부 라운드** — developer ⇄ tester 라운드 | 1..5 |
| `{v}` | **spec-verifier 검증 회차** | 1..3 |

네 값은 서로 다른 축이다. 한 문장에 `{n}` 과 회차가 같이 나오면 어느 쪽이 버전인지 읽을 수 없으므로
**검증 회차는 반드시 `{v}` 로 쓴다** — 예: `{name}-v{n}.md 를 검증. 단계: usecase-요구. {v}회차`.

## 파일명이 곧 버전이다

- 경로는 `backend/docs/new-domain/{name}/{name}-v{n}.md` 다. **초안도 `v1` 로 시작한다** —
  파일명에 항상 버전이 붙어서, 파일을 열지 않고도 지금 몇 번째 합의본인지 알 수 있다.
- **정본은 언제나 한 파일이다.** 요구·참고자료·용어 사전·도메인 모델이 그 안에 함께 산다.
  링크를 거는 쪽(다른 도메인 문서·커밋 메시지·리뷰)이 가리킬 대상이 하나여야 안 깨진다.

## 버전을 올린다 = 파일을 rename 한다

```
git mv backend/docs/new-domain/{name}/{name}-v{n}.md backend/docs/new-domain/{name}/{name}-v{n+1}.md
```

- **이전 버전 파일을 남기지 않는다.** 두 파일이 남으면 다음 사람이 어느 쪽을 읽어야 하는지 모르고,
  대개 먼저 눈에 띈 낡은 쪽을 읽는다. 이력은 파일이 아니라 git 과 `## 변경 이력` 이 보관한다.
- rename 후 **다른 문서가 걸어 둔 링크를 grep 으로 찾아 함께 고친다.**
  파일명에 버전이 박혀 있으므로 rename 은 반드시 링크를 깬다.

  ```
  grep -rn "{name}-v{n}" --include=*.md .
  ```

  같은 커밋에서 고친다. 나눠 커밋하면 그 사이 커밋들이 전부 깨진 링크를 가진다.

## 언제 버전을 올리나

**확정된 뒤** 요구·규칙·모델이 바뀔 때만.

> 확정 전(🔶 남은 초안) 수정은 버전이 아니다 — 그냥 고친다.
> 확정 전에 버전을 올리면 v5쯤에서 아직 아무것도 안 정해진 문서가 나온다.

**판정축은 상태 헤더 문자열이 아니라 섹션이다.** 이번에 쓸 섹션이 아직 없으면 보강(버전 유지),
이미 있는 섹션의 확정된 내용을 고치면 버전 올림이다.

- 용어 사전·참고자료를 **새로** 추가하는 것은 요구·규칙·모델의 변경이 아니므로 버전을 올리지 않는다.
  이미 확정된 용어의 영문명이나 요구 문장을 고칠 때만 버전 올림이다.
- `## 도메인 모델` 을 `/develop-design` 이 **최초로** 쓰는 것도 같은 이유로 버전 올림이 아니다.
- 상태 문자열만 보고 판정하면 `요구 확정` 문서에 용어 사전을 처음 붙이는 것까지 v2 가 되고,
  아무것도 안 바뀐 버전이 이력에 쌓인다.

## 상태 헤더가 단계를 표시한다

파일이 하나이므로 "요구 문서와 설계 문서의 버전을 맞춘다" 같은 동기화 작업이 없다.
대신 **상태 헤더**가 이 정의서가 어디까지 왔는지를 말한다.

```
> **버전 v{n}** · 상태: 요구 초안 | 요구 확정({날짜}) | 모델 초안 | **설계 확정({날짜})** | 구현 완료({날짜})
> 🔶 {n}건 — '## 🔶 결정 필요' 참조
```

- 단계를 넘길 때 **헤더를 먼저 고친다.** 상태와 내용이 어긋난 문서는 다음 스킬의 진입 판정을 속인다
  (`/develop-design` 은 "요구 확정"을, `/implement` 는 "설계 확정"을 보고 들어온다).
- 🔶 건수는 `## 🔶 결정 필요` 의 실제 항목 수와 **항상 같아야 한다.** 0건이면 `🔶 없음 (전부 확정)`.
  - `### 요구 🔶` · `### 모델 🔶` 두 그룹 제목은 **항상 둘 다** 있고, 항목이 없는 그룹은 제목 아래를 비운다.
    **불릿이 없는 빈 그룹은 0건으로 센다** — `- 없음` 같은 불릿을 쓰지 않는다 → [template.md "🔶 규약"](./template.md).

## 본문 표기 규약

| 변경 | 표기 | 예 |
|---|---|---|
| 추가 | 항목 끝에 `(v2)` | `- 재확인은 하루 1회로 제한한다 **(v2)**` |
| 수정 | 바뀐 값만 `~~이전~~ → 새값 (v2)` | `만료 완충 ~~14일~~ → 3일 **(v2)**` |
| 삭제 | 항목 전체 빗금 + 사유 | `~~만료 완충 14일~~ **(v2 삭제 — 웹훅 지연 실측 3일)**` |

적용 대상은 **본문 전부** — 요구 불릿·참고자료·용어 사전 행·도메인 모델의 속성/행위/규칙.
표 안이든 불릿이든 같은 규약을 쓴다.

## 지켜야 할 것

- **빗금 항목을 지우지 않는다.** "이런 규칙은 없다"가 아니라 **"있었는데 왜 없앴다"** 가 남아야
  같은 논의가 반복되지 않는다. 삭제 사유는 빗금 옆에 반드시 붙인다.
- **삭제 사유는 근거로 쓴다.** "불필요"가 아니라 무엇을 보고 그렇게 판단했는지 —
  실측값·사용자 결정·스펙 정정처럼.
- **에러 코드는 영구 결번이다.** 이미 배포된 코드를 다른 의미로 재사용하면 프론트의 기존 분기가
  조용히 오작동한다. 지운 코드는 다시 쓰지 않고 새 이름을 만든다.
  - **도메인 정의서 본문의** 번호(옛 U-번호)에 한해 결번 규칙이 사라졌다. 정의서에 번호를 박지 않기 때문이다
    → [template.md "번호를 쓰지 않는다"](./template.md).
  - 에러 코드 결번은 그대로 유지되고, `backend/workspace/{name}/v{n}/requirements.md` 의 **REQ-번호 결번은
    [handoff.md](../../implement/references/handoff.md) 가 따로 정한다.** 세 축을 한 규칙으로 묶지 않는다 —
    수명이 서로 다르다(에러 코드는 배포와 함께 영구, REQ-번호는 구현 회차를 넘어 유지, 본문 번호는 없다).
- **빗금 누적 상한** — v3 이상에서 한 섹션의 빗금이 절반을 넘으면
  **두 단계 이전 버전의 빗금만** `## 변경 이력` 으로 내리고 본문에서 뺀다. 사유는 이력에 보존한다.
  - 상한을 두는 이유: 이력이 본문을 밀어내면 현재 요구가 무엇인지 읽을 수 없다.
  - 두 단계로 잡는 이유: 직전 버전의 삭제는 아직 논의가 살아 있어 본문에서 보여야 한다.

## `## 변경 이력` (v2 이상일 때만)

| 버전 | 날짜 | 변경 | 사유 |
|---|---|---|---|
| v2 | 08-18 | +재확인 1일 1회 / ~~만료 완충 14일~~ → 3일 | 웹훅 지연 실측 |

- 한 줄에 `+추가 / ~~삭제~~ / 이전→새값` 을 모아 **그 버전의 변경분만** 적는다.
- 본문에서 내려온 빗금 항목은 사유를 그대로 옮겨 적는다. 요약하면서 근거를 지우지 않는다.

## 버전 올림 후 절차

1. `git mv` 로 rename → `grep` 으로 링크 수정 → 본문 표기·상태 헤더·`## 변경 이력` 갱신
2. `docs({name}): 도메인 정의서 v{n+1} — {한 줄 요약}` 커밋 (rename·링크 수정까지 같은 커밋)
3. 요구가 바뀌었으면 `## 용어 사전` 도 아직 유효한지 확인한다 —
   새로 생긴 `[대괄호]` 개념이 표에 없으면 `/usecase 용어 {name}` 을 이어서 호출하고,
   사라진 요구의 용어 행은 빗금 + 사유로 남긴다
   - 요구 모드가 새 `[대괄호]` 개념을 만드는 순간 용어 사전은 그 자리에서 낡는다.
     아무도 다시 안 보면 **이름 계약이 빈 채로 설계 확정까지 통과한다.**
4. 요구가 바뀌었으면 `## 도메인 모델` 이 아직 유효한지 확인한다 —
   같은 파일이라 겉으로는 멀쩡해 보이지만, 모델이 삭제된 요구를 여전히 구현하고 있을 수 있다
5. API 계약이 바뀌었으면 `/docs-sync` 로 문서를 반영한다
   — **프론트가 이미 이전 계약으로 구현했을 수 있다.** 변경분을 명시적으로 알린다
