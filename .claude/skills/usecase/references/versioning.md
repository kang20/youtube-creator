# 버저닝 규약 — 확정 문서를 고칠 때

> `{name}.md`(유스케이스)와 `{name}-design.md`(설계서) 공통 규약.
> develop-design 도 이 파일을 참조한다 — **표기 규칙의 단일 위치**.

## 언제 버전을 올리나

**확정된 문서**의 요구·정책·API 계약이 바뀔 때만. 파일을 새로 만들지 않고 **같은 문서의 버전을 올린다.**
정본이 하나여야 설계서·api-spec·프론트가 거는 링크가 안 깨진다.

> 초안 단계(🔶 확정 전) 수정은 버전이 아니다 — 그냥 고친다.
> 확정 전에 버전을 올리면 v5쯤에서 아직 아무것도 안 정해진 문서가 나온다.

## 표기 규약

| 변경 | 표기 | 예 |
|------|------|-----|
| 추가 | 항목 끝에 `(v2)` | `U7. 초안 임시저장 **(v2)**` |
| 수정 | 바뀐 값만 `~~이전~~ → 새값 (v2)` | `제목 길이 ~~20자~~ → 40자 **(v2)**` |
| 삭제 | 항목 전체 빗금 + 사유 | `~~U3. 익명 댓글~~ **(v2 삭제 — 신고 대응 비용)**` |

적용 대상은 **번호가 붙은 것 전부** — 요구(U-번호)·비즈니스 규칙·API 계약·호출 흐름·에러 코드.
표 안이든 불릿이든 같은 규약을 쓴다.

## 지켜야 할 것

- **번호는 영구 결번.** U3 을 지웠으면 U3 은 다시 쓰지 않고 새 요구는 다음 번호로 간다.
  설계서 §10 테스트 계획·커밋 메시지·REST Docs 스니펫 ID 가 U-번호를 참조하므로,
  번호를 돌려쓰면 과거 기록이 전부 다른 것을 가리키게 된다.
- **에러 코드도 결번.** 이미 배포된 코드를 다른 의미로 재사용하면 프론트의 기존 분기가
  조용히 오작동한다.
- **빗금 항목을 지우지 않는다.** "이 기능은 없다"가 아니라 "있었는데 왜 없앴다"가 남아야
  같은 논의가 반복되지 않는다. 삭제 사유는 빗금 옆에 반드시 붙인다.
- **빗금 누적 상한** — 본문이 읽기 어려워지면(대략 v3 이상, 한 섹션의 절반 초과)
  **두 단계 이전 버전의 빗금 항목만** §9-2 이력으로 내리고 본문에서 뺀다. 사유는 이력에 보존.

## 두 문서 버전을 맞춘다

유스케이스가 v2 로 가면 `{name}-design.md` 도 v2 로 올린다.
설계서 헤더의 **"대응 유스케이스 버전"** 이 동기화 신호다 —
요구가 v2 인데 설계서가 v1 이면 그 자체가 미반영 상태다.

설계서 쪽에서만 추가로 해야 하는 일(→ develop-design 이 담당):

- 삭제된 요구가 남긴 **코드 제거**를 리팩터링 표에 올린다. 안 지우면 죽은 코드로 남고
  테스트가 없으니 커버리지 게이트가 먼저 걸린다.
- **스키마 마이그레이션 순서**를 적는다. 운영은 `ddl-auto: validate` 라 앱보다 DB 가 먼저 맞아야 하고,
  컬럼 제거는 보통 "앱 배포 → 사용 중지 확인 → 다음 배포에서 DROP" 2단계다.

## 버전 올림 후 절차

1. `docs({name}): 유스케이스 v2 — {한 줄 요약}` 커밋
2. `/develop-design {name}` — 설계서 v2 반영
3. API 계약이 바뀌었으면 `/docs-sync` 로 api-spec 동기화
   — **프론트가 이미 v1 계약으로 구현했을 수 있다.** 변경분을 명시적으로 알린다.
