# usecase — 도메인 정의서의 요구·용어·참고자료를 쓴다

사용자가 말한 것을 **도메인 정의서**로 굳힌다 → `backend/docs/new-domain/{name}/{name}-v{n}.md`

정의서는 **파일 하나**다. 요구·참고자료·용어 사전·도메인 모델이 같은 파일에 순서대로 쌓인다.
이 스킬은 그중 앞의 셋을 쓰고, `## 도메인 모델` 은 `/develop-design` 이 같은 파일에 덧붙인다.
쪼개면 요구와 모델이 서로 다른 버전으로 표류하고, 프론트·구현자가 어느 쪽이 정본인지 묻게 된다.

**다루는 것**: 요구·정책·경계 선언 · 외부 API 스펙(참고자료) · 용어와 영문명
**다루지 않는 것**: 애그리거트·엔티티·테이블·트랜잭션·동시성 → 전부 `/develop-design` 몫

> **`backend/docs/domain/` 은 레거시(읽기 전용)다.** `auth.md` · `auth-design.md` · `payment.md` ·
> `payment-design.md` · `subtitle.md` 다섯 문서는 옛 양식이며 삭제·이동·재작성하지 않는다.
> 선례 참조로만 읽는다. **새 도메인은 `backend/docs/new-domain/` 에만 쓴다.**

## 입력

- `{name}` — 도메인명 (소문자)
- 사용자가 대화에서 말한 **확정 결정**
- (선택) 참고 정보 — 외부 API 스펙, 타 서비스 사례, 화면 흐름

## 모드 — 입력 형태로 가른다

| 입력 | 모드 | 쓰는 섹션 |
|---|---|---|
| `/usecase {name}` | 요구 | `## {도메인명} 도메인` |
| `/usecase 용어 {name}` | 용어 | `## 용어 사전` |
| `/usecase {name} {자유 텍스트}` 또는 `/usecase {자유 텍스트}` | 참고자료 | `## 참고자료 — {제목}` (요구와 용어 사이에 삽입) |

> **요구 섹션은 상태 헤더 다음의 첫 번째 `## ` 섹션이다. 제목 문자열로 찾지 않는다.**
> 제목은 `## {도메인명} 도메인` 형식으로 쓰되 `{도메인명}` 은 **한글이어도 되고 영문이어도 된다**
> (선례 `## 결제 도메인` 이 정상이다). 이름을 강제하지 않는다 —
> **기계적 식별은 '상태 헤더 다음의 첫 번째 `## ` 섹션' 으로 한다.**

- 판별 규칙: 첫 토큰이 `용어` 면 용어 모드. 인자가 도메인명 하나뿐이면 요구 모드. 그 외는 참고자료 모드.
- 대화 문맥에 작업 중인 도메인이 있으면 참고자료 모드는 `{name}` 을 생략할 수 있다.
- **모호하면 묻는다.** 잘못 고른 모드는 남의 섹션을 덮어쓴다.
- **각 모드는 자기 섹션만 쓴다.** 다른 섹션은 읽기만 하고 손대지 않는다 —
  세 모드가 며칠에 걸쳐 번갈아 호출되므로, 옆 섹션을 "정리"하면 사용자가 직접 고친 문장이 사라진다.
- 세 모드 모두 끝에 발견한 🔶 를 `## 🔶 결정 필요` 의 `### 요구 🔶` 에 누적한다.
  - 예외가 하나 있다. **용어 사전의 미확정(영문명 미정 포함)은 `### 모델 🔶` 에 넣는다** —
    영문명은 코드 식별자 계약이라 **구현 진입**을 막아야 하고,
    요구 확정과 develop-design 진입은 막을 이유가 없다.

> 첫 도메인이면 template.md 의 "첫 도메인일 때" 절을 따른다 — 이 문서가 이후 선례가 된다.

## 절차

### 0. 사전 검증 (세 모드 공통)

- **backend 브랜치인지 확인한다.** 아니면 중단하고 브랜치 전환을 안내한다.
- `backend/docs/new-domain/{name}/{name}-v*.md` 를 찾아 현재 버전과 상태 헤더를 읽는다. **덮어쓰기 금지.**

**판정축은 상태 헤더 문자열이 아니라 섹션이다.** 이번 모드가 쓸 섹션이 아직 없으면 보강,
이미 있는 섹션의 확정된 내용을 고치면 버전 올림이다.

| 파일과 섹션 상태 | 진입 모드 |
|---|---|
| 파일이 없다 | **신규** — 요구 모드만 새로 만든다. 파일명은 항상 `{name}-v1.md` |
| 파일은 있는데 **이번 모드가 쓸 섹션이 아직 없다** | **보강** — 버전을 올리지 않고 그 섹션을 새로 만든다 |
| 이번 모드가 쓸 섹션이 있고 **아직 🔶 가 남은 초안이다** | **보강** — 버전을 올리지 않고 그냥 고친다 |
| 이번 모드가 쓸 섹션의 **확정된 내용을 고친다** | **버전 올림** → [versioning.md](references/versioning.md) 대로 `git mv` 후 수정 (+ 용어 사전 재대조 — 아래 불릿) |

- 용어 사전·참고자료를 **새로** 추가하는 것은 요구·규칙·모델의 변경이 아니므로 버전을 올리지 않는다.
  이미 확정된 용어의 영문명이나 요구 문장을 고칠 때만 버전 올림이다.
  - 상태 문자열만 보면 `요구 확정` 문서에 `/usecase 용어 {name}` 을 **처음** 부르는 것까지
    버전 올림으로 잡혀, 아무것도 안 바꾼 문서가 v2 가 된다.
- **버전 올림 행일 때** — 요구가 바뀌었으면 `## 용어 사전` 도 아직 유효한지 확인한다.
  새로 생긴 `[대괄호]` 개념이 표에 없으면 `/usecase 용어 {name}` 을 이어서 호출하고,
  사라진 요구의 용어 행은 빗금 + 사유로 남긴다.
  - 요구 모드가 새 `[대괄호]` 개념을 만드는 순간 용어 사전은 그 자리에서 낡는다.
    아무도 다시 안 보면 **이름 계약이 빈 채로 설계 확정까지 통과한다.**
- 용어·참고자료 모드인데 파일이 없으면 **작성하지 않고 중단**한다.
  `/usecase {name}` 을 먼저 하라고 안내한다 — 요구 없이 만든 용어는 무엇을 가리키는지 알 수 없다.

**레거시 이관 분기** — `/usecase {name}` 대상이 `backend/docs/domain/` 에 있고 코드가 이미 있으면:

1. **그 사실을 사용자에게 알린다** — 레거시 도메인이고 **코드가 정본이다.**
2. **요구를 레거시 문서에서 옮길지, 코드를 읽고 새로 세울지 확인받는다.**
   문서와 코드가 이미 어긋나 있을 수 있어 우리가 고를 수 없다.
3. 어느 쪽이든 **레거시 파일은 그대로 둔다.** 새 정의서는 `backend/docs/new-domain/{name}/{name}-v1.md` 로 시작한다.
4. 코드가 정본인 부분은 요구 불릿에 그 사실을 적는다 — "현재 구현이 이렇게 돼 있다".
   그래야 다음 사람이 그 줄을 합의된 요구가 아니라 **현상 기술**로 읽는다.

이 분기를 도는 동안 상태는 `/pm` 이 말하는 **이관 진행 중**이다.

### 1. 요구 모드 — `## {도메인명} 도메인`

> **요구 섹션은 상태 헤더 다음의 첫 번째 `## ` 섹션이다. 제목 문자열로 찾지 않는다.**
> 제목은 한글이어도 되고 영문이어도 된다(선례 `## 결제 도메인`).

1. 사용자 발화에서 확정 결정을 뽑고, 계약·구현에 필요한데 안 정해진 것은 **🔶 + 제안값 + 근거**로 분리한다.
2. 계층 불릿 산문으로 쓴다. **번호를 붙이지 않는다** — 이유는 template.md "작성 원칙".
3. 핵심 개념은 `[대괄호]` 로 표시한다. 여기 표시한 말은 나중에 용어 사전에 **전부** 올라가야 한다.
4. 규칙마다 "왜"를 같은 불릿이나 바로 아래 하위 불릿에 붙인다. 근거 없는 규칙은 다음 사람이 되돌린다.
5. **섹션 끝에 경계 선언 절을 둔다** — "이 도메인이 하지 않는 일이 있다", "승계되지 않는 것이 있다".
   범위를 안 그으면 다음 단계가 범위를 발명한다.
6. API JSON·엔드포인트·플랫폼 스펙은 여기 섞지 않는다. 참고자료 모드로 뺀다.
7. **문서를 처음 만들 때 `## 🔶 결정 필요` 아래 두 그룹 제목을 미리 둔다** —
   `### 요구 🔶` 와 `### 모델 🔶` **둘 다.** 모델 그룹은 비어 있는 채로 둔다.
   항목이 없는 그룹은 제목 아래를 **비운다** — `- 없음` 같은 불릿을 쓰지 않는다.
   빈 그룹은 0건으로 센다 → template.md "🔶 규약".
   - 이것은 `## 도메인 모델` 을 미리 만드는 것과 다르다. 그 제목은 여전히 만들지 않는다(안전장치 참조).

### 2. 용어 모드 — `## 용어 사전`

1. 요구 섹션의 `[대괄호]` 개념을 전부 모은다. **하나라도 표에 없으면 누락이다.**
2. 그룹별 표로 쓴다. 열은 `용어 | 영문명 | 정의` 셋 고정.
3. **영문명이 코드 식별자의 계약이다.** 그 문장을 `## 용어 사전` 섹션 맨 위(표 바로 앞) 인용문으로 박는다 —
   클래스·메서드·필드·에러코드가 이 표 밖의 말을 쓰기 시작하면 문서와 코드가 서로를 못 찾는다.
4. 이름을 못 정한 것은 확정하지 말고 🔶 로 내린다.
   **용어 사전의 미확정(영문명 미정 포함)은 `### 모델 🔶` 에 넣는다** —
   영문명은 코드 식별자 계약이라 **구현 진입**을 막아야 하고,
   요구 확정과 develop-design 진입은 막을 이유가 없다.

### 3. 참고자료 모드 — `## 참고자료 — {제목}`

1. 요구 섹션과 용어 사전 **사이에** 삽입한다. 이미 같은 제목이 있으면 그 절을 갱신한다.
2. **출처 URL 과 조회 날짜를 반드시 적는다.** 원문이 정본이고 이 섹션은 사본이라고 명시한다.
3. 확인되지 않는 것은 추측으로 메우지 않는다. **"없다"는 사실 자체를 결과로 남긴다.**
4. 재조회로 뒤집힌 항목은 지우지 않고 **정정으로 남긴다** — 무엇을 왜 잘못 알았는지가 다음 조회를 아낀다.
5. 스펙이 도메인 규칙의 근거일 때는 "도메인 규칙과의 연결"을 붙인다. 표만 있으면 왜 옮겼는지 알 수 없다.

### 4. 작성

[references/template.md](references/template.md) 의 섹션 구조와 작성 원칙을 그대로 따른다.
밀도와 문체는 [payment-v2.md](../../../backend/docs/new-domain/payment/payment-v2.md) 를 읽고 맞춘다.

상태 헤더의 🔶 건수를 이번 작업 결과로 **갱신한다.** 헤더와 `## 🔶 결정 필요` 의 개수가 어긋나면
사용자는 둘 중 어느 쪽을 믿어야 할지 모른다.

### 5. 검증 — `spec-verifier` 에이전트에 위임

문서를 다 쓰면 **사용자에게 보고하기 전에** 검증 에이전트를 호출한다.
자기가 쓴 문서를 자기가 검토하면 "쓰면서 확인했다"고 느낀 항목을 다시 안 본다.

```
Agent(subagent_type="spec-verifier",
      prompt="backend/docs/new-domain/{name}/{name}-v{n}.md 를 검증. 단계: usecase-요구. {v}회차")
```

- **`{v}` = spec-verifier 검증 회차(1..3). `{n}`(정의서 버전)과 다른 값이다** —
  한 문장에 둘이 같이 나오므로 기호를 갈라 쓴다. 예: `payment-v2.md 를 검증. ... 2회차`
- **단계 토큰은 `usecase-요구` · `usecase-용어` · `usecase-참고자료` 셋 중 이번에 호출된 모드 하나로 치환한다.**
  파이프로 나열하지 않는다 — 세 값을 다 적어 보내면 에이전트가 어느 표로 검사할지 못 고른다.
- **어느 단계를 검증하는지 프롬프트에 반드시 쓴다.** 단계마다 성공 조건이 다르므로,
  용어만 추가한 작업을 요구 기준으로 검증하면 아직 안 쓴 것이 전부 FAIL 로 잡힌다.
  단계가 없으면 에이전트는 되묻지 않고 섹션 존재로 추론한다 — 그 추론이 틀리면 판정 전체가 무의미하다.
- **FAIL** → 지적된 항목을 수정하고 **재호출**한다(`{v}` 를 올려 회차를 알린다). **최대 3회.**
- 3회차(`{v}`=3)에도 FAIL 이면 루프를 멈추고, 남은 항목과 왜 못 고쳤는지를 사용자에게 보고한다.
  같은 항목이 두 번 연속 FAIL 이면 수정 방향이 틀린 것이므로 그때 바로 사용자에게 묻는다.
- **⚠️ 확인 요청** 항목(임의 확정 의심)은 에이전트가 판정할 수 없다 — 원 대화를 보지 못하기 때문.
  대화 맥락으로 직접 판단하고, 사용자가 정한 적 없으면 🔶 로 내린다.
- **판정 보류**(커밋 여부 · 자기 섹션 밖 수정 여부 등)는 이 스킬이 직접 확인한다 —
  검사 표에 없는 항목은 에이전트가 판정하지 않는다.

### 6. 보고 + 다음 단계

- 이번 모드가 채운 것과 🔶 목록을 요약 보고하고 확정을 유도한다.
- **커밋은 작업 단위마다.** 🔶 가 남아 있어도 결정 이력 자체가 보존 가치이므로 확정을 기다리지 않는다.
  - 요구: `docs({name}): 도메인 정의서 v1 — 요구 초안`
  - 참고자료: `docs({name}): 참고자료 — {제목}`
  - 용어: `docs({name}): 용어 사전`
- 요구 🔶 가 전부 확정되면 상태 헤더를 **요구 확정({날짜})** 으로 고치고
  `docs({name}): 요구 확정` 커밋 → `/develop-design {name}` 안내.
- 커밋은 사용자 확인을 받고 한다.

## 성공 조건

이 스킬은 아래를 만족해야 끝난 것이다. 판정은 [spec-verifier](../../agents/spec-verifier.md) 가
독립 컨텍스트에서 대조하되, **그 에이전트의 검사 표가 정본이며 표에 없는 항목은 이 스킬이 직접 확인한다** —
검증자가 안 보는 항목을 봤다고 착각하면 아무도 안 본 항목이 생긴다.
**공통은 세 모드 전부에, 모드별은 이번에 호출된 모드에만 적용한다.**

**공통**

- [ ] 경로와 이름이 `backend/docs/new-domain/{name}/{name}-v{n}.md` 다. 다른 디렉토리에 파일이 생기지 않았다
- [ ] 같은 도메인의 **다른 버전 파일이 남아 있지 않다** (버전 올림은 rename 이다)
- [ ] 섹션 순서가 `요구 → 참고자료(0..n) → 용어 사전 → 도메인 모델 → 🔶 결정 필요 → 변경 이력` 이다
      (`## 도메인 모델` 은 `/develop-design` 이 만들기 전까지 **제목조차 없다**)
- [ ] 상태 헤더가 있고, 표기된 🔶 건수가 `## 🔶 결정 필요` 의 실제 항목 수와 같다
      (**불릿이 없는 빈 그룹은 0건으로 센다**)
- [ ] **번호 체계가 없다** — `U1`·`§5-2` 같은 요구 번호·섹션 번호가 본문에 없다 (에러 코드는 예외)
- [ ] 🔶 가 **본문에는 마크만**, 내용은 전부 `## 🔶 결정 필요` 에 모여 있다
- [ ] `### 요구 🔶` 와 `### 모델 🔶` **두 그룹 제목이 항상 둘 다 있고**, 빈 그룹은 제목 아래가
      비어 있다 (`- 없음` 같은 불릿을 쓰지 않았다)
- [ ] 항목 형식이 `- **{질문}** — 제안: {값}. 근거: {한 줄}. 위치: {본문 어디}` 다
      (빈 그룹은 형식 검사 대상이 아니다)
- [ ] **데이터 모델·엔티티·테이블·컬럼·트랜잭션 서술이 하나도 없다**
- [ ] 사용자가 정하지 않은 것이 확정으로 적히지 않았다
- [ ] 이번 모드가 **자기 섹션 밖을 수정하지 않았다**
- [ ] 커밋됨
- [ ] (버전 올림 모드) 변경 지점에 `(v2)`·빗금·삭제 사유가 빠짐없이 붙고, 빗금 항목이 지워지지 않았다

**요구 모드**

- [ ] 계층 불릿 산문이다. 규칙을 표로 늘어놓지 않았다 (표는 상태 값 목록 같은 열거에만)
- [ ] 규칙마다 "왜"가 같은 불릿이나 하위 불릿에 붙어 있다
- [ ] 핵심 개념이 `[대괄호]` 로 표시돼 있다
- [ ] **경계 선언 절이 있다** — "이 도메인이 하지 않는 일" / "승계되지 않는 것"
- [ ] API JSON·엔드포인트 스펙이 요구 섹션에 섞여 있지 않다

**용어 모드**

- [ ] 표 열이 `용어 | 영문명 | 정의` 셋이고 그룹별로 나뉘어 있다
- [ ] "영문명이 코드 식별자의 계약이다"가 `## 용어 사전` 섹션 맨 위(표 바로 앞) 인용문으로 명시돼 있다
- [ ] 요구 섹션의 `[대괄호]` 개념이 **전부** 표에 있다

**참고자료 모드**

- [ ] 제목이 `## 참고자료 — {제목}` 이고 요구와 용어 사전 **사이**에 있다
- [ ] **출처 URL 과 조회 날짜**가 있고, 원문이 정본·이것은 사본이라고 명시돼 있다
- [ ] 확인 안 된 항목이 추측으로 메워지지 않고 "확인되지 않는 것"으로 남아 있다

## 안전장치

- **기존 문서 덮어쓰기 금지** — 있으면 보강/버전 올림 모드로 사용자 확인 후에 손댄다
- **남의 섹션 금지** — 요구 모드가 용어 사전을, 용어 모드가 요구를 고치지 않는다.
  세 모드가 시차를 두고 돌기 때문에 "겸사겸사 정리"가 곧 사용자 결정의 소실이다
- **임의 확정 금지** — 사용자가 안 정한 것은 전부 🔶 (제안값은 붙이되 확정 표기 금지)
- **확정 문서를 조용히 고치지 않는다** — 흔적 없는 수정은 프론트가 이미 구현한 계약을 말없이 깨는 일
- **없는 문서를 만들지 않는다** — 참조 문서가 없으면 공백을 보고하고 추측으로 메우지 않는다
- **`backend/docs/domain/` 을 건드리지 않는다** — 레거시는 읽기 전용이다
- **MVP 범위 우선** — 경계 밖 아이디어는 요구 섹션의 경계 선언 절로 내린다
- **모델을 쓰지 않는다** — `## 도메인 모델` 은 `/develop-design` 의 자리다. **제목조차 미리 만들지 않는다.**
  빈 제목을 만들어 두면 `/develop-design` 이 "이미 모델이 있다"고 갱신 모드로 오판해 매번 멈추고,
  `/pm` 도 단계를 잘못 읽는다. 이미 있으면 읽기만 하고 손대지 않는다

