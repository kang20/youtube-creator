# usecase — 유스케이스(비즈니스 요구사항) 명세 작성

사용자가 말한 기능 요구를 **요구사항 정본**으로 굳힌다 → `backend/docs/domain/{name}.md`

**다루는 것**: 요구·정책·API 계약·프론트↔백 호출 흐름
**다루지 않는 것**: 데이터 모델·엔티티·모듈 매핑·트랜잭션·동시성 → 전부 `/develop-design` 몫

## 입력

- `{name}` — 도메인/기능명 (소문자)
- 사용자가 대화에서 말한 **확정 결정** (날짜와 함께 기록할 것)
- (선택) 참고 UX — 스크린샷, 타 서비스 사례

## 참조 (필요할 때 읽는다)

| 무엇이 필요할 때 | 어디를 |
|---|---|
| 문서 양식·작성 원칙·🔶 기준 | [references/template.md](references/template.md) |
| 확정 문서를 고칠 때 (v2 표기·결번 규칙) | [references/versioning.md](references/versioning.md) |
| 기존 계약·에러 규격 | `docs/server/api-spec.md` |
| MVP 경계·인증 모델 | `docs/prd.md`, [CLAUDE.md](../../../CLAUDE.md) |
| 선례 패턴 | `backend/docs/domain/*.md` |
| 에러 코드 네이밍 | [error-handling.md](../../../backend/docs/rule/error-handling.md) |

> **없는 문서는 만들지 말고 그 사실을 보고한다.** 위 참조 중 아직 없는 것이 있으면
> (이 프로젝트는 초기라 api-spec·prd·도메인 문서가 없을 수 있다) 추측으로 메우지 말고,
> 그 공백이 어떤 결정을 막는지 사용자에게 알린다. 첫 도메인이면 template.md 의
> "첫 도메인일 때" 절을 따른다 — 이 문서가 이후 선례가 된다.

## 절차

### 0. 사전 검증
- backend 브랜치인지 확인
- `backend/docs/domain/{name}.md` 존재 여부 → **덮어쓰기 금지**. 상태 헤더로 모드를 가른다:
  - **초안**(🔶 확정 전) → 보강 모드. 그냥 고친다
  - **확정됨** → **버전 올림 모드** → [versioning.md](references/versioning.md)

### 1. 요구 수집 — 확정과 미확정을 가른다
사용자 발화에서 확정 결정을 추출하고, 계약에 필요한데 안 정해진 것은 **제안값 + 🔶** 로 목록화한다.
🔶 판정 기준표는 template.md 에 있다.

### 2. 작성
[references/template.md](references/template.md) 의 템플릿대로.

### 3. 검증 — `spec-verifier` 에이전트에 위임

문서를 다 쓰면 **사용자에게 보고하기 전에** 검증 에이전트를 호출한다.
자기가 쓴 문서를 자기가 검토하면 "쓰면서 확인했다"고 느낀 항목을 다시 안 본다.

```
Agent(subagent_type="spec-verifier",
      prompt="backend/docs/domain/{name}.md 를 usecase 성공 조건으로 검증. {n}회차")
```

- **FAIL** → 지적된 항목을 수정하고 **재호출**한다(회차를 알린다).
- **최대 3회.** 3회차에도 FAIL 이면 루프를 멈추고, 남은 항목과 왜 못 고쳤는지를 사용자에게 보고한다.
  같은 항목이 두 번 연속 FAIL 이면 수정 방향이 틀린 것이므로 그때 바로 사용자에게 묻는다.
- **⚠️ 확인 요청** 항목(임의 확정 의심)은 에이전트가 판정할 수 없다 — 원 대화를 보지 못하기 때문.
  대화 맥락으로 직접 판단하고, 사용자가 정한 적 없으면 🔶 로 내린다.
- **판정 보류**(커밋 여부 등)는 이 스킬이 직접 확인한다.

### 4. 보고 + 다음 단계
- 확정 사항과 🔶 목록을 요약 보고, 사용자 확정 유도
- **커밋은 초안 완성 시점에** (`docs({name}): 유스케이스 명세 작성`) — 🔶 가 남아 있어도
  결정 이력 자체가 보존 가치이므로 확정을 기다리지 않는다
- 확정되면: 상태 헤더 **v1 확정(날짜)** + 설계서 링크 → `docs({name}): 요구사항 확정` 커밋
  → `/develop-design {name}` 안내

## 성공 조건

이 스킬은 아래를 **전부** 만족해야 끝난 것이다.
판정은 [spec-verifier](../../agents/spec-verifier.md) 가 독립 컨텍스트에서 대조한다 —
이 목록이 그 에이전트의 판정 기준이므로, 항목을 고치면 검증 기준도 같이 바뀐다.

- [ ] `backend/docs/domain/{name}.md` 가 template.md 양식대로 존재한다
- [ ] 모든 미확정 결정이 🔶 + 제안값 + 근거 형태로 §9-1 에 모여 있다 (본문에 흩어져 있지 않다)
- [ ] §6 호출 흐름에 **에러 분기까지** 그려져 있다 (성공 케이스만 있으면 미완)
- [ ] 데이터 모델·엔티티·트랜잭션 서술이 **하나도 없다**
- [ ] 사용자가 정하지 않은 것이 확정으로 적히지 않았다
- [ ] 커밋됨
- [ ] (버전 올림 모드) 변경 지점에 `(v2)`·빗금·삭제 사유가 빠짐없이 붙고 §9-2 표와 본문이 일치한다

## 안전장치

- **기존 문서 덮어쓰기 금지** — 있으면 보강/버전 올림 모드로 사용자 확인 후
- **임의 확정 금지** — 사용자가 안 정한 것은 전부 🔶 (제안값은 붙이되 확정 표기 금지)
- **확정 문서를 조용히 고치지 않는다** — 흔적 없는 수정은 프론트가 이미 구현한 계약을 말없이 깨는 일
- **MVP 범위 우선** — 경계 밖 아이디어는 전부 백로그(§8)로
- **서버 계약이 바뀌면** §10 다음 단계에 `/docs-sync` 를 명시

## 파이프라인 위치

```

   │  (🔶 전부 확정 후)
   ▼

   ▼

```
