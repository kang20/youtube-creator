# 핸드오프 규격 — workspace 보고서

> `tester` ↔ `developer` 는 **파일로만 통신한다.** 서로를 직접 호출하지 않는다.
> 이 규격이 두 에이전트의 유일한 계약이므로, 양쪽 프롬프트가 이 파일을 참조한다.

## 위치

```
backend/workspace/{name}/
├── round-{n}-test.md      테스터 → 개발자 (무엇이 왜 실패했나 · 무엇을 고쳐야 하나)
├── round-{n}-dev.md       개발자 → 테스터 (무엇을 고쳤나)
└── blockers.md            설계서로 해결 불가 — 사용자 개입 필요 (있을 때만)
```

- `backend/workspace/` 는 gitignore 대상이다. **커밋되지 않는다.**
- 라운드마다 새 파일을 만든다(덮어쓰지 않는다). 같은 실패가 반복되는지 보이게 하기 위해서다.

## round-{n}-test.md — 테스터가 쓴다

```markdown
# {name} 라운드 {n} 테스트 보고

## 실행 결과
- 테스트: {통과}/{전체} · 실패 {n}건
- 변경 파일 라인 커버리지: {n}% (미달 파일: {목록})
- ModularityTest: 통과 | 실패({메시지})

## 실패 상세

### 1. {테스트 클래스}#{메서드}
- **덮으려던 것**: {name}.md U3 / {name}-design.md §5-2  ← 근거를 반드시 링크
- **기대**: {무엇이 일어나야 하나}
- **실제**: {무엇이 일어났나 — 예외 메시지·응답 코드 원문}
- **원인 분류**: 구현 누락 | 구현 오류 | 설계 모호 | 테스트 오류
- **수정 지시**: {파일:줄 단위로 무엇을 어떻게. "구현 필요" 같은 말 금지}

### 2. ...

## 커버리지 미달
| 파일 | 미달 라인 | 어떤 분기가 안 덮였나 | 필요한 것 |
|---|---|---|---|
- **테스트를 더 쓰면 되는 것**과 **죽은 코드라 지워야 하는 것**을 구분해서 적는다.

## 개발자가 손대면 안 되는 것
- `src/test/**` — 테스트는 테스터가 관리한다. 통과시키려고 테스트를 고치지 마라.
- {그 외 이번 라운드 범위 밖 파일}
```

**원인 분류가 이 문서의 핵심이다.**

| 분류 | 뜻 | 다음 행동 |
|---|---|---|
| 구현 누락 | 설계서에 있는데 코드가 없다 | 개발자가 구현 |
| 구현 오류 | 코드가 있는데 설계서와 다르게 동작 | 개발자가 수정 |
| 설계 모호 | 설계서만으로 무엇이 맞는지 판정 불가 | **blockers.md 로 올린다** — 개발자가 추측하면 안 된다 |
| 테스트 오류 | 테스트가 설계서를 잘못 읽었다 | **테스터가 자기 테스트를 고친다.** 개발자에게 넘기지 않는다 |

## round-{n}-dev.md — 개발자가 쓴다

```markdown
# {name} 라운드 {n} 개발 보고

## 처리한 지시
| 지시 | 처리 | 파일 |
|---|---|---|
| 1. {테스트 보고의 지시} | 구현 / 수정 / **미처리** | {경로} |

## 미처리 항목 (있으면)
- {지시} — {왜 못 했나}. 설계서로 판정 불가하면 blockers.md 에도 올렸는지 명시.

## 설계서 대비 구현 상태
- §4 모듈 매핑 산출물 중 완료: {목록}
- 아직 없는 것: {목록}

## 컴파일 확인
- `./gradlew compileJava` 통과 여부
```

## blockers.md — 양쪽 다 쓴다 (사용자 개입 필요)

```markdown
# {name} 블로커

## B1. {한 줄 요약}
- **발견**: 라운드 {n}, {누가}
- **상황**: {설계서 §N 이 무엇을 말하는지, 왜 부족한지}
- **선택지**: A) ... B) ... (각각의 결과)
- **추천**: {있으면, 근거와 함께}
- **막힌 것**: {이것 때문에 무엇을 못 하는지}
```

- 블로커가 생기면 **루프를 멈춘다.** 추측으로 진행하면 잘못된 구현 위에 테스트가 쌓인다.
- 해소는 `/develop-design {name}` 으로 설계서를 보강하는 것이 정석이다
  (요구 자체가 흔들리면 `/usecase {name}` 까지 거슬러 올라간다).

## 규격을 지키는 이유

- **근거 링크 강제**(`U3` · `§5-2`) — 어떤 요구를 덮으려던 테스트인지 없으면,
  실패했을 때 "이 테스트가 맞나"부터 다시 따져야 한다.
- **원인 분류 강제** — 분류가 없으면 개발자가 테스트 버그까지 떠안고 코드를 고친다.
- **라운드별 파일** — 같은 실패가 2라운드 연속이면 접근이 틀린 것이다. 파일이 남아야 그게 보인다.
