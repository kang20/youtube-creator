# 설계 의사결정 기록 (ADR) 보고서

기술 논의를 **결론만 남은 요약**이 아니라 **판단 과정이 보존된 기록**으로 만든다.

6개월 뒤 "이거 왜 이렇게 했지?"라고 물었을 때, 이 문서 하나로 답이 나와야 한다. 그러려면 채택된 안뿐 아니라 **검토했다가 버린 안과 버린 이유**가 남아 있어야 한다. 그게 이 형식의 존재 이유다.

산출물은 **단일 HTML 파일** 하나다. 외부 의존은 Google Fonts뿐이라 파일 하나만 주고받으면 된다.

## 산출물 위치와 이름

**결정이 속한 도메인 폴더 안에 둔다.** 그 도메인을 읽는 사람이 정의서 옆에서 바로 발견해야 한다 —
따로 모아 두면 도메인을 파악하러 온 사람이 ADR 이 있다는 사실조차 모른다.

```
backend/docs/new-domain/{도메인}/{주제}-{YYYY-MM-DD}.html    한 도메인 안에서 닫히는 결정
backend/docs/new-domain/{a}-{b}/{주제}-{YYYY-MM-DD}.html     두 도메인 사이의 결정 (알파벳순)
backend/docs/adr/{주제}-{YYYY-MM-DD}.html                    도메인에 속하지 않는 결정
```

- `{주제}` — 무엇에 대한 결정인지 알 수 있는 소문자 kebab-case
  (예: `script-storage`, `queue-selection`). 도메인명이 아니라 **결정 주제**다 —
  폴더가 이미 도메인을 말하므로 파일명에 또 넣으면 `subtitle/subtitle-storage.html` 이 된다.
- `{YYYY-MM-DD}` — 결정을 내린 날짜(문서 작성일). 마스트헤드 작성일과 같아야 한다.
- 디렉터리가 없으면 만든다.

**어느 폴더에 넣을지**

| 결정의 성격 | 위치 | 예 |
|---|---|---|
| 한 도메인 안에서 닫힌다 | `new-domain/{도메인}/` | 대본을 어디에 저장할 것인가 → `subtitle/` |
| 두 도메인의 계약이 걸린다 | `new-domain/{a}-{b}/` | 이용권을 누가 노출할 것인가 → `payment-subtitle/` |
| 도메인과 무관하다 | `backend/docs/adr/` | 큐 선택, 배포 방식, 모니터링 |

- **도메인이 애매하면 묻는다.** 잘못 넣으면 그 도메인을 읽는 사람이 영영 못 본다.
- 폴더 규약의 정본은 [backend/CLAUDE.md](../../../backend/CLAUDE.md) "도메인 문서 위치" 다.

예: `backend/docs/new-domain/subtitle/script-storage-2026-08-07.html`

같은 주제를 다시 결정하면 **덮어쓰지 않고 새 날짜로 파일을 하나 더 만든다.**
이전 판단이 남아 있어야 "그때는 왜 다르게 정했나"를 볼 수 있다.
새 문서에는 이전 결정을 뒤집는다는 사실과 무엇이 바뀌었는지를 명시한다(번복 기록).

## 언제 쓰나

설계 과정에서 **판단이 갈렸던 지점**을 남기고 싶을 때 쓴다. 대표적으로
`/develop-design` 으로 설계서를 쓰다가 대안을 비교해 하나를 고른 경우다.

같은 폴더에 나란히 놓이는 도메인 정의서(`{name}-v{n}.md`)와 역할이 다르다.

| | 도메인 정의서 | ADR |
|---|---|---|
| 답하는 질문 | 무엇을 어떻게 만드나 | **왜 그렇게 정했나** |
| 기각안 | 한 줄로 요약되거나 사라진다 | **카드로 전부 보존** |
| 수명 | 버전이 오르면 갱신 | 그 시점의 판단으로 **동결** |

정의서에 한 줄로 담기엔 아까운 논의였다면 ADR 로 따로 남긴다.
반대로 대안이 하나뿐이었던 결정은 ADR 로 만들지 않는다 — 기각 카드가 없는 ADR 은 빈 껍데기다.

## 작업 순서

1. **재료 확보** — 대화에 이미 논의가 있으면 그걸 쓴다. 긴 대화라면 전체를 훑어 결정 지점을 빠짐없이 뽑는다. 재료가 부족하면 억지로 채우지 말고 무엇이 비었는지 물어본다.
2. **결정 목록화** — 주제별로 `고민 → 선택지들 → 결정`을 표로 정리한다. 이 단계에서 **기각된 선택지가 하나도 없는 주제**가 보이면 대화를 다시 확인한다. 대안 없이 내려진 결정은 대개 기록 누락이지 진짜 만장일치가 아니다.
3. **템플릿 복사** — `assets/template.html`을 위 산출물 경로로 복사한다. CSS와 JS가 전부 들어 있으니 스타일을 새로 짜지 않는다.
   뼈대는 그 자체로 검사기를 통과한다(예시 1건씩이 들어 있다). 복사 직후 한 번 돌려 기준선을 확인하면, 이후 뜨는 오류는 전부 작성 중에 생긴 것이다.
4. **본문 작성** — `references/components.md`의 컴포넌트를 조합한다.
5. **확인 문제 삽입** — 아래 "확인 문제" 절을 따른다.
6. **검증** — 아래 "마무리 검증" 절의 체크를 실제로 돌린다.

## 문서 구조

```
마스트헤드      제목 + 메타(작성일/범위/스택) + 집계 배지
채택한 결정      맨 앞. 확정된 결정만 한 줄씩 + 본문으로 가는 링크
00 시스템 구성   (선택) 아키텍처 그림 + 구성요소 현황표
목차            번호와 섹션 eyebrow 번호가 일치해야 함
01..NN 주제     고민 → 선택지 카드들 → 결정 블록 → 확인 문제
NN 미해결 과제   Q01..QNN, 왜 막혀 있는지까지
NN 부록         (선택) 학습 로드맵, 참고 링크
확인 문제 결과   자동 집계
푸터            집계 재확인
```

주제 하나는 **결정 하나**를 다룬다. 한 섹션에 결정이 두 개 들어가면 나눈다.

## 맨 앞의 "채택한 결정"

마스트헤드 바로 다음, 목차보다 앞에 놓는다. 결론만 빠르게 확인하려는 사람이 본문을 뒤지지 않아도 되게 하는 블록이다.

**채택된 결정만 넣는다.** 보류·기각은 여기 오지 않는다. 이 블록의 가치는 "여기 있는 건 전부 확정된 것"이라는 신뢰에서 나오므로, 아직 안 정해진 걸 섞으면 블록 자체가 무의미해진다.

각 줄은 `D-NN` + 결정 한 줄 + 범주 태그이고, **줄 전체가 해당 섹션으로 가는 링크**다. 요약을 보다가 "왜?"가 생기면 바로 근거로 이동할 수 있어야 한다.

한 줄은 스캔되는 길이로 줄인다. 본문의 결정 문장을 그대로 복사하지 말고 핵심만 남기고, 판단의 핵심어에만 `<b>`를 건다.

> 본문: `대본은 오브젝트 스토리지에 파일로 저장하고, MySQL에는 파일 링크와 작업 상태만 남긴다. 대본 규격은 서비스가 정의하고...`
> 요약: `대본은 <b>오브젝트 스토리지에 파일로</b>, DB에는 링크와 상태만 남긴다.`

보류된 결정이 있으면 블록 끝의 `dg-foot`에 한 줄로 밝힌다. 요약만 읽은 사람이 **전부 정해졌다고 오해하는 것**을 막는 장치다. 보류가 없으면 이 부분은 통째로 뺀다.

## 각 주제를 쓰는 방식

### 고민 (`.q`)

의문문 한 줄. 답이 아니라 **질문**을 적는다.

- 좋음: `대본을 DB에 넣을 것인가, 파일로 저장할 것인가?`
- 나쁨: `대본 저장소 선정` ← 이건 제목이지 고민이 아니다

### 선택지 카드 (`.opt`)

검토한 안을 **전부** 카드로 만든다. 기각된 안이 이 문서의 핵심 자산이다.

각 카드에 상태 칩(`채택`/`기각`/`보류`/`유지`)을 달고, 근거를 `+장점 / −단점 / ·참고`로 나눈다. 채택된 안에도 **단점을 반드시 적는다.** 대가 없는 선택은 없고, 대가를 안 적으면 나중에 그 대가를 만났을 때 문서를 의심하게 된다.

기각 카드의 단점은 "안 좋음" 수준이 아니라 **기각을 결정지은 그 한 가지**가 드러나야 한다.

### 결정 블록 (`.cue`)

`D-01`부터 순번을 매긴다. 굵은 한 줄로 결정을 쓰고, 그 아래 이유를 쓴다.

이유는 이 형태를 지향한다: **무엇을 얻고, 무엇을 대가로 치렀는가.**

> 접근 패턴이 통째로 읽고 통째로 쓰기여서 관계형의 이점을 하나도 쓰지 않는다. 대신 파일 포맷이 곧 계약이 되므로 규격을 먼저 못박아야 한다.

**번복된 결정은 번복 사실을 명시한다.** 앞선 논의에서 A로 갔다가 B로 뒤집혔다면, 결정 블록에 그 경위를 남긴다. 번복은 부끄러운 게 아니라 가장 값진 기록이다 — 무엇을 놓쳤다가 발견했는지가 거기 들어 있다.

### 상태 표기

| 칩 | 의미 |
|---|---|
| `채택` | 이 안으로 간다 |
| `기각` | 검토했고 버렸다. 이유가 카드에 있어야 한다 |
| `보류` | 판단을 미뤘다. 무엇을 알아야 결론이 나는지 적는다 |
| `유지` | 기존 방식을 그대로 둔다 |

**보류를 채택으로 반올림하지 않는다.** 아직 안 정한 걸 정한 것처럼 쓰면 문서 전체의 신뢰가 무너진다.

## 미해결 과제 섹션

숨기지 말고 별도 섹션에 모은다. 각 항목은 질문 + **왜 아직 막혀 있는지**를 함께 적는다. "확인 필요"만 적힌 항목은 쓸모가 없다 — 어디서 어떻게 확인할지까지 적어야 다음 사람이 이어받는다.

다른 결정을 막고 있는 항목은 명시한다. 그게 다음에 할 일이다.

## 확인 문제

각 주제 섹션 끝에 객관식 한 문제를 넣는다. 검토자가 이해했는지 확인하고, 읽는 속도를 조절하고, 중요한 개념을 한 번 더 각인시키는 장치다.

문제를 만드는 원칙:

- **사실이 아니라 판단 근거를 묻는다.** "Redis Stream을 쓰기로 했다" 같은 암기 문제는 가치가 없다. "왜 Kafka가 아닌가"를 묻는다.
- **오답 보기에 흔한 오해를 넣는다.** 그 보기를 고르면 무엇을 잘못 이해한 것인지가 드러나야 한다.
- **대화 중 실제로 나왔던 착각을 오답으로 재활용한다.** 사용자가 논의 도중 잘못 짚었다가 교정된 지점이 있으면 그게 최고의 오답 보기다.
- 가끔 **"틀린 것을 고르시오"** 형태를 섞어 관성적 클릭을 끊는다.
- 해설에는 정답 근거뿐 아니라 **왜 그 오답이 매력적이었는지**를 적는다.

보기는 4개, 정답은 `data-ans`(0부터), 해설은 `data-exp`에 넣는다. HTML 태그(`<b>`, `<code>`)를 해설에 쓸 수 있지만 **큰따옴표는 쓰지 않는다** — 속성값이 깨진다.

채점은 `template.html`의 스크립트가 자동으로 한다. 진행 막대와 분모는 실제 문제 수를 세어 스스로 맞추므로 손댈 필요가 없다. 마스트헤드와 푸터의 집계 숫자만 직접 고친다.

## 톤

- **한국어. 평서체 종결(`~한다`).** 경어체나 설명조 늘어놓기를 쓰지 않는다.
- 짧게 끊는다. 한 문장에 한 가지.
- 판단 근거를 적을 땐 추상어를 피하고 구체적 사실을 쓴다. "비효율적이다"가 아니라 "재인코딩이 필요해 원가가 수십 배로 뛴다".
- 확정되지 않은 것에 단정적 표현을 쓰지 않는다.

## 마무리 검증

**먼저 검사기를 돌린다.** 눈으로 훑으면 숫자 정합성과 링크는 반드시 놓친다.

```bash
PYTHONIOENCODING=utf-8 python .claude/skills/adr-create/scripts/validate_adr.py <결과물.html>
```

> 이 환경에서는 `python3` 가 아니라 **`python`** 이다(`python3` 는 Windows Store 스텁이라 실패한다).
> `PYTHONIOENCODING=utf-8` 을 빼면 검사 결과의 한글이 깨져서 무엇이 틀렸는지 읽을 수 없다.

오류(`✗`)가 0이 될 때까지 고치고, 고칠 때마다 **다시 돌린다** — 수정 하나가 다른 숫자를 어긋나게 하는 일이 흔하다. 경고(`!`)는 판단이 필요하니 남길 거면 이유를 밝힌다.

검사기가 확인하는 것:

- [ ] `<section>` 여는 태그와 닫는 태그 수가 같다
- [ ] 목차 항목 수 = 섹션 수, 목차 번호와 각 섹션 `eyebrow` 번호가 일치한다 (`nav.toc ol`의 `counter-reset` 값으로 시작 번호를 맞춘다 — 00부터 시작하면 `counter-reset:toc -1`)
- [ ] `D-NN` 번호가 건너뛰거나 중복되지 않는다
- [ ] 맨 앞 요약에 **채택된 결정만** 있다. 보류·기각이 섞여 있지 않다
- [ ] 요약 줄 수 = 마스트헤드 확정 수 = `Adopted · N`
- [ ] 요약의 모든 `href="#sN"`가 실제 존재하는 섹션을 가리킨다
- [ ] 보류된 결정이 있다면 `dg-foot`에 밝혀져 있다
- [ ] 마스트헤드 집계 숫자 = 실제 칩 개수, 푸터 숫자도 동일
- [ ] 마스트헤드·푸터의 확인 문제 수가 실제 문제 수와 같다 (결과 블록 분모는 스크립트가 자동 계산한다)
- [ ] 각 확인 문제의 `data-ans`가 실제 정답 위치를 가리킨다
- [ ] `data-exp` 안에 큰따옴표가 없다
- [ ] **기각 카드가 하나도 없는 섹션이 있는지** 확인한다. 있다면 대안 검토를 빠뜨린 것이다

검사기가 **못 보는** 것은 직접 판단한다.

- 기각 이유가 기각을 결정지은 그 한 가지를 짚는가
- 근거가 형용사에서 멈추지 않고 검증 가능한 사실까지 내려갔는가
- 확인 문제가 암기가 아니라 판단 근거를 묻는가
- 미해결 항목이 어떻게 뚫을지까지 적었는가

`localStorage`나 `sessionStorage`를 쓰지 않는다. 점수는 메모리에만 둔다.

## 참고 파일

- `assets/template.html` — CSS·JS 포함 뼈대. 항상 여기서 시작한다
- `references/components.md` — 컴포넌트별 HTML 조각과 사용 시점 (흐름도, 상태머신, 계층도, 시스템 맵, 현황표, 콜아웃, 확인 문제)
- `references/example-section.md` — 완성된 섹션 하나의 전문. 밀도와 문장 톤의 기준
- `.claude/skills/adr-create/scripts/validate_adr.py` — 규격 검사기. 구조·클래스 오타·링크·결정 번호·집계 숫자·목차 번호·확인 문제를 기계적으로 확인한다
- `agents/adr-report.md` — 생성 + 자체 검증까지 도는 Claude Code 서브에이전트
- `agents/adr-auditor.md` — 이미 만든 문서를 읽기 전용으로 감사하는 서브에이전트

에이전트를 쓰려면 `agents/` 안의 파일을 `~/.claude/agents/`(전체 프로젝트) 또는 `.claude/agents/`(현재 프로젝트)에 복사한다.
