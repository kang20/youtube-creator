# 모듈 경계 검증

#arch-module-boundary #test-modularity

## 한 줄

`ApplicationModules.verify()` 한 줄이 순환 의존·`internal` 침범·미허용 의존을 전부 잡는다.
**단, 잡지 못하는 것도 있다** — 이 레포는 그 구멍을 실제로 밟았다.

## 실제 코드

`backend/src/test/java/kang20/ytcreator/ModularityTest.java`:

```java
class ModularityTest {

    static final ApplicationModules MODULES = ApplicationModules.of(YtcreatorApplication.class);

    @Test
    void 모듈_경계를_지킨다() {
        MODULES.verify();
    }

    @Test
    void 모듈_문서를_생성한다() {
        new Documenter(MODULES)
            .writeModulesAsPlantUml()
            .writeIndividualModulesAsPlantUml()
            .writeModuleCanvases();     // build/spring-modulith-docs/
    }
}
```

- 이 테스트는 **모든 프로젝트에 정확히 1개**만 있으면 된다.
- CI 필수 — 배포 워크플로의 `./gradlew test` 에 이미 포함된다.

```bash
cd backend
./gradlew test --tests "*ModularityTest"
```

## `verify()` 가 잡는 것

| 위반 | 예 |
|---|---|
| **순환 의존** | `auth → subscription → auth` |
| **`internal` 침범** | 다른 모듈이 `auth.internal.User` 를 import |
| **미허용 의존** | `allowedDependencies` 에 없는 모듈 호출 |
| **모듈 미선언 패키지** | 최상위 패키지에 `package-info.java` 가 없음 |

## ⚠️ `verify()` 가 잡지 **못하는** 것

> [!warning] 이 레포가 실제로 발견한 구멍이다
> `verify()` 는 **"선언된 규칙을 지키는지"** 를 본다. **"규칙 자체가 옳은지"** 는 못 본다.

| 못 잡는 것 | 왜 | 결과 |
|---|---|---|
| `allowedDependencies` 에 **`subscription` 을 적어 넣는 것** | 적으면 그 의존이 **정상**이 된다 | 막으려던 순환의 씨앗이 **조용히 통과** |
| `auth` 에 **컨트롤러가 생기는 것** | 컨트롤러는 모듈 경계 위반이 아니다 | "auth 가 서서히 홈 화면 API 가 된다" |
| **수동 DDL 이 매핑과 어긋나는 것** | Modulith 의 관심사가 아니다 | 운영 기동 실패 (`ddl-auto: validate`) |

### 그래서 별도 구조 테스트를 뒀다

`backend/src/test/java/kang20/ytcreator/auth/AuthModuleBoundaryTest.java` 가
`verify()` 가 못 잡는 불변식을 **리플렉션으로** 고정한다.

```java
// ① 컨트롤러가 생기면 실패
scanner.addIncludeFilter(new AnnotationTypeFilter(Controller.class));
assertThat(scanner.findCandidateComponents("kang20.ytcreator.auth")).isEmpty();

// ② allowedDependencies 에 subscription 이 끼면 실패
assertThat(module.allowedDependencies()).containsExactly("shared");
```

> [!tip] 여기서 배울 원칙
> **자동 검증 도구가 "무엇을 보지 않는지"를 아는 것이 그 도구를 쓰는 능력의 절반이다.**
> `verify()` 를 믿되, 그것이 검사하지 않는 설계 전제는 **직접 테스트로 못 박는다.**

## `Documenter` — 모듈 문서 자동 생성

```java
new Documenter(MODULES)
    .writeModulesAsPlantUml()            // 전체 모듈 다이어그램
    .writeIndividualModulesAsPlantUml()  // 모듈별 다이어그램
    .writeModuleCanvases();              // 모듈 캔버스(공개 API·이벤트·의존 요약)
```

산출물: `backend/build/spring-modulith-docs/` (gitignore 대상 — 빌드하면 다시 생긴다)

**모듈 캔버스**는 모듈 하나의 요약표다 — 공개 타입, 발행/구독 이벤트, 의존, 설정 프로퍼티.
설계서를 손으로 갱신하지 않아도 **코드가 곧 문서**가 된다.

## 런타임 확인 — `/actuator/modulith`

```bash
curl localhost:8080/actuator/modulith
```

기동한 앱의 모듈 구조를 JSON 으로 준다. 빌드 타임 검증(`verify()`)과 달리
**실제 기동한 애플리케이션의** 모듈 그래프라, 설정 실수로 모듈이 빠졌는지 확인할 때 쓴다.

> 외부에는 Caddy 가 `/actuator/*` 를 403 으로 막는다 — 수집은 SSH 역터널(루프백)로만 들어온다.

## 검증 계층 정리

```text
빌드 타임                                런타임
─────────────────────────────           ──────────────────
ModularityTest.verify()                 /actuator/modulith
  순환·internal·미허용 의존                  실제 기동한 모듈 그래프
        │
        │ 못 잡는 것
        ▼
AuthModuleBoundaryTest (리플렉션)
  컨트롤러 부재 · allowedDependencies 내용
  · 수동 DDL ↔ 매핑 대조
```
