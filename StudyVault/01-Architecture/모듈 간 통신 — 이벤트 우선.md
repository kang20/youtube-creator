# 모듈 간 통신 — 이벤트 우선

#arch-event-driven #pattern-outbox #arch-module-boundary

## 한 줄

모듈 간 통신의 **기본은 이벤트**다. 직접 호출은 **동기 응답이 반드시 필요할 때만** 쓰고, 그때도 `allowedDependencies` 에 적어 의도를 고정한다.

## 세 가지 통신 수단

| 수단 | 언제 | 결합도 | 이 레포 |
|---|---|---|---|
| **도메인 이벤트** | 기본. "이런 일이 일어났다"를 알릴 때 | 낮음 (발행자는 구독자를 모른다) | 아직 없음 |
| **모듈 공개 API 직접 호출** | 동기 응답이 꼭 필요할 때 | 높음 — `allowedDependencies` 명시 필수 | `bootstrap → auth` (설계됨) |
| **`@NamedInterface`** | 모듈의 **일부만** 노출하고 싶을 때 | 중간 | 미사용 |

## 이벤트 — 발행과 구독

```java
// 발행 (post 모듈)
events.publishEvent(new PostCreated(postId, memeId));

// 구독 (notification 모듈)
@ApplicationModuleListener
void on(PostCreated event) { ... }
```

### `@ApplicationModuleListener` 가 실제로 하는 일

이 어노테이션 하나가 **세 개를 합친 것**이다:

| 구성 | 효과 |
|---|---|
| `@TransactionalEventListener` | **발행자 트랜잭션이 커밋된 뒤에** 실행 |
| `@Async` | 별도 스레드 — 발행자를 막지 않는다 |
| `@Transactional(REQUIRES_NEW)` | 구독자는 **자기 트랜잭션**에서 실행 |

> [!important] 왜 이 조합인가
> - **커밋 후 실행**: 발행자가 롤백되면 구독자도 안 돈다. "일어나지 않은 일"을 알리지 않는다.
> - **REQUIRES_NEW**: 구독자가 실패해도 **발행자 트랜잭션을 오염시키지 않는다.**
>   (같은 트랜잭션이면 rollback-only 표식이 찍혀 발행자 커밋이 터진다 → [[스프링-트랜잭션]])

## 이벤트 발행 레지스트리 (트랜잭션 아웃박스)

`@Async` 로 넘긴 순간 **유실 위험**이 생긴다 — 구독자가 실행되기 전에 앱이 죽으면 그 이벤트는 사라진다.

Modulith 는 이를 **아웃박스 테이블**로 막는다.

```text
① 발행자 트랜잭션 커밋
     └─ 같은 트랜잭션에서 event_publication 테이블에 미완료 이벤트를 기록
② 구독자 실행 → 성공하면 완료 표시
③ 앱이 죽어도 미완료 행이 DB 에 남아 재시도 가능
```

의존: `spring-modulith-starter-jpa` (`backend/build.gradle.kts`)

> [!warning] 이 레포가 실제로 겪은 함정
> 운영은 `ddl-auto: validate` 라 **스키마가 배포로 만들어지지 않는다.**
> 그런데 `spring-modulith-starter-jpa` 는 아웃박스를 **JPA 엔티티로 등록**하므로,
> **어떤 모듈도 이벤트를 발행하지 않아도** 테이블이 없으면 기동이 실패한다.
>
> ```
> Schema validation: missing table [event_publication]
> ```
>
> → `backend/deploy/sql/event-publication-v1.sql` 이 **첫 배포 전에** 적용돼야 한다.
> 테이블명은 **소문자** `event_publication` 이다(Boot 물리 네이밍 전략).
> 대문자로 만들면 로컬(H2)에선 안 드러나고 **리눅스 MySQL 에서만** 깨진다.

## 순환 의존을 이벤트로 뒤집기

두 모듈이 서로를 참조하면 `verify()` 가 깨진다. **정석은 한쪽을 이벤트 구독으로 뒤집는 것**이다.

```text
❌ 순환                          ✅ 뒤집기
┌──────┐      ┌──────┐         ┌──────┐  이벤트   ┌──────┐
│ auth │─────▶│ subs │         │ auth │ ────────▶ │ subs │
│      │◀─────│      │         │      │ (구독 안 함)│      │
└──────┘      └──────┘         └──────┘           └──────┘
   verify() 실패                  auth 는 subs 를 모른다
```

### 이 레포는 세 번째 길을 택했다

`auth` 와 `subscription` 을 **둘 다 참조하는 집계 모듈**을 새로 뒀다.

```text
POST /api/v1/bootstrap
   └─▶ bootstrap (allowedDependencies = { shared, auth, subscription })
          ├─▶ AuthService.register(anonymousKey)
          └─▶ SubscriptionService.statusOf(anonymousKey)
```

**왜 이벤트가 아니라 직접 호출인가**: 진입 응답을 **동기로 조립**해야 한다. 이벤트는 비동기라 응답을 만들 수 없다.
그래서 `allowedDependencies` 에 명시하고 **한 방향**만 만든다 — 순환이 생기지 않는다.

**집계 모듈의 제약**: 자기 저장소도 도메인 규칙도 갖지 않는다. 판단·검증·저장이 생기면 그건 집계가 아니라 새 도메인이다.

## 이벤트를 만들지 않는 것도 결정이다

> [!tip] `auth` 는 `UserRegistered` 이벤트를 발행하지 않는다
> MVP 에 **구독할 모듈이 하나도 없기 때문**이다.
> 소비자 없는 이벤트는 아웃박스 테이블만 채우고 검증할 대상도 없다 — **소비자가 생길 때 만든다.**
>
> "이벤트 우선"은 "무조건 이벤트"가 아니다.

## `@NamedInterface` — 부분 노출

모듈 전체가 아니라 일부만 다른 모듈에 열고 싶을 때 쓴다.

```java
allowedDependencies = { "shared", "meme :: api" }   // meme 모듈의 api 네임드 인터페이스만
```

이 레포는 아직 쓰지 않는다. 모듈이 커져서 "공개 API 안에서도 등급을 나눠야" 할 때 도입한다.

## 테스트 — `@ApplicationModuleTest`

```java
@ApplicationModuleTest(mode = BOOTSTRAP_MODE.DIRECT_DEPENDENCIES)
class PostModuleTest {

    @Test
    void 글을_쓰면_PostCreated_이벤트가_발행된다(Scenario scenario) {
        scenario.stimulate(() -> postService.create(cmd))
                .andWaitForEventOfType(PostCreated.class)
                .toArriveAndVerify(ev -> assertThat(ev.postId()).isNotNull());
    }
}
```

- `Scenario` 가 **비동기 이벤트를 기다렸다** 검증한다 — `Thread.sleep` 금지.
- `BOOTSTRAP_MODE` 로 부팅 범위를 좁힌다: `STANDALONE`(이 모듈만) / `DIRECT_DEPENDENCIES` / `ALL_DEPENDENCIES`.
