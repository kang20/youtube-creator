== 결제 · 이용권 (payment)

돈은 토스가 받고, **"누가 무엇을 쓸 수 있는가"는 서버가 기억한다.**
결제의 절반은 클라 SDK 안에서 일어나므로, 이 장은 HTTP 계약과 함께 **클라이언트 책임**을 명시한다.
요구·정책의 정본은 `backend/docs/domain/payment.md` 다.

이용권은 두 종류다: **횟수권**(단건 2,200원 · 1회) · **기간권**(월 구독 3,960원 · 무제한, 30일 주기).

=== 상품 조회

`GET /api/v1/payments/products` — **인증 불필요** (결제 전 설득 화면의 데이터다).

operation::payment-products[snippets='http-request,http-response,response-fields']

[IMPORTANT]
====
**가격을 서버가 내려주지 않는다.** 응답의 `sku` 로 SDK `getProductItemList()` 결과를 찾아
`displayAmount` 를 표시한다 — SDK 만이 스토어 결제창과 일치하는 금액을 안다. **가격 하드코딩 금지.**
====

* `productType` 으로 주문 함수를 가른다 — `CONSUMABLE` → `createOneTimePurchaseOrder`,
  `SUBSCRIPTION` → `createSubscriptionPurchaseOrder`.
* 상품 키(`oneTime`/`subscription`)가 `null` 이면 **그 결제 버튼을 숨긴다** (미노출 상품).
* **구독 최소 앱 버전이 단건보다 높다** — Android 5.253.0 / iOS 5.250.0 (단건 5.219.0).
  미만 버전에서는 **구독 버튼을 숨기고 단건만 노출**한다.

=== 지급 (grant)

`POST /api/v1/payments/grant` — **인증 필요.** `processProductGrant` 콜백과 미결 주문 복원이
**같은 엔드포인트**를 쓴다(멱등). 단건·구독도 같은 엔드포인트 — 상품 판별은 서버가 토스 응답의
`sku` 로 한다. **`sku` 를 요청에 싣지 않는다.**

operation::payment-grant[snippets='http-request,request-headers,request-fields,http-response,response-fields']

[IMPORTANT]
====
**콜백 반환값 규칙: 200 일 때만 `true`, 그 외 전부 `false`.**

`false` 는 **결제 취소가 아니다** — 주문은 미결 상태로 남아 복원 대상이 된다.
안내 문구를 "결제 실패"로 쓰면 사실과 다르다. 재요청(복원·재시도)도 에러가 아니라 **200** 이다.
====

응답별 프론트 행동:

|===
| 응답 | 콜백 반환 | 프론트 행동

| 200 | `true` | `completeProductGrant({ params: { orderId } })` 호출 후 진행
| 409 `PAY_002` (결제 미확정) | `false` | "잠시 후 반영" 안내 → **복원에 위임. 재시도 루프 금지**
| 409 `PAY_003` (실패·환불) | `false` | 문의 안내. **재시도 금지**
| 404 `PAY_004` (주문 없음) | `false` | 문의 안내. **재시도 금지**
| 409 `PAY_005` (타인 귀속) | `false` | 문의 안내. **재시도 금지** (복원 중이면 조용히 건너뜀)
| 502 `PAY_006` (토스 확인 실패) | `false` | "잠시 후 재시도" → **복원에 위임**
|===

실패 응답 예시:

operation::payment-grant-fail-in-progress[snippets='http-response']
operation::payment-grant-fail-not-purchased[snippets='http-response']
operation::payment-grant-fail-not-found[snippets='http-response']

기타 클라 책임 (검수 항목):

* 결제 중 **음악·영상을 일시정지**하고 종료 후 재개한다.
* 주문 함수의 반환값 `cleanup()` 을 **반드시 호출**한다.
* 결제 시작 전 SDK 에러(`USER_CANCELED`·`UNSUPPORTED_APP_VERSION` 등)는 서버 호출 없이
  사유를 사용자에게 알린다.

=== 미결 주문 복원 — 필수 (검수 시나리오 ③)

[CAUTION]
====
**이 절에는 서버 스니펫이 없다 — 전부 클라 전용 흐름이다. 그래도 필수 계약이다.**
이 흐름이 없으면 "결제는 됐는데 못 쓰는" 사용자가 남는다. 30초 초과·앱 강제종료·네트워크 단절은
정상 흐름에서도 일어난다.
====

앱 기동(부트스트랩 성공) 직후, **화면을 막지 않고 배경에서**:

----
IAP.getPendingOrders()
 ├─ undefined(미지원) / 빈 배열 → 통과
 └─ 주문 N건 → 각 orderId 마다 POST /api/v1/payments/grant
     ├─ 200          → completeProductGrant({ params: { orderId } }) 로 미결 종료
     │                  ⚠️ 반환이 boolean | undefined — undefined 방어
     ├─ 409 PAY_002  → 닫지 않고 다음 기동에 재시도
     ├─ 409 PAY_003 / 404 PAY_004 → 지급 대상 아님 → completeProductGrant 로 닫는다
     ├─ 409 PAY_005  → 남의 주문. 조용히 건너뛴다 (사용자에게 노출 금지)
     └─ 502 PAY_006  → 다음 기동에 재시도. 알리지 않는다
----

* 진입이 느려지면 검수 "인터랙션 2초"에 걸린다 — **반드시 배경 실행.**

=== 이용권 상태

`GET /api/v1/payments/entitlement` — **인증 필요.** 결제 직후·403 복귀 후 재확인용.
진입 시에는 부트스트랩 응답의 `entitlement` 를 쓴다(모양이 같다).

operation::payment-entitlement[snippets='http-request,http-response,response-fields']

[IMPORTANT]
====
**분기는 `accessible` 하나로만 한다.** `subscription.status` 는 안내 문구용이지 분기 근거가 아니다.
서버가 정책(유예·STALE 판정)을 계산해 내려준다 — 프론트가 대신 판단하면 서버 게이트와 갈린다.
====

* 웹훅(구독 갱신·만료)은 **클라와 무관하다.** 갱신된 상태는 다음 진입의 `entitlement` 로만 보인다 —
  실시간 통지는 없다.
* 이용권이 없어도 404 가 아니라 200 이다 — "없음"은 정상 상태다.

=== 구독 상태 재확인 (STALE 해소)

서버가 구독 만료 시각이 지났는데 웹훅을 받지 못하면 — 만료인지 갱신인지 모르는 상태 —
`entitlement` 응답에 `subscriptionStale: true` 를 싣고 게이트를 닫는다.

operation::payment-entitlement-stale[snippets='http-response']

[IMPORTANT]
====
**`subscriptionStale: true` 는 결제 유도가 아니다** — 이미 결제한 사용자일 가능성이 높다.
아래 재확인 흐름으로 해소한다.
====

----
1. IAP.getCompletedOrRefundedOrders()               ← 최초 구독 orderId 확보
   (서버는 orderId 를 내려주지 않는다 — SDK 에서 직접 얻는다)
2. IAP.getSubscriptionInfo({ params: { orderId } })  ← 현재 구독 상태 조회
3. POST /api/v1/payments/subscription/recheck        ← 결과를 서버로
   ├─ 200 → 게이트 재개방 (또는 만료 확정 → 결제 유도로 전환)
   └─ 404 PAY_004 → 구독 이력 없음. 문의 안내
----

operation::payment-subscription-recheck[snippets='http-request,request-fields,http-response']
operation::payment-subscription-recheck-fail-not-found[snippets='http-response']

* 두 SDK 함수가 `undefined` 를 반환하는 구버전(Android 5.253.0 / iOS 5.250.0 미만)에서는
  해소가 불가능하다 — 안내 후 문의로 유도한다.

=== 이용 게이트 — 403 두 종류

유료 기능(작업 생성)은 이용권 게이트를 거친다. **403 이 두 종류이고 화면이 정반대다:**

|===
| 코드 | 의미 | 프론트 행동

| 403 `PAY_001` | 이용 가능한 이용권이 없다 | **결제 유도 화면**
| 403 `PAY_007` | 구독 상태 확인이 필요하다 (STALE) | **재확인 흐름** (결제 유도 금지)
|===

[CAUTION]
====
* **401 에 결제 유도를 띄우지 않는다** — 인증 문제이지 결제 문제가 아니다. 이미 결제한
  사용자에게 다시 결제를 요구하게 된다. 401 처리는 공통 규격(인증 게이트) 절을 따른다.
* **결제 유도 화면에는 닫기 경로를 반드시 둔다** — "나갈 선택지가 없는 경우"는
  다크패턴으로 **출시 불가 사유**다.
====

* 작업 목록·상태·결과 조회는 게이트 밖이다 — 이미 만든 결과물은 이용권 없이도 본다.
