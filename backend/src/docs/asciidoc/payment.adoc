== 결제 (payment)

돈은 토스가 받고, **"누가 무엇을 쓸 수 있는가"는 서버가 기억한다.** 요구 정본은
`backend/docs/new-domain/payment-v2.md` [주문 애그리거트] 절이다.

[IMPORTANT]
====
**엔드포인트는 지급 하나뿐이다.**

* **상품 조회 API 가 없다.** 가격은 결제 SDK 가 정본이라 서버가 말하면 결제창과 어긋난다.
  상품 코드도 코드가 아니라 **설정**에 있고, 비어 있는 유형은 어떤 주문으로도 지급되지 않는다(미노출 상품).
* **이용권 조회 API 가 없다.** 기간권과 횟수권을 합성하는 읽기 모델이 아직 없다 — 진입 응답의
  이용권 필드도 비어 있다. **프론트 계약으로 확정되기 전이다**(payment-v2.md "이번 범위에서 미뤄둔 것").
* **소모(차감) API 가 없다.** 부르는 쪽이 자막 생성 작업인데 그 도메인이 아직 없다.
====

=== `POST /api/v1/payments/grant` — 지급

결제된 주문을 우리 이용권으로 바꾼다. 인증 필요.
`processProductGrant` 콜백과 **미결 주문 복원이 같은 엔드포인트**를 쓰고,
단건·구독도 같은 엔드포인트다 — 무엇을 샀는지는 서버가 **토스에 직접 물어** 판별한다.

operation::payment-grant[snippets='http-request,request-headers,request-fields,http-response,response-fields']

* **`sku` 를 요청에 싣지 않는다.** 클라이언트의 주장으로 상품을 정하지 않는다. 서버가 토스에
  주문 상태를 조회해 받은 상품 코드로만 판별하고, 모르는 코드면 남의 상품이므로 지급하지 않는다.
* **같은 주문을 몇 번 요청해도 정확히 한 번만 지급하고, 재요청도 200 `granted: true` 다.**
  멱등의 근거는 `orderId` 하나다. 중복을 오류로 만들면 복원 흐름 자체가 깨진다.
* **먼저 지급을 요청한 사용자가 주문의 소유자가 된다(선점).** 토스에 "이 주문이 누구 것인가"를
  물어볼 수단이 없어서, 소유자는 끝까지 클라이언트의 주장이다. 보안 통제가 아니라 먼저 온 쪽을
  지키는 규칙이다.
* **응답에 잔량이 없다.** 잔량의 권위는 횟수권 쪽에 있고 지급 경로에는 그것을 읽을 수단이 없다.
  `productType` 은 화면 분기용이다 — `CONSUMABLE`(횟수권) · `SUBSCRIPTION`(구독).
* **30초 안에 답한다.** 넘기면 사용자에게 환불 안내 화면이 노출된다. 시간이 모자라면 붙잡지 않고
  실패로 답하며, 남은 것은 복원이 처리한다.

[CAUTION]
====
**주문 식별자는 어떤 응답에도 실리지 않는다** — 성공 응답에도, 실패 메시지에도 없다.
주문 식별자를 아는 것은 **미지급 주문을 가로챌 수 있는 것과 같다**.
====

=== 실패 처리

**콜백 반환값 규칙: 200 일 때만 `true`, 그 외 전부 `false`.**
`false` 는 **결제 취소가 아니다** — 주문은 미결 상태로 남아 복원 대상이 된다.
안내 문구를 "결제 실패"로 쓰면 사실과 다르다.

|===
| 응답 | 콜백 반환 | 프론트 행동

| 200 | `true` | `completeProductGrant({ params: { orderId } })` 호출 후 진행. **재요청도 200 이다**
| 409 `PAY_002` | `false` | 주문이 아직 진행 중이다. "잠시 후 반영" 안내 → **복원에 위임. 재시도 루프 금지**
| 409 `PAY_003` | `false` | 결제가 완료되지 않았거나 환불된 주문. 문의 안내 — **재시도해도 결과가 같다**
| 404 `PAY_004` | `false` | 우리 미니앱의 주문이 아니다(모르는 상품 코드 포함). 재시도 금지
| 409 `PAY_005` | `false` | 이미 다른 사용자에게 귀속된 주문. **복원 중이면 조용히 건너뛴다**
| 502 `PAY_006` | `false` | 토스에 주문 상태를 확인하지 못했다(실패 응답·타임아웃). **재시도 대상**
| 400 `COMMON_001` | `false` | `orderId` 누락·공백. 형식 축이라 지급 판정(`PAY_*`)과 섞지 않는다
| 401 | `false` | 토큰 문제. 인증 절 참조
|===

[NOTE]
====
**지급이 확정되면 무엇을 지급했는지가 사실로 발행되고**, 이용권을 만드는 일은 그 사실을 받는 쪽
(`credit` · `subscription` 모듈)이 한다. 응답이 200 이라는 것은 **원장이 확정됐다**는 뜻이고,
이용권 반영은 그 직후 비동기로 이어진다.
====
