# 결제 · 이용권 — 비즈니스 요구사항 설계서 (payment 도메인)

> **성격**: 토스 IAP 로 **단건 2,200원(1회 이용권)** 과 **월 구독 3,960원(무제한)** 두 상품을 팔고,
> **로그인 없이** 그 소유권을 지킨다. 이 도메인의 어려움은 결제를 붙이는 것이 아니라
> **소유권을 보관하는 것**이다 — 토스 로그인을 쓰지 않으므로(auth 확정 ①) 우리 서버의
> `익명키 ↔ orderId` 매핑이 이용권 소유의 **유일한 정본**이고, 그것이 끊기면 사용자는 **돈을 내고 못 쓴다.**
> 비즈니스 요구사항: 2026-08-07 · **2026-08-09** 사용자 결정(§9-1)
> 근거: [mvp-v1.md](../../../docs/planning/mvp-v1.md) 쟁점 1·3·4 · **플랫폼 스펙: [iap-spec.md](../../../docs/platform/iap-spec.md)**
> 관련: [auth.md](./auth.md) · [toss-integration.md](../rule/toss-integration.md) · [error-handling.md](../rule/error-handling.md)
> 상태: **요구사항 초안 — §9-1 🔶 확정 필요**

> 📌 **이 문서는 `subscription.md` 를 개명한 것이다** (커밋 `1b947a9` 에 이전 이름으로 보존).
> 2026-08-09 에 **단건 결제 병행이 확정**(구 🔶-2)되면서 도메인이 구독만 다루지 않게 됐다.
> 초안 단계이므로 버전을 올리지 않고 고쳤다(→ [versioning.md](../../../.claude/skills/usecase/references/versioning.md)).
> ⚠️ **auth.md 는 v2 확정본**이고, 거기서 이 도메인을 `subscription` 이라는 옛 이름으로 지칭한다
> (§용어·§2·§4-2·§4-3·§4-7·§5-2·§9-1 전제표) → 갱신 대상(§10).

> ⚠️ **이 도메인은 외부 의존이 가장 큰 도메인이다.** auth 는 `verify` 폐기로 외부 의존이 0 이 되었지만
> (auth §4-3), payment 는 **mTLS 인증서 · 토스 서버 API · 웹훅** 3개에 걸쳐 있다. 게다가
> **구독 IAP 는 샌드박스를 지원하지 않아** 계약 준수를 실결제 없이는 증명할 수 없다(§4-9).
>
> **플랫폼 사실은 전부 [docs/platform/iap-spec.md](../../../docs/platform/iap-spec.md) 에 있다.**
> 이 문서는 그 위에서 **우리가 정하는 것**만 다룬다. 사실과 결정을 섞지 않기 위해서다.

## 용어

| 용어 | 의미 |
|---|---|
| **이용권** | 유료 기능을 쓸 수 있게 하는 권리. 두 종류가 있고 **획득 경로도 소멸 방식도 다르다** |
| ├ **횟수권** | 단건 결제로 얻는 **1회 이용권**. 쓰면 소진된다. 토스 상품 유형 `CONSUMABLE` |
| └ **기간권** | 구독으로 얻는 **기간 내 무제한** 이용권. 토스 상품 유형 `SUBSCRIPTION` |
| 지급 (grant) | 결제된 주문을 **우리 이용권으로 바꾸는 행위**. 토스 SDK 의 `processProductGrant` 콜백이 우리 서버를 호출한다 |
| 소모 (consume) | 횟수권을 1 차감하는 것. **기간권에는 소모가 없다** |
| 미결 주문 | **결제는 됐는데 지급이 안 끝난** 주문. 정상 흐름에서도 발생한다(§4-5) |
| 이용 게이트 | 유료 기능 요청 앞단에서 “쓸 수 있는 이용권이 있는가”를 판정하는 지점 |
| 선점 | 하나의 `orderId` 에 대해 **먼저 지급을 요청한 익명키가 소유자가 되는** 규칙(§4-4) |
| `orderId` | 토스 IAP 주문 식별자. **주문 단위**로 발급되며 같은 `sku` 를 재구매하면 새 값이 생긴다 |

> ⚠️ **`processProductGrant`(주문 생성 옵션의 콜백)와 `completeProductGrant`(별도 SDK 함수)는
> 다른 것이다.** 이름이 비슷해 혼동하기 쉽다 → [iap-spec.md §3-5](../../../docs/platform/iap-spec.md).

## 1. 배경 · 목적

- mvp-v1 **쟁점 1 확정**으로 흐름이 `목록 → 결제 → 사용` 이 됐다. **결제가 서비스의 첫 관문**이고,
  이 도메인이 막히면 사용자는 아무 기능도 쓰지 못한다. 체험 구간이 없어 되돌릴 여지도 없다.
- **2026-08-09 결정으로 상품이 2종이 됐다.** 쟁점 3(“자막만으로 월 구독을 받을 수 있는가”)의 답이
  **“구독 + 단건 병행”** 으로 확정됐다. 자막 니즈가 간헐적이라는 문제 제기를 단건이 받아낸다.

  | 상품 | 가격 | 혜택 | 실수령(iOS/Android) |
  |---|---|---|---|
  | 단건 | **2,200원** | **1회 이용** | 1,749원 / 1,779원 |
  | 월 구독 | **3,960원** | **무제한** | 약 3,148원 / 3,202원 |

  → **3,960 ÷ 2,200 = 1.8.** 즉 **월 2편부터 구독이 이득**이다. 이 비율이 가격 설계의 메시지이고,
  화면 문구도 여기서 나온다. (수수료 계산 근거 → [iap-spec.md §2-2](../../../docs/platform/iap-spec.md))
- **로그인이 없다**(auth 확정 ①). 그래서 이 도메인의 요구는 “결제를 연동한다”가 아니라
  **“돈을 낸 사람이 언제·어떤 경로로 돌아와도 쓸 수 있게 한다”** 이다. 앱 재진입·결제 직후 이탈·
  기기 변경·웹훅 유실 — 어느 하나에서 소유권이 끊기면 그것이 곧 환불 요청이자 검수 반려 사유다.

**핵심 훅은 없다.** 결제는 훅이 아니라 마찰이다. 이 도메인이 잘 된 상태란 사용자가 **결제 이후로는
이용권을 의식하지 않는 것**이다.

## 2. 범위 결정 — 무엇을 하고 / 안 하는가

| 구분 | 포함 | 내용 |
|---|---|---|
| 상품 정보 제공 | ✅ | 프론트가 어떤 `sku` 로 결제창을 열지 서버가 알려준다. **가격은 내려주지 않는다**(§5-2) |
| 결제창 호출 | ❌(서버) / ✅(프론트) | `createOneTimePurchaseOrder` · `createSubscriptionPurchaseOrder` 는 **클라 SDK 의 일** |
| 주문 검증 | ✅ | 토스 `get-order-status` 로 **결제 사실을 서버가 직접 확인한 뒤에만** 지급한다 |
| 소유권 등록·보관 | ✅ | `익명키 ↔ orderId` 매핑. **이 도메인의 존재 이유**(§4-4) |
| **횟수권 잔량 관리** | ✅ | 단건 도입으로 새로 생긴 책임. 지급 +1 / 소모 −1 |
| **횟수권 소모 판정** | ✅(정책) | 언제 차감하고 언제 되돌리는가(§4-3·🔶-4). **실행 주체는 작업 도메인** |
| 지급 멱등 | ✅ | 같은 주문으로 두 번 지급되지 않는다(§4-5). **횟수권에서 특히 치명적** |
| 미결 주문 복원 | ✅(서버 계약) / ✅(프론트 트리거) | 서버는 지급 API 를 멱등하게 열어두고, **호출 시점은 프론트가 정한다** |
| 이용권 상태 제공 | ✅ | 부트스트랩 공급 + 단독 조회(§5-3) |
| 이용 게이트 | ✅ | 이용권 없이는 유료 기능을 거부한다. **대상 목록은 🔶**(§4-10 · §9-1 🔶-9) |
| 웹훅 수신·반영 | ✅ | **구독 전용**. 단건에는 웹훅이 없다(§4-1) |
| 단건 환불 감지 | 🔶 | 푸시가 없어 **폴링 또는 클라 조회**뿐이다 → §9-1 🔶-8 |
| 결제 수단·카드 정보 | ❌ | 토스가 전담한다. **우리 서버는 결제 수단을 보지도 저장하지도 않는다** |
| 환불 처리 | ❌ | iOS 는 Apple 전권, Android 도 최종 결정은 Google Play. 우리는 **결과만 받는다**(§4-8) |
| **이용권 현금 환급** | ❌ **금지** | 미니앱 내 현금·유사자산 교환/환불 기능은 **등록 자체가 불가**(자금세탁 악용 우려) |
| 무료 체험(FREE_TRIAL) | 🔶 | 플랫폼이 지원한다(3일/1주/2주/1개월). 쓸지는 미정 → §9-1 🔶-2 |
| 구독 해지·플랜 변경 | ❌ | **파트너가 호출할 수 있는 해지 API 가 없다.** 해지는 사용자가 스토어에서 직접 → §8 |
| 가격·플랜 다양화(연간 등) | ❌ | MVP 는 2종. **플랜 전환 시 중복 결제 사례가 보고돼 있다** → §8 |
| 쿠폰 · 프로모션 · 할인 | ❌ | 플랫폼이 지원하나 MVP 밖. ⚠️ **소모품 할인은 한 번 설정하면 수정 불가** → §8 |
| 결제 이력 화면 | ❌ | 토스 앱에서 확인된다. ⚠️ 단 체크리스트 8번(“결제 내역 사용자 확인 가능”) 충족 여부는 확인 필요 → §10 |
| 미니앱 재출시 시 이용권 이관 | ❌ | **플랫폼이 지원하지 않는다** — 토스 직원이 승계 불가를 명시(§4-4) |
| 관리자 결제 조회·수동 지급 | ❌ | 관리자 화면 자체가 MVP 밖 |

## 3. 기능 요구사항

| # | 요구 | 설명 |
|---|---|---|
| **U1** | 상품 정보 제공 | 판매 중인 단건·구독 `sku` 를 서버가 내려준다. 프론트가 하드코딩하면 상품 교체 시 앱 재배포+심사가 필요하다. **가격은 내려주지 않는다** — 가격의 정본은 SDK `getProductItemList` 의 `displayAmount` 이고, 체크리스트가 **주문 금액과 스토어 결제창 금액 일치**를 요구하므로 우리가 가격을 말하면 불일치 위험이 생긴다 |
| **U2** | 결제 검증 후 지급 | `orderId` 를 받아 **토스에 주문 상태를 확인한 뒤에만** 이용권을 부여한다. 클라가 “결제했다”고 말한 것만으로는 지급하지 않는다(서버 권위 원칙). 상품 유형에 따라 **횟수권 +1** 또는 **기간권 부여** |
| **U3** | 지급 멱등 | 같은 `orderId` 로 지급이 여러 번 요청돼도 이용권은 한 번만 생긴다. **중복 요청은 예외가 아니라 정상 동작**이다(§4-5). ⚠️ **횟수권에서 멱등이 깨지면 잔량이 부풀어 무료 이용권이 새어 나간다** — 기간권과 위험도가 다르다 |
| **U4** | 소유권 선점·불변 | 하나의 주문은 하나의 익명키에만 귀속된다. 이미 다른 익명키의 것이 된 주문은 거부한다 |
| **U5** | 이용권 상태 제공 | “지금 이 사용자가 쓸 수 있는가”를 답한다. **소비처가 둘**이다 — 진입 시 부트스트랩(집계 모듈에 공급) · 재확인 시 단독 조회. **두 경로의 응답 모양은 같아야 한다**(§5-3) |
| **U6** | 이용 게이트 | 유료 기능 요청을 이용권 없이는 거부한다. 401(신원)과 **구분되는 403**을 낸다 — 프론트의 행동이 다르기 때문(결제 유도 화면) |
| **U7** | 횟수권 소모 | 유료 작업이 횟수권을 1 차감한다. **기간권 보유자는 차감하지 않는다**(§4-3) |
| **U8** | 실패한 작업은 소모하지 않는다 | 작업이 실패하면 차감한 횟수권을 되돌린다. **2,200원을 내고 결과물을 못 받는 것이 이 서비스 최악의 경험**이고, 자막 작업은 STT·번인 단계에서 실제로 실패할 수 있다 |
| **U9** | 웹훅 반영 (구독) | `subscription.status_changed` 를 받아 기간권 상태를 갱신한다. **서버가 구독 상태를 조회할 API 가 없으므로**(§4-2) 이것이 갱신·만료를 아는 유일한 경로다 |
| **U10** | 웹훅 등록 검증 처리 | `callback.registration_verification` 을 정상 수신해야 콜백 URL 이 활성화된다. **이 요구를 빠뜨리면 U9 가 통째로 동작하지 않는다** |
| **U11** | 웹훅 진위 검증 | 콘솔에 등록한 **Basic Auth 헤더**로 검증한다. 웹훅은 인증 게이트 밖 공개 엔드포인트이므로, 이것이 없으면 누구나 위조 웹훅으로 기간권을 활성화할 수 있다(§4-7) |
| **U12** | 미결 주문 복원 지원 | 서버는 U2·U3 으로 이를 지원한다. “결제는 됐는데 못 쓰는” 상태를 사용자가 스스로 풀 수 있어야 한다. **검수 필수 시나리오**이기도 하다(§4-9) |
| **U13** | 환불·회수 반영 | 환불된 주문의 이용권을 회수한다. **구독은 웹훅으로 오지만 단건은 푸시가 없다**(§4-8) |
| **U14** | 주문 식별자 비노출 | `orderId` 를 로그·예외 메시지·에러 응답 본문에 원문으로 남기지 않는다. **선점 규칙(U4) 때문에 `orderId` 를 아는 것이 곧 미지급 주문을 가로챌 수 있는 것**이라, 취급 수준은 익명키에 준한다(auth U6 와 같은 선상) |

> **이 도메인은 외부 API 를 호출한다.** U2 는 토스 `get-order-status` 왕복을 포함하므로 auth 와 달리
> 검수 기준 “인터랙션 2초 이내”와 `processProductGrant` 30초 제약에 **직접 노출된다** → §4-6.

## 4. 비즈니스 규칙 (정책 상세)

### 4-1. 두 상품은 같은 도메인이지만 **같은 규칙이 아니다**

이 도메인이 어려운 이유가 여기 있다. 단건과 구독은 신뢰 경계·멱등 요구·복원 경로·환불 감지가 전부 다르다.

| 축 | 단건 (횟수권) | 구독 (기간권) |
|---|---|---|
| 지급 트리거 | 클라 콜백 `processProductGrant` | 클라 콜백 (**최초 1회만**) |
| **갱신** | 없음 (재구매 = 새 주문) | **웹훅 단독.** 갱신 시 콜백이 다시 오지 않는다 |
| 상태 변이 통지 | ❌ **없음** | ✅ 웹훅 `changeReason` 12종 |
| 멱등 위험도 | 🔴 **높음** — 중복이 곧 잔량 증가(무료 이용권) | 🟡 낮음 — 상태 세팅이라 자연 멱등 |
| 멱등 키 | `orderId` | `orderId` + `occurredAt` (**이벤트 고유 ID 가 없다**) |
| 환불 감지 | ⚠️ 폴링/클라 조회 | 웹훅 `REVOKED` 푸시 |
| 소모 | 있음 (−1) | 없음 |
| 샌드박스 | ✅ 지원 | ❌ **미지원** |
| 최소 앱 버전 | 5.219.0 | **Android 5.253.0 / iOS 5.250.0** |

- **한 도메인에 두는 이유**: 이용 게이트가 하나이기 때문이다. “쓸 수 있는가”의 답은
  두 이용권을 함께 봐야 나온다(§4-3). 게이트를 쪼개면 그 판정이 두 곳으로 갈라진다.
- ⚠️ 그 대가로 **상태 어휘를 하나로 합칠 수 없다.** 주문 상태 8종 · 구독 status 6종 ·
  changeReason 12종은 **서로 다른 축**이다. 하나의 상태 머신으로 합치려 하면 안 된다.

### 4-2. 이용권 상태의 진실 원천 — 무엇을 믿는가

| 소스 | 무엇을 알려주나 | 신뢰 | 한계 |
|---|---|---|---|
| 토스 `get-order-status` (서버→토스, mTLS) | **주문**의 상태 | ✅ 최고 — 서버가 직접 확인한다 | **구독의 만료 시점을 알려주지 않는다.** ⚠️ 구독 주문에 적용되는지도 문서 미명시 |
| 웹훅 `subscription.status_changed` | 구독 상태 **변경** | ⚠️ 높으나 조건부 | Basic Auth 외 서명 없음. **재전송 정책·이벤트 ID 없음** |
| 클라 `getSubscriptionInfo` | 구독 현재 상태 | ❌ 낮음 | **클라가 보낸 값이다.** 서버 권위 원칙상 그대로 받아 쓰지 않는다 |
| 클라 `getCompletedOrRefundedOrders` | 완료·환불 주문 목록 | ⚠️ 낮음 (재검증 트리거로만) | 마찬가지로 클라 값. 웹 SDK 는 **첫 페이지 50건 고정** |

⚠️ **서버가 구독 상태를 직접 조회할 방법이 없다 — 이 도메인 최대의 구조적 리스크.**
IAP 서버 API 는 `get-order-status` 하나뿐이다. 따라서 **서버가 아는 기간권 상태 =
최초 지급 시점의 주문 검증 + 그 이후 웹훅 누적**이다. 웹훅이 유실되면 서버 상태가 실제와 어긋나고,
**바로잡을 조회 수단이 우리에게 없다.** 보정 수단은 🔶-6.

⚠️ **유실의 방향별 손해가 비대칭이다.** 만료 웹훅을 놓치면 안 낸 사람에게 열어준다(우리 손해).
**갱신 웹훅을 놓치면 낸 사람을 막는다(훨씬 나쁨** — 환불·검수 반려로 이어진다).
보정 수단을 정할 때 이 비대칭을 기준으로 삼는다.

### 4-3. 이용 가능 판정 — 두 이용권을 함께 본다

**판정식**: `이용 가능 = 기간권이 살아 있다 OR 횟수권 잔량 > 0`

이 OR 결합 자체는 **확정 ⑤ 의 직접적 귀결**이라 별도 결정이 아니다 — “단건 = 1회 이용 가능”,
“월 구독 = 무제한”이라는 혜택 정의가 곧 이 식이다. **미확정인 것은 그 아래 두 층**이다:
기간권을 어떤 `status` 에서 살아 있다고 볼 것인가(🔶-3), 둘 다 있을 때 무엇을 먼저 쓸 것인가(🔶-4ⓒ).

**소모 우선순위(제안)**: **기간권을 먼저 쓴다.**
구독 중인 사용자가 횟수권도 갖고 있으면 횟수권을 **보존**한다 — 구독이 끝난 뒤에도 쓸 수 있어야
사용자에게 유리하고, 반대로 하면 “구독 중인데 왜 내 이용권이 줄지?”라는 문의가 된다. (🔶-4)

**기간권 개폐 판정** — 토스 구독 `status` 6종을 그대로 게이트에 쓰지 않는다.
“구독이 어떤 상태인가”와 “열어줄 것인가”는 우리가 정하는 별개의 정책이다.

| 토스 `status` | 의미 | 우리 판정(제안) |
|---|---|---|
| `ACTIVE` | 활성 | ✅ 연다 |
| `IN_GRACE_PERIOD` | 결제 실패 후 유예 기간 | 🔶-3 **연다** — 카드 문제로 잠깐 실패한 유료 사용자를 막는 것이 더 큰 손해 |
| `ON_HOLD` | 보류 | 🔶-3 **막는다** — 유예가 끝난 상태다 |
| `PAUSED` | 사용자가 일시정지 | 🔶-3 **막는다** — 사용자 의사다 |
| `EXPIRED` | 만료 | ❌ 막는다 |
| `REVOKED` | 회수(환불 등) | ❌ 막는다 |
| (구독 이력 없음) | — | ❌ 막는다 (횟수권만 본다) |

- ⚠️ **플랫폼의 `isAccessible` 을 쓰지 않는다.** 그 값은 클라 SDK 응답이고(§4-2),
  **산식이 문서에 정의돼 있지도 않다.** 토스 직원도 `status` 기준으로 판단하라고 답했다.
- 프론트는 **`accessible` 하나만 보고 분기한다.** `status` 는 안내 문구용이다(§5-3).
- ⚠️ **월 갱신 주기는 달력 1개월이 아니라 30일 고정**이다. 만료일 계산이 달력 월을 가정하면 어긋난다.

### 4-4. 소유권 — `익명키 ↔ orderId` (U4)

- **1:1 이다.** 한 주문은 한 익명키에만 귀속되고, 한 번 귀속되면 바뀌지 않는다.
- **선점 규칙**: 그 주문에 대해 **먼저 지급을 요청한 익명키가 소유자**가 된다. 이미 다른 익명키의
  것이 된 주문의 지급 요청은 거부한다(`PAY_005`).
- ⚠️ **토스에 “이 주문이 누구 것인가”를 물어볼 수 없다.** `get-order-status` 응답에 소유자 필드가 없고,
  사용자를 한정하는 `x-toss-user-key` 는 토스 로그인 사용자용인데 우리는 그 값이 없다.
  익명키(`x-anon-key`)로 대체 가능한지는 **문서에 없다**(🔶-11).
- ⚠️ **그러므로 “서버가 결제를 검증한다”는 말을 정확히 해야 한다.** 서버가 확인할 수 있는 것은
  **“이 `orderId` 가 결제됐다”뿐이고, “누구 것인가”는 끝까지 클라이언트의 주장**이다.
  **선점 규칙은 검증이 아니라, 그 사실을 감수하겠다는 선언이다.** 보안 통제인 척 쓰지 않는다.
- **실질 위험은 낮다고 본다**(수용 근거): `orderId` 는 결제한 기기와 우리 서버 밖으로 나가지 않고,
  정상 사용자의 클라는 결제 직후 수 초 안에 지급을 요청한다. 그래서 **U14(비노출)이 여기서
  실효 있는 방어**가 된다. 이 수준의 리스크 수용은 auth 확정 ③(“익명키를 아는 사람 = 그 사용자”)과 같은 선상이다.
  ⚠️ 단 **`orderId` 의 엔트로피가 검증되지 않았다**(🔶-12) — 추측 가능하면 이 근거가 무너진다.
- ⚠️ **이 매핑이 유실되면 사용자는 돈을 내고 못 쓴다.** 로그인이 없어 복구할 단서가 우리에게 없다.
  보관 요구 수준이 일반 데이터보다 높다(구체적 보장 수단은 설계서 몫).
- ⚠️ **승계되지 않는 두 경우** — 둘 다 우리가 막을 수 없다:
  1. **토스 완전 탈퇴 후 재가입** → 새 hash 발급. 게다가 **탈퇴 통지 수단이 없어** 서버가 알 방법도 없다.
  2. **미니앱 재출시** → 토스 직원이 *“기존 결제 사용자에게 새 미니앱에서 혜택을 승계하는 지원은 어렵다”* 고 명시.
     **재출시 전 반드시 해결해야 하는 선행 조건**임을 여기 남긴다(auth §4-6 과 같은 사유).

### 4-5. 멱등 — 중복 지급 요청은 정상이다 (U3)

- 같은 `orderId` 로 지급 요청이 여러 번 와도 **이용권은 한 번만 생긴다.**
- **중복은 예외가 아니라 정상 흐름이다.** 미결 주문 복원은 이미 지급된 주문을 다시 보낼 수 있고,
  네트워크 실패 후 재시도도 마찬가지다. “중복이면 에러”로 만들면 **복원 흐름 자체가 깨진다.**
- 그래서 **이미 지급된 주문의 재요청은 에러가 아니라 200** 이다. 프론트가 그 200 을 받고
  `completeProductGrant` 를 호출해 미결 상태를 닫을 수 있어야 하기 때문이다.
- 🔴 **횟수권에서 이 규칙이 깨지면 곧바로 무료 이용권이 샌다.** 기간권은 상태 세팅이라
  중복이 무해하지만, 횟수권은 `+1` 이 누적된다. **멱등의 근거를 `orderId` 하나에 둔다** —
  같은 `orderId` 는 몇 번 와도 잔량을 한 번만 올린다.
  ⚠️ 하필 **`completeProductGrant` 의 중복 호출 멱등성이 문서화돼 있지 않다**(🔶-13).

### 4-6. 지급 응답 시간 (U2)

- `processProductGrant` 콜백이 우리 지급 API 를 호출하고, 그 결과를 `boolean` 으로 토스에 돌려준다.
- ⚠️ 일회성 결제 문서는 *“결제 성공 후 30초내에 `processProductGrant` 콜백이 호출되지 않거나
  해당 콜백의 결과가 true가 아닌 경우, `{appName}에 문제가 생겼어요. 환불을 신청해주세요` 페이지가
  노출될 수 있어요.”* 라고 명시한다. **구독 문서에는 같은 문구가 없다**(🔶-10) —
  그러나 **같은 제약을 전제로 설계한다.** 없는 쪽으로 가정했다가 틀리면 결제 직후 환불 화면이 뜨는데,
  그 반대 방향의 손해는 없다. 커뮤니티에 구독에서도 같은 화면이 뜬 사례가 있다.
- 우리 지급 API 는 **토스 주문 조회 왕복을 포함해서** 응답해야 한다. 상한을 두고,
  초과하면 **실패로 처리하고 미결 주문 복원에 맡긴다** — 붙잡고 있는 것보다 낫다(§6-3).
- ⚠️ **타이머 기점이 문서에 없다.** 게다가 `processProductGrant` 가 **true 를 반환했는데도**
  30초 뒤 환불 안내가 뜬 사례가 보고돼 있다. **우리 응답 시간만으로 통제되지 않는 구간이 있다.**
- 🔶 구체 상한값(🔶-10).

### 4-7. 웹훅 (U9·U10·U11) — 구독 전용

**진위 검증 수단은 Basic Auth 하나뿐이다.** 콘솔에 등록하면 `Authorization: Basic {값}` 으로 실려 온다.
HMAC·서명 헤더는 문서·커뮤니티 어디에도 없다. 두 이벤트의 인증 방식은 동일하다(토스 직원 확인).

| 방어층 | 수단 | 상태 |
|---|---|---|
| 1차 | **Basic Auth 헤더 검증** | ✅ 채택 — 유일한 문서화된 수단 (U11) |
| 2차 | **Inbound IP 화이트리스트** (6개 대역, 443) | 🔶-5 — 인프라 결정이라 여기서 확정하지 않는다 |
| 3차 | **웹훅으로 구독을 새로 만들지 않는다** | 🔶-5 (제안) |

- **(제안) 웹훅은 이미 우리가 소유권을 아는 `orderId` 의 상태 변경만 반영하고, 모르는 `orderId` 는
  기록만 하고 무시한다.** → 위조 웹훅이 할 수 있는 최대치가 “없는 구독을 만드는 것”에서
  “이미 결제한 사람의 상태를 흔드는 것”으로 줄어든다. 구독 생성은 **반드시 mTLS 로 검증한 주문**(U2)만 거친다.
  → **§6-6 흐름은 이 제안을 전제로 그려져 있다. 뒤집히면 §6-6 도 바뀐다.**

나머지 처리 규칙:

| 상황 | 처리 |
|---|---|
| 서버 응답 | **204**. ⚠️ 토스 직원 답변이 유일한 근거이며 문서 규격은 없다 |
| 순서 역전 | `occurredAt` 이 **이미 반영한 것보다 과거면 무시**한다 |
| 중복 수신 | ⚠️ **이벤트 고유 ID 가 없다.** `eventType + orderId + occurredAt` 조합으로 판별할 수밖에 없다 |
| 유실 감지 | `previous` 와 우리가 아는 상태가 다르면 **그 사이 웹훅을 놓친 것**이다 — 감지는 확정하고, **보정 방법은 🔶-6** |
| 처리 실패 | **수신과 반영을 분리한다.** 반영에 실패해도 수신은 성공(204)으로 답한다 — **재전송 정책이 문서에 없어 재시도에 기댈 수 없으므로** 유실은 우리가 감당한다 |
| 자동갱신 재개 판정 | ⚠️ **`changeReason` 만으로 판정하지 않는다.** `RESTARTED` 를 받고도 `current.autoRenew` 가 `false` 인 사례가 보고돼 있다 — **`autoRenew` 값을 함께 본다** |
| 시각 해석 | timezone 없는 ISO-8601 이다. **기준 타임존을 토스가 확답하지 않았다** → 🔶-7 |
| 필드명 | 웹훅은 `accessGranted`/`autoRenew`, SDK 는 `isAccessible`/`isAutoRenew` — **이름이 다르다** |

### 4-8. 환불 · 해지 (U13)

- **우리는 환불을 처리하지 않는다.** iOS 는 Apple 전권이고 파트너는 **상태 조회만** 가능하며,
  Android 는 콘솔에서 승인/반려할 수 있으나 최종 결정은 Google Play 다.
  **파트너 서버가 환불을 요청·처리하는 API 자체가 없다.**
- **구독**: `REVOKED` → 즉시 기간권 회수. `AUTO_RENEW_DISABLED`(해지 예약) → **만료일까지는 계속 열어준다**
  (아직 유효 기간이다).
- ⚠️ **단건은 환불 푸시가 없다.** 감지 경로가 폴링(서버 `get-order-status`) 또는 클라 조회뿐이다 → 🔶-8.
  즉 **“환불되면 회수한다”는 한 문장이 상품별로 다른 SLA 를 갖는다.**
- ⚠️ **이미 소모한 횟수권이 환불되면 되돌릴 것이 없다.** 잔량을 음수로 만들지 않는다 — 🔶-8.
- **구독 해지를 우리가 해줄 수 없다.** 파트너 호출용 해지 API 가 없고 사용자가 스토어에서 직접 해야 한다.
  ⚠️ 미니앱 안에서 해지 경로를 안내하는 방법도 문서에 없다 → §10.

### 4-9. ⚠️ 검증 불가 구간 — 구독은 샌드박스가 없다

| 대상 | 샌드박스 | 결과 |
|---|---|---|
| **단건(소모품)** | ✅ 지원 | 출시 전 검증 가능 |
| **구독** | ❌ **미지원** | **실결제로만 검증된다** |

- 검수 **필수 시나리오 4가지**를 우리 계약이 지원해야 한다: ① 상품 목록 노출 ② 결제 성공
  ③ **결제 성공 + 서버 지급 실패**(미결 복원) ④ 에러 4종(네트워크/사용자 취소/내부 오류/파트너 지급 실패).
  → **③이 §6-3 복원 흐름의 존재 이유**이고, 검수 항목이므로 선택이 아니다.
- ⚠️ **QR 테스트에서 실결제가 발생한다**(토스 직원 확인). 테스트 비용과 환불 절차를 미리 잡아야 한다.
- ⚠️ 그 결과 **구독 부분은 자동화 테스트로 계약 준수를 증명할 수 없다.**
  테스트는 “우리 규칙이 맞게 도는가”까지만 답하고, **“토스와 실제로 맞물리는가”는 실결제가 답한다.**

### 4-10. 이용 게이트의 적용 범위 (U6) [공통 승격 후보]

- **auth 와의 경계**: auth 는 “누구인가”까지 답하고 401 을 낸다. **“쓸 수 있는가”와 403 은 이 도메인 몫**이다
  (auth §4-2 가 이미 그렇게 정해두었다). `AUTH_003` 대신 전용 코드를 낸다 —
  프론트가 “인증 문제”와 “결제 유도”를 구분해야 하기 때문이다.
- **익명키 인증 게이트 자체는 auth 확정 ⑥ 으로 이미 끝났다.** 남은 것은 그 위에 얹는 이용 게이트의 대상 목록뿐이다(🔶-9).

| 대상(제안) | 이용권 요구 | 근거 |
|---|---|---|
| 작업 생성 (업로드·자막 생성·번인) | ✅ 요구 + **횟수권 소모** | 원가가 드는 행위다. 쟁점 1(결제 선행)의 실체가 여기다 |
| 작업 목록·상태·결과 조회 | ❌ | **이미 만든 결과물은 이용권이 없어도 볼 수 있어야 한다** — mvp-v1 쟁점 6 이 “만료 작업도 남긴다”로 잡혀 있다 |
| 솔루션 목록·상세 | ❌ | 결제 전 설득 화면이다. auth §4-2 가 이미 **공개**로 열거해 두었다 |
| 상품 정보·이용권 조회·지급 | ❌ | 결제하려는 API 가 결제를 요구할 수는 없다. 단 **익명키 인증은 필요**하다 |
| **웹훅 수신** | ❌ **익명키 인증 게이트 자체가 적용되지 않는다** | 토스는 `X-Anonymous-Key` 를 보내지 않는다. auth §4-2 는 기본값 “인증 필요”로 **이미 확정**됐고 공개 목록에 웹훅이 없다 — 즉 **지금 상태로는 토스 웹훅이 401 로 튕긴다.** 가정이 아니라 현재 처리해야 할 요구다 → §10 |

### 4-11. 상품 등록 제약 (계약에 영향을 주는 것만)

- 가격은 **공급가(VAT 제외)** 로 입력한다: 단건 **2,000원** → 판매가 2,200원 / 구독 **3,600원** → 3,960원.
  10원 단위·400원 이상 규칙을 **둘 다 충족**한다.
- ⚠️ **상품명에 “무제한”을 쓰면 안 될 수 있다.** 토스가 과장 표현 반례로 **직접 “무제한”을 든다** —
  이용 기간이 정해진 상품에 금지한다. **우리 월 구독의 혜택이 정확히 “무제한”이므로 반려 위험이 있다.**
  갱신 주기·이용 조건을 함께 드러내는 문구로 재검토해야 한다 → 🔶-14.
- ⚠️ **가격 변경 절차·기존 구독자 영향이 문서에 없다.** → **2,200/3,960 을 코드에 상수로 박지 않는다.**
- 상품 등록 상한은 비게임 30개 — 2종이라 여유가 크다.

## 5. API 계약 (초안 — 확정 후 `docs/server/api-spec.md` 반영)

> 경로 prefix `/api/v1` 과 공통 헤더는 **auth 확정 ⑦·§5-1** 을 그대로 물려받는다 —
> **여기서 다시 정하지 않는다.** 반면 아래 **엔드포인트 경로·응답 스키마는 전부 제안값**이다(🔶-15).

### 5-1. 공통

| 항목 | 값 | 출처 |
|---|---|---|
| 경로 prefix | `/api/v1` | auth 확정 ⑦ |
| 인증 헤더 | `X-Anonymous-Key` (웹훅 제외 전 구간 필수) | auth §5-1 |
| 에러 응답 본문 | `{ "code": "...", "message": "..." }` 고정 | [error-handling.md](../rule/error-handling.md) |

### 5-2. 신규 — `GET /api/v1/payments/products` (인증 불필요)

판매 중인 상품을 알려준다. **가격은 내려주지 않는다**(U1).

```json
{
  "oneTime":      { "sku": "…", "productType": "CONSUMABLE" },
  "subscription": { "sku": "…", "productType": "SUBSCRIPTION",
                    "renewalCycle": "MONTHLY", "offerId": null }
}
```

- 프론트는 이 `sku` 로 `getProductItemList()` 결과를 찾아 **`displayAmount` 를 화면에 쓴다.**
- `productType` 이 **어느 주문 생성 함수를 쓸지 결정**한다:
  `CONSUMABLE → createOneTimePurchaseOrder`, `SUBSCRIPTION → createSubscriptionPurchaseOrder`.
- 상품이 미노출이면 그 키를 `null` 로 준다 — 프론트가 해당 결제 버튼을 숨긴다.
- 🔶 이 엔드포인트가 필요한지 자체가 미확정(🔶-15). 하드코딩이면 왕복이 1회 줄지만
  상품 교체 시 **앱 재배포 + 심사(영업일 최대 3일, 카테고리에 따라 7일+)** 가 필요해진다.

### 5-3. 이용권 상태 표현 — **auth 가 넘긴 스키마를 여기서 받는다**

이용권 상태는 **두 곳**에서 나간다. **둘은 같은 모양이어야 한다.**

| 소비처 | 소유 | 언제 |
|---|---|---|
| `POST /api/v1/bootstrap` 응답의 이용권 객체 | 집계 모듈(auth §5-2) | 진입 시 1회 |
| `GET /api/v1/payments/entitlement` (신규) | 이 도메인 | 결제 직후·403 복귀 후 **재확인** |

**제안 스키마 (양쪽 공통)**

```json
{
  "accessible": true,
  "credits": 2,
  "subscription": {
    "status": "ACTIVE",
    "expiresAt": "2026-09-08T00:00:00+09:00",
    "autoRenew": true
  }
}
```

| 필드 | 의미 | 프론트 용도 |
|---|---|---|
| `accessible` | **열어줄 것인가**(§4-3 판정 결과) | **분기는 이 값 하나로만 한다** |
| `credits` | 남은 **횟수권** 수 | “n회 남음” 표시 |
| `subscription.status` | 토스 구독 상태 원문 + 구독 없음(`NONE`) | 안내 문구 분기. ❗분기 근거로 쓰지 않는다 |
| `subscription.expiresAt` | 기간권 만료 시각. 없으면 `null` | 남은 기간 표시 |
| `subscription.autoRenew` | 자동 갱신 예정 여부 | “해지 예약됨” 표시 |

- ⚠️ **auth 의 잠정안은 `subscription: { status, expiresAt }` 이었다.** auth 는 이 스키마를
  *“auth 가 확정할 권한이 없다”* 며 이 문서로 넘겼다(auth §5-2). 바꾼 이유:
  - **`credits` 추가** — 단건이 확정되면서(2026-08-09) 구독만으로는 이용권을 표현할 수 없게 됐다.
    **auth 가 그 스키마를 잡을 당시(v1, 08-07)에는 없던 상품이다.**
  - **`accessible` 추가** — §4-3 판정은 두 이용권을 함께 보는 우리 정책이다.
    이 값이 없으면 **프론트가 그 정책을 대신 판단하게 되고**, 정책이 바뀔 때마다 앱을 재배포해야 하며,
    무엇보다 서버 게이트(§4-10)와 프론트 화면이 **서로 다른 기준으로 갈라진다.**
  - **`autoRenew` 추가** — “해지 예약됨”을 표시할 수단이 `status` 에 없다(해지 예약도 `ACTIVE` 다).
  - **🔶 이 확대는 auth 확정 계약을 건드리는 변경**이라 사용자 확정이 필요하다(🔶-15).
    확정되면 **auth.md 는 v3 로 올라간다**(auth 는 이미 v2 다 → §10).
- 이용권이 없는 사용자도 **404 가 아니라 200** 이다 — “없음”은 정상 상태다.
- ⚠️ **부트스트랩은 부분 실패를 허용하지 않는다**(auth 확정, §5-2) — 이용권 조회가 실패하면 전체 500 이다.
  다행히 **이 조회는 토스를 부르지 않는다**(§4-2 — 서버가 이미 아는 상태를 읽을 뿐이다).
  즉 부트스트랩에 토스 장애가 전파되지 않는다. **§4-2 의 구조가 여기서는 이점으로 작동한다.**
- ⚠️ **`expiresAt` 은 타임존을 붙여 내려준다.** 토스 웹훅은 timezone 없는 ISO-8601 이라
  **우리가 해석 기준을 정해 변환한다**(🔶-7). 프론트에 모호한 값을 그대로 넘기지 않는다.

### 5-4. 신규 — `POST /api/v1/payments/grant` (인증 필요)

`processProductGrant` 콜백과 미결 주문 복원이 **같은 엔드포인트**를 쓴다. 멱등하기 때문이다(§4-5).
**단건과 구독도 같은 엔드포인트**다 — 서버가 `get-order-status` 의 `sku` 로 상품을 판별한다.

**요청**

```
POST /api/v1/payments/grant
X-Anonymous-Key: {hash}

{ "orderId": "…" }
```

- ⚠️ **`sku` 를 클라에서 받지 않는다.** 클라가 “구독을 샀다”고 주장하면 그대로 믿게 되기 때문이다.
  상품 판별은 **토스 응답의 `sku`** 로만 한다(서버 권위 원칙).
  이것은 **`getPendingOrders` 가 낮은 앱 버전에서 `sku` 없이 `orderId` 만 주는 문제도 함께 해결한다.**

**응답 200** — 신규 지급과 재요청(이미 지급됨)이 **같은 응답**이다.

```json
{
  "granted": true,
  "productType": "CONSUMABLE",
  "entitlement": { "accessible": true, "credits": 3, "subscription": { "status": "NONE", "expiresAt": null, "autoRenew": false } }
}
```

- 서버는 응답 전에 **토스 `get-order-status` 로 결제 사실을 확인한다**(U2).
- 프론트는 **200 이면 `true`, 그 외에는 `false`** 를 `processProductGrant` 의 반환값으로 쓴다.
- **에러 응답에 `orderId` 를 되돌려주지 않는다**(U14).

**토스 주문 상태 → 우리 응답 매핑**

| 토스 `status` | 우리 응답 |
|---|---|
| `PURCHASED` | **200 지급** |
| `PAYMENT_COMPLETED` | 🔶-1 **200 지급**(제안) — 아직 지급 전 단계라 정상 흐름이다. ⚠️ **문서 근거 없음** |
| `ORDER_IN_PROGRESS` | 409 `PAY_002` — 아직 확정 전. 복원 흐름이 나중에 다시 가져온다 |
| `FAILED` · `REFUNDED` | 409 `PAY_003` — 지급 대상이 아니다 |
| `NOT_FOUND` · `MINIAPP_MISMATCH` | 404 `PAY_004` |
| `ERROR` · `resultType ≠ SUCCESS` · 타임아웃 | 502 `PAY_006` |
| (다른 익명키에 귀속됨 — 토스 조회 이전 단계) | 409 `PAY_005` |

- ⚠️ **`resultType` 이 `SUCCESS` 가 아니면 전부 실패로 다룬다.** `FAIL` 외에 `HTTP_TIMEOUT` ·
  `NETWORK_ERROR` · `EXECUTION_FAIL` · `INTERRUPTED` · `INTERNAL_ERROR` 가 올 수 있다.
- ⚠️ **비즈니스 오류가 HTTP 200 으로 내려온다.** HTTP 상태만 보고 성공 판정하면 안 된다.
- ⚠️ `errorCode: 4095`(분당 3,000 QPM 초과)면 `error.data.retryAfterSeconds` 를 백오프에 쓴다.

### 5-5. 신규 — `POST /api/v1/webhooks/toss/payment` (인증 게이트 밖)

콘솔의 **‘결제 알림 URL’** 로 등록한다. 두 이벤트가 같은 경로로 온다(→ [iap-spec.md §5](../../../docs/platform/iap-spec.md)).

| 항목 | 규격 |
|---|---|
| 진위 검증 | **`Authorization: Basic {값}`** — 콘솔에 등록한 값. **불일치 시 처리하지 않는다**(U11) |
| 응답 | **204**, 본문 없음. **반영 실패해도 204**(§4-7) |
| 이벤트 | `callback.registration_verification`(`{eventType, occurredAt}` 뿐 — challenge 없음) · `subscription.status_changed` |

- ⚠️ **단건 결제의 웹훅은 오지 않는다.** 문서화된 이벤트 2종은 둘 다 구독 스코프다.
- ⚠️ Inbound 방화벽에 **6개 IP 대역 전부**를 열어야 한다 — 하나만 열면 나머지 5개 출발지가 차단된다(🔶-5).

### 5-6. 서버 → 토스 (내부 호출, 프론트 계약 아님)

`POST /api-partner/v1/apps-in-toss/order/get-order-status` · Base `https://apps-in-toss-api.toss.im` ·
**mTLS 단독 인증** · 요청 `{ orderId }` · 분당 3,000 QPM.
전체 규격과 상충 사항은 **[iap-spec.md §4](../../../docs/platform/iap-spec.md)** 가 정본이다.

⚠️ **이 호출이 로그인 없이 되는지가 이 도메인 최대의 미확정**이다(🔶-11) —
불가면 U2(서버 검증)와 U13(단건 환불 감지)이 **동시에** 사라진다.

## 6. API 호출 흐름 (프론트 ↔ 백엔드)

### 6-1. 단건 결제 (2,200원 · 1회 이용권)

```
[S2 솔루션 상세 — "1편만 만들기"]
 → GET /api/v1/payments/products  → 200 { oneTime:{ sku, productType:"CONSUMABLE" } }
 → SDK IAP.getProductItemList()   → displayAmount 로 "2,200원" 표시
    ※ 가격은 SDK 값을 쓴다. 하드코딩 금지(체크리스트 2번)

[결제하기 탭]
 → SDK IAP.createOneTimePurchaseOrder({ options:{ sku, processProductGrant }, onEvent, onError })
    ├─ UNSUPPORTED_APP_VERSION → "토스앱 업데이트 필요" 안내 후 종료 (서버 호출 없음)
    ├─ USER_CANCELED           → S2 복귀. 서버 상태 변화 없음
    ├─ KOREAN_ACCOUNT_ONLY     → iOS 한국 계정 아님. 안내 후 종료
    ├─ INVALID_PRODUCT_ID / NETWORK_ERROR / INTERNAL_ERROR / ITEM_ALREADY_OWNED 등
    │     → 사유 안내(체크리스트 6번 "결제 실패 사유 인지"). 서버 호출 없음
    └─ 결제 성공 → processProductGrant({ orderId }) 콜백
        → POST /api/v1/payments/grant { orderId }          ※ 30초 예산(§4-6)
           ├─ 200 { granted:true, entitlement:{ credits:n } }
           │     → 콜백에 true 반환 → S4 영상 선택으로 진행
           ├─ 409 PAY_002 (아직 확정 전)
           │     → false 반환. "잠시 후 자동으로 반영됩니다"
           │       → 미결 주문으로 남아 6-3 이 처리한다. ❗재시도 루프 금지
           ├─ 409 PAY_003 / 404 PAY_004 / 409 PAY_005 → false 반환 + 문의 안내. 재시도 금지
           ├─ 502 PAY_006 (토스 조회 실패)  → false 반환 + "잠시 후 다시" → 6-3 에 맡긴다
           ├─ 401 AUTH_001/002 → auth §6-2 대로 부트스트랩 1회 재실행 후 1회 재시도
           └─ 타임아웃(30초 임박) → false 반환. ❗붙잡지 말고 6-3 으로 넘긴다
 → cleanup() 반드시 호출
```

- **프론트 책임**: 콜백 반환값은 **200 일 때만 `true`**. `false` 를 반환해도 **결제가 취소되는 것이
  아니라 미결 주문으로 남는다** — 안내 문구가 “결제 실패”가 되면 안 된다(사실과 다르다).
- **프론트 책임**: 결제 중 **재생 중인 음악·영상을 일시정지**하고 종료 후 재개한다(체크리스트 1번).

### 6-2. 구독 결제 (3,960원 · 무제한)

```
[S2 — "월 구독"]
 → SDK IAP.createSubscriptionPurchaseOrder({ options:{ sku, offerId:null, processProductGrant }, … })
    ├─ UNSUPPORTED_APP_VERSION → 안내 후 종료
    │     ⚠️ 구독의 최소 버전(Android 5.253.0 / iOS 5.250.0)이 단건(5.219.0)보다 높다.
    │        낮은 버전에서는 구독 버튼 자체를 숨기고 단건만 노출한다
    ├─ 사용자 취소 / onError → S2 복귀
    └─ 결제 성공 → processProductGrant({ orderId, subscriptionId? }) 콜백
        → POST /api/v1/payments/grant { orderId }   ※ subscriptionId 는 보내지 않는다(optional 이므로)
           ├─ 200 { productType:"SUBSCRIPTION", entitlement:{ accessible:true } } → true 반환
           └─ (에러 분기는 6-1 과 동일)

[이후 갱신 · 해지 · 결제실패 · 환불]
 → ❗ processProductGrant 가 다시 호출되지 않는다. 전부 6-6 웹훅으로만 온다
```

### 6-3. 앱 기동 시 미결 주문 복원 — **필수 (검수 시나리오 ③)**

```
[미니앱 진입, auth 부트스트랩 성공 직후 — 화면을 막지 않고 배경에서]
 → SDK IAP.getPendingOrders()
    ├─ undefined (미지원 버전) → 통과
    ├─ orders: [] → 통과
    └─ 주문 N건 → 각 orderId 마다
        → POST /api/v1/payments/grant { orderId }
           ├─ 200 → SDK IAP.completeProductGrant({ params:{ orderId } }) 로 미결 상태 종료
           │        ⚠️ 반환이 boolean | undefined 다 — undefined 를 방어한다
           ├─ 409 PAY_002 → 아직 확정 전. completeProductGrant 호출하지 않고 다음 기동에 재시도
           ├─ 409 PAY_003 / 404 PAY_004 → 지급 대상이 아니다
           │     🔶-16 completeProductGrant 로 닫을지 그대로 둘지 미확정
           ├─ 409 PAY_005 → 다른 사용자 주문. 조용히 건너뛴다(사용자에게 노출하지 않는다)
           └─ 502 PAY_006 → 다음 기동에 재시도. 사용자에게 알리지 않는다
```

- **이 흐름이 6-1·6-2 의 모든 실패를 받아내는 안전망**이다. 6-1 에서 재시도를 하지 않는 이유가 여기 있다.
- ⚠️ **진입이 느려지면 검수 기준 “인터랙션 2초 이내”에 걸린다.** 반드시 배경에서 돈다.
- ⚠️ **`getPendingOrders` 는 기기 변경 복원에 쓸 수 없다** — 이미 지급된 건은 pending 이 아니다.
  기기 변경 복원은 **익명키가 유지된다는 전제**에 기대고 있으며(§4-4), 그것이 깨지면
  `getCompletedOrRefundedOrders` 가 유일한 보조 수단이다 → 🔶-6.

### 6-5. 유료 기능 요청 — 이용 게이트

```
[S4 영상 선택 → 작업 생성 요청]
 → POST /api/v1/{작업 생성}   (X-Anonymous-Key)
    ├─ 200 → S5 처리 중 화면
    │        (기간권 보유자는 차감 없음 / 횟수권 보유자는 이 시점에 −1 예약 — §4-3·🔶-4)
    ├─ 403 PAY_001 (이용권 없음/만료)
    │     → 결제 유도 화면으로 보낸다. ❗401 과 다른 화면이다
    │       복귀 후 6-4 로 상태를 다시 확인하고 재시도
    └─ 401 AUTH_001/002 → auth §6-2 (결제 문제가 아니다 — 안내 문구를 구분한다)

[작업 실패 시]
 → 서버가 횟수권을 되돌린다 (U8). 프론트는 6-4 로 잔량을 다시 읽어 화면을 갱신한다
```

- ⚠️ **403 과 401 의 화면이 다르다.** 401 에 결제 유도를 띄우면 이미 결제한 사용자에게 다시 결제를 요구하게 된다.
- ⚠️ **결제 유도 화면에 다크패턴 금지 규정이 걸린다** — “나갈 수 있는 선택지가 없는 경우”와
  “CTA 버튼만 보고 다음 행동을 예상할 수 없는 경우”는 **출시 불가 사유**다. 닫기 경로를 반드시 둔다.

## 7. 에러 코드 · 정책

| 코드 | HTTP | 의미 | 프론트 행동 |
|---|---|---|---|
| `PAY_001` | 403 | 이용 가능한 이용권이 없습니다 | **결제 유도 화면** |
| `PAY_002` | 409 | 결제가 아직 확정되지 않았습니다 | 안내 후 대기. 복원 흐름(6-3)에 맡긴다 |
| `PAY_003` | 409 | 결제가 완료되지 않은 주문입니다 | 안내. 재시도 금지 |
| `PAY_004` | 404 | 주문을 찾을 수 없습니다 | 문의 안내. 재시도 금지 |
| `PAY_005` | 409 | 다른 사용자에게 귀속된 주문입니다 | 문의 안내. 재시도 금지 |
| `PAY_006` | 502 | 결제 정보를 확인하지 못했습니다 | 잠시 후 재시도. 복원 흐름에 맡긴다 |

- 네이밍은 [error-handling.md](../rule/error-handling.md) 의 `{DOMAIN}_{NNN}` 규약을 따른다(도메인 약어 `PAY`).
  > 📌 이전 초안의 `SUB_001~006` 을 `PAY_` 로 다시 매겼다. **아직 배포되지 않은 초안이라 결번 규칙이
  > 적용되지 않는다** (auth 도 초안 단계에서 U 번호를 재부여한 선례가 있다).
- **502 는 현재 `GlobalExceptionHandler` 에 없는 상태 코드**다 — 신설이 필요하다는 사실만 남긴다(방법은 설계서 몫).
- `AUTH_001`/`AUTH_002`(401)·`COMMON_002`(500)는 **기존 게이트가 그대로 적용**된다(auth §4-2).
- `AUTH_003`(403)은 **쓰지 않는다** — 이용권 미보유는 `PAY_001` 로 구분한다(§4-10).

> - ⑦ **구독은 ⑥ 에 더해 앱인토스 웹훅으로 상태 변이(결제 실패·취소 등)를 서버가 저장한다**

> - ④ **월 자동갱신 구독(MONTHLY)** 을 앱인토스 IAP 로 판다 — mvp-v1 1-1·1-5

**따라오는 전제 (플랫폼 문서·기존 규칙 근거 — 사용자 결정 아님)**

> 플랫폼 사실의 근거·인용은 전부 **[iap-spec.md](../../../docs/platform/iap-spec.md)** 에 있다.

| 전제 | 확신도 |
|---|---|
| 우리 가격 2,200 / 3,960 은 **콘솔 등록 규격을 충족**한다(공급가 2,000 / 3,600, 10원 단위) | ✅ 원문 명시 |
| 실수령액 = 단건 iOS 1,749 / Android 1,779, 구독 iOS 약 3,148 / Android 약 3,202 | ✅ 공식 계산 예시로 검산. ⚠️ 구독은 **절사 규칙 미확정**으로 ±1원 |
| **서버용 구독 상태 조회 API 는 없다** | ✅ 높음 — 사이트맵·서버 API·구독 가이드 3곳 대조. 단 **“없음”의 증명**이라 문서 갱신 시 뒤집힐 수 있다 |
| 구독 IAP 는 **샌드박스 미지원**, 단건은 지원 | ✅ 원문 명시 |
| 웹훅 진위 검증은 **Basic Auth 가 유일**. HMAC·서명 없음 | ✅ 원문 + 토스 직원 확인 |
| 웹훅 응답은 **204** | ⚠️ **토스 직원 답변이 유일한 근거.** 문서 규격 없음 |
| 익명키는 재설치·기기 변경에도 유지된다 (저장은 **64자**면 충분) | ⚠️ **토스 직원 답변(2026-07-27).** 단 **같은 직원이 2026-01-16 에는 “로그인 없으면 기기 변경 시 유지 안 됨”이라고 답해 상충한다.** 최신 답변이 우세하나 서면 재확인 필요 → 🔶-6 |
| ⚠️ 공식 가이드는 `get-order-status` 사용에 **“반드시 토스 로그인 연동을 먼저”** 를 요구한다 | **우리 결정과 정면 충돌.** 다만 OpenAPI spec(`parameters: []`, mTLS 단독)·헤더 표(`x-toss-user-key` 선택)·토스 직원 답변 3건이 반대 방향이다 → 🔶-11 |
| ⚠️ **hash(익명키) 인증 확장 API 는 프로모션·스마트발송·토스페이 3종이고 IAP 는 없다.** `getAnonymousKey` 레퍼런스는 반환 키를 **토스 서버 API 호출용으로 쓰지 말라**고 경고한다 | **[CLAUDE.md](../../../CLAUDE.md) 의 “hash 인증으로 인앱결제도 지원된다” 서술이 틀렸다.** IAP 는 `x-anon-key` 를 쓰지 않고 mTLS + `orderId` 로만 호출하므로 **설계에는 영향이 없으나 문서는 고쳐야 한다** → §10 |

**🔶 미확정 — 확정 전에는 구현에 들어가지 않는다**

| # | 항목 | 제안값 | 근거 / 확정 조건 |
|---|---|---|---|
| 🔶-1 | **어느 주문 상태에서 지급 확정인가** (`PAYMENT_COMPLETED` 도 지급 대상인가) | 둘 다 지급 | **문서 근거가 전혀 없다.** 틀리면 **이중 지급 또는 지급 누락** — 횟수권에서 특히 치명적. 채널톡 문의 |
| 🔶-2 | **무료 체험(FREE_TRIAL)을 쓸 것인가** | 쓰지 않음 | 쟁점 1(체험 없이 결제 선행)을 사용자가 재확인했다. 도입은 그 결정을 뒤집는 기획 판단이므로 임의로 켜지 않는다 |

| 🔶-5 | **웹훅 방어층을 어디까지 둘 것인가** | Basic Auth(채택 확정) + **Inbound IP 화이트리스트 6개 대역** + “웹훅으로 구독을 만들지 않는다” | **IP 제한은 인프라 결정**(→ `/infra`)이고, 3번째 규칙은 **§6-6 흐름 전체의 전제**라 뒤집히면 §6-6 도 바뀐다 |
| 🔶-6 | **웹훅 유실 · 익명키 단절 보정 수단** | 미정 | 서버 조회 API 가 없어(§4-2) 유실을 스스로 바로잡을 수 없다. 후보: ⓐ 프론트가 `getSubscriptionInfo`·`getCompletedOrRefundedOrders` 결과를 **불일치 신고**로만 올린다(값을 믿는 게 아니라 재검증 트리거로만) ⓑ `previous` 불일치 시 운영 알림 ⓒ 감수. **갱신 유실이 만료 유실보다 훨씬 나쁘다**(§4-2)가 판단 기준. 익명키 지속성 상충(위 전제표)도 여기 걸린다 |
| 🔶-7 | **웹훅 시각의 기준 타임존** | KST(Asia/Seoul) | timezone 없는 ISO-8601 이라는 사실만 확인됐고 **토스가 확답하지 않았다**(2026-08-06 스레드 진행 중). **틀리면 만료 판정이 최대 9시간 어긋난다.** 우리 서버 규약으로 정하되 문서 근거가 없음을 명시 |
| 🔶-8 | **단건 환불 감지 방식** | 감지하지 않음(감수) | 푸시가 없다. 폴링은 QPM·비용이 들고, 클라 조회는 신뢰할 수 없다. **이미 소모한 횟수권은 되돌릴 것도 없다.** 환불이 실제로 얼마나 나는지 모르는 상태에서 폴링을 만드는 것은 이르다고 본다 — **사용자 판단** |
| 🔶-9 | **이용 게이트 대상 엔드포인트** | §4-10 표 (작업 생성만 요구 + 소모) | [공통 승격 후보]. 대상이 사실상 `subtitle` 도메인 엔드포인트라 **그 문서와 함께 확정하는 것이 자연스럽다** |
| 🔶-10 | **지급 API 응답 시간 상한** + 30초 제약이 구독에도 적용되는가 | 적용된다고 가정 / 상한 미정 | 30초 문구는 **일회성 결제 문서에만** 있다. 없다고 가정했다가 틀리면 결제 직후 환불 화면이 뜬다 — 반대 방향 손해는 없으므로 보수적으로 간다. **타이머 기점이 문서에 없고**, true 반환에도 환불 안내가 뜬 사례가 있어 상한값은 실측이 필요하다 |
| 🔶-11 | **`get-order-status` 를 토스 로그인 없이 호출 가능한가** | 가능하다고 가정 | 위 전제표. **불가면 U2(서버 검증)와 U13(단건 환불 감지)이 동시에 사라진다.** 익명키(`x-anon-key`)로 소유자를 한정할 수 있는지도 함께 확인 — 가능하면 **소유권 방어가 선점에서 플랫폼 검증으로 올라간다.** 채널톡 서면 질의 |

| 🔶-13 | **`completeProductGrant` 중복 호출 멱등성** | 멱등하다고 가정 | 문서화돼 있지 않다. 우리 지급 API 는 자체 멱등(§4-5)이라 1차 방어는 되지만, 확인하지 않고 넘어가면 **횟수권이 새는 경로가 하나 남는다** |
| 🔶-14 | **구독 상품명 문구** | “월 이용권(자동 갱신)” 류 | ⚠️ **토스가 과장 표현 반례로 직접 “무제한”을 든다.** 우리 혜택이 정확히 그것이라 **반려 위험**이 있다. 상품명·상세 문구를 함께 정해야 한다. **이것이 정해져야 콘솔에 상품을 등록할 수 있다** |
| 🔶-15 | **엔드포인트 경로·응답 스키마 전반** (§5-2~5-5) + **부트스트랩 이용권 스키마 확대** | §5 의 제안값 | 프론트 계약이라 임의 확정 불가. `/api/v1`·공통 헤더는 **auth 확정 ⑦·§5-1 을 물려받으므로 여기서 다시 정하지 않는다.** 포함: ⓐ **부트스트랩 이용권 객체에 `accessible`·`credits`·`autoRenew` 추가**(§5-3) — auth 가 넘긴 재확인 항목이고 **채택하면 auth.md 가 v3 로 올라간다**(auth 는 이미 v2 다) ⓑ `products` 엔드포인트가 필요한지 ⓒ `status` 를 토스 원문 그대로 노출할지 |
| 🔶-16 | **지급 불가 미결 주문(`PAY_003`/`PAY_004`)을 `completeProductGrant` 로 닫을 것인가** | 닫는다 | 닫지 않으면 기동할 때마다 같은 주문을 계속 조회한다. 닫으면 **나중에 정상화될 여지가 사라진다.** `getPendingOrders` 보관 기간이 문서에 없어 실측이 필요하다 |
| 🔶-17 | **이용 중단 시 진행 중인 작업 처리** | 진행 중인 건은 끝까지 처리 | 자막 작업이 수십 초~수 분이라 처리 중 만료가 실제로 발생한다. 중간에 끊으면 “돈 낸 마지막 1편을 못 받는” 최악의 경험이 된다. **다만 무제한으로 열면 만료 직전 대량 투입이 가능하다** — 사용자 판단 |
