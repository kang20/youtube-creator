# 익명키 인증 — 비즈니스 요구사항 설계서 (auth 도메인)

> **성격**: 토스 로그인 없이 `X-Anonymous-Key` **하나로** 전 구간 사용자를 식별한다.
> 진입 마찰 0 이 이 서비스의 판매 논리(“앱 설치·가입 없이 폰만으로”)이므로, 이 도메인의 목표는
> **인증을 강화하는 것이 아니라 인증을 보이지 않게 만드는 것**이다. 사용자에게 노출되는 화면이 없다.
> 비즈니스 요구사항: 2026-08-07 사용자 결정(§9-1) · 근거: [mvp-v1.md](../../../docs/planning/mvp-v1.md) 쟁점 4
> 관련: [toss-integration.md](../rule/toss-integration.md) · [error-handling.md](../rule/error-handling.md) · [architecture.md](../rule/architecture.md)
> 상태: **요구사항 초안 — §9-1 🔶 확정 필요**

> ⚠️ **이 프로젝트의 첫 도메인 문서다.** `backend/docs/domain/` 에 선례가 없고
> `docs/server/api-spec.md` 도 아직 없다. 따라서 여기서 정하는 경로 스타일·헤더 규약·인증 게이트·
> 에러 코드 운용은 **이후 모든 도메인의 선례**가 된다. 그런 항목은 본문에
> **[공통 승격 후보]** 로 표시했고, 확정 시 `docs/server/api-spec.md` 로 올려 다음 도메인이
> 링크만 하게 만든다(→ §10).

## 용어

| 용어 | 의미 |
|---|---|
| 익명키 (anonKey) | 클라 SDK `User.getAnonymousKey()` 가 반환하는 hash 문자열. 미니앱마다 고유하고, **같은 사용자는 같은 미니앱에서 항상 같은 값**을 받는다 |
| verify | 토스 파트너 API `POST /api-partner/v1/apps-in-toss/users/anon-key/verify` — 익명키 hash 의 진위 확인 |
| 검증됨 | 익명키가 **토스가 발급한 진짜 값**임을 서버가 확인한 상태. **본인 확인(신원 확인)이 아니다** |
| 세션 | 서버가 보관하는 세션이 아니다. 요청마다 헤더로만 식별되는 stateless 상태를 가리킨다 |
| 부트스트랩 | 미니앱 진입 직후 프론트가 1회 호출해 “이 익명키로 서비스를 쓸 수 있는 상태”를 만드는 절차 |

## 1. 배경 · 목적

- 이 서비스의 핵심 약속은 **“앱 설치·가입 없이 폰만으로”** 다. 로그인 화면 하나가 그 약속을 깬다.
  2026-08-07 사용자 결정으로 **토스 로그인을 쓰지 않기로 확정**했고(쟁점 4), 그 결과 전 구간의
  사용자 식별이 익명키 하나에 걸린다.
- 그런데 **유료 서비스**다. 구독 소유권이 익명키에 묶이므로, 익명키는 “있으면 좋은 식별자”가 아니라
  **결제 소유권의 뿌리**다. 위조된 익명키를 그대로 신뢰하면 타인의 구독을 도용할 수 있다.
  → 그래서 **서버 측 verify 가 이 도메인의 실질적 존재 이유**다. 헤더를 읽는 것만으로는 부족하다.
- 동시에 검수 기준이 **“인터랙션 2초 이내”** 다. 매 요청마다 외부 API(verify)를 호출하면
  이 기준과 정면으로 충돌한다 — 이 도메인의 설계 긴장은 **“신뢰”와 “지연” 사이**에 있다(§4-3).

**핵심 훅은 없다.** 사용자에게 보이는 화면도, 사용자가 하는 행동도 없다. 성공한 인증은 아무것도
느껴지지 않아야 한다.

| 프론트의 SDK 호출·재시도 UI | ✅(계약만) | 에러별 프론트 행동은 §6 에 명시. 화면 문구는 프론트 재량 |

## 3. 기능 요구사항

| # | 요구 | 설명 |
|---|---|---|
| **U1** | 익명키 헤더 수신 | 모든 API 요청에서 `X-Anonymous-Key` 헤더를 읽어 요청 주체를 식별한다. 헤더가 없으면 “미식별 요청”으로 다룬다(즉시 401 이 아니다 — 판정은 U4) |
| **U2** | 익명키 진위 검증 | 토스 verify API 로 익명키가 실제 발급값인지 확인한다. 위조·만료·타 미니앱 값은 전부 거부한다 |
| **U3** | 사용자 등록 | 검증에 성공한 익명키가 우리 서비스에 처음 등장하면 사용자로 등록한다. 이미 있으면 그대로 쓴다(**멱등** — 같은 익명키로 몇 번을 호출해도 사용자는 하나) |
| **U4** | 인증 게이트 | 엔드포인트를 **공개 / 인증 필요** 두 부류로 나누고, 인증 필요 엔드포인트는 검증된 익명키 없이는 거부한다(§4-2) |
| **U5** | 부트스트랩 API | 프론트가 진입 직후 1회 호출해 “쓸 수 있는 상태”를 확보한다. 응답으로 **신규/기존 여부**를 받아 온보딩 분기에 쓴다 |
| **U6** | 검증 결과 재사용 | 매 요청마다 verify 를 호출하지 않는다. 재검증 주기 안에서는 이전 검증 결과를 신뢰한다 — **“2초 이내” 검수 기준을 지키기 위한 요구**(§4-3) |
| **U7** | verify 장애 시 동작 규정 | 토스 verify 가 응답하지 않거나 5xx 를 낼 때의 동작을 “위조 거부(401)”와 구분해 **별도 에러로** 응답한다. 프론트가 재시도와 포기를 구분할 수 있어야 한다 |
| **U8** | 익명키 형식 사전 검증 | 명백히 형식이 틀린 값은 verify 호출 없이 즉시 거부한다 — 외부 호출 낭비와 로그 오염을 막는다 |
| **U9** | 익명키 비노출 | 로그·예외 메시지·에러 응답 본문에 익명키 원문을 남기지 않는다. 결제 소유권의 뿌리이므로 유출 시 도용으로 직결된다 |

> 번호는 **영구 결번**이다. 삭제해도 재사용하지 않는다(→ [versioning.md](../../../.claude/skills/usecase/references/versioning.md)).

## 4. 비즈니스 규칙 (정책 상세)

### 4-1. 익명키의 신뢰 수준 — 무엇을 보장하고 무엇을 보장하지 않는가

| 질문 | 답 |
|---|---|
| 이 요청이 **어떤 사용자**의 것인가 | ✅ 보장 (검증 후) |
| 그 사용자가 **누구인지**(실명·연락처) | ❌ 모른다. 알 필요도 없다 |
| 같은 사용자가 **기기를 바꿔도** 같은가 | ✅ 토스 계정 기준이므로 유지되는 것으로 본다 — **단 실환경 미검증** (§9-1 🔶-1) |
| 익명키가 **비밀**인가 | ❌ **아니다.** 식별자다. 유출되면 도용 가능 → 노출 최소화(U9)가 유일한 방어 |
| **미니앱을 새로 출시**해도 같은가 | ❌ **승계되지 않는다** (§4-7) |

- ⚠️ 익명키는 비밀번호가 아니라 **식별자**다. 그러므로 이 인증은 “이 요청은 그 사람이 맞다”를
  **완전히** 보증하지 않는다. MVP 범위에서는 이 수준을 **의도적으로 수용**한다 —
  로그인을 붙이지 않기로 한 결정(2026-08-07)의 직접적 대가다.
- 현재 코드([AnonymousAuthentication.java](../../src/main/java/kang20/ytcreator/shared/security/AnonymousAuthentication.java))의
  주석은 *“로그인이 필요한 기능은 `appLogin()` 경로를 별도로 둔다”* 고 적고 있으나,
  이는 2026-08-07 결정 **이전**의 서술이다 → 갱신 대상(§10).

### 4-2. 인증 게이트 — 엔드포인트 분류 × 헤더 상태 [공통 승격 후보]

모든 엔드포인트는 아래 둘 중 하나에 속한다. **기본값은 “인증 필요”** 이며, 공개는 명시적으로 지정한다.

| 분류 | 대상(제안) | 헤더 없음 | 헤더 있음·검증 실패 | 헤더 있음·검증 성공 |
|---|---|---|---|---|
| **공개** | 헬스체크·솔루션 목록/상세 조회 🔶 | 200 | 200 (익명키 무시) | 200 |
| **인증 필요** | 그 외 전부 (작업 생성·조회·구독 등) | **401 `AUTH_001`** | **401 `AUTH_002`** | 200 |

- **헤더가 없다고 필터가 즉시 401 을 내지 않는다.** 판정은 경로 규칙이 한다 —
  현재 [AnonymousKeyFilter](../../src/main/java/kang20/ytcreator/shared/security/AnonymousKeyFilter.java)
  가 이미 이 방식이며 이 문서는 그 동작을 요구로 확정한다.
- 401 두 종류를 **코드로 구분**하는 이유: 프론트의 행동이 다르다.
  `AUTH_001`(헤더 누락) → SDK 재호출, `AUTH_002`(검증 실패) → 재호출해도 소용없으므로 안내 후 종료.
- 403 `AUTH_003` 은 **auth 도메인이 쓰지 않는다.** “구독이 없어 못 쓴다”는 인가 판정은
  `subscription` 도메인의 책임이다. auth 는 신원까지만 답한다.

### 4-3. 검증 시점과 재검증 주기 — 신뢰 vs 지연 [공통 승격 후보]

- **매 요청 verify 호출은 하지 않는다.** 검수 기준이 “인터랙션 2초 이내”인데 외부 API 왕복이
  모든 요청에 붙으면 우리 처리 시간과 무관하게 기준을 위협한다. 토스 API 장애가 곧 전체 장애가 되는
  단일 실패점이기도 하다.
- 따라서 **verify 는 첫 등장 시 1회 + 주기적 재검증**으로 한다. 주기 안에서는 이전 결과를 신뢰한다.
- ⚠️ **수용하는 트레이드오프**: 재검증 주기 동안은 토스에서 무효화된 익명키도 통과한다.
  익명키가 무효화되는 상황 자체가 드물고, 그 사이 발생하는 손해가 “모든 요청 +1 외부 호출”보다
  작다고 본다. **주기 값은 미확정**(§9-1 🔶-3).

| 시점 | verify 호출 |
|---|---|
| 부트스트랩(U5) — 처음 보는 익명키 | ✅ 필수 |
| 부트스트랩 — 이미 아는 익명키, 주기 내 | ❌ 생략 |
| 부트스트랩 — 이미 아는 익명키, 주기 경과 | ✅ 재검증 |
| 일반 API 요청 | ❌ (게이트만 통과) |

### 4-4. verify 장애 시 정책

- 토스 verify 의 **“위조라서 거부”** 와 **“토스가 응답을 못 함”** 은 **다른 사건**이다.
  둘을 같은 401 로 뭉치면 사용자는 정상 상태에서 “인증 실패” 안내를 받고, 프론트는 재시도할지
  포기할지 판단할 수 없다. → 장애는 별도 코드(§7 `AUTH_004`, 503)로 응답한다.
- **처음 보는 익명키**는 장애 시 통과시키지 않는다 — 검증되지 않은 신규 사용자를 만들면
  결제 소유권의 뿌리가 오염된다.
- **이미 검증된 적 있는 익명키**의 재검증 실패는 통과시킬지(fail-open) 막을지(fail-closed)가
  **미확정**(§9-1 🔶-4).

### 4-5. 형식 사전 검증 (U8)

| 항목 | 규칙 |
|---|---|
| 공백/빈 값 | 거부 (헤더 없음과 동일 취급) |
| 길이 상한 | 🔶 미확정 (§9-1 🔶-5) — 상한이 없으면 거대 헤더로 로그·메모리를 오염시킬 수 있다 |
| 허용 문자 | 🔶 미확정 (§9-1 🔶-5) |

- 형식 위반은 **verify 를 호출하지 않고** 즉시 `AUTH_002` 로 거부한다.

### 4-6. 로깅 · 개인정보 (U9)

- 익명키 원문은 **로그·예외 메시지·에러 응답 본문 어디에도** 남기지 않는다.
- 추적이 필요하면 **마스킹된 형태**로만 남긴다. 마스킹 방식은 🔶 (§9-1 🔶-6).
- 익명키는 그 자체로 개인을 특정하지 않지만 **결제 소유권과 1:1** 이므로 취급 수준은 자격증명에 준한다.

### 4-7. ⚠️ 미니앱 재출시 = 익명키 단절 (수용한 리스크)

- 미니앱이 바뀌면 익명키는 **승계되지 않는다.** 앱을 새로 출시하는 순간 기존 사용자는
  전원 신규 사용자가 되고, **구독이 끊긴다.**
- MVP 에서는 **이관 기능을 만들지 않는다**(§8). 다만 이것이 “나중에 붙이면 되는 기능”이 아니라
  **재출시 전에 반드시 해결해야 하는 선행 조건**임을 여기 남긴다 —
  로그인이 없으므로 두 익명키를 잇는 단서가 우리에게 없다.

## 5. API 계약 (초안 — 확정 후 `docs/server/api-spec.md` 반영)

> `docs/server/api-spec.md` 는 **아직 존재하지 않는다.** 이 절이 그 문서의 첫 입주자가 된다(→ §10).

### 5-1. 공통 요청 헤더 [공통 승격 후보]

| 헤더 | 필수 | 값 |
|---|---|---|
| `X-Anonymous-Key` | 인증 필요 엔드포인트에서 필수 | SDK `User.getAnonymousKey()` 의 `hash` 값 |

- 헤더명은 **한 글자도 바뀌지 않는다** — 프론트 계약이며 현재 코드가 이미 이 이름을 쓴다.
- 공통 에러 응답 본문은 `{ "code": "...", "message": "..." }` 고정
  (→ [error-handling.md](../rule/error-handling.md)). auth 도 예외 없이 이 형식을 따른다.

### 5-2. 신규 — `POST /api/v1/auth/session` 🔶

> 🔶 경로·메서드·응답 스키마 **전부 미확정** (§9-1 🔶-2). 아래는 제안값이다.
> `POST` 인 이유: 최초 호출이 **사용자 등록이라는 상태 변화**를 일으키므로 `GET` 이 아니다.
> 다만 **멱등**하다(U3) — 몇 번 호출해도 사용자는 하나이고 응답도 같다.

**요청**

```
POST /api/v1/auth/session
X-Anonymous-Key: {hash}
(본문 없음)
```

**응답 200**

```json
{
  "newUser": true,
  "verifiedAt": "2026-08-07T12:34:56Z"
}
```

| 필드 | 의미 | 프론트 용도 |
|---|---|---|
| `newUser` | 이번 호출로 처음 등록되었는가 | 온보딩/튜토리얼 노출 분기 |
| `verifiedAt` | 검증이 확정된 시각 | 디버깅·문의 대응 |

- **구독 상태는 이 응답에 넣지 않는다** — `subscription` 도메인의 책임이고, 섞으면 auth 가
  결제를 알게 되어 모듈 경계가 무너진다(→ [architecture.md](../rule/architecture.md)).
  🔶 프론트 왕복 1회를 줄이려 합치자는 논의는 가능하다(§9-1 🔶-7).
- **에러 응답에 익명키를 되돌려주지 않는다**(U9).

### 5-3. 인증 필요 엔드포인트 전반 [공통 승격 후보]

auth 도메인은 자기 엔드포인트 외에 **다른 모든 도메인의 요청 앞단**에 게이트로 존재한다.
각 도메인 문서는 엔드포인트마다 “공개 / 인증 필요”만 명시하면 되고, 401 응답 규격은 §4-2 를 링크한다.

## 6. API 호출 흐름 (프론트 ↔ 백엔드)

### 6-1. 최초 진입 — 부트스트랩

```
[미니앱 진입]
 → 프론트: SDK User.getAnonymousKey()
    ├─ 실패/미지원 → 서비스 이용 불가 안내 후 종료 (서버 호출 없음)
    └─ 성공 { type:'HASH', hash }
        → POST /api/v1/auth/session   (X-Anonymous-Key: hash)
           ├─ 200 { newUser:true }  → 온보딩 노출 → 솔루션 목록(S1)
           ├─ 200 { newUser:false } → 바로 솔루션 목록(S1)
           ├─ 401 AUTH_001 (헤더 누락)
           │     → 프론트 버그. SDK 재호출 1회 → 그래도 실패면 오류 안내 후 종료
           ├─ 401 AUTH_002 (위조·형식오류)
           │     → 재시도해도 결과가 같다. "이용할 수 없는 환경" 안내 후 종료
           └─ 503 AUTH_004 (토스 verify 장애)
                 → 재시도 가능한 상태. 백오프 재시도 + "잠시 후 다시" 안내
                    ⚠️ 종료시키지 않는다 — 우리 잘못도 사용자 잘못도 아니다
```

### 6-2. 일반 API 요청 (인증 필요 엔드포인트)

```
[임의 화면에서 보호 자원 요청]
 → METHOD /api/v1/{...}   (X-Anonymous-Key: hash)
    ├─ 200 → 정상 렌더링
    ├─ 401 AUTH_001 → 헤더가 빠졌다. 부트스트랩(6-1) 재실행 후 1회 재시도
    ├─ 401 AUTH_002 → 익명키가 무효해졌다(재검증 실패 등).
    │                 부트스트랩 재실행 → 거기서도 실패면 안내 후 종료
    └─ 503 AUTH_004 → 백오프 재시도. 진행 중 작업이 있으면 상태를 잃지 않게 유지
```

- **프론트 책임**: 401 을 받았을 때 **자동으로 부트스트랩을 한 번만** 재실행한다.
  무한 재시도 루프는 금지 — 검증 실패는 재시도로 풀리지 않는다.

### 6-3. 공개 엔드포인트 (헤더 없이 접근)

```
[솔루션 목록/상세 — 결제 전 열람] 🔶 공개 여부 미확정(§9-1 🔶-8)
 → GET /api/v1/{...}   (헤더 없어도 됨)
    ├─ 200 → 렌더링
    └─ 헤더가 붙어 있어도 검증하지 않고 무시한다 (지연을 만들지 않는다)
```

### 6-4. 재검증 주기 경과 후

```
[부트스트랩 재호출 — 주기 경과]
 → POST /api/v1/auth/session
    → 서버: 토스 verify 재호출
       ├─ 유효   → 200 { newUser:false }
       ├─ 무효   → 401 AUTH_002 → 프론트: 안내 후 종료
       └─ 장애   → 🔶 fail-open 이면 200 / fail-closed 면 503 AUTH_004
                   (§9-1 🔶-4 — 이 분기의 결과가 계약이므로 확정 필요)
```

## 7. 에러 코드 · 정책

**기존 코드로 대부분 커버된다.** 신규는 1건.

| 코드 | HTTP | 의미 | 신규 여부 |
|---|---|---|---|
| `AUTH_001` | 401 | 인증이 필요합니다 — 익명키 헤더 없음 | 기존 |
| `AUTH_002` | 401 | 유효하지 않은 인증 정보 — 형식 오류·위조·검증 실패 | 기존 |
| `AUTH_003` | 403 | 접근 권한 없음 — **auth 도메인은 사용하지 않는다**(§4-2) | 기존 |
| `AUTH_004` 🔶 | 503 | 인증 서버(토스) 일시 장애 — 재시도 가능 | **신규 제안** |
| `COMMON_002` | 500 | 우리 서버 내부 오류 | 기존 (자동) |

- `AUTH_004` 를 새로 만드는 이유는 §4-4 — “거부”와 “장애”를 프론트가 구분해야 하기 때문이다.
  🔶 신설 여부는 §9-1 🔶-4 와 함께 확정한다. 503 은 `GlobalExceptionHandler` 에 새 상태 매핑이
  필요할 수 있다(→ [error-handling.md](../rule/error-handling.md) “새 도메인 추가 시”).
- 코드는 **영구 결번**이다. 배포된 코드를 다른 의미로 재사용하지 않는다.

## 8. 백로그 (이번 범위 제외)

| 항목 | 미루는 이유 |
|---|---|
| 미니앱 재출시 시 익명키 이관 | 재출시 시점 문제. 단 **재출시 전 필수 선행 조건**(§4-7) |
| 회원 탈퇴 · 데이터 삭제 요청 | 보관 정책(mvp-v1 쟁점 6)이 미확정이라 함께 미룬다 |
| rate limit · 익명키 남용 방지 | 익명키는 비밀이 아니므로 언젠가 필요. 트래픽이 없는 지금은 이르다 |
| 익명키 도용 탐지 | 위와 동일 |
| 토스 로그인 연동(`appLogin()`) | 사용하지 않기로 확정. 붙이려면 기획 결정부터 |
| 관리자 인증 체계 | 관리자 화면 자체가 MVP 밖 |
| 다중 기기 동시 사용 정책 | 계정 기준이라 자연히 공유된다. 제한할 이유가 아직 없다 |

**따라오는 전제 (플랫폼 문서·기존 규칙 근거 — 사용자 결정 아님)**

| 전제 | 출처 | 확신도 |
|---|---|---|
| 익명키는 **토스 계정 기준**이라 기기 변경·재설치에도 유지된다 | 토스 블로그(“같은 사용자는 항상 같은 값”), mvp-v1 1-5 | ⚠️ **실환경 미검증** — 🔶-1 로 남는다. “기기 변경·재설치”를 명시한 공식 문구는 없다 |
| 익명키 검증은 **서버가 토스 verify API 로** 수행한다 | [toss-integration.md](../rule/toss-integration.md) “익명키 흐름”, mvp-v1 1-5 | 기존 규칙 문서에 이미 있음. 이 문서가 새로 정한 것이 아니다 |
| 구독 소유권은 **우리 서버가 보관하는 익명키↔주문 매핑**이 정본 | [toss-integration.md](../rule/toss-integration.md) “자동갱신 구독”, mvp-v1 1-5 | 기존 규칙 문서에 이미 있음. 관리 주체는 `subscription` 도메인이며 **이 문서의 확정 사항이 아니다** |

**🔶 미확정 — 확정 전에는 구현에 들어가지 않는다**

| # | 항목 | 제안값 | 근거 / 확정 조건 |
|---|---|---|---|
| 🔶-1 | **익명키 실환경 지속성** (재설치·기기 변경 후 동일 값인가) | “유지된다” 전제로 진행 | 공식 문구가 없고 커뮤니티에도 확답이 없다. **결제 소유권이 여기 걸려 있다.** 샌드박스는 mock 이라 무의미 → **mvp-v1 스파이크 6 (실환경 1회 확인) 결과가 이 도메인 전체의 전제** |
| 🔶-2 | 부트스트랩 엔드포인트 **경로·메서드·응답 스키마** | `POST /api/v1/auth/session` / `{newUser, verifiedAt}` | 프론트 계약이라 임의 확정 불가. 경로 prefix `/api/v1` 도 이번에 처음 정해지는 **공통 규약** |
| 🔶-3 | **재검증 주기** | 24시간 | 짧으면 외부 호출이 늘어 2초 기준을 위협하고, 길면 무효 익명키 통과 창이 커진다. verify 실측 지연이 나와야 정할 수 있다 |
| 🔶-4 | verify **장애 시 fail-open / fail-closed** (+ `AUTH_004` 신설 여부) | 기검증 익명키는 fail-open, 신규는 fail-closed | 신규를 열면 미검증 사용자가 생기고, 기존을 닫으면 토스 장애가 곧 전체 장애가 된다. **유료 서비스라 가용성 손실이 곧 환불 사유** — 사용자 판단 필요 |
| 🔶-5 | 익명키 **형식 규칙** (길이 상한·허용 문자) | 상한 256자 / 영숫자·`-_` | 실제 hash 형식을 확인해야 정할 수 있다. 스파이크 6 에서 함께 확인 |
| 🔶-6 | 로그 **마스킹 방식** | 앞 4자 + `***` | 추적 가능성과 노출 최소화의 절충. 운영 시 문의 대응 난이도로 결정 |
| 🔶-7 | 부트스트랩 응답에 **구독 상태를 합칠 것인가** | 합치지 않음(분리 유지) | 합치면 진입 왕복이 1회 준다. 대신 auth 가 결제를 알게 되어 모듈 경계가 깨진다. 진입 지연 실측 후 판단 |
| 🔶-8 | **공개 엔드포인트 범위** (솔루션 목록/상세를 헤더 없이 열 것인가) | 공개 | 결제 전 설득이 S2 에 전부 걸려 있으므로(쟁점 1) 열어두는 쪽이 자연스럽다. 다만 “전부 인증 필요”가 더 단순하다 |
| 🔶-9 | verify API 의 **mTLS 요구 여부** | 불필요 추정 | 토스가 명시한 mTLS 필수 목록에 verify 는 없으나 확답이 없다. **인증서 발급 리드타임이 개발보다 길다** → 확인이 늦으면 일정이 밀린다 |

> 🔶-1 과 🔶-9 는 **문서로 확정할 수 없는 항목**이다 — 실환경 확인(mvp-v1 §2 스파이크 6)이 선행되어야 한다.
