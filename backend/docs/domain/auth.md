# 익명키 인증 — 비즈니스 요구사항 설계서 (auth 도메인)

> **성격**: 토스 로그인 없이 `X-Anonymous-Key` **하나로** 전 구간 사용자를 식별한다.
> 진입 마찰 0 이 이 서비스의 판매 논리(“앱 설치·가입 없이 폰만으로”)이므로, 이 도메인의 목표는
> **인증을 강화하는 것이 아니라 인증을 보이지 않게 만드는 것**이다. 사용자에게 노출되는 화면이 없다.
> 비즈니스 요구사항: 2026-08-07 사용자 결정(§9-1) · 근거: [mvp-v1.md](../../../docs/planning/mvp-v1.md) 쟁점 4
> 관련: [toss-integration.md](../rule/toss-integration.md) · [error-handling.md](../rule/error-handling.md) · [architecture.md](../rule/architecture.md)
> 상태: **요구사항 초안 — §9-1 🔶 확정 필요**

> ⚠️ **이 프로젝트의 첫 도메인 문서다.** `backend/docs/domain/` 에 선례가 없고
> `docs/server/api-spec.md` 도 아직 없다. 따라서 여기서 정하는 경로 스타일·헤더 규약·인증 게이트는
> **이후 모든 도메인의 선례**가 된다. 그런 항목은 본문에 **[공통 승격 후보]** 로 표시했고,
> 확정 시 `docs/server/api-spec.md` 로 올려 다음 도메인이 링크만 하게 만든다(→ §10).

## 용어

| 용어 | 의미 |
|---|---|
| 익명키 (anonKey) | 클라 SDK `User.getAnonymousKey()` 가 반환하는 hash 문자열. 미니앱마다 고유하고, **같은 사용자는 같은 미니앱에서 항상 같은 값**을 받는다 |
| 식별됨 | 요청에 익명키가 실려 있어 요청 주체를 특정한 상태. **진위 확인도, 본인 확인도 아니다**(§4-1) |
| 세션 | 서버가 보관하는 세션이 아니다. 요청마다 헤더로만 식별되는 stateless 상태를 가리킨다 |
| 부트스트랩 | 미니앱 진입 직후 프론트가 1회 호출해 “이 익명키로 서비스를 쓸 수 있는 상태”를 만드는 절차 |
| verify | 토스 파트너 API `.../users/anon-key/verify`. **이 서비스는 쓰지 않기로 했다** — 기각 근거는 §4-3 |

## 1. 배경 · 목적

- 이 서비스의 핵심 약속은 **“앱 설치·가입 없이 폰만으로”** 다. 로그인 화면 하나가 그 약속을 깬다.
  2026-08-07 사용자 결정으로 **토스 로그인을 쓰지 않기로 확정**했고(쟁점 4), 그 결과 전 구간의
  사용자 식별이 익명키 하나에 걸린다.
- 그래서 이 도메인이 하는 일은 **“들어온 익명키를 사용자로 삼고, 필요한 곳에서 그 존재를 요구한다”**
  가 전부다. 진위 검증도 하지 않는다(§4-3). 인증을 얇게 유지하는 것이 이 도메인의 요구사항이다.
- ⚠️ **그 대가로 “익명키를 아는 사람 = 그 사용자” 가 된다.** 익명키가 새면 구독과 영상이 함께 샌다.
  이 리스크는 **막지 않고 감안한다**(2026-08-07 사용자 결정, §4-1). 로그인을 붙이지 않는 한
  어떤 서버 측 조치로도 막을 수 없기 때문이다 — 근거는 §4-3.

**핵심 훅은 없다.** 사용자에게 보이는 화면도, 사용자가 하는 행동도 없다. 성공한 인증은 아무것도
느껴지지 않아야 한다.

## 2. 범위 결정 — 무엇을 하고 / 안 하는가

| 구분 | 포함 | 내용 |
|---|---|---|
| 익명키 수신 | ✅ | 모든 요청의 `X-Anonymous-Key` 헤더를 읽어 요청 주체로 삼는다 |
| 사용자 등록 | ✅ | 처음 보는 익명키를 우리 서비스의 사용자로 등록(최초 1회, 멱등) |
| 인증 게이트 | ✅ | 엔드포인트별로 “익명키 필요/불필요”를 판정하고 미충족 시 차단 |
| 형식 사전 검증 | ✅ | 명백히 형식이 틀린 값 거부. **진위 검증을 안 하므로 유일하게 남은 입력 방어**다 |
| 익명키 로깅 정책 | ✅ | 로그·예외 메시지·응답 본문에 원문 노출 금지 |
| 부트스트랩 응답 내용 | ✅(계약) / ❌(구현) | 프론트가 진입 시 무엇을 받는지는 계약이라 여기서 정한다 |
| **토스 `verify` API 호출** | ❌ | **2026-08-07 사용자 결정으로 폐기.** 소유권을 증명하지 못해 실효가 없다 → **기각 근거 §4-3** |
| 토스 로그인 / `appLogin()` | ❌ | **사용하지 않음 확정(2026-08-07)**. 붙이는 것 자체가 별도 기획 결정 |
| 구독 상태 판정·결제 | ❌ | `subscription` 도메인 몫. auth 는 “누구인가”까지만 답한다 |
| 익명키 ↔ 주문 소유권 관리 | ❌ | `subscription` 도메인 몫 |
| 회원 탈퇴·데이터 삭제 | ❌ | 보관 정책(mvp-v1 쟁점 6)이 미확정이라 함께 미룬다 → §8 |
| 미니앱 재출시 시 익명키 이관 | ❌ | 발생 시점이 출시 이후 → §8. 단 리스크는 §4-6 에 명시 |
| rate limit · 남용 방지 | 🔶 | verify 를 뺀 지금 **위조 계정 대량 생성을 막는 유일한 수단**이다 → §9-1 🔶-7 |
| 관리자 인증 | ❌ | 관리자 화면 자체가 MVP 범위 밖 |
| 프론트의 SDK 호출·재시도 UI | ✅(계약만) | 에러별 프론트 행동은 §6 에 명시. 화면 문구는 프론트 재량 |

## 3. 기능 요구사항

| # | 요구 | 설명 |
|---|---|---|
| **U1** | 익명키 헤더 수신 | 모든 API 요청에서 `X-Anonymous-Key` 헤더를 읽어 요청 주체를 식별한다. 헤더가 없으면 “미식별 요청”으로 다룬다(즉시 401 이 아니다 — 판정은 U3) |
| **U2** | 사용자 등록 | 처음 등장한 익명키를 사용자로 등록한다. 이미 있으면 그대로 쓴다 — **멱등**하다. 같은 익명키로 몇 번을 호출해도 사용자는 하나다 |
| **U3** | 인증 게이트 | 엔드포인트를 **공개 / 인증 필요** 두 부류로 나누고, 인증 필요 엔드포인트는 익명키 없이는 거부한다(§4-2) |
| **U4** | 부트스트랩 API | 프론트가 진입 직후 1회 호출해 “쓸 수 있는 상태”를 확보한다. 응답으로 **신규/기존 여부**를 받아 온보딩 분기에 쓴다 |
| **U5** | 형식 사전 검증 | 공백·과도한 길이·허용 밖 문자를 거부한다. **외부 검증이 없으므로 이것이 유일한 입력 방어선**이다(§4-4) |
| **U6** | 익명키 비노출 | 로그·예외 메시지·에러 응답 본문에 익명키 원문을 남기지 않는다. 익명키를 아는 것이 곧 그 사용자가 되는 것이므로(§4-1), 노출 최소화가 **유일하게 실효 있는 보호 수단**이다 |

> **auth 도메인은 외부 API 를 호출하지 않는다.** 이 도메인의 처리 시간은 전적으로 우리 서버 안에서
> 끝나므로 검수 기준 “인터랙션 2초 이내”에 대해 auth 는 위험 요인이 아니다.

## 4. 비즈니스 규칙 (정책 상세)

### 4-1. 익명키의 신뢰 수준 — 무엇을 보장하고 무엇을 보장하지 않는가

| 질문 | 답 |
|---|---|
| 이 요청이 **어떤 사용자**의 것인가 | ⚠️ **자기 신고를 그대로 믿는다.** 익명키를 제시한 쪽을 그 사용자로 취급한다 |
| 그 사용자가 **누구인지**(실명·연락처) | ❌ 모른다. 알 필요도 없다 |
| 같은 사용자가 **기기를 바꿔도** 같은가 | ✅ 토스 계정 기준이므로 유지되는 것으로 본다 — **단 실환경 미검증**(§9-1 🔶-1) |
| 익명키가 **비밀**인가 | ❌ **아니다.** 식별자다. 그러나 우리 서비스에서는 **사실상 비밀번호처럼 동작한다**(아는 사람이 곧 그 사용자) |
| **미니앱을 새로 출시**해도 같은가 | ❌ **승계되지 않는다**(§4-6) |

**⚠️ 의도적으로 수용한 트레이드오프 (2026-08-07 사용자 결정)**

- 익명키가 유출되면 **타인이 그 사용자의 구독과 영상에 접근할 수 있다.** 이 도용을 **막지 않는다.**
- 근거: 로그인이 없는 이상 “제시자가 소유자인가”를 확인할 수단이 서버에 존재하지 않는다.
  토스의 `verify` 도 이것을 보장하지 않는다(§4-3). 즉 **막을 수 없는 것을 막는 척하지 않는다.**
- 노출 면적이 작다는 점이 실질적 완화책이다 — 익명키는 미니앱 웹뷰가 TLS 로만 전송하고
  화면에 표시되지 않는다. 그래서 **U6(비노출)이 이 도메인에서 가장 실효 있는 요구**가 된다.
- 현재 코드([AnonymousAuthentication.java](../../src/main/java/kang20/ytcreator/shared/security/AnonymousAuthentication.java))
  주석의 *“로그인이 필요한 기능은 `appLogin()` 경로를 별도로 둔다”* 는 이 결정 **이전**의 서술이다 → 갱신 대상(§10).

### 4-2. 인증 게이트 — 엔드포인트 분류 × 헤더 상태 [공통 승격 후보]

모든 엔드포인트는 아래 둘 중 하나에 속한다.
🔶 **기본값을 “인증 필요”로 둘지, 대상 목록은 무엇인지 모두 미확정**(§9-1 🔶-6).
아래 표의 분류는 제안값이다 — 현재 코드는 오히려 반대로
[SecurityConfig](../../src/main/java/kang20/ytcreator/config/SecurityConfig.java) 가 `anyRequest().permitAll()` 이다.

| 분류 | 대상(제안) | 헤더 없음 | 헤더 있음·형식 위반 | 헤더 있음·형식 정상 |
|---|---|---|---|---|
| **공개** | 헬스체크·솔루션 목록/상세 조회 🔶(§9-1 🔶-6) | 200 | 200 (익명키 무시) | 200 |
| **인증 필요** | 그 외 전부 (작업 생성·조회·구독 등) | **401 `AUTH_001`** | **401 `AUTH_002`** | 200 |

- **헤더가 없다고 필터가 즉시 401 을 내지 않는다.** 판정은 경로 규칙이 한다 —
  현재 [AnonymousKeyFilter](../../src/main/java/kang20/ytcreator/shared/security/AnonymousKeyFilter.java)
  가 이미 이 방식이며 이 문서는 그 동작을 요구로 확정한다.
- 401 두 종류를 **코드로 구분**하는 이유: 프론트의 행동이 다르다.
  `AUTH_001`(헤더 누락) → SDK 재호출, `AUTH_002`(형식 위반) → 재호출해도 소용없으므로 안내 후 종료.
- 403 `AUTH_003` 은 **auth 도메인이 쓰지 않는다.** “구독이 없어 못 쓴다”는 인가 판정은
  `subscription` 도메인의 책임이다. auth 는 신원까지만 답한다.

### 4-3. 기각 — 토스 `verify` API 를 쓰지 않는다 (2026-08-07 사용자 결정)

> 같은 논의가 반복되지 않도록 기각 근거를 남긴다.

**초안에서는 verify 를 “결제 소유권의 뿌리”로 두었으나, 그 전제가 틀렸다.**

- 토스 공식 답변: *“해당 API는 전달받은 hash 값이 토스에서 정상적으로 발급된 유효한 값인지를
  확인합니다. 다만, **해당 hash를 보낸 요청자가 실제 그 값의 소유자인지까지는 보장하지 않습니다.**”*
  ([커뮤니티 4506](https://techchat-apps-in-toss.toss.im/t/getanonymouskey-api/4506))
- 즉 verify 가 걸러내는 것은 **위조**(아무 문자열 지어내기)뿐이고, 실제 위협인 **도용**(진짜 익명키
  탈취)은 verify 를 그대로 통과한다. 우리가 감안하기로 한 리스크(§4-1)는 verify 유무와 무관하다.
- 위조를 막아서 얻는 것도 없다. 위조범이 얻는 것은 **구독이 없는 빈 계정**이라 공격 가치가 없다.
  남는 영향은 무의미한 사용자 레코드가 쌓이는 것뿐이며, 그것은 rate limit 의 몫이다(🔶-7).
- 공식 문서도 *“유효한 값인지 **미리 확인하려면**”* 이라는 선택 표현이고, 토스가 명시한
  **mTLS 필수 기능 목록(로그인·토스페이·인앱결제·스마트발송·프로모션)에 식별키 검증은 없다**
  ([인증 문서](https://developers-apps-in-toss.toss.im/documentation/api/auth)).

**폐기로 사라진 것** — 재검증 주기 정책, verify 장애 시 fail-open/closed 판단, 그에 딸린
503 에러 코드 신설, verify 용 mTLS 인증서 확인. **auth 도메인의 외부 의존이 0 이 된다.**

- ⚠️ **mTLS 인증서 자체는 여전히 필요하다** — 인앱결제가 요구한다. 다만 그것은
  `subscription` 도메인의 일정 리스크이지 auth 의 것이 아니다.
- ⚠️ **결제 소유권을 실제로 지키는 것은 결제 시점의 IAP 주문 검증**(서버→토스 주문 상태 조회)이다.
  auth 가 아니다 → [toss-integration.md](../rule/toss-integration.md) “인앱 결제(IAP) 검증”.

### 4-4. 형식 사전 검증 (U5)

| 항목 | 규칙 |
|---|---|
| 공백 / 빈 값 | 거부 — 헤더 없음과 동일 취급(`AUTH_001`) |
| 길이 상한 | 🔶 미확정(§9-1 🔶-3). 상한이 없으면 거대 헤더로 로그·메모리를 오염시킬 수 있다 |
| 허용 문자 | 🔶 미확정(§9-1 🔶-3) |

- 형식 위반은 즉시 `AUTH_002` 로 거부한다. **형식을 통과하면 그대로 신뢰한다** — 추가 검증은 없다.

### 4-5. 로깅 · 개인정보 (U6)

- 익명키 원문은 **로그·예외 메시지·에러 응답 본문 어디에도** 남기지 않는다.
- 추적이 필요하면 **마스킹된 형태**로만 남긴다. 마스킹 방식은 🔶(§9-1 🔶-4).
- 익명키는 그 자체로 개인을 특정하지 않지만, §4-1 대로 **아는 것이 곧 그 사용자가 되는 값**이다.
  취급 수준은 자격증명에 준한다.

### 4-6. ⚠️ 미니앱 재출시 = 익명키 단절 (수용한 리스크)

- 미니앱이 바뀌면 익명키는 **승계되지 않는다.** 앱을 새로 출시하는 순간 기존 사용자는
  전원 신규 사용자가 되고, **구독이 끊긴다.**
- MVP 에서는 **이관 기능을 만들지 않는다**(§8). 다만 이것이 “나중에 붙이면 되는 기능”이 아니라
  **재출시 전에 반드시 해결해야 하는 선행 조건**임을 여기 남긴다 —
  로그인이 없으므로 두 익명키를 잇는 단서가 우리에게 없다.

## 5. API 계약 (초안 — 확정 후 `docs/server/api-spec.md` 반영)

> `docs/server/api-spec.md` 는 **아직 존재하지 않는다.** 이 절이 그 문서의 첫 입주자가 된다(→ §10).

### 5-1. 공통 요청 헤더 [공통 승격 후보]

| 헤더 | 필수 | 값 |
|---|---|---|
| `X-Anonymous-Key` | 인증 필요 엔드포인트에서 필수 | SDK `User.getAnonymousKey()` 의 `hash` 값 |

- 헤더명은 **한 글자도 바뀌지 않는다** — 프론트 계약이며 현재 코드가 이미 이 이름을 쓴다.
- 공통 에러 응답 본문은 `{ "code": "...", "message": "..." }` 고정
  (→ [error-handling.md](../rule/error-handling.md)). auth 도 예외 없이 이 형식을 따른다.

### 5-2. 신규 — `POST /api/v1/auth/session` 🔶

> 🔶 경로·메서드·응답 스키마 **전부 미확정**(§9-1 🔶-2). 아래는 제안값이다.
> `POST` 인 이유: 최초 호출이 **사용자 등록이라는 상태 변화**를 일으키므로 `GET` 이 아니다.
> 다만 **멱등**하다(U2) — 몇 번 호출해도 사용자는 하나이고 응답도 같다.

**요청**

```
POST /api/v1/auth/session
X-Anonymous-Key: {hash}
(본문 없음)
```

**응답 200**

```json
{
  "newUser": true,
  "registeredAt": "2026-08-07T12:34:56Z"
}
```

| 필드 | 의미 | 프론트 용도 |
|---|---|---|
| `newUser` | 이번 호출로 처음 등록되었는가 | 온보딩/튜토리얼 노출 분기 |
| `registeredAt` | 이 사용자가 처음 등록된 시각 | 디버깅·문의 대응 |

- **구독 상태는 이 응답에 넣지 않는다** — `subscription` 도메인의 책임이고, 섞으면 auth 가
  결제를 알게 되어 모듈 경계가 무너진다(→ [architecture.md](../rule/architecture.md)).
  🔶 프론트 왕복 1회를 줄이려 합치자는 논의는 가능하다(§9-1 🔶-5).
- **에러 응답에 익명키를 되돌려주지 않는다**(U6).

### 5-3. 인증 필요 엔드포인트 전반 [공통 승격 후보]

auth 도메인은 자기 엔드포인트 외에 **다른 모든 도메인의 요청 앞단**에 게이트로 존재한다.
각 도메인 문서는 엔드포인트마다 “공개 / 인증 필요”만 명시하면 되고, 401 응답 규격은 §4-2 를 링크한다.

## 6. API 호출 흐름 (프론트 ↔ 백엔드)

### 6-1. 최초 진입 — 부트스트랩

```
[미니앱 진입]
 → 프론트: SDK User.getAnonymousKey()
    ├─ 실패 / 미지원 환경 → 서비스 이용 불가 안내 후 종료 (서버 호출 없음)
    └─ 성공 { type:'HASH', hash }
        → POST /api/v1/auth/session   (X-Anonymous-Key: hash)
           ├─ 200 { newUser:true }  → 온보딩 노출 → 솔루션 목록(S1)
           ├─ 200 { newUser:false } → 바로 솔루션 목록(S1)
           ├─ 401 AUTH_001 (헤더 누락)
           │     → 프론트 버그. SDK 재호출 1회 → 그래도 실패면 오류 안내 후 종료
           ├─ 401 AUTH_002 (형식 위반)
           │     → 재시도해도 결과가 같다. "이용할 수 없는 환경" 안내 후 종료
           └─ 500 COMMON_002 (우리 서버 오류)
                 → 백오프 재시도 + "잠시 후 다시" 안내. 종료시키지 않는다
```

### 6-2. 일반 API 요청 (인증 필요 엔드포인트)

```
[임의 화면에서 보호 자원 요청]
 → METHOD /api/v1/{...}   (X-Anonymous-Key: hash)
    ├─ 200 → 정상 렌더링
    ├─ 401 AUTH_001 → 헤더가 빠졌다. 부트스트랩(6-1) 재실행 후 1회 재시도
    ├─ 401 AUTH_002 → 형식이 깨진 값이 실렸다. 부트스트랩 재실행
    │                 → 거기서도 실패면 안내 후 종료
    └─ 500 COMMON_002 → 백오프 재시도. 진행 중 작업이 있으면 상태를 잃지 않게 유지
```

- **프론트 책임**: 401 을 받았을 때 **자동으로 부트스트랩을 한 번만** 재실행한다.
  무한 재시도 루프는 금지 — 형식 위반은 재시도로 풀리지 않는다.
- ⚠️ **401 은 “도용 감지”가 아니다.** 우리는 도용을 감지하지 않는다(§4-1).
  프론트도 그런 안내 문구를 쓰지 않는다.

### 6-3. 공개 엔드포인트 (헤더 없이 접근)

```
[솔루션 목록/상세 — 결제 전 열람] 🔶 공개 여부 미확정(§9-1 🔶-6)
 → GET /api/v1/{...}   (헤더 없어도 됨)
    ├─ 200 → 렌더링
    ├─ 헤더가 붙어 있어도 형식 검증조차 하지 않고 무시한다
    └─ 500 COMMON_002 → 백오프 재시도
```

## 8. 백로그 (이번 범위 제외)

| 항목 | 미루는 이유 |
|---|---|
| 미니앱 재출시 시 익명키 이관 | 재출시 시점 문제. 단 **재출시 전 필수 선행 조건**(§4-6) |
| 회원 탈퇴 · 데이터 삭제 요청 | 보관 정책(mvp-v1 쟁점 6)이 미확정이라 함께 미룬다 |

| 토스 로그인 연동(`appLogin()`) | 사용하지 않기로 확정. 붙이려면 기획 결정부터 |
| 토스 `verify` API 도입 | **기각(§4-3).** 되살리려면 그 근거부터 뒤집어야 한다 |
| 관리자 인증 체계 | 관리자 화면 자체가 MVP 밖 |
| 다중 기기 동시 사용 정책 | 계정 기준이라 자연히 공유된다. 제한할 이유가 아직 없다 |

## 9. 결정 · 변경 이력

### 9-1. 결정 이력

> **확정 완료 (사용자 결정)**
> - (08-07) **토스 로그인을 사용하지 않는다.** 전 구간 익명키 단일 식별 — mvp-v1 쟁점 4
> - (08-07) **토스 `verify` API 를 쓰지 않는다.** 소유권을 증명하지 못해 실효가 없다 — 기각 근거 §4-3
> - (08-07) **익명키 도용 리스크를 막지 않고 감안한다.** 로그인 없이는 막을 수단이 없다 — §4-1

**따라오는 전제 (플랫폼 문서·기존 규칙 근거 — 사용자 결정 아님)**

| 전제 | 출처 | 확신도 |
|---|---|---|
| 익명키는 **토스 계정 기준**이라 기기 변경·재설치에도 유지된다 | 토스 블로그(“같은 사용자는 항상 같은 값”), mvp-v1 1-5 | ⚠️ **실환경 미검증** — 🔶-1 로 남는다. “기기 변경·재설치”를 명시한 공식 문구는 없다 |
| 구독 소유권은 **우리 서버가 보관하는 익명키↔주문 매핑**이 정본 | [toss-integration.md](../rule/toss-integration.md) “자동갱신 구독”, mvp-v1 1-5 | 기존 규칙 문서에 이미 있음. 관리 주체는 `subscription` 도메인이며 **이 문서의 확정 사항이 아니다** |
| 결제 소유권의 실질적 방어는 **IAP 주문 검증**(서버→토스, mTLS) | [toss-integration.md](../rule/toss-integration.md) “인앱 결제(IAP) 검증” | 기존 규칙 문서에 이미 있음. `subscription` 도메인 몫 |

**🔶 미확정 — 확정 전에는 구현에 들어가지 않는다**

| # | 항목 | 제안값 | 근거 / 확정 조건 |
|---|---|---|---|
| 🔶-1 | **익명키 실환경 지속성** (재설치·기기 변경 후 동일 값인가) | “유지된다” 전제로 진행 | 공식 문구가 없고 커뮤니티에도 확답이 없다. **결제 소유권이 여기 걸려 있다.** 샌드박스는 mock 이라 무의미 → **mvp-v1 스파이크 6 (실환경 1회 확인) 결과가 이 도메인 전체의 전제**. verify 를 뺐으므로 이제 **유일하게 남은 외부 불확실성**이다 |
| 🔶-2 | 부트스트랩 엔드포인트 **경로·메서드·응답 스키마** | `POST /api/v1/auth/session` / `{newUser, registeredAt}` | 프론트 계약이라 임의 확정 불가. 경로 prefix `/api/v1` 도 이번에 처음 정해지는 **공통 규약** |
| 🔶-3 | 익명키 **형식 규칙** (길이 상한·허용 문자) | 상한 256자 / 영숫자·`-_` | 실제 hash 형식을 봐야 정할 수 있다(스파이크 6 에서 함께 확인). **진위 검증을 뺐으므로 이 규칙이 유일한 입력 방어선**이라 초안보다 중요도가 올라갔다 |
| 🔶-4 | 로그 **마스킹 방식** | 앞 4자 + `***` | 추적 가능성과 노출 최소화의 절충. 운영 시 문의 대응 난이도로 결정 |
| 🔶-5 | 부트스트랩 응답에 **구독 상태를 합칠 것인가** | 합치지 않음(분리 유지) | 합치면 진입 왕복이 1회 준다. 대신 auth 가 결제를 알게 되어 모듈 경계가 깨진다. 진입 지연 실측 후 판단 |
| 🔶-6 | **인증 게이트 기본값 + 공개 엔드포인트 범위** — ⓐ 기본값을 “인증 필요”로 두고 공개를 열거할지, 아니면 반대로 할지 ⓑ 솔루션 목록/상세를 헤더 없이 열지 | ⓐ 기본값 “인증 필요” ⓑ 솔루션 목록/상세는 공개 | ⓐ 는 표준 보안 관행이지만 **이 레포의 기존 관행은 아니다** — 현재 `SecurityConfig` 는 `anyRequest().permitAll()` 이다. 게다가 [공통 승격 후보]라 이후 모든 도메인의 게이트 정책이 된다. ⓑ 는 결제 전 설득이 S2 에 전부 걸려 있어(쟁점 1) 여는 쪽이 자연스럽지만, “전부 인증 필요”가 더 단순하다 |
| 🔶-7 | **위조 익명키 대량 생성 방어(rate limit)를 MVP 에 넣을 것인가** | MVP 제외, 출시 후 모니터링 | verify 를 뺀 지금 아무 문자열로도 사용자가 생긴다. 다만 위조범이 얻는 것은 빈 계정뿐이라 **피해가 저장 공간에 그친다.** 트래픽이 없는 출시 시점에 미리 넣는 것은 이르다고 본다 — **사용자 판단 필요** |

> 🔶-1 과 🔶-3 은 **문서로 확정할 수 없다** — 실환경 확인(mvp-v1 §2 스파이크 6)이 선행되어야 한다.

### 9-2. 버전 이력

v1 확정 전이므로 없음.

> 초안 단계의 수정은 버전이 아니다(→ [versioning.md](../../../.claude/skills/usecase/references/versioning.md)).
> `verify` 폐기(08-07)로 초안의 U2·U6·U7(verify·재검증·장애 대응)과 🔶 3건이 사라졌고 요구 번호를
> U1~U6 으로 다시 매겼다. **이전 초안은 커밋 `f196871` 에 보존되어 있다.**
