# 익명키 인증 — 비즈니스 요구사항 설계서 (auth 도메인)

> **성격**: 토스 로그인 없이 `X-Anonymous-Key` **하나로** 전 구간 사용자를 식별한다.
> 진입 마찰 0 이 이 서비스의 판매 논리(“앱 설치·가입 없이 폰만으로”)이므로, 이 도메인의 목표는
> **인증을 강화하는 것이 아니라 인증을 보이지 않게 만드는 것**이다. 사용자에게 노출되는 화면이 없다.
> 비즈니스 요구사항: 2026-08-07 사용자 결정(§9-1) · 근거: [mvp-v1.md](../../../docs/planning/mvp-v1.md) 쟁점 4
> 관련: [toss-integration.md](../rule/toss-integration.md) · [error-handling.md](../rule/error-handling.md) · [architecture.md](../rule/architecture.md)
> 상태: **v5 확정 (2026-08-13) — 변경분 §9-2** · 단 §9-1 🔶-3(익명키 형식 규격) 1건은 **사용자 지시로 보류**.
> 설계 착수를 막지 않는다(사유는 🔶-3 행 참조).
> → 설계: [auth-design.md](./auth-design.md)
> **v5 변경 요지 (권한 도입 — 사용자 결정 08-13)**:
> ⓐ 사용자에게 **권한(Role) 이 생긴다 — `USER` / `ADMIN` 둘뿐**(§4-8)
> ⓑ 권한은 **access 토큰의 `role` 클레임**에 실린다 — 매 요청 DB 조회 0회(U8)를 지키기 위해서다
> ⓒ **`ADMIN` ⊃ `USER`** — 계층을 명시한다(운영자가 일반 기능에서 403 을 맞지 않는다)
> ⓓ 운영자 전용 경로 **`/api/v1/admin/**`** 신설(경로 규칙 축) · 권한 부족은 **403 `AUTH_003`**
> ⓔ **승격 API 는 만들지 않는다** — 운영자 부여는 DB 직접 변경이 유일한 경로다
> **v4 변경 요지 (JWT 전환 — 사용자 결정 08-12, 추천값 5건 전부 채택)**:
> ⓐ 익명키 제시는 **부트스트랩(=로그인) 1회**로 줄고, 이후 전 API 는 **`Authorization: Bearer {access}`**
> ⓑ access = JWT(`userId` claim · 30분 · HS256+환경변수 키) — **매 요청 DB 조회 0회**
> ⓒ refresh = 불투명 랜덤값(14일 · **MySQL 에 SHA-256 해시로 저장** · 회전식 · 재사용 감지 시 전체 폐기)
> ⓓ 신규 `POST /api/v1/auth/refresh` — **auth 가 처음으로 HTTP 엔드포인트를 갖는다**(§5-3 번복)
> ⓔ 구 헤더 병행 없음 — 프론트 미구현이라 단절 비용 0
> **v3 변경 요지**: payment 도메인 확정([payment.md](./payment.md) v1)에 따라 ⓐ §4-2 공개 목록에
> **웹훅·상품 조회 경로** 추가 ⓑ §5-2 부트스트랩 응답의 이용권 객체를 **payment.md §5-3 스키마로 확정**
> ⓒ 상대 도메인 이름 `subscription` → **`payment`** (응답 JSON 의 `"subscription"` 키는 그대로 — ⓑ의 정본이 유지)

> ⚠️ **이 프로젝트의 첫 도메인 문서다.** `backend/docs/domain/` 에 선례가 없고
> `docs/server/api-spec.md` 도 아직 없다. 따라서 여기서 정하는 경로 스타일·헤더 규약·인증 게이트는
> **이후 모든 도메인의 선례**가 된다. 그런 항목은 본문에 **[공통 승격 후보]** 로 표시했고,
> 확정 시 `docs/server/api-spec.md` 로 올려 다음 도메인이 링크만 하게 만든다(→ §10).

## 용어

| 용어 | 의미 |
|---|---|
| 익명키 (anonKey) | 클라 SDK `User.getAnonymousKey()` 가 반환하는 hash 문자열. 미니앱마다 고유하고, **같은 사용자는 같은 미니앱에서 항상 같은 값**을 받는다 |
| 식별됨 | 요청에 익명키가 실려 있어 요청 주체를 특정한 상태. **진위 확인도, 본인 확인도 아니다**(§4-1) |
| 세션 | 서버가 보관하는 세션이 아니다. 요청마다 헤더로만 식별되는 stateless 상태를 가리킨다 |
| 부트스트랩 | 미니앱 진입 직후 프론트가 1회 호출해 “쓸 수 있는 상태”를 만드는 절차. **HTTP 엔드포인트의 주인은 auth 가 아니라 집계 모듈**이다(§5-2) |
| 집계 모듈 | 부트스트랩 응답을 만들기 위해 `auth` 와 `payment` 를 **불러다 합치기만** 하는 모듈. 자기 도메인 규칙을 갖지 않는다(§4-7) |
| 권한 (Role) | 사용자가 무엇을 할 수 있는지. `USER`(기본) / `ADMIN`(운영자) 둘뿐이다 — §4-8. **신원(누구인가)과 다른 축**이다 |
| verify | 토스 파트너 API `.../users/anon-key/verify`. **이 서비스는 쓰지 않기로 했다** — 기각 근거는 §4-3 |

## 1. 배경 · 목적

- 이 서비스의 핵심 약속은 **“앱 설치·가입 없이 폰만으로”** 다. 로그인 화면 하나가 그 약속을 깬다.
  2026-08-07 사용자 결정으로 **토스 로그인을 쓰지 않기로 확정**했고(쟁점 4), 그 결과 전 구간의
  사용자 식별이 익명키 하나에 걸린다.
- 그래서 이 도메인이 하는 일은 **“들어온 익명키를 사용자로 삼고, 필요한 곳에서 그 존재를 요구한다”**
  가 전부다. 진위 검증도 하지 않는다(§4-3). 인증을 얇게 유지하는 것이 이 도메인의 요구사항이다.
- ⚠️ **그 대가로 “익명키를 아는 사람 = 그 사용자” 가 된다.** 익명키가 새면 구독과 영상이 함께 샌다.
  이 리스크는 **막지 않고 감안한다**(2026-08-07 사용자 결정, §4-1). 로그인을 붙이지 않는 한
  어떤 서버 측 조치로도 막을 수 없기 때문이다 — 근거는 §4-3.

**핵심 훅은 없다.** 사용자에게 보이는 화면도, 사용자가 하는 행동도 없다. 성공한 인증은 아무것도
느껴지지 않아야 한다.

## 3. 기능 요구사항

| # | 요구 | 설명 |
|---|---|---|
| **U1** | 익명키 헤더 수신 | 모든 API 요청에서 `X-Anonymous-Key` 헤더를 읽어 요청 주체를 식별한다. 헤더가 없으면 “미식별 요청”으로 다룬다(즉시 401 이 아니다 — 판정은 U3) |
| **U2** | 사용자 등록 | 처음 등장한 익명키를 사용자로 등록한다. 이미 있으면 그대로 쓴다 — **멱등**하다. 같은 익명키로 몇 번을 호출해도 사용자는 하나다 |
| **U3** | 인증 게이트 | 엔드포인트를 **공개 / 인증 필요** 두 부류로 나누고, 인증 필요 엔드포인트는 익명키 없이는 거부한다(§4-2) |
| **U4** | 등록·식별의 모듈 공개 API 제공 | 집계 모듈이 부트스트랩 응답을 조립할 수 있도록 “등록하고 신규 여부를 돌려주는” 기능을 **모듈 공개 API 로** 노출한다. **HTTP 엔드포인트는 만들지 않는다**(§4-7) |
| **U5** | 형식 사전 검증 | 공백·과도한 길이·허용 밖 문자를 거부한다. **외부 검증이 없으므로 이것이 유일한 입력 방어선**이다(§4-4) |
| **U6** | 익명키 비노출 | 로그·예외 메시지·에러 응답 본문에 익명키 원문을 남기지 않는다. **(v4 강화)** 익명키가 네트워크에 실리는 것 자체가 부트스트랩 1회로 준다 |
| **U7 (v4)** | 토큰 발급 | 부트스트랩 성공 시 access(JWT, `userId` claim, 30분)와 refresh(불투명, 14일)를 발급한다. **부트스트랩이 곧 로그인이다** — 별도 로그인 화면·API 없음 |
| **U8 (v4)** | 토큰 게이트 | 인증 필요 엔드포인트는 `Authorization: Bearer {access}` 를 **서명·만료 검증만으로**(DB 조회 없이) 통과시키고 `userId` 를 요청 주체로 삼는다 |
| **U9 (v4)** | 갱신·회전·재사용 감지 | refresh 제출 시 **구 토큰을 폐기하고 새 쌍을 발급**한다(회전). 폐기된 refresh 가 다시 제출되면 **그 사용자의 refresh 전부를 폐기**한다 — 탈취 신호로 간주. 익명키 재로그인이 가능하므로 사용자 피해가 없다 |
| **U10 (v4)** | refresh 비노출 저장 | refresh 원문을 저장하지 않는다 — **SHA-256 해시만** MySQL 에 남긴다(U6 와 같은 규율) |

> **auth 도메인은 외부 API 를 호출하지 않는다.** 이 도메인의 처리 시간은 전적으로 우리 서버 안에서
> 끝나므로 검수 기준 “인터랙션 2초 이내”에 대해 auth 는 위험 요인이 아니다.

## 4. 비즈니스 규칙 (정책 상세)

### 4-1. 익명키의 신뢰 수준 — 무엇을 보장하고 무엇을 보장하지 않는가

| 질문 | 답 |
|---|---|
| 이 요청이 **어떤 사용자**의 것인가 | ⚠️ **자기 신고를 그대로 믿는다.** 익명키를 제시한 쪽을 그 사용자로 취급한다 |
| 그 사용자가 **누구인지**(실명·연락처) | ❌ 모른다. 알 필요도 없다 |
| 같은 사용자가 **기기를 바꿔도** 같은가 | ✅ 토스 계정 기준이므로 유지되는 것으로 본다 — **단 실환경 미검증**(§9-1 확정 ⑤) |
| 익명키가 **비밀**인가 | ❌ **아니다.** 식별자다. 그러나 우리 서비스에서는 **사실상 비밀번호처럼 동작한다**(아는 사람이 곧 그 사용자) |
| **미니앱을 새로 출시**해도 같은가 | ❌ **승계되지 않는다**(§4-6) |

**⚠️ 의도적으로 수용한 트레이드오프 (2026-08-07 사용자 결정)**

- 익명키가 유출되면 **타인이 그 사용자의 구독과 영상에 접근할 수 있다.** 이 도용을 **막지 않는다.**
- 근거: 로그인이 없는 이상 “제시자가 소유자인가”를 확인할 수단이 서버에 존재하지 않는다.
  토스의 `verify` 도 이것을 보장하지 않는다(§4-3). 즉 **막을 수 없는 것을 막는 척하지 않는다.**
- 노출 면적이 작다는 점이 실질적 완화책이다 — 익명키는 미니앱 웹뷰가 TLS 로만 전송하고
  화면에 표시되지 않는다. 그래서 **U6(비노출)이 이 도메인에서 가장 실효 있는 요구**가 된다.
- 현재 코드([AnonymousAuthentication.java](../../src/main/java/kang20/ytcreator/shared/security/AnonymousAuthentication.java))
  주석의 *“로그인이 필요한 기능은 `appLogin()` 경로를 별도로 둔다”* 는 이 결정 **이전**의 서술이다 → 갱신 대상(§10).

### 4-2. 인증 게이트 — 엔드포인트 분류 × 헤더 상태 [공통 승격 후보]

**기본값은 “인증 필요”** 이며, 공개는 명시적으로 열거한다(2026-08-07 확정).

**(v4) 게이트의 자격 증명이 익명키에서 access 토큰으로 바뀐다.** 익명키를 받는 곳은
부트스트랩과 `auth/refresh` 뿐이다.

| 분류 | 대상 | 자격 증명 없음 | 무효(서명·형식) | 만료 | 정상 |
|---|---|---|---|---|---|
| **공개** | ~~헬스체크~~ → **운영 엔드포인트 전체 `/actuator/**` (v2)** · 솔루션 목록/상세 조회 · 부트스트랩(§5-2) · **`POST /api/v1/auth/refresh` (v4)** · **상품 조회 `GET /api/v1/payments/products` (v3)** · **토스 웹훅 `/api/v1/webhooks/toss/**` (v3)** | 200 | 200 (무시) | 200 | 200 |
| **인증 필요** | 그 외 전부 — `Authorization: Bearer {access}` | **401 `AUTH_001`** | **401 `AUTH_002`** | **401 `AUTH_004` (v4)** | 200 |
| **운영자 전용 (v5)** | `/api/v1/admin/**` — `Authorization: Bearer {access}` + `role=ADMIN` | **401 `AUTH_001`** | **401 `AUTH_002`** | **401 `AUTH_004`** | `ADMIN` 200 / `USER` **403 `AUTH_003`** |
| **CORS preflight (v2)** | 모든 경로의 `OPTIONS` preflight | **게이트를 거치지 않는다** | 〃 | 〃 | 〃 |

- **(v4) 만료를 별도 코드로 가르는 이유**: 프론트 행동이 다르다 — `AUTH_004`(만료) → **refresh 후 1회 재시도**,
  `AUTH_002`(무효) → 재시도 무익, **부트스트랩 재로그인**. 만료가 `AUTH_002` 에 섞이면
  30분마다 전 사용자가 재로그인하게 된다.
- **(v4) 검증은 서명·만료뿐이다 — DB 를 보지 않는다.** 사용자 존재·상태 확인 없음. 그 대가로
  **강제 폐기가 access 수명(30분)만큼 지연**된다 — 수용한다(밴·차단 기능 자체가 MVP 밖).

- ⚠️ **현재 코드는 아직 반대다** — [SecurityConfig](../../src/main/java/kang20/ytcreator/config/SecurityConfig.java) 가
  `anyRequest().permitAll()` 이다. 이 확정은 **기존 코드를 바꾸는 결정**이며 설계·구현에서 반영해야 한다.
- **헤더가 없다고 필터가 즉시 401 을 내지 않는다.** 판정은 경로 규칙이 한다 —
  현재 [AnonymousKeyFilter](../../src/main/java/kang20/ytcreator/shared/security/AnonymousKeyFilter.java)
  가 이미 이 방식이며 이 문서는 그 동작을 요구로 확정한다.
- 401 두 종류를 **코드로 구분**하는 이유: 프론트의 행동이 다르다.
  `AUTH_001`(헤더 누락) → SDK 재호출, `AUTH_002`(형식 위반) → 재호출해도 소용없으므로 안내 후 종료.
- **부트스트랩이 “공개”인 이유**: 부트스트랩은 익명키를 **처음 등록시키는** 호출이라, 등록을 요구하는
  게이트 뒤에 두면 최초 사용자가 영원히 통과하지 못한다. 다만 **익명키 헤더 자체는 필수**다 —
  없으면 등록할 대상이 없으므로 `AUTH_001` 로 거부한다(§6-1).
- **`/actuator/**` 를 여는 이유 (v2)**: 운영 수집 경로는 **네트워크로 막도록 이미 설계돼 있다** —
  외부는 Caddy 가 403 으로 차단하고, 수집은 모니터링 서버의 SSH 역터널(루프백)로만 들어온다.
  익명키 게이트는 **사용자 요청을 위한 장치이지 운영 수집 경로를 위한 장치가 아니다.**
  ⚠️ 초안대로 헬스체크만 열면 **Prometheus 스크레이프가 전부 401 이 되어 Grafana 알림이 조용히 멎는다**
  (구현 라운드 1 실측). 인증 없이 열리는 표면이 넓어지는 것은 **의도적으로 수용**한다.
- **preflight 가 게이트를 거치지 않는 이유 (v2)**: 브라우저는 preflight 에 커스텀 헤더
  `X-Anonymous-Key` 를 **싣지 않는다.** 원리상 인증될 수 없으므로 게이트에 걸면 크로스 오리진 호출이
  전부 막힌다. **경로가 아니라 메서드 축의 예외**라 공개 경로 열거로는 해결되지 않는다.
- **웹훅이 "공개"인 이유 (v3)**: 발신자가 토스 서버라 `X-Anonymous-Key` 를 실을 수 없다 —
  익명키 게이트는 **사용자 요청을 위한 장치**다(actuator 를 연 것과 같은 논리).
  ⚠️ **무방비가 아니다** — 진위 검증(Basic Auth)은 `payment` 모듈이 수행한다(payment.md U11).
- **상품 조회가 "공개"인 이유 (v3)**: 결제 전 설득 화면의 데이터다 — 결제하려는 API 가
  결제·등록을 요구할 수 없다(payment.md §4-10).
- **(v5) 403 `AUTH_003` 은 이제 auth 도 쓴다** — “권한이 모자라다”(§4-8)가 그 축이다.
  ~~auth 도메인이 쓰지 않는다~~ 는 v4 까지의 서술이다.
  단 **“이용권이 없어 못 쓴다”는 여전히 payment 몫**(`PAY_001`·`PAY_007`)이다 — 세 403 은 프론트
  행동이 전부 다르다: `AUTH_003`(안내 후 종료·재시도 무익) / `PAY_001`(결제 유도) / `PAY_007`(recheck).

### 4-3. 기각 — 토스 `verify` API 를 쓰지 않는다 (2026-08-07 사용자 결정)

> 같은 논의가 반복되지 않도록 기각 근거를 남긴다.

**초안에서는 verify 를 “결제 소유권의 뿌리”로 두었으나, 그 전제가 틀렸다.**

- 토스 공식 답변: *“해당 API는 전달받은 hash 값이 토스에서 정상적으로 발급된 유효한 값인지를
  확인합니다. 다만, **해당 hash를 보낸 요청자가 실제 그 값의 소유자인지까지는 보장하지 않습니다.**”*
  ([커뮤니티 4506](https://techchat-apps-in-toss.toss.im/t/getanonymouskey-api/4506))
- 즉 verify 가 걸러내는 것은 **위조**(아무 문자열 지어내기)뿐이고, 실제 위협인 **도용**(진짜 익명키
  탈취)은 verify 를 그대로 통과한다. 우리가 감안하기로 한 리스크(§4-1)는 verify 유무와 무관하다.
- 위조를 막아서 얻는 것도 없다. 위조범이 얻는 것은 **구독이 없는 빈 계정**이라 공격 가치가 없다.
  남는 영향은 무의미한 사용자 레코드가 쌓이는 것뿐이며, 그것은 rate limit 의 몫이다(MVP 제외, §8).
- 공식 문서도 *“유효한 값인지 **미리 확인하려면**”* 이라는 선택 표현이고, 토스가 명시한
  **mTLS 필수 기능 목록(로그인·토스페이·인앱결제·스마트발송·프로모션)에 식별키 검증은 없다**
  ([인증 문서](https://developers-apps-in-toss.toss.im/documentation/api/auth)).

**폐기로 사라진 것** — 재검증 주기 정책, verify 장애 시 fail-open/closed 판단, 그에 딸린
503 에러 코드 신설, verify 용 mTLS 인증서 확인. **auth 도메인의 외부 의존이 0 이 된다.**

- ⚠️ **mTLS 인증서 자체는 여전히 필요하다** — 인앱결제가 요구한다. 다만 그것은
  `payment` 도메인의 일정 리스크이지 auth 의 것이 아니다.
- ⚠️ **결제 소유권을 실제로 지키는 것은 결제 시점의 IAP 주문 검증**(서버→토스 주문 상태 조회)이다.
  auth 가 아니다 → [toss-integration.md](../rule/toss-integration.md) “인앱 결제(IAP) 검증”.

### 4-4. 형식 사전 검증 (U5)

| 항목 | 규칙 |
|---|---|
| 공백 / 빈 값 | 거부 — 헤더 없음과 동일 취급(`AUTH_001`) |
| 길이 상한 | 🔶 **보류**(§9-1 🔶-3) — 규격을 아직 제안하지 않는다 |
| 허용 문자 | 🔶 **보류**(§9-1 🔶-3) |

- 형식 위반은 즉시 `AUTH_002` 로 거부한다. **형식을 통과하면 그대로 신뢰한다** — 추가 검증은 없다.
- **검증이 존재한다는 것은 확정**이고, 보류된 것은 **구체 수치뿐**이다. 설계는 “형식 검증 지점이
  하나 있다”는 사실만으로 진행할 수 있다(수치는 상수 하나).

### 4-5. 로깅 · 개인정보 (U6)

- 익명키 원문은 **로그·예외 메시지·에러 응답 본문 어디에도** 남기지 않는다.
- 추적이 필요할 때는 **앞 4자 + `***`** 형태로만 남긴다(2026-08-07 확정).
- 익명키는 그 자체로 개인을 특정하지 않지만, §4-1 대로 **아는 것이 곧 그 사용자가 되는 값**이다.
  취급 수준은 자격증명에 준한다.

### 4-6. ⚠️ 미니앱 재출시 = 익명키 단절 (수용한 리스크)

- 미니앱이 바뀌면 익명키는 **승계되지 않는다.** 앱을 새로 출시하는 순간 기존 사용자는
  전원 신규 사용자가 되고, **구독이 끊긴다.**
- MVP 에서는 **이관 기능을 만들지 않는다**(§8). 다만 이것이 “나중에 붙이면 되는 기능”이 아니라
  **재출시 전에 반드시 해결해야 하는 선행 조건**임을 여기 남긴다 —
  로그인이 없으므로 두 익명키를 잇는 단서가 우리에게 없다.

### 4-7. 부트스트랩을 집계 모듈이 소유한다 (2026-08-07 안 ⓒ 확정)

**결정**: 진입 시 프론트가 필요로 하는 “나는 누구인가 + 쓸 수 있는가”를 **한 번의 호출**로 주되,
그 응답을 만드는 주체는 `auth` 도 `payment` 도 아닌 **제3의 집계 모듈**이다.

```
POST /api/v1/bootstrap  ──▶ [집계 모듈]  ──▶ auth    : 등록·식별 (U4)
                                        └─▶ payment : 이용권 상태
```

**왜 auth 에 합치지 않는가**

- `auth` 는 **모든 요청이 지나가는 최하부 모듈**이다. 여기가 결제를 알게 되면, 이후 다른 도메인이
  진입 시 뭔가를 더 필요로 할 때마다 같은 논리로 `auth` 에 얹혀 `auth` 가 서서히 “홈 화면 API”가 된다.
- `payment` 가 사용자를 참조하는 방식에 따라 `auth ↔ payment` **순환 의존**이 생길 수 있고,
  그러면 `ModularityTest` 가 실제로 실패한다(→ [architecture.md](../rule/architecture.md)).
  집계 모듈은 **한 방향으로만** 두 모듈을 참조하므로 순환이 생기지 않는다.
  **(v3 확정)** `payment` 는 auth 가 노출한 **타입화된 기본키 `UserId`** 를 참조한다 —
  `payment → auth` 단방향이라 예상대로 순환이 없다(architecture.md "타입화된 기본키").
- ⚠️ **되돌리기 비용의 비대칭**이 결정 근거다. 분리해 두었다가 나중에 합치는 것은 엔드포인트 추가로
  끝나지만, 합쳐 두었다가 떼는 것은 **프론트가 이미 쓰는 계약을 깨는 일**이다.

**집계 모듈의 제약**

- **자기 도메인 규칙을 갖지 않는다.** 두 모듈의 공개 API 를 부르고 응답을 합치기만 한다.
  판단·검증·저장이 생기면 그건 집계가 아니라 새 도메인이므로 별도 문서가 필요하다.
- `auth` 와 `payment` 는 집계 모듈의 존재를 **모른다**. 의존은 집계 → 도메인 한 방향뿐이다.

### 4-8. 권한 모델 (v5 — 2026-08-13 사용자 결정)

**`USER` 와 `ADMIN` 둘뿐이다.** 모더레이터·읽기 전용 같은 중간 등급은 만들지 않는다 —
쓰이지 않는 분기만 남는다. 필요해지면 그때 값을 추가한다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 기본값 | **모든 신규 사용자는 `USER`** | 익명키만으로 등록되므로 승격의 근거가 될 정보가 없다 |
| 저장 위치 | `users.role` (문자열) | 사용자 속성이지 세션 속성이 아니다 |
| 요청당 판정 근거 | **access 토큰의 `role` 클레임** | U8(매 요청 DB 조회 0회)을 지키려면 서명된 값이어야 한다 |
| 계층 | **`ADMIN` ⊃ `USER`** — 운영자는 일반 기능을 전부 쓸 수 있다 | 계층이 없으면 일반 기능을 `USER` 로 막는 순간 운영자가 403 을 맞는다 |
| 부여 경로 | **승격 API 없음 — DB 직접 변경** (`UPDATE users SET role='ADMIN' WHERE id=?`) | 익명키 기반이라 "누가 승격시킬 자격이 있는가"를 서버가 판단할 수단이 없다. 만들면 그게 권한 상승 경로가 된다 |
| 운영자 경로 | **`/api/v1/admin/**` 접두사 하나로 고정** | 공개 경로를 열거로 관리하는 것과 같은 규율 — 어노테이션 누락 = 조용한 노출을 막는다 |

**⚠️ 권한 변경은 즉시 반영되지 않는다.** 부여·회수 후 그 사용자의 access 토큰이 만료(최대 30분)되고
refresh 로 갱신돼야 실제로 바뀐다. **강제 폐기가 지연되는 것(§4-2 v4)과 같은 축의 트레이드오프**이며
같은 이유로 수용한다. 즉시 반영이 필요해지면 그것은 "요청당 DB 조회"를 되살리는 별개의 결정이다.

- 토큰의 authority 는 **자기 권한 하나뿐**이다. `ADMIN` 토큰에 `USER` 를 같이 싣지 않는다 —
  그러면 "일반 사용자만"이라는 규칙을 표현할 수 없게 된다. 포함 관계는 계층 선언 한 곳에만 산다.
- 모르는 `role` 값·`role` 클레임이 없는 토큰은 **`USER` 로 읽는다.** 실패는 권한 축소 방향이어야 한다 —
  없는 값을 `ADMIN` 으로 읽으면 배포 순간 전 사용자가 운영자가 된다.
- **운영자용 화면·기능은 이번 범위에 없다.** 지금 확정한 것은 *경로 규칙과 판정 방식*뿐이고,
  실제 운영 기능은 필요해질 때 각 도메인 문서가 정한다(§8).

## 5. API 계약 (확정 — `docs/server/api-spec.md` 반영 대상)

> `docs/server/api-spec.md` 는 **아직 존재하지 않는다.** 이 절이 그 문서의 첫 입주자가 된다(→ §10).

### 5-1. 공통 요청 헤더 [공통 승격 후보] **(v4 전면 개정)**

| 헤더 | 어디서 | 값 |
|---|---|---|
| `Authorization` | **인증 필요 엔드포인트 전부** | `Bearer {access}` — 부트스트랩이 발급한 JWT |
| `X-Anonymous-Key` | **부트스트랩에서만** | SDK `User.getAnonymousKey()` 의 `hash` 값 |

- **(v4) 구 헤더 병행 없음** — 프론트가 미구현이라 깨질 클라가 없다. 인증 필요 엔드포인트에
  `X-Anonymous-Key` 를 보내도 **무시된다**(자격 증명은 Bearer 뿐).
- access 는 **HS256** 서명 JWT, 클레임: `sub`(=`userId` 값)·`iat`·`exp`(발급 +30분).
  서명 키는 **환경 변수로만** 주입(커밋·로그 금지 — mTLS 인증서와 같은 규율). 키 회전은 백로그.
- 공통 에러 응답 본문은 `{ "code": "...", "message": "..." }` 고정
  (→ [error-handling.md](../rule/error-handling.md)). 예외 없이 이 형식을 따른다.
- 경로 prefix 는 **`/api/v1`** 로 한다(2026-08-07 확정). [공통 승격 후보]

### 5-2. 신규 — `POST /api/v1/bootstrap` (집계 모듈 소유)

> **auth 도메인의 엔드포인트가 아니다.** auth 는 이 응답의 일부(U4)를 모듈 공개 API 로 공급할 뿐이다.
> `POST` 인 이유: 최초 호출이 **사용자 등록이라는 상태 변화**를 일으키므로 `GET` 이 아니다.
> 다만 **멱등**하다(U2) — 몇 번 호출해도 사용자는 하나이고 응답도 같다.

**요청**

```
POST /api/v1/bootstrap
X-Anonymous-Key: {hash}
(본문 없음)
```

**응답 200 (v4 — 토큰 동봉. 부트스트랩이 곧 로그인이다)**

```json
{
  "newUser": true,
  "registeredAt": "2026-08-07T12:34:56Z",
  "auth": {
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "refreshToken": "AAAA...(불투명 랜덤값)"
  },
  "entitlement": {
    "accessible": false,
    "credits": 0,
    "subscriptionStale": false,
    "subscription": { "status": "NONE", "expiresAt": null, "autoRenew": false }
  }
}
```

| 필드 | 주인 | 의미 | 프론트 용도 |
|---|---|---|---|
| `newUser` | auth | 이번 호출로 처음 등록되었는가 | 온보딩/튜토리얼 노출 분기 |
| `registeredAt` | auth | 이 사용자가 처음 등록된 시각 | 디버깅·문의 대응 |
| `auth.accessToken` **(v4)** | auth | JWT (30분). 만료는 `exp` claim | 이후 전 API 의 `Authorization: Bearer` |
| `auth.refreshToken` **(v4)** | auth | 갱신용 불투명 값 (14일·회전) | `AUTH_004` 수신 시 §5-5 로 갱신. **로컬에만 보관** |
| `entitlement` | **payment** | 이용권 상태 — **내부 스키마의 정본은 [payment.md](./payment.md) §5-3** | S1 배지 · 결제 진입 분기. **분기는 `accessible` 하나로만** |

- **(v4) 재호출 = 재로그인.** 부트스트랩은 여전히 멱등(사용자 1명)이지만 **토큰은 호출마다 새로 발급**된다.
  기존 refresh 는 폐기하지 않는다 — 기기 여러 대(같은 토스 계정)가 각자의 refresh 를 갖는 정상 상황과
  구분할 수 없기 때문이다. 만료(14일)가 자연 정리한다.

- **(v3) ~~잠정~~ → 확정.** v2 의 *"`subscription` 객체 스키마는 잠정"* 이 payment.md v1 확정(✅-15ⓐ)으로
  닫혔다 — 잠정안 `{status, expiresAt}` 이 `accessible`·`credits`·`subscriptionStale`·`autoRenew` 를 담은
  `entitlement` 객체로 확대됐다. 확대 사유는 payment.md §5-3 이 정본이다.
  **auth 가 확정하는 것은 여전히 `newUser`·`registeredAt` 두 필드뿐**이고, `entitlement` 내부가 바뀌면
  그건 payment.md 의 버전이지 이 문서의 버전이 아니다.
- ⚠️ **응답에 사용자 식별자(`userId`)를 싣지 않는다.** 서버 내부 식별자(타입화된 기본키)는
  모듈 간 계약이지 프론트 계약이 아니다 — 프론트는 익명키로 충분하다.
- **부분 실패를 허용하지 않는다**(2026-08-07 확정). 이용권 조회가 실패하면 `entitlement` 를 비운
  200 을 주지 않고 **전체를 500 으로** 응답한다 — 비어 있는 값을 프론트가 “이용권 없음”으로 오해하면
  **이미 결제한 사용자에게 결제를 다시 유도**하게 되기 때문이다. 조용한 오작동보다 명시적 실패가 낫다.
- **에러 응답에 익명키를 되돌려주지 않는다**(U6).

### 5-3. ~~auth 는 자체 HTTP 엔드포인트를 두지 않는다~~ **(v4 번복 — refresh 1개를 갖는다)**

v3 까지의 결정은 안 ⓒ 의 귀결이었으나, **토큰 갱신은 합칠 곳이 없다** — 부트스트랩에 합치면
"갱신하러 갔다가 재로그인"이 되어 갱신의 의미가 없다. auth 가 밖에 내놓는 것은 셋이다:

| 내놓는 것 | 형태 | 소비자 |
|---|---|---|
| 등록·식별 + 토큰 발급 (U4·U7) | **모듈 공개 API** (HTTP 아님) | 집계 모듈(부트스트랩) |
| 토큰 게이트 (U3·U8) | 전 요청 앞단의 보안 규칙 | 모든 도메인 |
| **`POST /api/v1/auth/refresh` (v4·U9)** | **HTTP 엔드포인트** | 프론트 (게이트 밖 — 자격 증명이 만료된 상태에서 부르는 API 다) |

### 5-5. 신규 (v4) — `POST /api/v1/auth/refresh`

```
POST /api/v1/auth/refresh          (인증 게이트 밖 · 본문이 자격 증명)
{ "refreshToken": "AAAA..." }
```

**응답 200** — 회전된 새 쌍. 요청에 쓴 refresh 는 **그 순간 폐기**된다.

```json
{ "accessToken": "eyJ...", "refreshToken": "BBBB..." }
```

| 실패 | 코드 | 프론트 행동 |
|---|---|---|
| 만료·미존재·**이미 회전된 토큰의 재사용** | **401 `AUTH_005`** | **부트스트랩 재로그인.** 익명키는 SDK 가 늘 주므로 마찰 없음 |

- **재사용 감지 = 전체 폐기**(U9): 이미 폐기된 refresh 가 오면 탈취 신호로 보고 **그 사용자의
  refresh 를 전부 폐기**한다. 정당한 사용자도 로그아웃되지만 재로그인 비용이 0 이라 손해가 없다 —
  이 비대칭이 이 정책의 근거다.
- 동시 갱신 경쟁(같은 refresh 2회 동시 제출)은 **한쪽만 성공**해야 한다 — 원자 회전은 설계 몫.

### 5-4. 인증 필요 엔드포인트 전반 [공통 승격 후보]

auth 도메인은 **다른 모든 도메인의 요청 앞단**에 게이트로 존재한다.
각 도메인 문서는 엔드포인트마다 “공개 / 인증 필요”만 명시하면 되고, 401 응답 규격은 §4-2 를 링크한다.

## 6. API 호출 흐름 (프론트 ↔ 백엔드)

### 6-1. 최초 진입 — 부트스트랩

```
[미니앱 진입]
 → 프론트: SDK User.getAnonymousKey()
    ├─ 실패 / 미지원 환경 → 서비스 이용 불가 안내 후 종료 (서버 호출 없음)
    └─ 성공 { type:'HASH', hash }
        → POST /api/v1/bootstrap   (X-Anonymous-Key: hash)
           ├─ 200 { newUser, auth:{...}, entitlement:{...} } → 토큰 로컬 보관 (v4)
           │      → newUser:true 면 온보딩 → 솔루션 목록(S1)
           │      ↳ S1 배지를 entitlement 로 즉시 렌더링 (분기는 accessible — v3)
           ├─ 401 AUTH_001 (헤더 누락)
           │     → 등록할 대상이 없다. SDK 재호출 1회 → 그래도 실패면 오류 안내 후 종료
           ├─ 401 AUTH_002 (형식 위반)
           │     → 재시도해도 결과가 같다. "이용할 수 없는 환경" 안내 후 종료
           └─ 500 COMMON_002 (등록 실패 또는 이용권 조회 실패 — §5-2 부분 실패 불허)
                 → 백오프 재시도 + "잠시 후 다시" 안내. 종료시키지 않는다
                    ⚠️ 프론트는 이때 화면을 "미구독"으로 그리지 않는다
```

### 6-2. 일반 API 요청 (인증 필요 엔드포인트) **(v4 — Bearer + 갱신 인터셉터)**

```
[임의 화면에서 보호 자원 요청]
 → METHOD /api/v1/{...}   (Authorization: Bearer {access})
    ├─ 200 → 정상 렌더링
    ├─ 401 AUTH_004 (만료) → POST /auth/refresh (§5-5) → 새 쌍 보관 → 원 요청 1회 재시도
    │     └─ refresh 도 401 AUTH_005 → 부트스트랩(6-1) 재실행(재로그인) → 원 요청 1회 재시도
    ├─ 401 AUTH_001 (토큰 없음) / AUTH_002 (무효) → 부트스트랩 재실행 후 1회 재시도
    │                 → 거기서도 실패면 안내 후 종료
    └─ 500 COMMON_002 → 백오프 재시도. 진행 중 작업이 있으면 상태를 잃지 않게 유지
```

- **프론트 책임**: 갱신·재로그인·재시도는 **각 1회씩만** — 무한 루프 금지.
  `AUTH_004 → refresh → 재시도` 는 HTTP 인터셉터 한 곳에 두고 화면 코드는 모르게 한다.
- ⚠️ **401 은 “도용 감지”가 아니다.** 우리는 도용을 감지하지 않는다(§4-1).
  프론트도 그런 안내 문구를 쓰지 않는다.

### 6-3. 공개 엔드포인트 (헤더 없이 접근)

```
[솔루션 목록/상세 — 결제 전 열람]
 → GET /api/v1/{...}   (헤더 없어도 됨)
    ├─ 200 → 렌더링
    ├─ 헤더가 붙어 있어도 형식 검증조차 하지 않고 무시한다
    └─ 500 COMMON_002 → 백오프 재시도
```

## 7. 에러 코드 · 정책 **(v4 — 401 이 네 종류가 된다)**

| 코드 | HTTP | 의미 | 프론트 행동 |
|---|---|---|---|
| `AUTH_001` | 401 | 자격 증명 없음 (토큰/익명키 누락) | 부트스트랩 재실행 후 1회 재시도 |
| `AUTH_002` | 401 | 무효한 자격 증명 (서명 오류·형식 불량) | **재시도 무익** — 부트스트랩 재로그인 |
| `AUTH_004` **(v4)** | 401 | **만료된 access 토큰** | **refresh 후 1회 재시도** (§6-2 인터셉터) |
| `AUTH_005` **(v4)** | 401 | **무효한 refresh** (만료·미존재·재사용) | 부트스트랩 재로그인 |
| `AUTH_003` **(v5)** | **403** | **권한 부족** — 인증은 됐으나 `ADMIN` 이 아니다 | **재시도 무익** — 안내 후 종료. ⚠️ **refresh·재로그인을 하지 마라**(토큰은 멀쩡하다 → 무한 루프) |

- **(v5)** `AUTH_003` 은 **권한 축의 403** 이다(§4-8). “이용권이 없다”는 여전히 payment 몫(`PAY_001`·`PAY_007`) —
  ~~auth 가 쓰지 않는다~~ 는 v4 까지의 서술이다.
- 코드 정본: [ErrorCode.java](../../src/main/java/kang20/ytcreator/shared/exception/ErrorCode.java) ·
  [error-handling.md](../rule/error-handling.md).

| 관리자 인증 체계 | 관리자 화면 자체가 MVP 밖 |
| 다중 기기 동시 사용 정책 | 계정 기준이라 자연히 공유된다. 제한할 이유가 아직 없다 |
