## 결제 도메인

- ytcreator 는 토스 미니앱으로 제공되는 영상 자막 생성 서비스이고, 자막 생성은 유료 기능이다.
- 이 도메인의 목적은 "결제를 연동하는 것"이 아니라 **"돈을 낸 사람이 언제 어떤 경로로 돌아와도 쓸 수 있게 하는 것"** 이다.
  - 돈은 토스가 받는다. 우리 서버는 돈을 다루지 않는다.
  - 우리가 기억하는 것은 "누가 무엇을 쓸 수 있는가" 하나다.
  - 이 서비스에는 로그인이 없다. 사용자는 익명키로만 식별된다.
  - 그래서 우리 서버의 `익명키 ↔ 주문` 매핑이 소유권의 유일한 정본이고, 그것이 끊기면 사용자는 돈을 내고 못 쓴다.
- [이용권]: 유료 기능을 쓰려면 [이용권]이 있어야 한다.
  - 이용권은 두 종류이고, 획득 경로도 소멸 방식도 다르다.
  - [횟수권]은 단건 결제로 얻는 1회 이용권이다. 쓰면 소진된다.
  - [기간권]은 구독으로 얻는 기간 내 무제한 이용권이다. 소모라는 개념이 없다.
  - "쓸 수 있는가"의 답은 두 이용권을 함께 봐야 나온다. ~~그래서 하나의 도메인이다~~ →
    **하나의 도메인이되 하나의 모듈은 아니다 (v2)**. 두 이용권은 변경 트리거도 권위자도 달라서
    모듈이 셋으로 갈렸고(주문·구독·횟수권), 합치는 일은 **읽는 쪽**에서만 일어난다.
  - 대신 두 이용권의 상태 어휘는 합치지 않는다. 주문 상태와 구독 상태는 서로 다른 축이며, 하나의 상태 머신으로 합치려 하면 안 된다.
- 결제는 토스 앱 안에서 끝나고, 우리는 결제 자체에 관여하지 않는다.
- 결제가 끝나면 토스 앱이 클라이언트에 주문 식별자를 넘기고, 클라이언트가 우리 서버에 지급을 요청한다.
  - 지급은 결제된 주문을 우리 이용권으로 바꾸는 행위다.
  - 서버는 클라이언트의 주장만으로 지급하지 않는다. 토스 서버에 주문 상태를 직접 물어 확인한 뒤에만 지급한다.
  - 어떤 상품을 샀는지도 클라이언트가 아니라 토스가 답한 상품 코드로 판별한다.
  - 우리가 모르는 상품 코드면 남의 상품이므로 지급하지 않는다.
  - 지급 요청은 30초 안에 답해야 한다. 넘기면 사용자에게 환불 안내 화면이 노출된다.
  - 시간이 모자라면 붙잡지 않고 실패로 답한다. 남은 것은 복원이 처리한다.
  - 주문 검증을 위한 외부 왕복은 지급 트랜잭션 밖에서 한다. 검증한 뒤에 열고, 쓰고, 닫는다.
  - 성공 응답은 지급이 확정된 뒤에 만든다. 확정되지 않은 성공을 돌려주면 클라이언트가 미결을 닫아버려 복원 대상에서도 사라진다.
  - **지급이 확정되면 무엇을 지급했는지가 사실로 발행되고, 이용권을 만드는 일은 그 사실을 받는 쪽이 한다 (v2)**.
    원장을 쓴 쪽이 잔량까지 직접 올리면 "누가 무엇에 권위를 갖는가"가 한 곳에 뭉친다.
- 한 주문은 한 사용자에게만 귀속되고, 한 번 정해진 소유자는 바뀌지 않는다.
  - 먼저 지급을 요청한 익명키가 소유자가 된다.
  - 이미 남의 것이 된 주문에 대한 지급 요청은 거부한다.
  - 토스에 "이 주문이 누구 것인가"를 물어볼 수단이 없다. 그래서 소유자는 끝까지 클라이언트의 주장이다.
  - 선점은 검증이 아니라 그 사실을 감수하겠다는 선언이다. 보안 통제인 척 쓰지 않는다.
  - 그래서 주문 식별자는 밖으로 내보내지 않는다. 응답에도 예외 메시지에도 싣지 않는다.
  - 주문 식별자를 아는 것은 미지급 주문을 가로챌 수 있는 것과 같다.
- 같은 주문으로 지급 요청이 여러 번 오는 것은 오류가 아니라 정상이다.
  - 미결 주문 복원, 네트워크 재시도, 타임아웃 후 실은 성공한 경우가 모두 중복 요청을 만든다.
  - 그래서 같은 주문은 몇 번 요청해도 정확히 한 번만 지급하고, 재요청도 성공으로 답한다.
  - 중복을 오류로 만들면 복원 흐름 자체가 깨진다.
  - 멱등의 근거는 주문 식별자 하나다. 조회해서 없으면 넣는 방식은 근거가 되지 않는다.

    **(v2 수정 — 지급 응답은 잔량을 담지 않는다.** 잔량의 권위는 횟수권 쪽에 있고 지급 경로에는 그것을
    읽을 수단이 없다. 대신 같은 규칙을 **발행**으로 옮긴다: **재요청은 지급 사실을 다시 발행하지 않는다**.
    발행이 두 번 되면 잔량이 두 번 오른다 — 멱등이 깨지는 지점이 응답이 아니라 발행으로 이동했다.**)**
  - 결제됐는데 지급이 끝나지 않은 주문을 미결 주문이라 하고, 정상 흐름에서도 발생한다.
  - 미결 주문은 다음 진입 때 복원으로 다시 지급을 시도한다. 복원은 검수 필수 시나리오다.
- [구독의 상태 변환 감지]: 구독은 최초 결제 이후의 상태 변화를 우리가 알 방법이 웹훅뿐이다.
  - 서버가 구독 상태를 직접 조회할 수단이 없다. 이 도메인 최대의 구조적 제약이다.
  - 갱신 결제는 매월 우리 밖에서 일어나고, 우리는 웹훅으로만 그 사실을 안다.
  - 그래서 서버가 아는 구독 상태는 "최초 주문 검증 + 이후 웹훅 누적"이 전부이고, 어긋나도 바로잡을 조회 수단이 없다.
  - 웹훅은 위조될 수 있으므로 진위를 검증한다. 수단은 **콜백 등록 시 정한 Basic Auth 값 대조** 하나뿐이다(참고자료 ⑥-1). 서명도 HMAC 도 없다.
  - **진위 → 이벤트 종류 → 형식 순으로 본다 (v2)**. 형식을 먼저 물으면 위조 요청이 인증 실패가 아니라
    형식 오류를 받아 본문 모양에 따라 응답이 갈리고, 그 차이가 페이로드 구조를 알려준다.
    종류를 가르기 전에 형식을 물으면 **콜백 URL 등록 검증 이벤트가 거부돼 URL 이 활성화되지 않는다**.
  - 웹훅으로 구독을 새로 만들지 않는다. 구독 생성은 검증된 주문을 거친 경우뿐이다.(웹훅은 구독의 상태 갱신으로만 사용)
  - 이 규칙 덕분에 위조 웹훅의 최대 피해가 "없는 구독 생성"에서 "이미 결제한 사람의 상태 흔들기"로 줄어든다.
  - 웹훅에는 이벤트 식별자도 재전송 정책도 없다. 발생 시각이 유일한 순서 판단 근거다.
  - 이미 반영한 것보다 과거의 웹훅은 무시한다.
  - **무시는 오류가 아니다 (v2)** — 과거·중복 웹훅도, **모르는 주문의 웹훅**도 정상 무동작으로 성공을 답한다.
    모르는 주문에 오류를 답하면 "그 주문이 우리에게 있는가"를 알려주는 표면이 된다.
  - 웹훅은 직전 상태를 함께 알려준다. 그것이 우리가 아는 상태와 다르면 그 사이의 웹훅을 놓친 것이다. 놓친 사실은 감지하되 반영은 그대로 진행한다.

- [구독 갱신의 유실 상태] : 구독 상태를 우리가 모르게 된 구간을 상태 미확인이라 한다.
  - 구독이 활성인데 만료 시각과 유예 기간이 지나도록 다음 웹훅이 오지 않으면 상태 미확인이다.
  - 판정 기준은 시간 경과다. 웹훅을 한 번이라도 받았는지로 판정하지 않는다. 그러면 매월 반복되는 갱신 유실을 잡지 못한다.
  - 만료와 회수는 웹훅으로 확인된 종료이므로 상태 미확인이 아니다.
  - 상태 미확인이면 실제 상태를 모르므로 소모를 막고 사용자에게 재확인을 유도한다.
    **(소모를 막는 쪽은 v2 이연 — 소모 자체가 이번 범위에 없다. 재확인 경로는 구현했다.)**
  - 재확인은 클라이언트가 토스 앱에서 읽은 구독 정보로 임시 보정한다.
  - **재확인은 상태 미확인일 때만 반영한다 (v2)**. 아니면 무동작이다 — 정본이 멀쩡히 살아 있는 구간을
    검증되지 않은 값이 이기면, 웹훅을 정본으로 둔 의미가 사라진다.
  - **재확인의 대상은 클라이언트가 지목하고, 소유자는 토큰이 확정한다 (v2)**. 지목만으로 반영하면
    주문 식별자가 곧 권한이 된다. **모르는 주문과 남의 주문은 같은 무동작**이다 — 갈라 답하면
    주문의 존재 여부가 새어 나간다.
  - 클라이언트 값은 정본이 아니다. 웹훅이 정본이고 재확인은 임시 보정이다.

  - 이 경로는 클라이언트 값을 신뢰하는 구멍이며, 알고 여는 구멍이다.
  - 이러한 유실 상태의 구멍은 로그를 사용한 모니터링으로 대체한다.
- [이용 가능 판정]은 유료 기능 앞단에서 한 번에 이뤄진다.
  - 기간권이 살아 있거나 횟수권 잔량이 있으면 이용 가능하다.

    하나의 답을 내는 자리는 없다. 유료 기능(작업 도메인)이 아직 없어 그 답을 물을 소비자가 없다.**)**
  - 토스가 알려주는 구독 상태를 그대로 게이트에 쓰지 않는다. "어떤 상태인가"와 "열어줄 것인가"는 별개다.
  - 활성이면 연다. 다만 만료 후 유예 기간이 지나면 닫는다. 웹훅 지연을 흡수하기 위해서다.
  - 결제 실패 유예 중이면 연다. 카드 문제로 잠깐 실패한 유료 사용자를 막는 손해가 더 크다. (이 결제 실패 유예와 미확인 유예와는 다른 단어이다.)
  - **결제 실패 유예에는 만료 경과를 보지 않는다 (v2)**. 유예의 종료 시각은 웹훅에 오지 않아

    종료는 토스가 다음 웹훅으로 알린다.
  - [기간권의 제지 조건] 유예 종료, 사용자 일시정지, 만료, 회수는 막는다.
  - 구독 이력이 없으면 횟수권만 본다.
  - 플랫폼이 주는 이용 가능 여부 값을 쓰지 않는다. 클라이언트 값이고 산식이 공개돼 있지 않다.
  - 프론트는 "이용 가능한가" 하나만 보고 분기한다. 구독 상태는 안내 문구용이다. **(v2 이연)**
  - 이용권 상태는 진입 시 함께 내려가는 경로와 단독 조회 경로 둘 다로 제공되고, 두 경로의 응답 모양은 같아야 한다.
    **(v2 이연 — 두 경로 모두 없다.** 진입 응답의 이용권 필드도 아직 비어 있다.**)**
  - 이용권이 없어서 거부하는 것은 인증 실패와 구분되어야 한다. 프론트의 행동이 다르기 때문이다.
- [소모]는 횟수권에만 있다. **(이 항목 전체가 v2 이연 — 규칙은 유효하고 구현만 없다.**
  소모를 부르는 것은 자막 생성 작업이고, **작업 도메인이 아직 없다**. 호출자가 없는 상태에서 만들면
  참조값의 의미도, 실패 이벤트의 모양도 추측으로 정해진다.**)**
  - 기간권 보유자에게는 차감하지 않는다.
  - [기간권, 소모권의 차감 기준] 둘 다 있으면 기간권을 먼저 쓴다. 구독 중에 횟수권이 줄면 사용자는 손해라고 느낀다.
  - 잔량은 절대 음수가 되지 않는다. **(이 불변식만은 이번 범위에서도 지켰다 — 잔량 타입이 음수를 거부한다.)**
  - [소모 시점] 소모는 작업을 시작할 때 예약하고, 작업이 끝나면 확정한다.
  - 작업이 실패하면 예약을 해제하고 잔량을 되돌린다. 돈을 내고 결과물을 못 받는 것이 최악의 경험이다.
  - 확정과 해제는 각각 한 번만 일어난다. 해제가 두 번 일어나면 무료 이용권이 샌다.
  - 지급에는 주문 식별자라는 자연스러운 멱등 키가 있지만, 소모에는 그런 키가 없다.
  - 소모 이력은 지우지 않는다. 분쟁 대응에 쓴다.
- 환불과 회수는 우리가 처리하지 않는다.
  - 환불 처리 주체는 스토어다. 우리는 그 결과를 반영할 뿐이다.
  - 구독 회수는 웹훅으로 통보되지만, 단건 환불은 통보 수단이 없다.
  - 이미 소모한 횟수권은 환불로 되돌리지 않는다.
  - 이용이 중단돼도 진행 중인 작업은 끝까지 처리한다.
  - 이용권을 현금으로 환급하지 않는다. 현금성 상품은 등록 자체가 불가능하다.
- 이 도메인이 하지 않는 일이 있다.
  - 결제창 호출, 결제 수단, 카드 정보는 클라이언트와 토스의 몫이다.
  - 가격을 말하지 않는다. 가격은 결제 SDK 가 정본이고, 우리가 말하면 결제창과 어긋난다. 상품 코드만 내려준다.
  - **상품 코드도 코드에 박지 않는다 (v2)** — 설정으로 뺀다. 코드에 박으면 상품을 바꿀 때 배포가 필요하고,
    설정을 비우면 그 유형은 어떤 주문으로도 지급되지 않는다(미노출 상품).
  - 구독 해지와 플랜 변경을 하지 않는다. 호출할 API 자체가 없다.
  - 쿠폰, 프로모션, 무료체험, 연간 플랜, 결제 이력 화면, 관리자 기능은 범위 밖이다.
- **이번 범위에서 미뤄둔 것이 있다 (v2)** — 범위 밖(영영 안 함)과 다르다. **소비자가 생기면 만든다.**
  - **이용 티켓과 소모** — 부르는 쪽이 자막 생성 작업인데 그 도메인이 없다. 참조값의 의미를 우리가 정할 수 없다.
  - **이용권 읽기 모델(기간권 + 횟수권 합성)** — 물어보는 화면이 없다. 조회 경로도, 진입 동봉 경로도 없다.
  - **진입 응답의 이용권 필드** — 위와 같은 이유로 비어 있다. 프론트 계약은 그만큼 복구되지 않은 상태다.
  - **횟수권 차감·조회 경로** — 증가 경로만 있다. 줄이는 쪽의 호출자가 소모이고, 소모가 없다.
  - 미뤄둔 자리에는 **자리만 잡는 코드도 두지 않는다.** 쓰이지 않는 포트·DTO 는 다음 사람에게
    "이미 정해진 계약"으로 보이고, 실제로는 아무도 검증하지 않은 추측이다.

### ① 주문이 결제됐는지 확인 — `get-order-status`

출처: [인앱 결제 API](https://developers-apps-in-toss.toss.im/documentation/api/iap) ·
[인앱 결제 가이드](https://developers-apps-in-toss.toss.im/documentation/common/monetization/iap/in-app-purchase)


| 항목       | 값                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------- |
| 엔드포인트 | `POST /api-partner/v1/apps-in-toss/order/get-order-status`                               |
| 서버       | `https://apps-in-toss-api.toss.im`                                                       |
| 인증       | **mTLS 단독.** OpenAPI 원문의 `parameters` 가 **비어 있다** — 헤더 인증 파라미터가 없다 |
| 요청       | `{ "orderId": "..." }` — 주문 식별자 하나뿐이다                                         |
| 요청 한도  | 앱당**분당 3,000회**. 초과 시 `errorCode: 4095`                                          |

**응답 봉투**

```json
{
  "resultType": "SUCCESS",
  "success": {
    "orderId": "13c9a1ff-...",
    "sku": "ait.0000010000.af647449....",
    "status": "PAYMENT_COMPLETED",
    "statusDeterminedAt": "2025-09-12T16:57:12",
    "reason": "결제가 완료되었어요."
  }
}
```

- 🔴 **비즈니스 오류가 HTTP 200 으로 온다.** `resultType` 이 `SUCCESS` 가 아니면 전부 실패로 다룬다
- `resultType` 실패 값: `FAIL` · `HTTP_TIMEOUT` · `NETWORK_ERROR` · `EXECUTION_FAIL` · `INTERRUPTED` · `INTERNAL_ERROR`
- `sku` 와 `statusDeterminedAt` 은 **상태를 확정하지 못하면 내려오지 않는다**(`MINIAPP_MISMATCH`·`NOT_FOUND`·`ERROR`)
- `statusDeterminedAt` 은 **KST 고정**이다
- **권장 타임아웃이 원문에 없다 (v2)** — 30초 예산 안에서 우리가 정한다(연결 3초 · 응답 10초).

**`status` 값 8종**


| 값                  | 의미                              | 지급 판정       |
| ------------------- | --------------------------------- | --------------- |
| `PURCHASED`         | 결제·지급이 모두 끝났다          | 지급 대상       |
| `PAYMENT_COMPLETED` | 결제는 됐고**지급이 실패한 상태** | 지급 대상       |
| `ORDER_IN_PROGRESS` | 주문이 아직 진행 중이다           | 아직 아니다     |
| `FAILED`            | 결제가 실패했다                   | 지급하지 않는다 |
| `REFUNDED`          | 환불됐다                          | 지급하지 않는다 |
| `NOT_FOUND`         | 주문을 찾을 수 없다               | 지급하지 않는다 |
| `MINIAPP_MISMATCH`  | 우리 미니앱의 주문이 아니다       | 지급하지 않는다 |
| `ERROR`             | 카탈로그 조회 실패 등 비정상      | 지급하지 않는다 |

- **모르는 값이 오면 `ERROR` 와 같게 다룬다 (v2)**. 플랫폼이 어휘를 늘려도 조용히 지급되지 않게 한다.
- **`PAYMENT_COMPLETED` 를 지급 대상으로 보는 것은 우리 판단이다 (v2)**. 원문은 "지급하라"고 말하지
  않는다 — 뒤집힐 수 있으므로 판정을 **한 곳에 몰아 둔다**.

**도메인 규칙과의 연결**

- `OrderVerifier` 가 부르는 API 가 이것이다. **"이 주문이 결제됐다"만 알려주고 "누구 것인가"는 알려주지 않는다** — 응답에 소유자 필드가 없다
- `ProductCatalog` 가 판별하는 상품 코드는 이 응답의 `sku` 다. 클라이언트가 준 값이 아니다

### ② 구독 상태가 바뀌었음을 통보 — `subscription.status_changed`

출처: [IAP 정기결제](https://developers-apps-in-toss.toss.im/documentation/common/monetization/iap/in-app-subscription)

- 콘솔에 콜백 URL 을 등록하면 수신한다. **서버가 구독 상태를 물어볼 API 는 없다** — 이 웹훅이 유일한 경로다
- 시간 값(`occurredAt`·`expiresAt`)은 **timezone 없는 ISO-8601** 이다. 예: `"2026-05-06T00:00:00"`
- 원문: *"`orderId`는 직접 사용자 식별자는 아니지만, 주문과 사용자를 매핑하고 있다면 상관관계 식별자로 활용할 수 있어요"*

**이벤트 2종**


| `eventType`                          | 언제                                                            |
| ------------------------------------ | --------------------------------------------------------------- |
| `callback.registration_verification` | 콜백 URL 등록·변경 시.**이걸 정상 수신해야 URL 이 활성화된다** |
| `subscription.status_changed`        | 구독 상태가 확정된 뒤                                           |

**페이로드**

```json
{
  "eventType": "subscription.status_changed",
  "eventVersion": "1.0",
  "occurredAt": "2026-05-06T00:00:00",
  "orderId": "order-1",
  "sku": "premium.monthly",
  "changeReason": "RENEWED",
  "subscription": {
    "previous": { "status": "ACTIVE", "accessGranted": true, "expiresAt": "2026-05-06T00:00:00", "autoRenew": true },
    "current":  { "status": "ACTIVE", "accessGranted": true, "expiresAt": "2026-06-06T00:00:00", "autoRenew": true }
  }
}
```

- `subscription.previous` 는 **생략될 수 있다**(`CREATED` 처럼 이전 상태가 없을 때)
- `expiresAt` 은 **`null` 일 수 있다.** `CREATED` 예시가 실제로 `null` 이다
- 스냅샷 필드는 `status` · `accessGranted` · `expiresAt` · `autoRenew` 넷이다
- **등록 검증 이벤트에는 `orderId` 도 스냅샷도 없다 (v2)** — 스키마가 다른 두 이벤트가 **한 URL 로**
  온다. 하나의 형식 검증으로 둘을 함께 다루면 등록 검증이 형식 오류로 떨어진다.

**`changeReason` 12종**

`CREATED` 생성 · `RENEWED` 갱신 · `RECOVERED` 결제 실패에서 복구 · `RESTARTED` 재시작 ·
`ENTERED_GRACE_PERIOD` 유예 진입 · `ON_HOLD` 결제 보류 · `PAUSED` 일시정지 ·
`AUTO_RENEW_ENABLED` / `AUTO_RENEW_DISABLED` 자동 갱신 전환 · `EXTENDED` 기간 연장 ·
`EXPIRED` 만료 · `REVOKED` 회수 또는 환불

**`status` 6종** — `ACTIVE` · `EXPIRED` · `IN_GRACE_PERIOD` · `ON_HOLD` · `PAUSED` · `REVOKED`

**도메인 규칙과의 연결**

- `WebhookEvent` 가 이 페이로드다. **`changeReason` 이 12종인데 `status` 는 6종이다** — 사유로 분기하지 않고 `current` 스냅샷으로 판정하는 이유가 이 비대칭이다
- `previous` 가 선택 필드이므로 유실 감지는 **`previous` 가 있을 때만** 성립한다
- `expiresAt` 이 `null` 로 올 수 있으므로 정본을 무로 덮지 않는다는 규칙이 필요하다
- **`autoRenew`·`occurredAt` 도 같다 (v2)** — 비어 오면 기존 값을 유지한다
- **`accessGranted` 를 쓰지 않는다** — 스냅샷에 들어 있지만 산식이 공개돼 있지 않다

### ③ 참고 — 클라이언트가 읽는 구독 상태 (`getSubscriptionInfo`)

재확인 경로가 쓰는 값이다. **서버 API 가 아니라 SDK 함수이므로 정본이 아니다.**

```ts
interface IapSubscriptionInfoResult {
  catalogId: number;
  status: 'ACTIVE' | 'EXPIRED' | 'IN_GRACE_PERIOD' | 'ON_HOLD' | 'PAUSED' | 'REVOKED';
  expiresAt: string | null;
  isAutoRenew: boolean;
  gracePeriodExpiresAt: string | null;
  isAccessible: boolean;
}
```

- ⚠️ **`gracePeriodExpiresAt` 은 여기에만 있고 웹훅에는 없다.** 서버는 결제 실패 유예의 종료 시점을 알 수 없다
- ⚠️ **`isAccessible` 을 쓰지 않는다** — 클라이언트 값이고 산식이 공개돼 있지 않다
- **응답에 `orderId` 가 없다 (v2)** — SDK 가 그 값을 **인자로 받으므로** 클라이언트는 이미 알고 있다.
  그래서 재확인 요청은 주문 식별자를 함께 보낼 수 있고, 웹훅과 같은 식별자로 대상을 지목한다
- 최소 지원 버전: Android `5.253.0` / iOS `5.250.0`

### ⑤ 이번 조회로 새로 확인된 것

- **구독 주문의 지급 콜백에는 `subscriptionId` 가 함께 온다**
  (`processProductGrant: ({ orderId, subscriptionId }) => ...`).
  다만 **웹훅 페이로드에는 `subscriptionId` 가 없다** — 서버가 구독을 찾는 키는 여전히 `orderId` 하나다
- **구독은 샌드박스 테스트를 지원하지 않는다.** 원문: *"현재 샌드박스 앱에서는 구독 기능 테스트를 지원하지 않아요"*
- 구독 상품은 `offers`(무료 체험·신규 할인·복귀 할인)를 가질 수 있다. **우리 범위 밖이지만 `getProductItemList` 응답에 섞여 내려온다**

## 도메인 모델

> **애그리거트는 ~~4개~~ → 3개다 (v2)** — 주문 · 구독 · 횟수권 잔량. 이용 티켓은 **이연**이다.
> 변경 트리거가 서로 다르기 때문이고, 하나로 합치면 동시성 대책이 전부 한 행에 몰린다.
> 애그리거트끼리는 **연관관계를 갖지 않고 식별자로만 참조한다.**
> 사용자는 언제나 `UserId` 로만 표현한다 — 결제 도메인은 `User` 엔티티를 알지 못한다.
>
> **세 애그리거트는 세 모듈로 갈렸다 (v2)** — `payment`(주문) · `subscription`(구독) · `credit`(횟수권).
> 나눈 근거는 애그리거트 경계와 같다: 주문은 지급 요청이, 구독은 웹훅이, 잔량은 지급 사실이 바꾼다.
> 모듈 경계는 **호출이 아니라 발행**으로 넘는다 — 아래 `### 애그리거트 간 관계` 참조.

  - 해당 시점은 사용자의 최초 주문일 때만 해당한다.(웹훅으로 오는 기간권의 상태 변경은 제외)
  - **만들어질 때 상품 유형에 맞는 지급 사실을 함께 단다 (v2)** — 원장 한 행과 그 사실이 같은 순간에
    태어나야 "원장은 있는데 이용권은 없는" 상태가 생기지 않는다
- `ownedBy()`: 이 주문이 해당 사용자의 것인지 판정한다

#### 규칙

- 주문 식별자는 중복될 수 없다. **이 제약 하나가 멱등의 유일한 근거다**
- 멱등 판정을 "조회해서 없으면 삽입"으로 하지 않는다. 동시에 들어온 두 요청이 둘 다 조회를 통과한다
- **먼저 조회하는 것 자체는 한다 (v2)** — 이미 지급된 주문이면 **토스를 부르지 않고** 바로 답하기
  위해서다. 그것은 지름길이지 판정 근거가 아니다. 판정은 유일성 제약이 한다
- **경쟁에 진 요청은 승자 행을 다시 읽어 같은 답을 만든다 (v2)**. 유일성 위반은 실패가 아니라
  "누군가 이미 넣었다"는 확정 사실이다
- 한 주문의 소유자는 한 번 정해지면 바뀌지 않는다. 소유자 필드는 수정할 수 없다
- 이미 다른 사용자의 것인 주문에 대한 지급 요청은 거부한다
- 지급 일시를 따로 두지 않고 생성 일시를 그대로 쓴다. 원장은 생성 이후 변하지 않기 때문이다
- 주문은 지급 이후 상태가 변하지 않는다. **취소·환불로도 변하지 않는다** — 환불은 우리가 처리하지 않는다
- **재요청은 지급 사실을 발행하지 않는다 (v2)**. 원장 삽입에 이긴 요청만 발행한다 — 재요청에서도
  발행하면 잔량이 두 번 오르고 구독이 두 번 열리려 한다

### 주문 식별자(OrderId)

_Value Object_

#### 속성

- `value`: 토스가 발급한 주문 식별값

#### 행위

- `masked()`: 로그·응답에 쓸 마스킹 값을 만든다
- `toString()`: **항상 마스킹된 값을 반환한다**
- `raw()`: 원문. **토스 호출과 저장 두 경로 전용이다 (v2)**

#### 규칙

- 원문 값은 밖으로 나가지 않는다. 응답 본문·예외 메시지·로그 어디에도 싣지 않는다
- 주문 식별자를 아는 것은 미지급 주문을 가로챌 수 있는 것과 같다
- 그래서 마스킹을 호출자의 선택에 맡기지 않고 **값 객체가 강제한다**
- **이 값은 모듈 경계를 넘는다 (v2)** — 구독이 웹훅으로 계약을 찾는 유일한 키라서다. 경계를 넘는 값이
  원시 문자열이면 마스킹 보장이 경계에서 끊기지만, **타입으로 넘기면 보장이 값과 함께 이동한다**
- **마스킹 폭은 이 도메인의 정책이다 (v2)**. 다른 도메인의 마스킹을 재사용하지 않는다 — 재사용하면
  저쪽 정책이 바뀔 때 이쪽 노출 폭이 조용히 함께 바뀐다

### 상품 유형(ProductType)

_Enum_

#### 상수

- `CONSUMABLE`: 단건 — 지급하면 횟수권이 1 오른다
- `SUBSCRIPTION`: 구독 — 지급하면 구독 계약이 생긴다

#### 규칙

- **플랫폼에는 이 둘 말고 다른 유형도 있지만 우리 카탈로그에 없다 (v2)**. 카탈로그에 없는 것은 남의 상품이다

### 상품 카탈로그(ProductCatalog)

_Domain Service_

#### 행위

#### 규칙

- 카탈로그에 없는 상품 코드는 우리 상품이 아니다. 지급하지 않는다
- 가격은 담지 않는다. 가격의 정본은 결제 SDK 이고, 우리가 말하면 결제창과 어긋난다
- **상품 코드는 설정에서 온다 (v2)**. 값이 비면 그 유형은 **미노출 상품**이 되어 어떤 주문도 그것으로
  판별되지 않는다 — 판별 실패는 지급 거부이지 오류가 아니다

### 주문 검증기(OrderVerifier)

_Domain Service_

#### 행위

- `verify()`: 토스에 주문 상태를 물어 지급해도 되는 주문인지 판정한다

#### 규칙

- 클라에서 요청 받은 orderId 식별자로 검증한다
- 클라이언트의 주장만으로 지급하지 않는다. **사실이 처음 확인되는 지점이다**
- 검증이 확인해주는 것은 "이 주문이 결제됐다"뿐이다. **"누구 것인가"는 알려주지 않는다**
- 검증은 지급 트랜잭션 밖에서 한다. 외부 왕복이 트랜잭션을 물고 있으면 응답 시간과 커넥션이 함께 무너진다
- 응답이 늦으면 붙잡지 않고 실패로 답한다. 남은 것은 복원이 처리한다
- **판정은 두 단계다 (v2)** — 지급 가능한 상태인가, 그리고 **우리 상품인가**. 뒤쪽에서 걸리면
  "우리가 파는 것이 아니다"이고 결제 실패와 다른 사건이다
- 참고자료 — 플랫폼 API 스펙 1번 get-order-status 를 참고하여 구현한다.

### 토스 주문 조회(TossOrderClient) **(v2 추가)**

_Domain Service_

#### 행위

- `statusOf()`: 주문 상태를 토스에 묻는다

#### 규칙

- **토스를 부르는 유일한 지점이다.** IAP 서버 API 는 이것 하나뿐이고 인증은 **mTLS 단독**이다
- **모든 실패를 한 결과로 접는다** — 봉투 실패 6종·전송 실패·타임아웃·비활성이 전부 "확인하지 못했다"

- **끄고도 뜰 수 있어야 한다** — 인증서가 준비되기 전에도 서버는 기동해야 하고, 그때 모든 조회는
  실패로 답한다. 반대로 **켜 놓고 인증서가 비면 기동을 멈춘다** — 조용히 뜨면 지급이 전부 실패로 죽는다
- 로그에 주문 식별자 원문을 싣지 않는다

### 선착 판정(UniqueRace) **(v2 추가)**

_Policy / Concurrency Skeleton_

#### 행위

- `firstWriterWins()`: 삽입을 시도하고, 유일성 경쟁에 지면 승자 행으로 결과를 만든다

#### 규칙

- **잠금을 세우지 않는다.** 낙관적으로 넣어 보고, 유일성 위반이 나면 그것 자체가 "누군가 이미 넣었다"는
  확정 사실이므로 승자를 다시 읽는다. 멱등한 재요청과 동시 요청이 **같은 경로로 수렴한다**
- **삽입은 호출자와 분리된 트랜잭션에서 끝나야 한다.** 같은 트랜잭션에서 터지면 되돌리기로 표시돼
  뒤따르는 재조회가 무의미해진다
- **대상 테이블의 유일성 제약은 하나여야 한다.** 둘이면 엉뚱한 위반을 경쟁으로 오판해 성공으로 접는다
- 유일성 위반이 아닌 무결성 오류는 삼키지 않는다. 삼키면 진짜 버그가 숨는다
- **주문·구독·잔량 세 곳이 같은 골격을 쓴다** — 같은 문제를 세 벌로 풀면 한 곳만 고쳐지는 날이 온다

### 구독(Subscription)

_Aggregate Root_

#### 속성

- `id`: `Long`
- `orderId`: `OrderId` 최초 구독 주문 식별자 - **UNIQUE**. 웹훅이 이 값으로 찾아온다
- `userId`: `UserId` ~~- **UNIQUE**~~ **(v2 삭제 — 재구독을 영구히 막는다.** 종료된 계약이 행을 남긴 채
  그 자리를 점유하고, 유일성 제약은 상태를 보지 못해 "활성은 하나"를 표현할 수 없다.**)**
- `status`: `SubscriptionStatus` 구독 상태
- `expiresAt`: 만료 시각
- `autoRenew`: 자동 갱신 예정 여부
- `lastWebhookOccurredAt`: 마지막으로 반영한 웹훅의 발생 시각. `null` 이면 웹훅 미수신

#### 행위

- `static start()`: 최초 지급. 활성 상태, 추정 만료, 웹훅 미수신으로 태어난다
- `applyWebhook()`: 웹훅을 반영한다. **더 나중에 발생한 웹훅일 때만 반영된다**
  - **반영했는지를 답한다 (v2)** — 반영하지 않은 것은 실패가 아니라 정상 무동작이고, 부른 쪽은
    그 사실을 로그로 남긴다
- `applyClientSnapshot()`: 재확인을 반영한다. 임시 보정이다
- `hasMissedWebhook()`: 웹훅이 알려준 직전 상태가 우리 상태와 다른지 판정한다

#### 규칙

- ~~한 사용자에게 활성 구독은 하나다. 두 번째 구독은 거부한다 — 조용히 두 개를 갖는 것보다 낫다~~
  **(v2 삭제 — 재구독이 정상 경로다.** 만료·해지 뒤 다시 사면 새 주문으로 새 계약이 열린다.
  "한 사용자의 현재 계약"은 가장 최근 계약이고, 여는가 마는가는 개폐 판정이 상태로 정한다.**)**
- **같은 주문으로는 계약이 하나다 (v2)**. 유일성의 축이 사용자에서 **주문**으로 옮겨졌고, 같은 주문의
  재지급은 경쟁에서 떨어져 **멱등 성공**으로 접힌다
- **웹훅으로 구독을 새로 만들지 않는다.** 구독은 검증된 주문을 거쳐서만 생긴다
- 반영 순서의 근거는 발생 시각 하나다. 웹훅에는 이벤트 식별자가 없다
- 이미 반영한 것보다 과거의 웹훅은 반영하지 않는다. **같은 시각도 반영하지 않는다 (v2)** — 같은 시각을
  통과시키면 재전송된 사본이 최신 상태를 되감을 수 있다
- **순서 판정과 반영은 분리될 수 없다.** 읽어서 비교한 뒤 쓰면 동시에 도착한 두 웹훅이 둘 다 통과한다.
  ~~판정 조건을 갱신문 자체에 넣는다~~ → **고쳐 쓸 대상을 잠그고 읽는다 (v2 수정)**.
  갱신문 하나로는 "직전 상태 불일치 감지"와 "무엇이 반영됐는가"를 함께 알 수 없고, 그 둘이 이 도메인의
  관측 수단이다. **읽는 순간부터 잠근다** — 잠그지 않은 경로가 하나라도 있으면 그쪽이 옛 스냅샷을
  들고 있다가 나중에 커밋해 잠근 쪽의 갱신을 통째로 덮는다
- **쓰기 경로는 예외 없이 잠그고 읽는다 (v2)** — 웹훅도, 재확인도. 격리 수준으로 대신할 수 없고
  (두 트랜잭션이 각자 스냅샷을 본다) 프로세스 안의 잠금으로도 안 된다(서버가 두 대다)
- 재확인은 웹훅 순서 판단 기준값을 건드리지 않는다. 건드리면 뒤늦게 도착한 웹훅이 과거로 취급돼 버려지고, 클라이언트 값이 영구히 정본이 된다
- **재확인은 상태 미확인일 때만 반영한다 (v2)**. 그 밖에는 무동작이다
- 만료 시각과 발생 시각은 플랫폼이 비워 보낼 수 있다. 비어 있으면 기존 값을 유지한다 — 정본을 무로 덮으면 만료 판정이 통째로 죽는다
- **자동 갱신 여부도 같다 (v2)** — 비어 오면 기존 값을 유지한다
- 만료 시각이 추정값인지를 따로 기억하지 않는다. **어떤 판정에도 쓰지 않을 값이고**, 필요하면 웹훅 발생 시각의 유무가 답한다 — 추정 여부로 분기하면 웹훅을 받은 뒤의 갱신 유실을 잡지 못한다
- 직전 상태 불일치는 웹훅을 놓쳤다는 뜻이다. **감지해서 남기되 반영은 그대로 진행한다**
- **추정 만료는 31일이다 (v2 확정)** — 월 주기 30일 확정(참고자료 ⑥-2) + 여유 1일. 짧게 잡으면 돈 낸 사람을 막는다

### 구독 상태(SubscriptionStatus)

_Enum_

#### 상수

- `ACTIVE`: 활성
- `IN_GRACE_PERIOD`: 결제 실패 유예 — 카드 문제로 잠깐 실패한 구간
- `ON_HOLD`: 유예 종료 후 보류
- `PAUSED`: 사용자가 일시정지함
- `EXPIRED`: 만료
- `REVOKED`: 회수

#### 규칙

- **토스의 어휘를 그대로 옮긴 것이다.** 우리가 만든 상태를 여기 섞지 않는다
- **상태 미확인은 이 enum 의 값이 아니다 (v2)** — 시간 경과로 판정하는 **별개의 축**이다. 섞으면
  토스가 준 사실과 우리 추론이 한 필드에서 뭉갠다
- 이 상태를 게이트에 직접 쓰지 않는다. "어떤 상태인가"와 "열어줄 것인가"는 별개다
- **모르는 어휘가 오면 비어서 돌아온다 (v2)**. 예외로 터뜨릴지 무시할지는 경로마다 다르므로
  (웹훅은 무시, 재확인은 입력 오류) 판단을 부른 쪽에 남긴다
- 프론트에게는 안내 문구용으로만 내려간다 **(v2 이연 — 내려보내는 경로가 아직 없다)**

### 웹훅 사건(WebhookEvent)

_Value Object_

#### 속성

- `eventType`: 이벤트 종류 2종. **등록 검증 이벤트는 본문이 다르다 (v2)**

- **시간 값은 벽시계 그대로 다룬다 (v2)**. 기준 타임존이 원문에 없어 환산할 근거가 없고, 그 오차는

### 웹훅 검사(WebhookEventInspector) **(v2 추가)**

_Domain Service_

#### 행위

#### 규칙

- **진위 → 종류 → 형식 순서가 곧 계약이다.** 셋을 쪼개 호출자에게 순서를 맡기면 한 줄 빠뜨린 것이
  조용한 보안 구멍이 된다 — 순서를 한 자리 안에 넣어 틀릴 여지를 없앤다
- **진위가 먼저다.** 형식이 앞서면 위조 요청이 인증 실패 대신 형식 오류를 받고, 본문 모양에 따라
  응답이 갈려 페이로드 구조가 새어 나간다
- **종류가 그다음이다.** 등록 검증 이벤트에는 주문 식별자도 스냅샷도 없어서, 종류를 가르기 전에
  형식을 물으면 콜백 URL 이 영원히 활성화되지 않는다
- **프레임워크의 본문 검증으로 대신할 수 없다** — 스키마가 하나일 때만 성립하고, 진위 검증보다
  먼저 돌아 순서를 뒤집는다
- 헤더 값 대조가 진위 검증의 전부다. **헤더 이름은 우리가 고를 수 없다**(참고자료 ⑥-1)
- 값 대조는 상수 시간으로 한다. 설정이 비면 항상 거부한다

### 클라이언트 스냅샷(SubscriptionSnapshot) **(v2 추가)**

_Value Object_

#### 속성

- `orderId`: 보정 대상 주문. **대상을 지목할 뿐 소유자를 정하지 않는다**
- `status`: 구독 상태 6종
- `expiresAt`: 만료 예정. 비어 있을 수 있다

- **정본이 아니다.** 웹훅이 정본이고 이것은 상태 미확인을 푸는 임시 보정이다

- **플랫폼이 주는 이용 가능 여부와 유예 종료 시각은 받지 않는다.** 앞은 산식이 공개돼 있지 않고,
  뒤는 우리가 판정에 쓰지 않는다
- 모르는 상태 어휘는 **입력 오류**다 — 웹훅과 달리 이 경로는 우리가 만든 계약이라 무시할 이유가 없다

### 이용 게이트(AccessGate)

_Domain Service_

#### 행위

- `accessible()`: 기간권이 살아 있는지 판정한다
- `stale()`: 구독 상태가 미확인 구간에 들어갔는지 판정한다

#### 규칙

- 활성이면 연다. 다만 만료 시각에 **만료 완충**을 더한 시점이 지나면 닫는다
- 결제 실패 유예 중이면 연다. 카드 문제로 잠깐 실패한 유료 사용자를 막는 손해가 더 크다
- **결제 실패 유예에는 만료 경과를 보지 않는다 (v2)** — 유예의 종료 시각이 웹훅에 오지 않아 우리가
  판정할 수 없고, 종료는 토스가 다음 웹훅으로 알린다
- 유예 종료·일시정지·만료·회수는 막는다
- 구독 이력이 없으면 막는다. 그 경우 횟수권만 본다
- 상태 미확인은 **활성인데 만료 완충까지 지나도록 다음 웹훅이 없는 것**이다. 판정 근거는 시간 경과뿐이다
- 만료와 회수는 웹훅으로 확인된 종료다. 상태 미확인이 아니다
- 상태 미확인과 접근 허용은 같은 만료 기준을 쓴다. 기준이 어긋나면 "열려 있는데 미확인"이라는 모순 상태가 생긴다
- **두 판정이 같은 계산을 공유해야 한다 (v2)**. 각자 계산하면 한쪽만 고쳐지는 날 모순이 되살아난다 —
  활성 구간에서 두 판정은 정확히 상보다
- **경계는 포함이다 (v2)** — 만료 + 완충 정각까지는 열려 있고 그 다음 순간부터 닫힌다
- 상태를 갖지 않는 순수 판정이다. 저장소를 알지 못한다. **시간도 인자로 받는다 (v2)**
- **이 판정은 "이용 가능"의 구독 쪽 절반이다 (v2)**. 횟수권 잔량과 합치는 일은 읽기 모델의 몫이고, 아직 없다

### 횟수권 잔량(CreditBalance)

_Aggregate Root_

#### 속성

- `id`: `Long`
- `userId`: `UserId` - **UNIQUE**
- `balance`: `Balance` 잔량. 금액이 아니라 **개수**다

#### 행위

- `static create()`: 첫 지급 때 잔량 행을 연다. **잔량 1로 태어난다 (v2)** — 0으로 열고 곧바로 올리면
  두 문장 사이가 비고, 그 사이를 본 요청은 "결제했는데 잔량이 0"을 본다
- ~~`minus()`: 잔량을 1 차감한다.~~ **(v2 이연 — 부르는 쪽이 소모이고, 소모가 없다.)**
- ~~`plus()`: 잔량을 1 증가한다.~~ **(v2 수정 — 엔티티의 행위로 두지 않는다.** 읽어서 더한 뒤 저장하는
  모양이 되기 때문이다. 증가는 **판정과 갱신이 한 문장인 원자 갱신**으로만 일어난다.**)**

#### 규칙

- 잔량은 사용자당 한 행이다
- 행이 없는 것과 잔량이 0인 것은 **같은 뜻**이다. 결제한 적 없는 사용자에게는 행이 없다
- **잔량을 바꾸는 행위를 엔티티가 갖지 않는다.** 읽어서 계산한 뒤 저장하면, 잔량 1을 두 요청이 함께 읽고 둘 다 통과한다
- 잔량은 절대 음수가 되지 않는다. 이 불변식은 "잔량이 남아 있을 때만 줄인다"는 갱신 조건이 지킨다
- 증감은 동시성 제어를 신경써야한다.
- **증가는 원자 갱신 한 문장이고, 그 문장이 행 유무까지 답한다 (v2)** — 갱신된 행이 없으면 첫 지급이고
  삽입 경로로 넘어간다. 동시 첫 지급 경쟁의 심판은 `UNIQUE(user_id)` 이며, **진 쪽은 승자 행에 원자
  갱신으로 합류한다**
- 음수 금지를 저장소 제약으로 걸지 않는다. 걸면 잔량 부족이 오류로 튀어 정상 판정 경로와 갈라진다
- 잔량 행을 만들 때도 음수를 허용하지 않는다. 불변식이 갱신 경로에만 있으면 생성 경로가 새는 곳이 된다
- **주문 식별자를 저장하지 않는다 (v2)** — 자연키 복제 금지. "같은 주문으로 두 번 오르지 않는다"는
  이쪽이 아니라 **발행하는 쪽의 멱등**이 지킨다

_Aggregate Root_

- 해제는 **작업 실패** 이벤트 에만 쓴다. 환불로 소모를 되돌리지 않는다
- 티켓은 지우지 않는다. 소모 이력은 분쟁 대응에 쓴다
- 참조값은 불투명 문자열이다. 아직 결제 도메인은 작업 도메인을 알지 못하며, 이 값의 의미도 모른다(나중에 선정되면 변경)

- 구독 상태가 미확인이라 소모를 막았다 — 재확인이 필요하다 **(v2 이연)**
- 웹훅 진위 검증에 실패했다 — **인증 실패로 답한다 (v2)**. 형식 오류가 아니다
- 웹훅·재확인의 형식이 어긋난다 — **공통 입력 오류를 쓴다 (v2)**. 이 도메인의 코드를 새로 만들지 않는다

#### 규칙

- 이용권이 없어서 거부하는 것과 인증에 실패한 것은 **다른 코드**다. 프론트의 행동이 다르다
- **이용권 없음과 재확인 필요도 다른 코드다 (v2)**. 둘 다 접근 거부지만 프론트의 행동이 정반대다 —
  앞은 결제로 보내고, 뒤는 재확인으로 보낸다
- 오류 메시지에 주문 식별자를 싣지 않는다
- 지급 재요청은 오류가 아니다. **성공으로 답한다**
- **무시도 오류가 아니다 (v2)** — 과거·중복 웹훅, 모르는 주문의 웹훅, 남의 주문으로 온 재확인은
  전부 정상 무동작으로 성공을 답한다. **반영 실패만 실패다**

### 애그리거트 간 관계

- ~~네~~ → **세 애그리거트는 서로를 참조하지 않는다 (v2).** 연결고리는 `UserId` 와 `OrderId` 값뿐이다
- **세 애그리거트가 세 모듈에 흩어져 있고, 경계는 호출이 아니라 발행으로 넘는다 (v2).**
  지급이 확정되면 상품 유형에 맞는 **지급 사실**이 발행되고, 이용권을 만드는 쪽이 그것을 받아 자기
  애그리거트를 연다. 받는 쪽을 부르는 쪽이 알지 못하므로 이용권이 하나 더 생겨도 지급 경로는 그대로다
- **의존 방향은 한 방향이다 (v2)**: 구독과 횟수권이 결제(주문)를 알고, **결제는 그 둘을 알지 못한다.**
  셋 모두 인증에서 `UserId` 하나만 알고, 인증은 셋을 알지 못한다. 이 방향이 곧 각 모듈이 선언하는
  허용 의존이며, 반대로 흐르는 참조는 컴파일 이전에 아키텍처 테스트가 막는다
- **결제가 밖으로 내보내는 것은 지급 사실 둘과 주문 식별자 타입(+ 저장 어댑터)뿐이다 (v2).**
  지급을 부르는 것은 자기 진입뿐이라 지급 진입은 공개하지 않는다 — **밖에서 실제로 쓰는 것만 공개한다**
- **구독은 주문 식별자를 저장하고, 횟수권은 저장하지 않는다 (v2).** 구독에게 그 값은 웹훅이 계약을
  찾아오는 유일한 키라 기능이 성립하려면 원문이 필요하고, 횟수권에게는 로그 추적용일 뿐이다.
  **같은 값이라도 저장하는 쪽만 그 타입을 알아야 한다**
- **지급 사실을 받는 일은 지급과 같은 트랜잭션에서 끝난다 (v2)** — 원장 삽입과 이용권 생성이 함께
  커밋되거나 함께 되돌아간다. 대신 **받는 쪽에서 던진 예외가 지급 요청을 되돌린다.** 유실을 복구가
  아니라 **부재**로 막는 선택이고, 그래서 받는 쪽은 예외를 삼키지 않는다 — 삼키면 **돈은 받았는데
  이용권은 없는** 상태가 조용히 남는다
- 주문과 구독은 최초 지급 시 **함께 만들어져야 한다.** 주문만 남으면 돈을 내고 못 쓰고, 이용권만 오르면 멱등이 깨져 재요청 때 또 오른다
- 주문과 횟수권 잔량도 같다. 지급은 **원장 기록과 이용권 증가가 한 덩어리**여야 한다
- 이용 티켓은 잔량과 별개로 산다. 티켓의 생명주기는 작업의 생명주기이고, 잔량의 생명주기는 사용자의 생명주기다 **(v2 이연)**
- 이용권 읽기 모델만이 세 애그리거트를 한 번에 본다. **쓰기는 어디서도 합쳐지지 않는다** **(v2 이연)**
